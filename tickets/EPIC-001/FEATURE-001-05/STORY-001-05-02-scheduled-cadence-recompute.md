#### 4.2.1 The Execution Model This Demonstration And Section 5 Are Written Against

**This has to come before the demonstration path and before section 5, because what counts as completion differs by model and a criterion written against the wrong one passes while nothing has been derived.**

**The choice between a task that derives inline, a queued job, and a task that enqueues a job is settled: the epic closed it as architectural entry 1** [tickets/EPIC-001-reorder-and-replenishment.md:§8.2 Architectural Decisions] and the parent feature records it as closed [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§4.5 Open Decisions This Feature Waits On]. **An earlier revision of this section held both positions at once** — it called the choice an open decision this story "may not proceed past by assuming a default", and then specified the enqueue model in full anyway. That is not a cautious position but an unacceptable one: it left every completion criterion below satisfiable by naming whichever model the reader preferred, including a model the deployment does not run.

**What this story specifies, so that nothing here is implicit: the task enqueues one idempotent job per channel through `JobQueueService.createQueue` [packages/core/src/job-queue/job-queue.service.ts:L82] and derives nothing inside `execute` itself** — which is the settled model, decided on evidence rather than adopted as a default: it is the pattern a shipped core task already uses [packages/core/src/scheduler/tasks/clean-sessions-task.ts:L46-L47], it is the only one of the three whose completion is observable without inventing a signal, and it keeps a long derivation out of the scheduler's timeout race [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L113]. The queue factory's usage idiom — a queue created on module initialisation with a name and a process function — is documented on the service itself [packages/core/src/job-queue/job-queue.service.ts:L28].

**The context the run executes in, stated as the platform actually builds it rather than as a role the run "holds".** A scheduled task is handed a context the platform creates for it against the default channel with an administrative API type and **no user at all** [packages/core/src/scheduler/scheduled-task.ts:L130-L138], and that factory sets the context's authorised flag to true with no session attached when no user is passed [packages/core/src/service/helpers/request-context/request-context.service.ts:L76-L85]. Three consequences, and each is a rule rather than an observation:

- **The run is not authorised by permissions and holds none.** It is a context flagged authorised with no session, so describing the recompute as running "as an administrator" or as "holding" any permission is wrong in the same way that describing a customer session as holding `Permission.Owner` is wrong [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings].
- **`ctx.activeUserId` is undefined for the whole run**, so no code path in the derivation may key off the active user. The run enumerates customers explicitly from placed-order history; an ownership predicate of the kind the buyer-facing reads use would match nothing here and would silently derive zero rows.
- **The channel must be rebound per channel and cannot be inherited**, because the context arrives bound to the default channel whatever channels the work spans — which is what the fifth scenario in section 7 asserts.

The scheduled recompute path — trigger, run identifier, channel enumeration, the per-channel enqueue with the note that no dedupe check precedes it, the platform's write of the task record, the job's own batched derivation, and the buyer's read — is drawn as **Figure F5-SEQ** in the parent feature file, whose filename is `FEATURE-001-05-purchase-cadence-and-replenishment.md` [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.7 Figure F5-SEQ].

**Step one — give the buyer a history the derivation can read, with *separated* placement timestamps rather than two orders placed back to back.** A derived interval is measured between placements, so two orders placed within the same minute yield an interval of zero whole days and **no due entry at all** — which is the single most likely way to run this demonstration and conclude, wrongly, that nothing works. The setup is therefore explicit:

**1a — the customer session.** Against `http://localhost:3000/shop-api`, execute `login(username: "<a seeded customer's email address>", password: "test")` [packages/core/src/api/schema/shop-api/shop.api.graphql:L116] — the address read from the Admin API `customers` query rather than assumed [packages/core/src/api/schema/admin-api/customer.api.graphql:L2], and `test` being the fixed password the seed applies to every seeded customer [packages/testing/src/data-population/populate-customers.ts:L19]. **Retain the session cookie for 1b.** Expected: `CurrentUser`, not an error result. **Record the customer's id** — the recompute writes cadence rows keyed on it.

**1b — place two orders carrying the same variant, each as six calls in this exact order.** Run the sequence once, then run it again unchanged; every operation already ships and the `vendure-token` header is omitted throughout so both resolve to the default channel [packages/core/src/entity/channel/channel.entity.ts:L62]:

- `setOrderShippingAddress(input: { streetLine1: "1 Test Street", city: "London", postalCode: "SW1A 1AA", countryCode: "GB" })` [packages/core/src/api/schema/shop-api/shop.api.graphql:L88], then `eligibleShippingMethods` [packages/core/src/api/schema/shop-api/shop.api.graphql:L19] — expected to return the two seeded quotes at 500 and 1000 in the smallest currency unit [packages/core/mock-data/data-sources/initial-data.ts:L76-L79] — then `setOrderShippingMethod(shippingMethodId: ["<the Standard Shipping id>"])` [packages/core/src/api/schema/shop-api/shop.api.graphql:L103].

**1c — separate the two placements in time, because two placements at the same instant derive no interval.** The demonstration needs a measurable gap between them, and the Shop API sets `orderPlacedAt` from the server clock rather than accepting one. **Backdate the first order after both are placed**, against the disposable database the shared prerequisite brought up:

```bash
# Terminal 2, from the repository root. <OID1> is the FIRST order's id, <OID2> the SECOND's.
# The new value is derived from the SECOND order's own persisted orderPlacedAt rather than from
# the clock at the moment this runs, so the gap does not shrink by however long the reader took
# to place the two orders and reach this step. The closing SELECT prints the gap it produced.
# The client is named "mariadb", not "mysql": this image ships no mysql-named client.
docker compose exec -T mariadb mariadb -uvendure -ppassword vendure-dev -e "
  SELECT orderPlacedAt INTO @second FROM \`order\` WHERE id = <OID2>;
  UPDATE \`order\` SET orderPlacedAt = DATE_SUB(@second, INTERVAL 30 DAY) WHERE id = <OID1>;
  SELECT TIMESTAMPDIFF(DAY, (SELECT orderPlacedAt FROM \`order\` WHERE id = <OID1>), @second)
         AS interval_days;"
```

**Expected intermediate state:** the closing statement prints an `interval_days` of exactly 30, which is the interval AC-4 asserts as `intervalDays` of exactly thirty. Without this step the derived interval is zero or one and every number downstream of it becomes a timing accident rather than an expected response.

**Why the second order's stored value is the operand, and not `NOW()`.** An earlier revision of this step subtracted the interval from `NOW()` instead, which measures back from the moment the statement runs rather than from the placement it has to be thirty days before. The second order was placed earlier — by however long the six calls of 1b took, plus reading time — so the gap that reached the derivation was thirty days *minus* that delay: on one run of this path a delay of seven minutes produced twenty-nine days, twenty-three hours and fifty-three minutes, and a derivation that counts whole days reports twenty-nine. **The assertion of exactly thirty would then fail for a reason that has nothing to do with the code under test**, and the printed `interval_days` is what makes that visible before the recompute is triggered rather than after. Both statements run on one connection, which is what lets the second read the user variable the first set. The table name is quoted because `order` is a reserved word on this engine, and it is the platform's own table rather than one this epic adds.

**The client is invoked as `mariadb` rather than as `mysql`, and that is a correction rather than a preference.** The Compose service this path brings up declares the floating `mariadb:latest` tag [docker-compose.yml:L7], and current MariaDB images ship no `mysql`-named client at all — the historic `mysql*` symlinks were dropped, so `docker compose exec -T mariadb mysql …` fails with an executable-not-found error before any statement is parsed. The same is true of the version continuous integration pins for its own MariaDB job [.github/workflows/build_and_test.yml:jobs], so the `mariadb` name is the one that works on both. The container name, the database name, the user and the password are the ones the Compose service declares [docker-compose.yml:L6], [docker-compose.yml:L10], [docker-compose.yml:L11] and [docker-compose.yml:L12], and they are development fixtures for a disposable database rather than deployment credentials.

## 5. Acceptance Criteria

**The settled execution model these criteria are written against is the enqueue model of section 4.2.1, settled by the epic's ruling rather than chosen here: the task enqueues one idempotent job per channel and derives nothing inside `execute`.** That sentence comes first because the parent feature requires it to [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.9.1 The Observable Completion Signal, Under The One Settled Execution Model], because the ruling that fixed it is the epic's [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings], and because a completion criterion written against the wrong model passes while nothing has been derived.

Eight criteria. **Each names exactly one GraphQL operation in its `When` clause, and that operation is the one under test**, so a failing criterion points at a single published contract. A reference to an earlier criterion is written by criterion number rather than by naming that criterion's operation. No criterion names a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not.

The five required coverage classes map onto the eight as follows. Valid input is AC-1, AC-2, AC-3 and AC-4, which is four rather than one because the trigger, the task's own signal, the derivation's signal and the buyer-visible effect are four separate observations of one successful run. Invalid or incomplete input is AC-5. An error naming the exact type returned is AC-6. An edge case is AC-7. The assertion that an existing operation is unchanged is carried by AC-8 for the read path this story consumes and by the second half of AC-2 for the administrative surface it registers into.

Seven properties of this story hold across every criterion and are stated once here rather than repeated in each.

- **The trigger is named in every case, and there are exactly two.** The cron schedule the task declares [packages/core/src/scheduler/scheduled-task.ts:L60-L75], which accepts either a standard cron expression or a cron-time-generator function and which every shipped core task writes in the generator form [packages/core/src/scheduler/tasks/clean-sessions-task.ts:L43]; or an explicit administrative invocation through the already-published trigger mutation [packages/core/src/api/schema/admin-api/scheduled-task.api.graphql:L12]. Every criterion below uses the second, so that no test waits on wall-clock time.
- **The observable completion signal is named in every asynchronous case, and it is two-part.** The task's own returned object, captured by the platform and persisted into `lastResult` [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L28] beside `lastExecutedAt` [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L22], reports **what was enqueued**; each per-channel job reaching a terminal state reports **what was derived** [packages/core/src/api/schema/admin-api/job.api.graphql:L28-L35]. The buyer-visible read is a third observation and is never asserted alone, because an empty due list cannot be told apart from a derivation that has not finished.
- **The correlation procedure is followed rather than shortcut.** The trigger mutation returns before execution [packages/core/src/scheduler/scheduler.service.ts:L119-L122] and the platform clears the trigger flag before attempting the run [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L212-L222], so a criterion asserting an outcome first captures the run identifier inside `lastResult` and then requires a **newer** one. A changed `lastExecutedAt` alone satisfies nothing.
- **Every derived row comes from placed orders only.** The inputs are `Order.orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] and `OrderLine.orderPlacedQuantity` [packages/core/src/entity/order-line/order-line.entity.ts:L104]. Orders where `Order.active` is true [packages/core/src/entity/order/order.entity.ts:L82] are carts and are excluded, because a cart is not evidence of a purchase and its lines carry the zero that `orderPlacedQuantity` defaults to — walking them would silently corrupt the interval rather than fail [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3.1 Cadence Is Computed From Placed Orders]. The live `quantity` column [packages/core/src/entity/order-line/order-line.entity.ts:L97] is never read, because an administrative modification can alter it after placement.
- **Every read and every write is bound to one channel, and the run cannot inherit that channel.** A scheduled task's own request context is created against the **default channel** with an administrative API type [packages/core/src/scheduler/scheduled-task.ts:L131-L138], so the run enumerates channels and builds a fresh context per channel, and every history read and cadence write additionally carries an explicit channel predicate. The channel is identified by the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L62], and each request's language resolves from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]; the criteria below use the language code `en`. No field this story writes is language-varying, because it stores no string of its own beyond one closed enumeration member.
- **No monetary value appears anywhere in this story.** The cadence table carries no money column and the derivation reads no price. Were a deployment to extend the row, any monetary value would be an integer in the smallest unit of its currency stated alongside its currency code, which the order carries [packages/core/src/entity/order/order.entity.ts:L142] and which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A decimal monetary value is a defect rather than a formatting preference.
- **No numeric target is asserted, because this repository declares none.** **This repository declares no recompute-duration target, no freshness or staleness budget, no cadence-accuracy figure, no coverage-of-customers figure and no throughput figure, and none is invented here** — the epic reports that absence as a finding rather than filling it [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers]. Where such a target would conventionally appear, the criteria assert a verifiable state instead: an exact row count for a named triple, an exact member of the platform's closed job enumeration, an exact error type name, or a named field present in a result payload. The platform's own task timeout is referred to by location and its value is deliberately not restated [packages/core/src/scheduler/scheduled-task.ts:L76-L83]; where a default value has to be named at all it is named as the constant `DEFAULT_TIMEOUT` [packages/core/src/plugin/default-scheduler-plugin/constants.ts:L2], as is the manual-trigger poll constant `DEFAULT_MANUAL_TRIGGER_CHECK_INTERVAL` [packages/core/src/plugin/default-scheduler-plugin/constants.ts:L3]. The single numeric figure in this file is the line-coverage target in section 10, which the requirements supply rather than this story inventing.

## 7. Edge Cases

Exactly five scenarios. The first three are the unconditionally required categories; the fourth and fifth are the two conditional categories that apply to this story, concurrency because a scheduled task is the one place in this epic where two runs can meet, and channel scope because the context a scheduled task is handed names the default channel only. Each opens with its category label. Two of the five resolve to *proceed* rather than to a block, and that is stated honestly rather than force-fitted into a failure this work does not have.

* Scenario: Zero, null or empty collection — the buyer has no placed order at all, so there is nothing to derive from
   * Given a channel in which a Returning Buyer exists with zero placed orders, so no order line carrying a set `orderPlacedAt` exists for that buyer [packages/core/src/entity/order/order.entity.ts:L92], and the only orders present in that channel are active carts whose `orderPlacedQuantity` is the zero it defaults to [packages/core/src/entity/order-line/order-line.entity.ts:L104]
   * When the recompute for that channel is triggered through the shipped trigger mutation and runs to settlement
   * Then proceed and complete: the job settles in the completed member of the platform's job enumeration rather than the failed member, its result reports a written-row count of exactly zero, no cadence row is written for that buyer, and the buyer's due list stays empty without any error being returned. An empty source is a specified outcome rather than a failure path [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]. **A variant purchased exactly once resolves the same way and for the same reason** — an interval cannot be derived from one placement, so no row is written at all rather than a row carrying a guessed interval

* Scenario: An item unavailable, deleted or disabled since the last purchase — the variant behind a derived interval is now disabled, or has been soft-deleted
   * Given a Returning Buyer has two placed orders in the channel containing variant A and two containing variant B, and since those placements variant A has had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] while variant B has been soft-deleted, its `deletedAt` column now carrying a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When the recompute for that channel is triggered and runs to settlement
   * Then both cases resolve **the same way, and the ruling is deterministic rather than left open**. Variant A's cadence row is **written and kept**, its figures recomputed as normal, because the derivation predicates on placed-order history and on none of `enabled`, `deletedAt`, price or stock: this feature asserts nothing about a variant's enabled state, which belongs to FEATURE-001-03 and FEATURE-001-04 [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched], and a disabled variant may be enabled again, so discarding a derived interval would throw away information the placements still support. **Variant B's cadence row is written and kept too, and this reverses what an earlier revision of this scenario required** — that revision had the run remove the row on the ground that "a soft delete fires no cascade and the row would otherwise name a variant that no longer exists", which is the wrong premise: a soft delete sets the nullable `deletedAt` timestamp and **leaves the variant row and its translations in place** [packages/core/src/entity/product-variant/product-variant.entity.ts:L48], so nothing is dangling, the non-null relation resolves, and there is no referential hygiene to perform. **So a disabled variant and a soft-deleted one resolve identically rather than differently, and the deterministic ruling is that both rows survive the run** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched]. The sibling read is consistent with that: it filters on the owning customer, the channel and the signal state only, so it returns both entries with their variants resolved and repairs nothing, and neither this run nor that read removes either row [tickets/EPIC-001/FEATURE-001-05/STORY-001-05-01-replenishment-due-list.md:§7. Edge Cases]

* Scenario: A price changed since the last purchase — the catalogue price of a variant behind a derived interval has moved
   * Given the price of a variant behind one of this buyer's derived intervals has changed since the placements the interval was derived from, and the buyer's placement dates and quantities are unchanged
   * When the recompute for that channel is triggered and runs to settlement
   * Then proceed with the cadence row unchanged in every derived figure: **cadence is derived from timing and quantity, never from price, so a price movement cannot alter a cadence row** — the derivation reads `orderPlacedAt` and `orderPlacedQuantity` and reads no monetary column, and the cadence table holds none. **The boundary is stated rather than the case being pretended away:** making a buyer aware of a price change before they commit is FEATURE-001-03's work through its `reorderPreview` operation, and copying a price onto a derived row here would put two answers to one question in two features [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]

* Scenario: A concurrent modification or race — two runs meet, or a buyer snoozes an entry while a run is in flight
   * Given the task declares `preventOverlap` as a literal true rather than relying on its annotated default, which is never materialised anywhere between the stored configuration object and the truthiness test the scheduler applies to it [packages/core/src/scheduler/scheduled-task.ts:L84-L90] and [packages/core/src/scheduler/scheduler.service.ts:L172]; the deployment runs the default scheduler plugin, whose own documentation states that each task executes exactly once at the scheduled time even with more than one worker process running [packages/core/src/plugin/default-scheduler-plugin/default-scheduler.plugin.ts:L14-L19] — **a claim this criterion's `Then` narrows rather than repeats**, because the lock behind it is acquired pessimistically on only three of the four engines this work is evidenced on and backed by a record uniquely constrained on the task identifier [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L6] carrying a lock column [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L19]; and the cadence table carries a composite unique key over customer, channel and variant
   * When two runs are driven against the same history at the same time, an additional trigger arrives while a run holds the lock, and a buyer snoozes one entry while a run is in flight
   * Then the outcome is **defined and harmless rather than prevented, which is the guarantee this platform can actually support.** Exactly one cadence row exists per customer, channel and variant triple, because every write is an upsert against that composite key rather than an insert. The trigger that arrived while the lock was held is classified as the lock-contention **observation** and not as a failure, and **that observation has no code in either closed set** — it is an *absence* rather than a stored value, which is why `SKIPPED_LOCK_HELD` is a member of neither [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.6a Two Platform Hazards This Feature Designs Around, Both Verified In Source]: the strategy returns without running and **writes nothing at all**, so the assertion is unchanged `lastExecutedAt`, no newer run identifier and `isRunning` true at trigger time [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L92-L97]. **A specification that polled `lastResult` for that code would wait forever.** **And the exclusion the lock buys is engine-dependent, which is why this scenario asserts the outcome rather than the exclusion**: the strategy takes the lock with pessimistic row locking only on PostgreSQL, MySQL and MariaDB [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L279] and falls back to a non-locking path on SQLite and sql.js [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L318], so on `e2e-sqljs` two runs may genuinely overlap. That is harmless here for one reason only — every write is an idempotent upsert on the composite key — and it is why this criterion is written as "exactly one row per triple afterwards" and never as "exactly one run executed". The snoozed entry keeps its snoozed state and its stored expiry through the run, **because none of the four transitions the recompute owns matches it: the expiry has not passed and the buyer has not purchased again** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8.1 The Recompute's Transition Contract — Four Transitions, Each With Its Predicate]. Each transition is one conditional statement whose predicate the database evaluates rather than a read followed by a write. **An earlier revision of this scenario instead barred the run from writing `state` wherever the current state was the snoozed member, which is withdrawn** — that predicate would also have barred the expiry transition, leaving a snoozed entry unable ever to return to the due state. **What is no longer claimed here is a time fence:** an earlier revision of this scenario additionally made the write conditional on the row's stamped computation instant not being newer than the run's own start, which compares two processes' clocks and reverses under skew, and it is withdrawn together with the guarantee it appeared to give [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.6d What Actually Serialises Two Runs — The Guarantee, Weakened To What The Primitives Deliver]. **The guarantee asserted instead is convergence and not monotonicity:** two runs that read different history may commit in either order, the later commit wins even where it read the older history, and the next run corrects it. **On the sql.js engine job the exclusion is weaker still** and is asserted as such rather than assumed away, the platform's fallback lock being a single atomic update whose own source comment records that it may race across connections [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L317-L336]. **And one thing is not claimed:** a task-level timeout is not a cancellation — the platform writes a failure and releases the lock while the losing operand keeps running [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L130-L136], which is why overlap is made harmless rather than asserted to be impossible. The verification route is shipped: the multi-worker procedure documented in `packages/dev-server/test-plugins/scheduler-race-test/scheduler-race-test-task.ts` is how this is exercised across processes [packages/dev-server/test-plugins/scheduler-race-test/scheduler-race-test-task.ts:L16-L21]

* Scenario: A channel, currency or language mismatch — the run is handed a context naming one channel while the purchases span two
   * Given a deployment with two channels whose tokens are distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], each channel resolving its own `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74], and one Returning Buyer holding two placed orders of the same variant under the first channel and two placed orders of that variant under the second channel with different placement dates
   * When the recompute is triggered once and runs to settlement for both channels, the platform having handed the task a request context created against the **default channel** with an administrative API type [packages/core/src/scheduler/scheduled-task.ts:L131-L138]
   * Then the required behaviour is that the run **enumerates channels and rebinds to each one**: exactly one cadence row exists per channel for that customer and variant, each carrying its own channel identifier and an interval derived only from that channel's placements, and no row carries the default channel's identifier for a purchase made elsewhere. A run that used the inherited context would write every row against the default channel, and the buyer-facing read — which filters on the request's channel — would then return nothing under any other token. **That failure is silent, which is why it is written as a required scenario rather than left to an implementer's care**, and the isolation is made structural by making one channel the unit of enqueue and carrying an explicit channel predicate on every read and every write. No currency conversion occurs and none can, the row carrying no monetary value at all
