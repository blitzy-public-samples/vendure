## 4. User Story

As a Returning Buyer,
I want the interval at which I repurchase each variant derived from my placed orders by a task that runs on its own schedule rather than when I ask,
So that the replenishment due list I open is already computed, and the platform tells me what is due from work it has finished instead of walking my order history while I wait.

### 4.2 The Execution Model This Story Is Written Against

**This has to come before the demonstration path and before section 5, because what counts as completion differs by model and a criterion written against the wrong one passes while nothing has been derived.**

The choice between a task that derives inline, a queued job, and a task that enqueues a job is **an open architectural decision recorded by the epic**, and it is the one open decision this story may not proceed past by assuming a default [tickets/EPIC-001-reorder-and-replenishment.md:§8.2 Architectural Decisions] and [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§4.5 Open Decisions This Feature Waits On]. The ruling belongs to a maintainer, not to this ticket.

**What this story specifies, so that nothing here is implicit: the task enqueues one idempotent job per channel through `JobQueueService.createQueue` [packages/core/src/job-queue/job-queue.service.ts:L82] and derives nothing inside `execute` itself** — which is the epic's stated recommended resolution, adopted here for one reason: it is the only one of the three models whose completion is observable without inventing a signal, and it keeps a long derivation out of the scheduler's timeout race [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L113]. The queue factory's usage idiom — a queue created on module initialisation with a name and a process function — is documented on the service itself [packages/core/src/job-queue/job-queue.service.ts:L28].

**Where to see that model drawn.** This file embeds no diagram. The scheduled recompute path — trigger, run identifier, channel enumeration, the per-channel enqueue with its skipped branch, the platform's write of the task record, the job's own batched derivation, and the buyer's read — is drawn as **Figure F5-SEQ** in the parent feature file, whose filename is `FEATURE-001-05-purchase-cadence-and-replenishment.md` [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.7 Figure F5-SEQ].

**What moves if a maintainer takes the inline model instead**, stated so the delta is a known quantity rather than a rewrite: the task's own returned object becomes the derivation's result rather than a report of what was enqueued; the declared `timeout` then bounds the derivation rather than the enqueue [packages/core/src/scheduler/scheduled-task.ts:L76-L83]; the declared overlap option then becomes the overlap answer rather than one half of it [packages/core/src/scheduler/scheduled-task.ts:L84-L90]; and criteria AC-3 and AC-7 in section 5 assert the task's result instead of a job's. **The resolved execution model these criteria are written against is the enqueue model of section 4.2: the task enqueues one idempotent job per channel and derives nothing inside `execute`.** That sentence comes first because the parent feature requires it to [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.9.1 The Observable Completion Signal Depends On The Execution Model], and because a completion criterion written against the wrong model passes while nothing has been derived.

Eight criteria. **Each names exactly one GraphQL operation in its `When` clause, and that operation is the one under test**, so a failing criterion points at a single published contract. A reference to an earlier criterion is written by criterion number rather than by naming that criterion's operation. No criterion names a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not.

The five required coverage classes map onto the eight as follows. Valid input is AC-1, AC-2, AC-3 and AC-4, which is four rather than one because the trigger, the task's own signal, the derivation's signal and the buyer-visible effect are four separate observations of one successful run. Invalid or incomplete input is AC-5. An error naming the exact type returned is AC-6. An edge case is AC-7. The assertion that an existing operation is unchanged is carried by AC-8 for the read path this story consumes and by the second half of AC-2 for the administrative surface it registers into.

Seven properties of this story hold across every criterion and are stated once here rather than repeated in each.

- **The trigger is named in every case, and there are exactly two.** The cron schedule the task declares [packages/core/src/scheduler/scheduled-task.ts:L60-L75], which accepts either a standard cron expression or a cron-time-generator function and which every shipped core task writes in the generator form [packages/core/src/scheduler/tasks/clean-sessions-task.ts:L43]; or an explicit administrative invocation through the already-published trigger mutation [packages/core/src/api/schema/admin-api/scheduled-task.api.graphql:L12]. Every criterion below uses the second, so that no test waits on wall-clock time.
- **The observable completion signal is named in every asynchronous case, and it is two-part.** The task's own returned object, captured by the platform and persisted into `lastResult` beside `lastExecutedAt` [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L28], reports **what was enqueued**; each per-channel job reaching a terminal state reports **what was derived** [packages/core/src/api/schema/admin-api/job.api.graphql:L28-L35]. The buyer-visible read is a third observation and is never asserted alone, because an empty due list cannot be told apart from a derivation that has not finished.
- **The correlation procedure is followed rather than shortcut.** The trigger mutation returns before execution [packages/core/src/scheduler/scheduler.service.ts:L119-L122] and the platform clears the trigger flag before attempting the run [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L212-L222], so a criterion asserting an outcome first captures the run identifier inside `lastResult` and then requires a **newer** one. A changed `lastExecutedAt` alone satisfies nothing.
- **Every derived row comes from placed orders only.** The inputs are `Order.orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] and `OrderLine.orderPlacedQuantity` [packages/core/src/entity/order-line/order-line.entity.ts:L104]. Orders where `Order.active` is true [packages/core/src/entity/order/order.entity.ts:L82] are carts and are excluded, because a cart is not evidence of a purchase and its lines carry the zero that `orderPlacedQuantity` defaults to — walking them would silently corrupt the interval rather than fail [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3.1 Cadence Is Computed From Placed Orders]. The live `quantity` column [packages/core/src/entity/order-line/order-line.entity.ts:L97] is never read, because an administrative modification can alter it after placement.
- **Every read and every write is bound to one channel, and the run cannot inherit that channel.** A scheduled task's own request context is created against the **default channel** with an administrative API type [packages/core/src/scheduler/scheduled-task.ts:L131-L138], so the run enumerates channels and builds a fresh context per channel, and every history read and cadence write additionally carries an explicit channel predicate. The channel is identified by the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L62], and each request's language resolves from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]; the criteria below use the language code `en`. No field this story writes is language-varying, because it stores no string of its own beyond one closed enumeration member.
- **No monetary value appears anywhere in this story.** The cadence table carries no money column and the derivation reads no price. Were a deployment to extend the row, any monetary value would be an integer in the smallest unit of its currency stated alongside its currency code, which the order carries [packages/core/src/entity/order/order.entity.ts:L142] and which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A decimal monetary value is a defect rather than a formatting preference.
- **No numeric target is asserted, because this repository declares none.** **This repository declares no recompute-duration target, no freshness or staleness budget, no cadence-accuracy figure, no coverage-of-customers figure and no throughput figure, and none is invented here** — the epic reports that absence as a finding rather than filling it [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers]. Where such a target would conventionally appear, the criteria assert a verifiable state instead: an exact row count for a named triple, an exact member of the platform's closed job enumeration, an exact error type name, or a named field present in a result payload. The platform's own task timeout is referred to by location and its value is deliberately not restated [packages/core/src/scheduler/scheduled-task.ts:L76-L83]; where a default value has to be named at all it is named as the constant `DEFAULT_TIMEOUT` [packages/core/src/plugin/default-scheduler-plugin/constants.ts:L2], as is the manual-trigger poll constant `DEFAULT_MANUAL_TRIGGER_CHECK_INTERVAL` [packages/core/src/plugin/default-scheduler-plugin/constants.ts:L3]. The single numeric figure in this file is the line-coverage target in section 10, which the requirements supply rather than this story inventing.

## 7. Edge Cases

Exactly five scenarios. The first three are the unconditionally required categories; the fourth and fifth are the two conditional categories that apply to this story, concurrency because a scheduled task is the one place in this epic where two runs can meet, and channel scope because the context a scheduled task is handed names the default channel only. Each opens with its category label. Two of the five resolve to *proceed* rather than to a block, and that is stated honestly rather than force-fitted into a failure this work does not have.

* Scenario: Zero, null or empty collection — the buyer has no placed order at all, so there is nothing to derive from
   * Given a channel in which a Returning Buyer exists with zero placed orders, so no order line carrying a set `orderPlacedAt` exists for that buyer [packages/core/src/entity/order/order.entity.ts:L92], and the only orders present in that channel are active carts whose `orderPlacedQuantity` is the zero it defaults to [packages/core/src/entity/order-line/order-line.entity.ts:L104]
   * When the recompute for that channel is triggered through the shipped trigger mutation and runs to settlement
   * Then proceed and complete: the job settles in the completed member of the platform's job enumeration rather than the failed member, its result reports a written-row count of exactly zero, no cadence row is written for that buyer, and the buyer's due list stays empty without any error being returned. An empty source is a specified outcome rather than a failure path [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]. **A variant purchased exactly once resolves the same way and for the same reason** — an interval cannot be derived from one placement, so no row is written at all rather than a row carrying a guessed interval

* Scenario: An item unavailable, deleted or disabled since the last purchase — the variant behind a derived interval is now disabled, or has been soft-deleted
   * Given a Returning Buyer has two placed orders in the channel containing variant A and two containing variant B, and since those placements variant A has had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] while variant B has been soft-deleted, its `deletedAt` column now carrying a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When the recompute for that channel is triggered and runs to settlement
   * Then the two cases resolve **differently, and the ruling is deterministic rather than left open**. Variant A's cadence row is **written and retained**, its figures recomputed as normal, because the derivation predicates on placed-order history and on none of `enabled`, `deletedAt`, price or stock: this feature asserts nothing about a variant's enabled state, which belongs to FEATURE-001-03 and FEATURE-001-04 [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched], and a disabled variant may be enabled again, so discarding a derived interval would throw away information the placements still support. Variant B's cadence row is **removed by this run**, because a soft delete fires no cascade and the row would otherwise name a variant that no longer exists — removing it is referential hygiene rather than an availability judgement. The sibling read behaves consistently either way: it filters on the owning customer, the channel and the signal state only, so it returns whatever rows exist at read time and repairs nothing, which is why the stale entry is resolved by this run and not by that read [tickets/EPIC-001/FEATURE-001-05/STORY-001-05-01-replenishment-due-list.md:§7. Edge Cases]

* Scenario: A price changed since the last purchase — the catalogue price of a variant behind a derived interval has moved
   * Given the price of a variant behind one of this buyer's derived intervals has changed since the placements the interval was derived from, and the buyer's placement dates and quantities are unchanged
   * When the recompute for that channel is triggered and runs to settlement
   * Then proceed with the cadence row unchanged in every derived figure: **cadence is derived from timing and quantity, never from price, so a price movement cannot alter a cadence row** — the derivation reads `orderPlacedAt` and `orderPlacedQuantity` and reads no monetary column, and the cadence table holds none. **The boundary is stated rather than the case being pretended away:** making a buyer aware of a price change before they commit is FEATURE-001-03's work through its `reorderPreview` operation, and copying a price onto a derived row here would put two answers to one question in two features [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]

* Scenario: A concurrent modification or race — two runs meet, or a buyer snoozes an entry while a run is in flight
   * Given the task declares `preventOverlap` as a literal true rather than relying on its annotated default, which is never materialised anywhere between the stored configuration object and the truthiness test the scheduler applies to it [packages/core/src/scheduler/scheduled-task.ts:L84-L90] and [packages/core/src/scheduler/scheduler.service.ts:L172]; the deployment runs the default scheduler plugin, documented as executing each task exactly once at the scheduled time even with more than one worker process running [packages/core/src/plugin/default-scheduler-plugin/default-scheduler.plugin.ts:L14-L19] and backed by a record uniquely constrained on the task identifier [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L6] carrying a lock column [packages/core/src/plugin/default-scheduler-plugin/scheduled-task-record.entity.ts:L19]; and the cadence table carries a composite unique key over customer, channel and variant
   * When two runs are driven against the same history at the same time, an additional trigger arrives while a run holds the lock, and a buyer snoozes one entry while a run is in flight
   * Then the outcome is **defined and harmless rather than prevented, which is the guarantee this platform can actually support.** Exactly one cadence row exists per customer, channel and variant triple, because every write is an upsert against that composite key rather than an insert. The trigger that arrived while the lock was held reports the skip code `SKIPPED_LOCK_HELD` as an expected outcome and not a failure, the platform's strategy returning without running when it cannot acquire the lock [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L92-L97]. The snoozed entry keeps its snoozed state through the run, because the run writes the state column only for the transition it owns and only where the current state is not the snoozed member, and its write is additionally conditional on the row's stamped computation instant not being newer than the run's own start. **And one thing is not claimed:** a task-level timeout is not a cancellation — the platform writes a failure and releases the lock while the losing operand keeps running [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L130-L136], which is why overlap is made harmless rather than asserted to be impossible. The verification route is shipped: the multi-worker procedure documented in `packages/dev-server/test-plugins/scheduler-race-test/scheduler-race-test-task.ts` is how this is exercised across processes [packages/dev-server/test-plugins/scheduler-race-test/scheduler-race-test-task.ts:L16-L21]

* Scenario: A channel, currency or language mismatch — the run is handed a context naming one channel while the purchases span two
   * Given a deployment with two channels whose tokens are distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], each channel resolving its own `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74], and one Returning Buyer holding two placed orders of the same variant under the first channel and two placed orders of that variant under the second channel with different placement dates
   * When the recompute is triggered once and runs to settlement for both channels, the platform having handed the task a request context created against the **default channel** with an administrative API type [packages/core/src/scheduler/scheduled-task.ts:L131-L138]
   * Then the required behaviour is that the run **enumerates channels and rebinds to each one**: exactly one cadence row exists per channel for that customer and variant, each carrying its own channel identifier and an interval derived only from that channel's placements, and no row carries the default channel's identifier for a purchase made elsewhere. A run that used the inherited context would write every row against the default channel, and the buyer-facing read — which filters on the request's channel — would then return nothing under any other token. **That failure is silent, which is why it is written as a required scenario rather than left to an implementer's care**, and the isolation is made structural by making one channel the unit of enqueue and carrying an explicit channel predicate on every read and every write. No currency conversion occurs and none can, the row carrying no monetary value at all

Recorded by the epic as blocking five stories, this one among them** [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. **The mechanism is settled and is not what is open:** cadence rows are deleted outright rather than anonymised, and the epic's persistence contract drives that deletion from this feature's scheduled task [tickets/EPIC-001-reorder-and-replenishment.md:§7.8 The Seven Plugin-Owned Tables].
