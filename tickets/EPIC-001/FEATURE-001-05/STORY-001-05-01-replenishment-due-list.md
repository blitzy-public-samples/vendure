**How the clause maps onto this story, word for word.** The phrase "the items they purchase regularly" is the whole subject of this story: an item purchased regularly is one a buyer has placed an order for more than once, and the interval between those placements is what "regularly" means once it is made computable. ## 4. User Story

As a Returning Buyer,
I want to read a list of the variants I buy on a repeating interval whose next purchase date has arrived, each entry naming the variant, the derived interval in whole days, the date I last bought it and the signal's state,
So that I can act on a repeat purchase the platform has already worked out for me instead of scanning my own order history to reconstruct which items are due.

### 4.2 Demonstration Requirement

One path, runnable by a reader holding only this file. It is a read, so it demonstrates without placing an order.

```bash

cd packages/dev-server
bun run populate
bun run dev
```

`bun run populate` is the seed script declared in that package [packages/dev-server/package.json:scripts.populate] and `bun run dev` is its server-and-worker script [packages/dev-server/package.json:scripts.dev], matching the two numbered steps the contribution guide documents for populating test data [CONTRIBUTING.md:L141] and running the dev server [CONTRIBUTING.md:L176].

> [!WARNING]
> `bun run populate` clears the database it is pointed at before seeding it. Point it at a disposable development database and nothing else. The engine it targets is selected by the `DB` environment variable, which the agent handbook documents as `DB=postgres` or `DB=sqlite` set before the populate step [AGENTS.md:L15].

**Authenticate.** The seed creates ten customers through `populateCustomers(app, 10, ...)` [packages/dev-server/populate-dev-server.ts:L46], each with the fixed password the seed sets [packages/testing/src/data-population/populate-customers.ts:L19]. Use **a seeded customer email address from the populated data set** — read one through the Admin API `customers` query [packages/core/src/api/schema/admin-api/customer.api.graphql:L2] rather than guessing it — and sign in with the Shop API `login` mutation [packages/core/src/api/schema/shop-api/shop.api.graphql:L116].

**Send the operation.** POST to the Shop API, whose path is declared as a shared constant [packages/common/src/shared-constants.ts:L7] on the port declared beside it [packages/common/src/shared-constants.ts:L5], giving `http://localhost:3000/shop-api`. Carry the session credential returned by the sign-in, and carry the active channel in the request header whose name is declared as `vendure-token` [packages/common/src/shared-constants.ts:L19]. While only the default channel exists the header may be omitted and the default channel is resolved; once a second channel exists it is required, because the channel is part of every row's identity.

```graphql
query {
  activeCustomerReplenishmentDue(options: { take: 10, skip: 0 }) {
    totalItems
    items {
      id
      productVariantId
      productVariant { id name }
      intervalDays
      observationCount
      lastPurchasedAt
      dueAt
      state
      snoozedUntil
    }
  }
}
```

**Expected response shape.** A `ReplenishmentSignalList` carrying `totalItems` as an integer and `items` as an array of `ReplenishmentSignal`, ordered ascending by `dueAt` and then by `productVariantId`. Against a freshly seeded database no cadence has been derived yet, so the demonstrable outcome is `totalItems` equal to zero and `items` equal to the empty array — **an empty list and not an error**, which is the specified behaviour rather than a gap [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]. To see a populated list, insert `PurchaseCadence` rows through a test fixture or run the recompute that story 05-02 delivers; the read is acceptable either way, which is what makes this story independent.

**The field names above are transcribed from the parent feature's published SDL block**, which that file designates as fixed for every argument, field and nullability [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. Where the prose sketch above that block uses a different pair of type names, the SDL block governs, and the generated-options naming rule confirms it: the options input is derived from the returned list type by stripping its `List` suffix [packages/core/src/api/config/generate-list-options.ts:L52], so `ReplenishmentSignalList` is what makes `ReplenishmentSignalListOptions` the generated name.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. Criteria name operations and their arguments and never a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. The five required coverage classes map onto them as follows: valid input is AC-1, invalid input is AC-2, an error naming the exact type returned is AC-3, an edge case is AC-4, and the assertion that an existing operation is unchanged is AC-7 and AC-8. AC-5 and AC-6 carry the two isolation assertions the parent feature's test matrix makes mandatory for this operation [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5.1 Surface Ownership And Test Matrix].

Five properties of the operation are stated once here rather than repeated in every criterion.

- **The read is synchronous.** It enqueues no job and schedules no task, so it has no asynchronous trigger and no observable completion signal to name. The recompute that writes the rows is story 05-02's work and names its own trigger and signal there.
- **Every row it returns is derived from placed orders only.** A row's inputs are `Order.orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] and `OrderLine.orderPlacedQuantity` [packages/core/src/entity/order-line/order-line.entity.ts:L104]. Orders where `Order.active` is true [packages/core/src/entity/order/order.entity.ts:L82] are carts, and their lines are excluded, because a cart is not evidence of a purchase and walking one would read the zero that `orderPlacedQuantity` defaults to and silently corrupt the interval [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3.1 Cadence Is Computed From Placed Orders]. Every criterion below states its history preconditions in those terms.
- **Every request is channel-scoped and language-scoped.** The active channel is identified by the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L62] and the request's language resolves from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]; the criteria below use the language code `en`, a member of the published language enumeration [packages/core/src/api/schema/common/language-code.graphql:L72]. The payload holds no string of its own, so no field below varies by language.
- **The payload carries no monetary field.** No criterion below asserts a price, so no monetary value appears in this file. Were a deployment to extend the payload, any monetary value would be an integer in the smallest unit of its currency stated alongside its currency code, which the order carries [packages/core/src/entity/order/order.entity.ts:L142] and which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A decimal monetary value is a defect rather than a formatting preference.
- **No numeric target is asserted, because this repository declares none.** There is no latency bound, no accuracy figure, no adoption figure and no engagement figure anywhere in this file. Where such a target would conventionally appear, the criterion asserts a verifiable state instead — an exact entry count with its ordering, an exact error type name, or an exact field set. The single numeric figure in this file is the line-coverage target in section 10, which is supplied by the requirements rather than invented.

AC-1: An authenticated buyer with repeat placed-order history reads an exact ordered entry count whose tie-break is declared
* Given a Returning Buyer is authenticated against the Shop API in the channel identified by the token carried in the `vendure-token` request header, that request resolves the language code `en` from the channel, and that customer has exactly three `PurchaseCadence` entries in that channel whose state is the due member of `ReplenishmentSignalState` — two of the three carrying `dueAt` values byte-identical to each other for two variants with different identifiers, and the third carrying a later `dueAt` — plus one further entry whose state is the dismissed member
* When that customer executes the `activeCustomerReplenishmentDue` query with no `options` argument supplied, requesting `totalItems` and, for each item, `productVariantId`, `intervalDays`, `observationCount`, `lastPurchasedAt`, `dueAt`, `state` and `snoozedUntil`
* Then `items` contains exactly three entries and `totalItems` equals exactly three, the entries appear in ascending order of `dueAt` with the two sharing one `dueAt` ordered between themselves in ascending order of `productVariantId` as the declared tie-break, every entry carries an `intervalDays` that is a whole number greater than zero and an `observationCount` that is two or greater, `lastPurchasedAt` on each entry equals the `orderPlacedAt` of that customer's latest placed order containing that variant, and the omitted `options` argument resolves the page size to the configured `shopListQueryLimit` [packages/core/src/config/default-config.ts:L89] rather than to every row

**Why the tie-break is part of AC-1 rather than a criterion of its own.** Without a declared tie-break, "the first three due entries" is not reproducible across the four database engines this migration is evidenced on, so an entry count asserted without one would be asserting an accident of row order. The primary sort and its tie-break share one operation, one coverage class and one test, so they are one criterion with one Given, When and Then.

AC-2: A page size above the configured shop limit is refused rather than silently reduced
* Given a Returning Buyer is authenticated in the active channel and `shopListQueryLimit` holds its shipped default [packages/core/src/config/default-config.ts:L89], the option being declared on the platform's own configuration interface [packages/core/src/config/vendure-config.ts:L151]
* When that customer executes the `activeCustomerReplenishmentDue` query with a `take` value one greater than that configured limit
* Then the request returns an error entry of the platform's own input-error type `UserInputError` [packages/core/src/common/error/errors.ts:L27-L29] and no `activeCustomerReplenishmentDue` payload, and no entry list is returned in reduced form, because the query resolves its items through the platform's list-query helper with query limits left enforced [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L637-L638]

**A note on AC-2, because the obvious version of this criterion is unpassable and was rejected.** A criterion asserting that a *negative* or zero `take` is rejected would fail against this platform. The helper clamps a negative `take` to zero rather than refusing it, evaluating the page size as the minimum of the requested value and the limit after first raising it to zero [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L643], and the guard that throws fires only when the requested value **exceeds** the limit [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L637-L638]. A negative `skip` is clamped in the same way. So the over-limit case is the one invalid-input case that genuinely produces the required error type, and it is the case this criterion asserts. The clamping behaviour is disclosed here rather than left for an implementer to discover against a red test.

AC-3: An unauthenticated session reads nothing and no other buyer's data
* Given no customer is authenticated, so the request carries no active user, and at least two customers hold due `PurchaseCadence` entries in the active channel
* When the `activeCustomerReplenishmentDue` query is executed on that unauthenticated session
* Then the request returns the platform's forbidden-access error `ForbiddenError` [packages/core/src/common/error/errors.ts:L67-L69] and no entry from any customer, following the shipped guard in this repository's own customer-scoped plugin read, which tests the request for an active user and raises that same error when there is none [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L74-L75]

AC-4: A buyer with no placed order reads an empty list rather than an error
* Given a Returning Buyer is authenticated in the active channel and has zero placed orders in that channel, so no `PurchaseCadence` entry exists for that customer and that channel
* When that customer executes the `activeCustomerReplenishmentDue` query
* Then `items` is the empty array, `totalItems` equals exactly zero, and no error entry of any type is returned, an empty collection being the specified outcome for a buyer with no history rather than a failure path [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]

AC-5: A second customer's entries never appear in the first customer's result
* Given two Returning Buyers each hold due `PurchaseCadence` entries in the same channel, the first holding exactly two and the second holding exactly five, and the first buyer is authenticated
* When the authenticated first buyer executes the `activeCustomerReplenishmentDue` query
* Then `totalItems` equals exactly two, every returned `productVariantId` belongs to the first buyer's own entries, and no identifier from the second buyer's five entries appears; the ownership predicate is applied in the service on the customer resolved from the session together with the channel before any row is read, because the operation's permission gate admits a customer session without itself proving ownership, so a gate alone is not the control [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]

AC-6: A token for a second channel returns that channel's entries only
* Given one Returning Buyer holds exactly two due `PurchaseCadence` entries under a first channel token and exactly one due entry under a second channel token, the two tokens being distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62]
* When that authenticated buyer executes the `activeCustomerReplenishmentDue` query twice, once carrying the first channel token and once carrying the second
* Then the first execution returns `totalItems` equal to exactly two and the second returns `totalItems` equal to exactly one, neither result contains an entry belonging to the other channel, and no argument on the query widens the scope beyond the token's channel, the channel being part of each row's identity rather than a filter a caller may relax

* Given this story's plugin is registered and its additive migration is applied, and a Returning Buyer is authenticated in the active channel
* When that customer executes the existing `activeCustomer` query [packages/core/src/api/schema/shop-api/shop.api.graphql:L5] requesting the field set it published before this story existed
* Then the query returns that same field set with the same types and the same nullability, its signature is byte-identical, and the regenerated Shop API root `Query` type declares twenty root queries where it declared nineteen [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52] — the single added field being this story's own query. ## 7. Edge Cases

Four scenarios. The three unconditionally required categories are the first three, and the fourth covers the conditional channel category, which applies because the channel is part of every row's identity. Two of the four resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure this read cannot have. The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — the buyer has no placed order at all
   * Given a Returning Buyer is authenticated in the active channel and has zero placed orders in that channel, so no `PurchaseCadence` row exists for that customer and that channel
   * When that customer executes the `activeCustomerReplenishmentDue` query
   * Then proceed with an empty result: `items` is the empty array and `totalItems` equals exactly zero, and no error entry of any type is returned. A buyer with no history is a specified outcome rather than a failure path, and it is the property that lets this story be accepted before the recompute exists [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§4.3 Intra-Feature Story Order]

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant named by an existing entry is now disabled or soft-deleted
   * Given a Returning Buyer holds exactly two due `PurchaseCadence` entries in the active channel, and since the recompute that wrote them one of the two variants has had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] while the other has been soft-deleted, its `deletedAt` column now carrying a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When that customer executes the `activeCustomerReplenishmentDue` query
   * Then proceed and **list both entries rather than omitting either** — this is the deterministic ruling for this operation, and it is stated as a choice between the two available behaviours rather than left open. The query filters on the owning customer, the channel and the signal state, and on none of `enabled`, `deletedAt`, price or stock, so both rows are returned. The payload carries no staleness field of its own, because the published field set declares none; a buyer-visible staleness is observable through each entry's resolved `productVariant`, which the existing catalogue read path serves. The entry is removed by the **next** recompute rather than by this read, so the read never fails and never repairs a row [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.11 A Due Signal Is A Point-In-Time Computation]. Whether a disabled variant can in fact be added to an order is decided later, at preview time by FEATURE-001-03 and at resolution time by FEATURE-001-04, never here

* Scenario: A price changed since the last purchase — the catalogue price of a variant named by an existing entry has moved
   * Given the price of a variant named by one of this buyer's due `PurchaseCadence` entries has changed since the order that entry was derived from was placed
   * When that customer executes the `activeCustomerReplenishmentDue` query
   * Then proceed with no warning and no price field: **this operation does not report a price change, and that boundary is explicit rather than an oversight.** The `PurchaseCadence` table holds no monetary column and the published payload declares no monetary field, so this story holds no price that could go stale. A buyer is made aware of a price movement before committing through FEATURE-001-03's `reorderPreview` operation, which owns that comparison; duplicating it here would put two answers to one question in two features [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. Copying a price onto a cadence row would be a defect rather than an optimisation

* Scenario: A channel, currency or language mismatch — the variant was purchased under a different channel token from the one the read carries
   * Given a Returning Buyer has placed orders containing a variant under a first channel token, holds exactly one due `PurchaseCadence` entry for it under that channel, and has placed no order for that variant under a second channel token, the two tokens being distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62]
   * When that customer executes the `activeCustomerReplenishmentDue` query carrying the second channel token, with the language resolved from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * Then proceed with an empty result for that channel: `totalItems` equals exactly zero under the second token while the same query under the first token returns exactly one entry. Cadence is derived per channel and the channel is part of the row's identity, so a purchase history under one token produces due signals readable only under that token. No currency conversion and no cross-channel reconciliation occurs, and none can, because the payload carries no monetary value at all

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this operation performs no availability check and makes no commitment; the staleness it does have is the derived row's own, and it is carried by the second scenario above and by the fourth. A concurrent modification or race does not apply to this read: two simultaneous reads cannot conflict, and the write-side race — two recomputes converging on one row per customer, channel and variant triple — is prevented by the unique constraint this story's migration creates and is asserted in section 6 as a unit case and in the parent feature's test matrix as an end-to-end case for this story [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5.1 Surface Ownership And Test Matrix].
