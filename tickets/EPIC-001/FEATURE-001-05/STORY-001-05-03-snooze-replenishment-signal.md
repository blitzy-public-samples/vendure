### 4.3 The Signal Lifecycle This Story Owns

This story owns the buyer-caused transition, so the whole lifecycle is restated here in prose. **Four states, named and ordered exactly as Figure F5-STATE names and orders them** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8 Figure F5-STATE]: **due**, **snoozed**, **dismissed**, and **due again**. No fifth state exists and none is renamed here. The published enumeration carries three members, because **due again** is the due state re-entered on a later cycle rather than a distinct value on the wire, and publishing it as a member would put a name in the schema that no row ever holds.

The parent feature models two readings of how a snooze ends, and every transition below carries the reading it belongs to. They are **the fixed-interval reading**, under which the mutation persists an expiry, and **the next-purchase reading**, under which it persists none. Which of the two is taken is an open ruling and not this story's to take [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions].

- **Entry into due.** Cause: a recompute observes that the interval derived from that customer's placed orders has elapsed since the last placed purchase of that variant. Observable: the entry is returned by `activeCustomerReplenishmentDue`. Both readings.
- **due to snoozed.** Cause: the buyer calls `snoozeReplenishmentSignal` naming the variant. Observable: the mutation returns `snoozed` equal to true with the entry's state reading snoozed, and the entry is no longer returned by `activeCustomerReplenishmentDue`. Both readings. **This is the only transition a buyer causes, the only write path this feature exposes, and the transition this story is accepted against.**
- **snoozed to due.** Cause: a later recompute observes that the stored expiry has passed while the derived interval is still elapsed. Observable: the entry is returned by `activeCustomerReplenishmentDue` again. **Fixed-interval reading only** — under the next-purchase reading no expiry is stored and this transition does not exist.
- **due to dismissed.** Cause: the buyer places an order containing that variant, which satisfies the signal. Observable: the entry is no longer returned by `activeCustomerReplenishmentDue`. Both readings.
- **snoozed to dismissed.** Cause: the same purchase. Under the fixed-interval reading it fires when the purchase happens before the stored expiry passes; under the next-purchase reading it is the **only** exit from snoozed. Observable: the entry stays absent from `activeCustomerReplenishmentDue`. Both readings.
- **dismissed to due again.** Cause: a later recompute finds the interval elapsed measured from the **new** last placed date. Observable: the entry is returned by `activeCustomerReplenishmentDue` once more. Both readings, and under the next-purchase reading it is the only route by which a snoozed entry ever becomes actionable again.
- **due again to snoozed.** Cause: the buyer snoozes the new cycle through the same mutation. Observable: as for the due to snoozed transition. Both readings.
- **due again to dismissed.** Cause: the buyer purchases the variant again. Observable: the entry stays absent. Both readings.

**Re-emergence, stated deterministically and per reading, because "it comes back later" is not a contract.** Under the fixed-interval reading a snoozed entry re-emerges when, and only when, a recompute runs after the stored expiry has passed and finds the derived interval still elapsed; the buyer's own action is not what returns it, so a snooze that has expired stays absent until the next recompute. Under the next-purchase reading a snoozed entry never re-emerges as the same cycle at all: the buyer's next purchase of that variant moves it to dismissed, and it becomes actionable again only through the dismissed to due-again transition on a later recompute. **A dismissed entry does not return through the passage of time alone under either reading** — it returns only when a recompute measures a fresh interval from the new last placed date.

**Idempotence, resolved without ambiguity.** A second snooze of an entry already in the snoozed state returns `snoozed` equal to true and **leaves the row unchanged**, which the parent feature settles rather than leaves open [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. Read as the binary a reviewer will want answered: **the second call leaves the deadline untouched rather than extending it.** The single deterministic deadline is the one the first call stored; the second call does not recompute it from its own timestamp, does not add the two intervals together, does not create a second row and does not return an error. The consequence is worth stating because it is a product behaviour and not an implementation detail: **a buyer cannot lengthen a snooze by repeating it**, and under the fixed-interval reading the entry returns at the deadline the first call set. Under the next-purchase reading no expiry exists, so the repeat is a state-preserving action with nothing to leave untouched.

**What a snooze is not.** It is not a reservation: it holds no stock and the variant can go out of stock, be disabled or be deleted while the entry sits in the snoozed state. It is not a commitment: no future obligation is created, no schedule of payments exists and nothing cancels. It is not a subscription: nothing renews, and the entry's return is a recompute observing history rather than a cycle ticking over. The parent feature states this at feature level because all three stories inherit it, and describing a signal as an upcoming order, a scheduled delivery, a renewal or a plan breaks the epic's scope boundary rather than merely choosing loose words [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.11 A Due Signal Is A Point-In-Time Computation].

**How long a snooze lasts, and the figure this file refuses to invent.** Under the fixed-interval reading the length is a **plugin option carrying a default that the deployment configures**, expressed in whole days, and it is not an argument on the mutation — the published input carries one field and no interval [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. **This repository declares no numeric target for the snooze interval, so no default is presented here as a tuned or recommended figure.** No engagement figure, no dismissal figure and no latency bound is asserted anywhere in this file, because the repository declares no target against which any of them could be validated [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. Where such a figure would conventionally appear, section 5 asserts a verifiable state instead.

## 7. Edge Cases

Five scenarios. The three unconditionally required categories are the first three; the fourth is the idempotence case this story owns; the fifth covers the conditional channel category, which applies because the channel is part of every entry's identity. **Four of the five resolve to *proceed* rather than to a block or a warning**, and that is stated honestly rather than force-fitted into a failure this write does not have. The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — the buyer holds no replenishment signal at all
   * Given a Returning Buyer is authenticated in the active channel and holds zero `PurchaseCadence` entries in that channel, so no entry exists in any state, and a variant exists in the catalogue
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant
   * Then proceed with the normalized negative payload: `snoozed` equals false, `signal` is null, no row is created and no error entry of any type is returned. Naming the exact types so the outcome is unambiguous, **neither is raised** — not the platform's forbidden-access error `ForbiddenError` [packages/core/src/common/error/errors.ts:L67], which is reserved for a session carrying no active user, and not its input-error type [packages/core/src/common/error/errors.ts:L27], because an authenticated buyer naming a variant that addresses no entry is a specified outcome rather than a failure path [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]

* Scenario: An item unavailable, deleted or disabled since the last purchase — the variant an entry names is now disabled or soft-deleted
   * Given a Returning Buyer holds exactly two entries in the active channel whose state is the due member of `ReplenishmentSignalState`, and since the recompute that wrote them one of the two variants has had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] while the other has been soft-deleted, its `deletedAt` column now carrying a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming each of the two variants in turn
   * Then proceed and **snooze both entries rather than refusing either** — this is the deterministic ruling for this operation, stated as a choice between the two available behaviours rather than left open. A soft delete sets a timestamp and does not remove the row, so both entries are still present and addressable. The conditional update filters on the owning customer, the channel, the variant and the current state, and on none of `enabled`, `deletedAt`, price or stock, so both move into the snoozed state and each returns `snoozed` equal to true. A stale entry is removed by the **next** recompute rather than by this write, so the write never fails and never repairs an entry [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.11 A Due Signal Is A Point-In-Time Computation]. Refusing the snooze here would be the worse ruling on its own terms: it would leave the buyer unable to silence a prompt for an item they can no longer buy

* Scenario: A price changed since the last purchase — the catalogue price of a variant an entry names has moved
   * Given the price of a variant named by one of this buyer's due entries has changed since the order that entry was derived from was placed
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant
   * Then proceed with no warning and no price field: **this operation neither reports nor reacts to a price change, and that boundary is explicit rather than an oversight.** The `PurchaseCadence` table holds no monetary column and the published payload declares no monetary field, so a snooze carries no price that a movement could invalidate, and a price change alters no snooze. A buyer is made aware of a price movement before committing through the `reorderPreview` operation that FEATURE-001-03 owns; duplicating that comparison here would put two answers to one question in two features [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. Copying a price onto a cadence row so that a snooze could hold one would be a defect rather than an optimisation

* Scenario: An idempotent repeat — the buyer snoozes an entry that is already snoozed
   * Given a Returning Buyer is authenticated in the active channel and holds exactly one entry there whose state is already the snoozed member of `ReplenishmentSignalState`, carrying whatever `snoozedUntil` value the resolved ruling stores and the row identifier an earlier snooze of the same variant returned
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that same variant again, and then a third time
   * Then proceed and report success on every call: each returns `snoozed` equal to true with the state still reading the snoozed member, and **the stored row is byte-identical after the second and third calls to what it was after the first.** The deadline is left untouched rather than extended, it is not recomputed from the later call's timestamp, the intervals are not added together, no second row is created and no error entry of any type is returned. The behavioural consequence is stated because a buyer will meet it: **a snooze cannot be lengthened by repeating it**, and under the fixed-interval reading the entry returns at the deadline the first call set [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]

* Scenario: A channel, currency or language mismatch — the entry was derived under a different channel token from the one the snooze carries
   * Given a Returning Buyer holds exactly one due entry for a variant under a first channel token and holds no entry for that variant under a second channel token, the two tokens being distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], with each request's language resolving from its own channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant while carrying the second channel token
   * Then proceed with the normalized negative payload under that token: `snoozed` equals false, `signal` is null, and **the entry under the first token is still in the due state and was not snoozed.** Repeating the mutation under the first token then returns `snoozed` equal to true for that entry. Cadence is derived per channel and the channel is part of each entry's identity, so a snooze applied under one token has no effect under another and no argument widens the scope beyond the token's channel. No currency conversion and no cross-channel reconciliation occurs, and none can, because the payload carries no monetary value at all

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this mutation performs no availability check and makes no commitment; the staleness a snooze does have is the derived entry's own, and it is carried by the second and third scenarios above. A concurrent modification or race is real on this operation and is not omitted — it is the recompute overwriting a row a buyer snoozes mid-run, which the parent feature names as a worst case whose result is a signal silently returning to the due state, and which it assigns to the recompute's design rather than to this write [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8 Figure F5-STATE]. This story's contribution to that defence is stated in section 6 as a single conditional update over the current state rather than a read followed by a write, so two snoozes of the same entry cannot interleave into two rows, and it is asserted in section 5 as AC-5.

- [ ] Every acceptance criterion in section 5 is covered by an automated test that names the same GraphQL operation the criterion names, with none waived or partially accepted, **and every one of the five scenarios in section 7 is covered by a test as well** — a scenario outside the gate is an untested behaviour whatever the prose around it says.
- [ ] Unit tests are co-located with the files which they test and carry the `.spec.ts` suffix [CONTRIBUTING.md:§Server Unit Tests], and they reach minimum 80% line coverage over the new service method, its conditional update and the resolution of the snooze length from the plugin option.
- [ ] An end-to-end specification lives in the package's own `e2e/` directory [CONTRIBUTING.md:§End-to-end Tests] and is written with the `@vendure/testing` package [packages/testing/src/index.ts:L4], and it exercises every acceptance criterion in section 5, every scenario in section 7, and **every transition in section 4.3 that the resolved ruling makes reachable** — the write into the snoozed state, the idempotent repeat, the move to dismissed on a repeat purchase, the recompute-driven return to a due state, and the exit from the snoozed state that the resolved reading defines. It arranges its due entries through a test fixture rather than through the recompute, so the specification passes without story 05-02.
- [ ] **This story generates no migration, and that is evidenced rather than assumed:** it creates no table, adds no column and alters no column type, the `PurchaseCadence` column set and the feature's single additive migration belonging to story 05-01 [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§4.3 Intra-Feature Story Order]. Its end-to-end specification nonetheless runs on the four database engine jobs that already exist — `e2e-sqljs` [.github/workflows/build_and_test.yml:L174], `e2e-mariadb` [.github/workflows/build_and_test.yml:L202], `e2e-mysql` [.github/workflows/build_and_test.yml:L240] and `e2e-postgres` [.github/workflows/build_and_test.yml:L276] — with **native SQLite recorded as an unevidenced engine rather than an unsupported one**, a distinction that is exact rather than pedantic: the dev server can be pointed at it, the agent handbook documenting a `DB=sqlite` switch before the populate step [AGENTS.md:§Development Workflow], but the test package exports MySQL, PostgreSQL and sql.js initializers only [packages/testing/src/index.ts:L10], [packages/testing/src/index.ts:L11], [packages/testing/src/index.ts:L12], and no engine job exercises it — while the contribution guide lists SQLite among the officially supported engines [CONTRIBUTING.md:L143]. That discrepancy is reported here and in the epic rather than propagated as a claim of coverage.
- [ ] The cached end-to-end seed data under the package's own `e2e/__data__/` directory was deleted to reset it after any schema change reaching this specification, which the agent handbook requires [AGENTS.md:§Testing], and the existing specifications in `packages/core/e2e/` then pass unmodified.
- [ ] No existing Shop API operation signature changed: the root `Query` type gains nothing from this story because it publishes no query [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52], the root `Mutation` type declared in the same file gains **exactly one** field [packages/core/src/api/schema/shop-api/shop.api.graphql:L70] with no argument, return type or nullability altered on any existing field, and `activeOrder` [packages/core/src/api/schema/shop-api/shop.api.graphql:L11] and `activeCustomer` [packages/core/src/api/schema/shop-api/shop.api.graphql:L5] are byte-identical. That single added field brings this feature's whole public surface to one query plus one mutation, and it is declared and referred to the epic's Feasibility Collisions section rather than accepted silently [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].
- [ ] The published `ErrorCode` enum grows by zero members, evidenced rather than assumed: this story declares no type implementing the `ErrorResult` interface, and that enum's members are generated from the types which do [packages/core/src/api/config/generate-error-code-enum.ts:L5-L33] over the seed form declared in the schema [packages/core/src/api/schema/common/common-enums.graphql:L28-L30].
