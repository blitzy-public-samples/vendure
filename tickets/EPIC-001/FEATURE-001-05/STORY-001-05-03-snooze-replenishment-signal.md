- **Route A, for a reader holding only this file — write the rows into the disposable database directly.** The compose service that supplies that database declares its name, user and password [docker-compose.yml:L10-L12] on the port it publishes [docker-compose.yml:L16-L17], so the three rows are inserted with one statement against `purchase_cadence`, each row naming the customer `id` noted in step 2, the default channel's `id`, one of the three variant ids read in step 2, an `intervalDays` value, an `observationCount` of at least two, a `lastPurchasedAt` far enough in the past that `dueAt` has passed, and the `DUE` member of the state enum, written in that case because the column stores it that way — the column set being the one story 05-01 creates [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched]. **This route is why step 1's warning matters twice over:** it writes to that database by hand, and it must not be a database anyone cares about. The invocation is:

```bash
# Terminal 2, from the repository root. Writes into the disposable database only. The service
# name, database, user and password are the ones the compose file declares [docker-compose.yml:L6-L17].
# The client is named "mariadb", not "mysql": this image ships no mysql-named client. `-T` is
# present because the statements arrive on standard input rather than from an interactive session.
# THE FIVE IDENTIFIERS ARE SUPPLIED ONCE, on the call at the bottom, under one naming convention.
# The function is the guard: it writes nothing until every identifier is a positive integer, it
# treats a client failure as a failure rather than as an empty result, and it reads the row count
# back and returns non-zero unless that count is exactly 3. It never calls `exit`, so pasting it
# into an interactive terminal cannot end the session.
# NO SHELL VALUE EVER BECOMES SQL. Every statement below is a QUOTED heredoc or a fixed `-e`
# string, so the shell expands nothing inside it; the five validated integers reach the server
# as session variables set by `--init-command`, and the statements reference only those
# variables. That is what the positive-integer guard protects: what `--init-command` carries is
# provably a number. An earlier revision used an unquoted heredoc and referenced `$CID` and
# `$CHID` inside the statement, so an undefined value degenerated the predicate to
# `WHERE customerId =  AND channelId = ` and a value carrying SQL text would have run verbatim.
# AS WRITTEN THE CALL PASSES THE FIVE PLACEHOLDER NAMES, which the guard refuses. Replace each with
# the integer resolved in step 2 — the customer id, the default channel's id, then the three
# variant ids in ascending order. Every time value is relative to the instant this runs, so the
# rows are due whenever the path is followed.
reorder_require_id() { # name, value
    case "$2" in
        ''|*[!0-9]*) echo "STOP: $1 is '$2', which is not a positive integer. Resolve it in step 2."
                     return 1 ;;
        0)           echo "STOP: $1 is 0, which no seeded row carries."
                     return 1 ;;
    esac
    return 0
}

reorder_arrange_due_signals() {
    CID="$1"; CHID="$2"; VID1="$3"; VID2="$4"; VID3="$5"
    problems=0
    reorder_require_id CID   "$CID"   || problems=$((problems + 1))
    reorder_require_id CHID  "$CHID"  || problems=$((problems + 1))
    reorder_require_id VID1  "$VID1"  || problems=$((problems + 1))
    reorder_require_id VID2  "$VID2"  || problems=$((problems + 1))
    reorder_require_id VID3  "$VID3"  || problems=$((problems + 1))
    if [ "$problems" -ne 0 ]; then
        echo "STOP: $problems identifier(s) unresolved. Nothing was written."
        return 1
    fi

    # The heredoc is QUOTED, so the shell expands NOTHING inside it and no shell variable is
    # spliced into SQL; the five validated integers arrive as session variables. In batch mode the
    # client stops at the first error and exits non-zero, so the test below is what makes a refused
    # insert stop the run instead of reaching the count.
    if ! docker compose exec -T mariadb mariadb -uvendure -ppassword vendure-dev \
            --init-command="SET @cid=$CID, @chid=$CHID, @vid1=$VID1, @vid2=$VID2, @vid3=$VID3" <<'SQL'
INSERT INTO purchase_cadence
  (createdAt, updatedAt, computedAt, customerId, channelId, productVariantId,
   intervalDays, observationCount, lastPurchasedAt, dueAt, state, snoozedUntil)
VALUES
  (NOW(), NOW(), NOW(), $CID, $CHID, $VID1, 30, 2, DATE_SUB(NOW(), INTERVAL 31 DAY), DATE_SUB(NOW(), INTERVAL 1 DAY), 'DUE', NULL),
  (NOW(), NOW(), NOW(), $CID, $CHID, $VID2, 30, 2, DATE_SUB(NOW(), INTERVAL 31 DAY), DATE_SUB(NOW(), INTERVAL 1 DAY), 'DUE', NULL),
  (NOW(), NOW(), NOW(), $CID, $CHID, $VID3, 30, 2, DATE_SUB(NOW(), INTERVAL 31 DAY), DATE_SUB(NOW(), INTERVAL 1 DAY), 'DUE', NULL);
-- Validate rather than assume: this must print exactly 3 before the operation is sent.
SELECT COUNT(*) AS due_rows_written FROM purchase_cadence
 WHERE customerId = @cid AND channelId = @chid AND state = 'DUE';
SQL
    then
        echo 'STOP: the insert did not complete. No count is trusted and the operation is not sent.'
        return 1
    fi

    # The count is CAPTURED rather than printed, so the comparison below is the gate and the reader
    # is not the one comparing. --skip-column-names keeps the value bare.
    if ! written=$(docker compose exec -T mariadb mariadb -uvendure -ppassword vendure-dev \
            --batch --skip-column-names \
            --init-command="SET @cid=$CID, @chid=$CHID" \
            -e "SELECT COUNT(*) FROM purchase_cadence WHERE customerId = @cid AND channelId = @chid AND state = 'DUE';"); then
        echo 'STOP: the verification read failed, so the row count is unknown.'
        return 1
    fi
    written=$(printf '%s' "$written" | tr -d '[:space:]')
    if [ "$written" != '3' ]; then
        echo "STOP: purchase_cadence holds '$written' due row(s) for that customer and channel, not 3."
        echo '      Do not send the operation: the drop from exactly 3 to exactly 2 is what this path'
        echo '      observes, and an empty or over-full table satisfies it for the wrong reason.'
        return 1
    fi
    echo 'OK: exactly 3 due rows written. Step 4 may be sent.'
    return 0
}

reorder_arrange_due_signals 'CID' 'CHID' 'VID1' 'VID2' 'VID3'
```

**That block is the only direct-insert route in this file, and an earlier revision carried two of them.** The second wrote a different column list, absolute literal timestamps in place of relative ones, and literal identifiers of one, one and one through three, under a second client name — so a reader met two blocks writing the same three rows differently and no statement of which to run. The two are reconciled into the one above rather than both being kept, and the reconciliation resolves each difference in a stated direction.

- **Every column section 2.3 of the parent feature declares non-nullable is supplied, including `computedAt`** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched]. **Both earlier blocks omitted it**, and an insert that omits a non-nullable column with no default is refused by the engine before any row is written rather than filled in — so the arrangement step failed and the demonstration stopped at a database error the story did not mention. The table and column names are the ones that section fixes rather than names chosen here, so a divergence between this insert and the migration is a defect in one of the two rather than a mismatch a reader has to resolve.
- **`createdAt` and `updatedAt` are supplied explicitly** because both are inherited from `VendureEntity` [packages/core/src/entity/base/base.entity.ts:L31] and [packages/core/src/entity/base/base.entity.ts:L33] and a raw insert bypasses the ORM that would otherwise fill them.
- **Every time value is relative and none is a literal date.** `dueAt` is set one day in the past and `lastPurchasedAt` thirty-one days before the instant the statement runs, so all three rows qualify as due whenever the path is followed — which is what makes the expected `totalItems` of exactly 3 before the snooze, and exactly 2 after it, reproducible rather than a timing accident. The absolute timestamps the removed block carried were due only for as long as they stayed in the past.
- **Every identifier is a validated substituted value rather than a literal, and it reaches the statement as a session variable rather than as spliced text**, because nothing here may assert how a seeded database numbers its rows: `CID` comes from step 2's administrative read, `CHID` is the default channel, and `VID1` to `VID3` are the three variant ids step 2 read in ascending order. **Two properties of that arrangement are the point of it rather than housekeeping.** The heredoc is quoted, so the shell performs no expansion inside the statement at all and no shell value can become SQL; and the five values are refused before the client is invoked unless each is a bare decimal integer, so what `--init-command` carries is provably a number. **An earlier revision of this block used an unquoted heredoc and referenced `$CID` and `$CHID` inside the statement**, which the shell expanded — undefined at that point, so the predicate degenerated to `WHERE customerId =  AND channelId = `, and a value carrying SQL text would have been executed verbatim. Both halves of that are withdrawn. They are passed **once**, as the five arguments of the call at the foot of the block, so no identifier appears twice and none can drift between the insert and the count.
- **The block is fail-closed at four points, and each one is a check that exists rather than an instruction to be careful.** Every identifier is tested for being a positive integer and **nothing is written** unless all five pass — which is why the block as printed, carrying the five placeholder names, refuses itself and reports each unresolved name. The insert's exit status is tested, so a refused statement stops the run instead of falling through to the count. The verification read's exit status is tested, so an unreachable client is distinguished from a wrong answer. And the count is **captured and compared to exactly 3**, so the reader is not the one comparing: any other value, including an empty result, stops the path before the operation is sent. ### 4.3 The Signal Lifecycle This Story Owns

This story owns the buyer-caused transition, so the whole lifecycle is restated here in prose. **Four states, named and ordered exactly as Figure F5-STATE names and orders them** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8 Figure F5-STATE]: **due**, **snoozed**, **dismissed**, and **due again**. No fifth state exists and none is renamed here. The published enumeration carries three members, because **due again** is the due state re-entered on a later cycle rather than a distinct value on the wire, and publishing it as a member would put a name in the schema that no row ever holds.

**The lifecycle is one lifecycle, and an earlier revision of this section carried two.** That revision marked every transition below with the reading it belonged to — a fixed-interval reading under which the mutation persists an expiry, and a next-purchase reading under which it persists none — and declared the choice "an open ruling and not this story's to take". The cost of that neutrality was this story's own contract: with the choice open, `snoozedUntil` might or might not be written, the exit from the snoozed state might or might not exist, and a criterion asserting what a second call returns had nothing to assert it against. **The parent feature now builds the fixed-interval reading and this story is written against it without qualification** [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8 Figure F5-STATE]. Confirmation remains a maintainer's, the bounded delta if it is reversed is enumerated in the epic entry, and **no transition or criterion below is conditional** [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions].

- **Entry into `DUE`.** Cause: a recompute observes that the interval derived from that customer's placed orders has elapsed since the last placed purchase of that variant. Observable: the entry is returned by `activeCustomerReplenishmentDue`, carrying a null `snoozedUntil` because `CHK_purchase_cadence_snooze_expiry_paired` requires a non-snoozed row to carry none [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.3 Named Entities Touched].
- **`DUE` to `SNOOZED`.** Cause: the buyer calls `snoozeReplenishmentSignal` naming the variant. Observable: the mutation returns `snoozed` equal to true with the entry's state reading snoozed and a non-null `snoozedUntil`, and the entry is no longer returned by `activeCustomerReplenishmentDue`. **This is the only transition a buyer causes, the only write path this feature exposes, and the transition this story is accepted against.**
- **`SNOOZED` to `SNOOZED`.** Cause: a second call naming the same variant. Observable: the mutation returns `snoozed` equal to true and the `snoozedUntil` read back is **identical** to the one the first call stored. It is listed as a transition rather than left implicit because it is a criterion — AC-5 — and because the statement that achieves it is the same conditional update rather than a branch taken after a read.
- **`SNOOZED` to `DUE`.** Cause: a later recompute observes that the stored expiry has passed while the derived interval is still elapsed. Observable: the entry is returned by `activeCustomerReplenishmentDue` again, with `snoozedUntil` back to null.
- **`DUE` to `DISMISSED`.** Cause: the buyer places an order containing that variant, which satisfies the signal. Observable: the entry is no longer returned by `activeCustomerReplenishmentDue`.
- **`SNOOZED` to `DISMISSED`.** Cause: the same purchase, arriving before the stored expiry passes. Observable: the entry stays absent from `activeCustomerReplenishmentDue`, and `snoozedUntil` is cleared as part of the move because a non-snoozed row may not carry one.
- **`DISMISSED` to `DUE again`.** Cause: a later recompute finds the interval elapsed measured from the **new** last placed date. Observable: the entry is returned by `activeCustomerReplenishmentDue` once more.
- **`DUE again` to `SNOOZED`.** Cause: the buyer snoozes the new cycle through the same mutation. Observable: as for the `DUE` to `SNOOZED` transition.
- **`DUE again` to `DISMISSED`.** Cause: the buyer purchases the variant again. Observable: the entry stays absent.

**Re-emergence, stated deterministically because "it comes back later" is not a contract.** A snoozed entry re-emerges when, and only when, a recompute runs after the stored expiry has passed and finds the derived interval still elapsed. **The buyer's own action is not what returns it**, so an expired snooze stays absent until the next recompute — which means the return is visible no sooner than that run and this story asserts no sooner either. **A dismissed entry does not return through the passage of time alone** — it returns only when a recompute measures a fresh interval from the new last placed date.

**Idempotence, resolved as a statement rather than as an outcome.** A second snooze of an entry already in the snoozed state returns `snoozed` equal to true and **leaves the row unchanged**, and the mechanism is the parent feature's single conditional update rather than a read that inspects the state and returns early [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. The distinction is the whole of this paragraph: a read-then-write has a window between its halves, and the mutation instead issues one update whose predicate admits both the due and the snoozed state and whose expiry expression preserves any value already there, then reads the row once to build the payload. Read as the binary a reviewer will want answered: **the second call leaves the deadline untouched rather than extending it.** It does not recompute the deadline from its own timestamp, does not add two intervals together, does not create a second row and does not return an error. The consequence is a product behaviour rather than an implementation detail: **a buyer cannot lengthen a snooze by repeating it**, and the entry returns at the deadline the first call set.


**What a snooze is not.** It is not a reservation: it holds no stock and the variant can go out of stock, be disabled or be deleted while the entry sits in the snoozed state. It is not a commitment: no future obligation is created, no schedule of payments exists and nothing cancels. It is not a subscription: nothing renews, and the entry's return is a recompute observing history rather than a cycle ticking over. The parent feature states this at feature level because all three stories inherit it, and describing a signal as an upcoming order, a scheduled delivery, a renewal or a plan breaks the epic's scope boundary rather than merely choosing loose words [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.11 A Due Signal Is A Point-In-Time Computation].

**How long a snooze lasts, and the figure this file refuses to invent.** The length is the plugin option `snoozeDays`, expressed in whole days, and it is **not** an argument on the mutation — the published input carries one field and no interval [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. **This ticket set supplies no default for it and presents no figure as tuned or recommended**, because the repository declares no numeric target for a snooze interval; a deployment configures it, and an invalid or absent value prevents the server from starting rather than falling back to a number this file invented [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.6b Parameter Validation — Declaring A Parameter Is Not Knowing It Is Usable]. No engagement figure, no dismissal figure and no latency bound is asserted anywhere in this file, and where such a figure would conventionally appear section 5 asserts a verifiable state instead.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation under test, so a failing criterion points at a single published contract. Criteria name operations and their arguments and never a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. The five required coverage classes map onto them as follows: valid input is AC-1, invalid input is AC-2, an error naming the exact type returned is AC-4, an edge case is AC-5, and the assertion that an existing operation is unchanged is AC-6 and AC-7. AC-3 carries the non-disclosure assertion the parent feature's test matrix makes mandatory for this operation [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5.1 Surface Ownership And Test Matrix].

Six properties of the operation are stated once here rather than repeated in every criterion.

- **The payload has exactly two readings on the wire and four in the data.** A true `snoozed` with the updated signal is returned only where an entry the caller owns in the active channel moved into the snoozed state or was already there. A false `snoozed` with a null signal is returned for all four of a variant the buyer never bought, a variant whose entry belongs to another customer, an entry in another channel, and an entry that is not currently due — and those four are indistinguishable from outside by design [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces].
- **The write is synchronous.** It enqueues no job and schedules no task, so it has no asynchronous trigger and no observable completion signal to name. The recompute that writes and re-evaluates the rows is story 05-02's work and names its own trigger and signal there. No criterion below asserts that something happens eventually.
- **Every entry acted on derives from placed orders only**, on the columns and exclusions named in the preconditions block above, so no criterion below reads a cart and none alters one.
- **Every request is channel-scoped and language-scoped**, on the token and language code named in the preconditions block above. The payload holds no string of its own, so no field below varies by language.
- **The payload carries no monetary field.** No criterion below asserts a price. Were a deployment to extend the payload, any monetary value would be an integer in the smallest unit of its currency stated alongside its currency code, which the order carries [packages/core/src/entity/order/order.entity.ts:L142] and which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A decimal monetary value is a defect rather than a formatting preference.
- **No numeric target is asserted, because this repository declares none.** Every criterion below substitutes a verifiable state assertion for the figure a criterion of this kind would conventionally carry — an exact entry count, an exact state value drawn from a closed three-member enumeration, an exact error type name, or an exact field set. The single numeric figure in this file is the line-coverage target in section 10, which is supplied by the requirements rather than invented.

**Three criterion forms were considered and rejected, and the reasons are recorded here rather than left for an implementer to discover against a red test.**

The first was a criterion asserting that a non-positive snooze interval is refused with the platform's own input-error type [packages/core/src/common/error/errors.ts:L27]. **It is not expressible against the published contract.** The input declares exactly one field, `productVariantId`, and no interval; the length of a snooze is a deployment-configured plugin option rather than an operation argument [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]. There is therefore no scalar on this operation whose range a caller could violate, and a criterion written against one would be asserting against an argument the schema does not declare. The invalid-input class is exercised in AC-2 against the one field that does exist.

The second was a criterion asserting that snoozing another customer's entry returns the platform's forbidden-access error. **It would break a contract the parent feature settled.** That response is required to be identical field by field to the response for an entry that exists in no row, so that neither discloses which case occurred [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5.1 Surface Ownership And Test Matrix]. The third was a criterion asserting the exit from the snoozed state, **and it is now written rather than withheld**. ## 7. Edge Cases

Five scenarios. The three unconditionally required categories are the first three; the fourth is the idempotence case this story owns; the fifth covers the conditional channel category, which applies because the channel is part of every entry's identity. **Four of the five resolve to *proceed* rather than to a block or a warning**, and that is stated honestly rather than force-fitted into a failure this write does not have. The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — the buyer holds no replenishment signal at all
   * Given a Returning Buyer is authenticated in the active channel and holds zero `PurchaseCadence` entries in that channel, so no entry exists in any state, and a variant exists in the catalogue
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant
   * Then proceed with the normalized negative payload: `snoozed` equals false, `signal` is null, no row is created and no error entry of any type is returned. Naming the exact types so the outcome is unambiguous, **neither is raised** — not the platform's forbidden-access error `ForbiddenError` [packages/core/src/common/error/errors.ts:L67], which is reserved for a session carrying no active user, and not its input-error type [packages/core/src/common/error/errors.ts:L27], because an authenticated buyer naming a variant that addresses no entry is a specified outcome rather than a failure path [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.12 The Error Vocabulary]

* Scenario: An item unavailable, deleted or disabled since the last purchase — the variant an entry names is now disabled or soft-deleted
   * Given a Returning Buyer holds exactly two entries in the active channel whose state is the due member of `ReplenishmentSignalState`, and since those two entries were written one of the two variants has had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] while the other has been soft-deleted, its `deletedAt` column now carrying a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming each of the two variants in turn
   * Then proceed and **snooze both entries rather than refusing either** — this is the deterministic ruling for this operation, stated as a choice between the two available behaviours rather than left open. A soft delete sets a timestamp and does not remove the row, so both entries are still present and addressable. The conditional update filters on the owning customer, the channel, the variant and the current state, and on none of `enabled`, `deletedAt`, price or stock, so both move into the snoozed state and each returns `snoozed` equal to true. **A stale entry is removed neither by this write nor by the next recompute** — the placed orders it derives from still exist, so its row is refreshed rather than dropped — so the write never fails, never repairs an entry and never leaves the buyer with a prompt they cannot silence [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.11 A Due Signal Is A Point-In-Time Computation]. Refusing the snooze here would be the worse ruling on its own terms: it would leave the buyer unable to silence a prompt for an item they can no longer buy

* Scenario: A price changed since the last purchase — the catalogue price of a variant an entry names has moved
   * Given the price of a variant named by one of this buyer's due entries has changed since the order that entry was derived from was placed
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant
   * Then proceed with no warning and no price field: **this operation neither reports nor reacts to a price change, and that boundary is explicit rather than an oversight.** The `PurchaseCadence` table holds no monetary column and the published payload declares no monetary field, so a snooze carries no price that a movement could invalidate, and a price change alters no snooze. A buyer is made aware of a price movement before committing through the `reorderPreview` operation that FEATURE-001-03 owns; duplicating that comparison here would put two answers to one question in two features [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. Copying a price onto a cadence row so that a snooze could hold one would be a defect rather than an optimisation

* Scenario: An idempotent repeat — the buyer snoozes an entry that is already snoozed
   * Given a Returning Buyer is authenticated in the active channel and holds exactly one entry there whose state is already the snoozed member of `ReplenishmentSignalState`, carrying the non-null `snoozedUntil` the earlier snooze stored and the row identifier that call returned
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that same variant again, and then a third time
   * Then proceed and report success on every call: each returns `snoozed` equal to true with the state still reading the snoozed member, and **the stored row is byte-identical after the second and third calls to what it was after the first.** The deadline is left untouched rather than extended, it is not recomputed from the later call's timestamp, the intervals are not added together, no second row is created and no error entry of any type is returned. The behavioural consequence is stated because a buyer will meet it: **a snooze cannot be lengthened by repeating it**, and the entry returns at the deadline the first call set [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.5 Named API Surfaces]

* Scenario: A channel, currency or language mismatch — the entry was derived under a different channel token from the one the snooze carries
   * Given a Returning Buyer holds exactly one due entry for a variant under a first channel token and holds no entry for that variant under a second channel token, the two tokens being distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], with each request's language resolving from its own channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When that customer executes the `snoozeReplenishmentSignal` mutation naming that variant while carrying the second channel token
   * Then proceed with the normalized negative payload under that token: `snoozed` equals false, `signal` is null, and **the entry under the first token is still in the due state and was not snoozed.** Repeating the mutation under the first token then returns `snoozed` equal to true for that entry. Cadence is derived per channel and the channel is part of each entry's identity, so a snooze applied under one token has no effect under another and no argument widens the scope beyond the token's channel. No currency conversion and no cross-channel reconciliation occurs, and none can, because the payload carries no monetary value at all

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this mutation performs no availability check and makes no commitment; the staleness a snooze does have is the derived entry's own, and it is carried by the second and third scenarios above. A concurrent modification or race is real on this operation and is not omitted — it is the recompute overwriting a row a buyer snoozes mid-run, which the parent feature names as a worst case whose result is a signal silently returning to the due state, and which it assigns to the recompute's design rather than to this write [tickets/EPIC-001/FEATURE-001-05-purchase-cadence-and-replenishment.md:§2.8 Figure F5-STATE]. This story's contribution to that defence is stated in section 6 as a single conditional update over the current state rather than a read followed by a write, so two snoozes of the same entry cannot interleave into two rows, and it is asserted in section 5 as AC-5.
