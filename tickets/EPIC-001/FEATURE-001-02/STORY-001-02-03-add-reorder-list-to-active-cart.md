## 1. Story Title

**Materialise a saved reorder list into the active cart through the platform's existing bulk add, so that a returning buyer turns a curated list into cart lines in one call and receives a named outcome for every list line.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Add a reorder list to the active cart** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work is the **second source form** of a mutation that already exists after STORY-001-02-01. The mutation gains no new field and no new operation: it gains the ability to resolve its source from `reorderListId` instead of `sourceOrderId`, projecting one requested line per list line and taking each quantity from the list line's own stored integer rather than from purchase history [tickets/EPIC-001-reorder-and-replenishment.md:§9.2.1 Every Published Operation Has Exactly One Owning Story]. Everything downstream of the projection — prevalidation, the single core call, the quantity-delta reconciliation, the per-line report — is the contract the parent feature fixes for all four stories and this story reuses without restating [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract].

**Four neighbouring pieces of work could be mistaken for part of this one and are not.** Creating, naming, editing and reading a list is FEATURE-001-01, and this story defines no list operation and no list table [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces]. **Reordering from a list that is shared with the caller rather than owned by them is FEATURE-001-06, whose story 06-03 owns it together with `ReorderPermissionDeniedError`; this story covers the buyer's own list only** [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.5 Named API Surfaces]. Reading price and availability deltas before the commit is FEATURE-001-03's `reorderPreview`, named here and not defined here [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.5 Named API Surfaces]. Choosing what to do about a line that cannot be added — skip, reduce, substitute or abort — is FEATURE-001-04 and its story 04-01; this story reports outcomes and offers no choice [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.3 The Four Resolution Outcomes]. The audit rows and typed events that record what this story did are FEATURE-001-07's, and neither is defined here [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched].

**One property of a list makes this path different from the order path, and it is load-bearing rather than incidental: a list line stores no price and no stock reservation.** It holds a parent list id, a `ProductVariant` id and an integer quantity, and nothing else [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]. A reorder from a list therefore prices every line from the current catalogue at add time, through the bulk add's own single adjustment pass [packages/core/src/service/services/order.service.ts:L751], and this story copies no monetary value and performs no arithmetic on money. Reporting an in-cart change after the add is already done by the platform's existing calculated getters `unitPriceChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L168] and `unitPriceWithTaxChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L181], which this story must not duplicate [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated].

## 2. Source Traceability

The label is a **quoted objective clause**. The clause is C1 [tickets/EPIC-001-reorder-and-replenishment.md:§10.2 Objective-Clause Map], reproduced verbatim:

> "Make it effortless for returning buyers to reorder the items they purchase regularly"

The label is a quoted clause and **not `Inferred`**. Twelve of the twenty-five stories in this set carry the inferred label naming the requirements block they derive from, and this story is not one of them [tickets/EPIC-001-reorder-and-replenishment.md:§10.1 The Headline Number, Reported At Its True Value].

**Clause C1 decides which of the two source forms this story is, and the reasoning is worth stating because it is the clause's own wording that settles it.** The clause speaks of "the items they purchase regularly" — a standing set the buyer maintains — rather than of one past order. A placed order is a record of a single event and is the source clause C2 serves through STORY-001-02-01 and STORY-001-02-02; a saved list is the buyer's own curated statement of what they buy repeatedly, which is why the list source is the form C1 maps onto. Both are recorded against C1 and C2 respectively in the epic's clause map rather than assigned here.

**What the clause does not license is a figure.** "Effortless" is a claim about experience, and this repository declares no numeric business target of any kind, an absence the epic reports as a finding rather than filling in [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers]. The observable claim this story is measured against is therefore a **countable** one — one call in place of one add-to-cart call per list line — and every criterion in section 5 asserts an exact count, an exact integer quantity, an exact error type name or an exact enum member instead of a rate, a duration or a lift.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when the file is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Returning Buyer,
I want to turn one of my saved reorder lists into lines on my current cart with a single call, at the quantities I stored on the list,
So that a standing repeat purchase costs me one call instead of one add-to-cart call per item, and every list line that did not land is named back to me with its own outcome.
```

### 4.1 INVEST Criteria

- **Independent** — **not fully, and the dependency is disclosed rather than glossed.** This story cannot be delivered before FEATURE-001-01 supplies a list to read, because `ReorderListLine` rows must exist before there is anything to project, and it cannot be delivered before STORY-001-02-01 supplies the mutation and the service it extends. The parent feature states the same edge from its own side and classifies it [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§4.3 Intra-Feature Story Order]. **What it still delivers on its own once a list exists is a whole buyer capability rather than a fragment of one:** a buyer who has curated a list can put that list on their cart, and no other story in this set delivers that. Section 8 names the minimum prerequisite set and nothing beyond it.
- **Negotiable** — parts of the shape are open and parts are deliberately not. Whether a list is addressed by its id alone or by id together with a subset of its lines through `lineSelections` is a design choice this story may settle either way, since the selection input already names `reorderListLineId` for exactly this purpose [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. **What is not negotiable** is the ascending-identifier ordering the `requestIndex` is assigned in, the quantity coming from the list line rather than from history, the single call into the existing bulk add, and the prevalidation pass that keeps an unresolvable variant off that call.
- **Valuable** — it is the point at which a curated list stops being a private record and becomes a cart, which is the clause C1 promise in section 2 and the one step of the buyer journey this story owns [tickets/EPIC-001-reorder-and-replenishment.md:§2.5 The Returning-Buyer Journey This Epic Builds].
- **Estimable** — the surface is bounded and countable: zero new tables, zero new operations, one new branch in an existing service method, and one source resolution through a service FEATURE-001-01 already publishes [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.5 Named Services]. Section 9 carries the numbers and transcribes them.
- **Sized Appropriately** — one source-resolution branch, one projection step and one set of criteria over zero new tables and zero new migrations. It sits at five points on the epic's rubric, the value for consumption of a core service with per-item outcome accumulation, and is not a candidate for splitting: the projection and the report it feeds cannot be delivered separately, because a projection with no report is unobservable.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact line count, an exact integer quantity, an exact enum member or an exact error type name. No criterion asserts a state that has to be judged.

### 4.2 Demonstration Path

One path, ending on **exactly one named operation** with its inputs and its expected response, observable to a non-coder. Because a list has to exist before it can be materialised, the steps that build one are stated as **prerequisites** rather than as part of the demonstration, so the demonstration itself remains a single call.

Every command carries its own working directory, matching the form the contribution guide documents, so the steps can be pasted in sequence without a second directory change failing against the first.

The command and its working directory are the pair the contribution guide documents for seeding [CONTRIBUTING.md:L147-L150] and for starting the server [CONTRIBUTING.md:L178-L181], and the two scripts are the ones the package declares [packages/dev-server/package.json:L8] and [packages/dev-server/package.json:L13]. The second command does not return: it occupies terminal 1 until interrupted, so every step below is issued from terminal 2. **The five read-only preflight checks that make these two commands fail plainly rather than obscurely on a bare checkout are set out once by STORY-001-02-01 and are deliberately not repeated here** [tickets/EPIC-001/FEATURE-001-02/STORY-001-02-01-reorder-complete-past-order.md:§4.2 Demonstration Path].

**Prerequisite B — a deterministic customer identity.** The seed creates ten customers [packages/dev-server/populate-dev-server.ts:L46] and gives every one of them the password `test` [packages/testing/src/data-population/populate-customers.ts:L19]. **No email address is written down in this file**, because the seeded addresses are generated rather than fixed literals [packages/testing/src/data-population/mock-data.service.ts:L30]; the address is read out of the running server instead. Sign in to the Admin UI as `superadmin` with password `superadmin`, the documented default pair [CONTRIBUTING.md:L189-L192], open the customer list and take one `emailAddress` [packages/core/src/entity/customer/customer.entity.ts:L42]. Then authenticate over the Shop API as that customer with the password `test`.

**Prerequisite C — one list holding one line, and one active cart.** Both are built through operations that already exist by the time this story runs. Create the list with `createReorderList` and add one line at quantity 2 with `addItemToReorderList`, the two FEATURE-001-01 operations owned by STORY-001-01-01 and STORY-001-01-02 [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces]; note the list id it returns. Then create an active cart by adding one unrelated variant at quantity 1 with the existing `addItemToOrder` mutation [packages/core/src/api/schema/shop-api/shop.api.graphql:L72], so that the cart holds exactly one line before the demonstration begins.

**The demonstration — one mutation, from terminal 2.** The shape below is what this story proposes; it does not exist in this checkout and is written as a target, not as a citation. Substitute the list id from prerequisite C.

```graphql
mutation {
  applyReorderToActiveOrder(
    input: { source: { reorderListId: "<the list id>" } }
  ) {
    ... on ReorderResult {
      requestOutcome
      order { id totalQuantity lines { id quantity } }
      lineOutcomes {
        requestIndex
        reorderListLineId
        productVariantId
        requestedQuantity
        addedQuantity
        orderLineId
        outcome
        errorCode
      }
      unattributedErrorCodes
      sourceCurrencyCode
      targetCurrencyCode
    }
    ... on NoReorderableLinesError { errorCode message }
    ... on ReorderListNotFoundError { errorCode message }
    ... on NoActiveOrderError { errorCode message }
    ... on OrderModificationError { errorCode message }
  }
}
```

Every type, field, enum and union member in that selection is transcribed from the one place this feature declares them, and this story invents none of its own [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. The `lineSelections` and `lineResolutions` fields the same input declares are deliberately absent from this call: the first is STORY-001-02-02's subject and the second belongs to FEATURE-001-04 and is inert until that feature ships.

**The expected response, stated as an exact observable.** For the prerequisites above — a list of one line at quantity 2, and a cart already holding one line of a different variant — the response carries a `requestOutcome` of `SETTLED`, an `order` holding exactly two lines whose `quantity` values [packages/core/src/entity/order-line/order-line.entity.ts:L97] are 1 and 2 and whose `totalQuantity` is 3 [packages/core/src/entity/order/order.entity.ts:L286], `lineOutcomes` of length 1 whose single entry carries `requestIndex` 0, an `outcome` of `ADDED`, an `addedQuantity` equal to its `requestedQuantity` of 2, a set `orderLineId` and a null `errorCode`, `unattributedErrorCodes` holding zero entries, and `sourceCurrencyCode` equal to `targetCurrencyCode` equal to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A non-coder can read that response against the cart they built in prerequisite C and see one line become two without having selected a variant.

## 5. Acceptance Criteria

Seven criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria are expressed in operations, their arguments, and entity and column names as database preconditions; **no criterion is expressed in terms of a resolver class, a file path or an internal method name**, and where a criterion rests on a fact about the existing platform it carries that fact's inline citation as evidence rather than making the cited path part of the assertion. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

Three preconditions hold for every criterion without being repeated in each, because they are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]: an authenticated session, a channel resolved from the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L58] and held on the `token` column [packages/core/src/entity/channel/channel.entity.ts:L62], and a language resolved from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. Where an outcome varies with them the criterion names the token and the language code.

**How the seven map onto the five required coverage classes.** Valid input is AC-1. Invalid or incomplete input is AC-4, with AC-5 covering the input that is well formed but over a bound. An error naming the exact type returned is AC-2, AC-3, AC-4 and AC-5. An edge case is AC-6. An existing operation asserted unchanged is AC-7, which is the named regression the parent feature assigns to this story rather than one chosen here [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.1 Operation Ownership And Test Matrix]. **AC-2 and AC-3 are two criteria rather than one on purpose:** a single criterion covering "the reorder could not proceed" is satisfied by a test of either branch, and the two branches return different error results for different reasons — which is the swap the parent feature warns is testable rather than a matter of interpretation [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling].

The error vocabulary these criteria may name is closed and is split across **two levels**, a distinction the parent feature fixes and this story asserts on both sides [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. **Request level** is the four error members of the plugin-owned `ApplyReorderResult` union — `NoReorderableLinesError`, `ReorderListNotFoundError`, `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] and `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80] — and a request-level result means nothing was added at all. **Line level** is a `ReorderLineOutcomeCode` on each entry of `lineOutcomes`, optionally carrying the `errorCode` of one of the existing types below, and a line-level outcome sits inside a **settled** response, because a reorder in which one line of five failed is a success carrying a report.

The existing types whose codes may appear at line level are the five members of the closed core union [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], listed as bullets here rather than in the schema's own union form:

- `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80]
- `OrderLimitError`, carrying `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L37]
- `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44]
- `InsufficientStockError`, carrying `quantityAvailable` [packages/core/src/api/schema/common/common-error-results.graphql:L50]
- `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103]

`ReorderListNotFoundError` is declared by FEATURE-001-01 and is named here rather than introduced [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10 The Error Vocabulary This Feature Introduces]; `NoReorderableLinesError` is the single error result the parent feature declares [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]. Declaring either grows the published Shop `ErrorCode` enum automatically, which is a side-effect widening owned by the epic's collision section and by STORY-001-01-04, referenced here in this one line and **not** accepted in silence [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions] and [tickets/EPIC-001/FEATURE-001-01/STORY-001-01-04-read-reorder-lists-via-shop-api.md:§5. Acceptance Criteria].

Availability preconditions name `GlobalSettings.trackInventory` as true and `GlobalSettings.outOfStockThreshold` as 0, because those are the values the platform's saleable-stock path reads rather than the annotated Channel columns of the same names — the epic settles this as ruling R6 and this story follows it rather than re-deriving it [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings] and [tickets/EPIC-001-reorder-and-replenishment.md:§6.3 Repository Documentation Discrepancies].

AC-1: A list of exactly three lines materialises into an empty cart at its stored quantities, in ascending list-line order
* Given an authenticated Returning Buyer whose request carries the channel token of the active channel in the `vendure-token` header and resolves to the `languageCode` value `en`; **that buyer's active cart holds zero lines before the call**; `GlobalSettings.trackInventory` is true and `GlobalSettings.outOfStockThreshold` is 0; and one `ReorderList` row owned by that buyer and stored against that channel holds exactly three `ReorderListLine` rows whose stored integer quantities are 2, 1 and 4 in ascending row-identifier order, each naming a distinct variant that satisfies the enabled-and-not-deleted predicate the bulk add loads every variant with [packages/core/src/service/services/order.service.ts:L684-L689] and whose saleable quantity is at or above the quantity on its line
* When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list, no `lineSelections` and no `lineResolutions`
* Then the mutation returns `ReorderResult` whose `requestOutcome` is `SETTLED`; its `order` carries exactly three lines, in ascending list-line-identifier order, whose `quantity` values [packages/core/src/entity/order-line/order-line.entity.ts:L97] are 2, 1 and 4 and whose `totalQuantity` [packages/core/src/entity/order/order.entity.ts:L286] is 7; `lineOutcomes` holds exactly three entries with `requestIndex` values 0, 1 and 2 in that order, each naming the `reorderListLineId` it projected from, each `outcome` being `ADDED`, each `addedQuantity` equal to its `requestedQuantity`, each `orderLineId` set and each `errorCode` null; `unattributedErrorCodes` holds zero entries; and `sourceCurrencyCode` equals `targetCurrencyCode` equals the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88], with every monetary value on the returned order expressed as an integer in the smallest unit of that currency stated alongside that code [packages/core/src/entity/order/order.entity.ts:L142]

**Two notes on AC-1, because both are ways a faithful implementation could still fail it.** First, the report has **no separate errors or failures collection** and no criterion in this file describes one: a fully settled reorder is observed as every `lineOutcomes` entry carrying `ADDED` with a null `errorCode` together with `unattributedErrorCodes` holding zero entries, which is the parent feature's single-vocabulary rule and not a paraphrase of it [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. Second, the **empty-cart precondition is load-bearing** rather than tidy: the platform's write path sums the requested quantity with the quantity already held on the line for that variant before it clamps [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133], so a cart already holding one of the first variant would end at 3 rather than 2 and the criterion would fail against an implementation that did nothing wrong. Every criterion below that asserts an exact resulting quantity states the cart's prior state for the same reason.

AC-2: A deployment whose configured active-order strategy can neither resolve nor create a cart receives a typed refusal rather than an untyped error
* Given an authenticated Returning Buyer who owns a `ReorderList` in the active channel holding at least one line whose variant resolves and has addable quantity; that buyer's session holds no active order; and the deployment's configured active-order strategy set can neither determine nor create a cart from an empty strategy input, which is the one condition under which the target-cart resolution the parent feature specifies fails [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling]
* When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
* Then the mutation returns `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] as a typed member of its result union rather than surfacing an untyped server error; no cart line is written; no `ReorderList` or `ReorderListLine` row is modified; and the buyer still holds no active order

**The other branch of the same behaviour is settled, not left open, and it is stated here so this criterion is not misread as its opposite.** On any deployment whose configured strategy set can resolve or create a cart from an empty strategy input — which includes the default strategy and therefore every unmodified deployment — the same call **creates** the cart and returns `ReorderResult`. The published schema is what grounds that: the active-cart read states its value is null until an order is created via `addItemToOrder` [packages/core/src/api/schema/shop-api/shop.api.graphql:L7-L11], and a reorder is an add, so it creates. The parent feature rules both halves and this story asserts the second [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling]. `NoActiveOrderError` therefore means "the cart could not be determined or created" and never "the list held nothing", which is AC-3; returning either one for the other's condition is a defect a test catches rather than a matter of reading.

AC-3: A list that resolves to zero requested lines is refused whole, and nothing at all is written
* Given an authenticated Returning Buyer; a `ReorderList` row owned by that buyer in the active channel holding zero `ReorderListLine` rows; and an active cart holding exactly one line of an unrelated variant at `quantity` 1
* When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that empty list
* Then the mutation returns `NoReorderableLinesError`; the cart still holds exactly one line at `quantity` 1 and its `totalQuantity` is still 1; no `ReorderList` or `ReorderListLine` row is modified; and **no partial write occurred**, because the resolver runs the source read and the write as one unit of work that commits or rolls back together [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract]

**The condition this criterion does not cover is the one most likely to be conflated with it.** A list whose every line resolves to **zero addable quantity** is not this error: the source resolved to lines rather than to none, so the mutation returns `ReorderResult` with `requestOutcome` `SETTLED`, each `lineOutcomes` entry carrying `NOT_ADDED_OUT_OF_STOCK` and an `addedQuantity` of 0, and the cart's line count exactly as it was. `NoReorderableLinesError` is reserved for a source that resolves to zero requested lines in the first place — an empty list here, and an empty selection in STORY-001-02-02 [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]. FEATURE-001-06 defers the empty-shared-list case to this story on the same reading [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.5 Named API Surfaces].

AC-4: Every list reference that does not resolve to a list of the authenticated buyer in the active channel yields one indistinguishable result and adds no cart line
* Given an authenticated Returning Buyer whose active cart holds exactly one line, and each of these three references in turn: one `reorderListId` matching no `ReorderList` row at all; one matching a row whose owning customer is a different customer; and one matching a row stored against a channel other than the one the request's token resolves to
* When `applyReorderToActiveOrder` is executed with each reference
* Then all three calls return `ReorderListNotFoundError`; the cart carries exactly the one line it carried before each call; no `ReorderListLine` row of any customer is read on the caller's behalf; and **the three responses are identical to one another**, so a caller cannot tell an absent list from another customer's list and the existence of another customer's list is not disclosed

**Three short notes, none of them re-argued here.** Ownership is enforced in the service layer over the list and the target cart alike, because the gate a buyer-facing operation carries is not itself a control — the epic's collision entry states the platform's own warning and ruling R3 makes the predicate the whole of the control [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions] and [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. The channel branch is a hard boundary rather than a filter a caller may widen: a list stores the channel it was created under, so a list created under one token is not readable under another [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping]. And a request setting **both** `sourceOrderId` and `reorderListId`, or neither, is a request-level input failure rather than one of these three outcomes — a distinct condition the parent feature fixes on the source input itself [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces].

AC-5: A list larger than the cart can hold is bounded by the platform's own limit, and every refused line is named rather than dropped
* Given an authenticated Returning Buyer whose active cart holds zero lines; the deployment's order-items limit configured to a value the platform reads when it validates every item of the bulk add through its four-step validation chain [packages/core/src/service/services/order.service.ts:L675-L679]; and a `ReorderList` owned by that buyer whose resolved lines and stored quantities together exceed that configured value, while every one of its variants has a saleable quantity at or above the quantity on its line
* When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
* Then the lines that fit within the configured value are written and each carries an `outcome` of `ADDED`; every further line carries an `outcome` of `NOT_ADDED_LIMIT_REACHED` with an `addedQuantity` of 0 and an `errorCode` naming `OrderLimitError` [packages/core/src/api/schema/common/common-error-results.graphql:L37] whose `maxItems` equals the configured value [packages/core/src/api/schema/common/common-error-results.graphql:L40]; `lineOutcomes` holds exactly one entry per resolved list line in `requestIndex` order so the buyer sees which lines were refused rather than that some were; `requestOutcome` is `SETTLED`; and **no figure in this criterion is supplied by this story** — the bound asserted is the deployment's own

**This is the list half of a bound the parent feature splits across two stories**, the order half belonging to STORY-001-02-01 [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.1 Operation Ownership And Test Matrix]. A **plugin-level** bound on projected source lines is a different thing and is deliberately not asserted: the list itself is already capped by `ReorderPluginOptions.maxLinesPerList` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency], and whether the plugin declares a separate maximum on projected lines, and whether an over-bound source is refused before projection or truncated with the remainder reported, is an open product decision this story may not settle because no value exists to assert against [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions] and [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§4.5 Open Decisions This Feature Waits On]. **One contract detail is reported rather than absorbed, in the parent feature's own terms:** its definition of done describes an over-bound source as refused with `OrderLimitError` at request level [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§5. Definition of Done (Feature-Level)], while the union it publishes carries five members and its own reading places that error's code on individual outcomes and never at the top level [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. Both cannot hold; reconciling them is the parent feature's to settle, and this criterion asserts only the line-level form the two statements agree on.

AC-6: A list line naming a variant already on the cart accumulates onto that line instead of creating a second line for the same variant
* Given an authenticated Returning Buyer whose active cart already holds **exactly one** line for one variant at `quantity` 1 [packages/core/src/entity/order-line/order-line.entity.ts:L97]; `GlobalSettings.trackInventory` true and `GlobalSettings.outOfStockThreshold` 0; a `ReorderList` owned by that buyer holding exactly one `ReorderListLine` naming that same variant at a stored quantity of 2; and a saleable quantity for that variant of at least 3
* When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
* Then the cart holds **exactly one** line rather than two, that line's `quantity` is exactly 3, the order's `totalQuantity` is 3 [packages/core/src/entity/order/order.entity.ts:L286], and `lineOutcomes` holds exactly one entry carrying `requestIndex` 0, an `outcome` of `ADDED`, a `requestedQuantity` of 2, an `addedQuantity` of 2, a null `errorCode` and the `orderLineId` of the line that already existed

**Why this behaviour is the platform's rather than the plugin's, and why it still needs a criterion.** The quantity clamp sums the requested quantity with the quantity already on the line for that variant before clamping [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133], so accumulation is what the write path does and a plugin that tried to produce a second line would be working against it. The criterion exists because the *report* is the plugin's: the `addedQuantity` above is derived from the target order's per-variant line-quantity delta rather than from any position in the core's own error collection, which carries no key [packages/core/src/service/services/order.service.ts:L665], and this is the case where a delta and a naive read of the resulting line quantity differ. The saleable quantity behind the precondition is read **point-in-time**, can go stale between the read and the commit, and is **not a reservation** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.10 A Point-In-Time Read Is Not A Reservation].

AC-7: The existing bulk add operation is unchanged after the plugin is registered
* Given the new plugin is registered in the dev-server plugin array [packages/dev-server/dev-config.ts:L121-L155] and the dev-server custom-fields object is still empty [packages/dev-server/dev-config.ts:L116], because this story declares no custom field on any core entity
* When `addItemsToOrder(inputs: [AddItemInput!]!): UpdateMultipleOrderItemsResult!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L74] is executed against the generated schema
* Then its argument list, its return type and its nullability are identical to their declaration before registration; `AddItemInput` still declares exactly `productVariantId` and `quantity` [packages/core/src/api/schema/shop-api/shop.api.graphql:L303-L305]; `UpdateMultipleOrderItemsResult` still declares exactly `order` and `errorResults` [packages/core/src/api/schema/shop-api/shop.api.graphql:L298-L300]; the root `Query` type still declares nineteen root queries [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52]; and the existing `shop-order` end-to-end specification passes unmodified [CONTRIBUTING.md:§End-to-end Tests]

**This operation and no other is the named regression for this story**, assigned by the parent feature's matrix rather than chosen here, because the list path writes through the service behind it [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.1 Operation Ownership And Test Matrix]. The two mutations whose signatures a custom field would widen — `addItemToOrder` [packages/core/src/api/schema/shop-api/shop.api.graphql:L72] and `adjustOrderLine` [packages/core/src/api/schema/shop-api/shop.api.graphql:L80], each carrying the schema's own admission of that widening in its docstring [packages/core/src/api/schema/shop-api/shop.api.graphql:L71] and [packages/core/src/api/schema/shop-api/shop.api.graphql:L79] — are asserted unchanged as a merge gate in section 10 rather than as a second criterion here, because STORY-001-02-01 already carries them as criteria and this story adds no custom field of its own.

## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story reads availability and projects rows across a request scope. Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

* Scenario: Category — zero, null or empty collection. A list emptied by removing its last line, rather than one that was never populated.
   * Given a `ReorderList` row owned by the authenticated Returning Buyer in the active channel that once held one `ReorderListLine` and now holds zero, because the owner removed the last line through FEATURE-001-01's own line-removal mutation [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces], and an active cart holding exactly one line of an unrelated variant
   * When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
   * Then the mutation returns `NoReorderableLinesError`, the cart still holds exactly one line at its original quantity, and no row of either list table is modified. **This is the same outcome AC-3 asserts, reached from the other side on purpose:** AC-3 covers a list created and never populated, and this scenario covers the state a list arrives at through deletion, which is the state a long-lived list is far more likely to be in. A test that covers only the never-populated case leaves the row-removal path unexercised

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. One list line's variant no longer resolves.
   * Given a `ReorderList` owned by the authenticated Returning Buyer holding exactly four `ReorderListLine` rows, one of which names a variant that no longer satisfies the `enabled: true` and null `deletedAt` predicate the bulk add loads every variant with [packages/core/src/service/services/order.service.ts:L684-L689], or whose parent product has since been disabled, which raises a thrown error rather than an accumulated one [packages/core/src/service/services/order.service.ts:L692-L693]
   * When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
   * Then **the other three lines are added** and the fourth is reported as `NOT_ADDED_VARIANT_UNAVAILABLE` with an `addedQuantity` of 0 against its own `requestIndex`, because the plugin service **excludes that line before delegating** and never passes it to the core call. The requirement is on the plugin and it is not a footnote: there is no `try` and no `catch` in that method, so a single unresolvable variant would abandon the loop and the surrounding transaction would discard every line already written, making one line disabled since the last purchase enough to lose the whole reorder [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds]. **A saved list makes this the ordinary case rather than a rare one**, because a list is long-lived by construction and its rows are not refreshed when the catalogue changes — the platform's variant deletion is a soft delete, so the row survives the variant [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]. What stays out of scope here is the buyer's **choice** about the withheld line: skip, reduce, substitute or abort is FEATURE-001-04 and its story 04-01, and the resolution input is declared but inert until then [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.3 The Four Resolution Outcomes]
   * Note: where a variant instead becomes unresolvable **between** that exclusion read and the core call, the response carries the request-level outcome `ABORTED_UNRESOLVABLE_SOURCE_LINE`, names the variant that ended the request and carries zero per-line entries — the residual race the parent feature specifies and the reason the per-line guarantee is always stated for a settled request [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6b The Request-Level Outcome]

* Scenario: Category — a price changed since the last purchase. The variant now prices at a different integer than when the buyer added it to the list.
   * Given a `ReorderListLine` naming a variant the buyer added when it priced at 129900, which now prices at 134900, both integers in the smallest unit of the currency named by the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88], and whose gross-or-net reading is governed by the channel's `pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113] and by the resulting line's own `listPriceIncludesTax` [packages/core/src/entity/order-line/order-line.entity.ts:L128]
   * When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
   * Then the new cart line is priced from the **current catalogue** by the bulk add's own single adjustment pass [packages/core/src/service/services/order.service.ts:L751] and no historical figure is carried onto it, because **a list line stores no price and holds no reservation** [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]; the resulting line records `initialListPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L113] and `listPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L121] from that pass; and this story computes no delta and performs no arithmetic on money. Reporting a delta **before** the commit is FEATURE-001-03's `reorderPreview` [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.5 Named API Surfaces], and reporting one **after** the add is already done by the platform's existing calculated getters `unitPriceChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L168] and `unitPriceWithTaxChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L181], which this story must not duplicate [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]

* Scenario: Category — a point-in-time read gone stale between check and commit. Another order allocated the stock after the list line was read.
   * Given the plugin service read a list line's variant as having addable quantity during prevalidation, and between that read and the single core call another order allocated the stock behind that variant
   * When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
   * Then the authoritative decision is the one the core call makes at write time through its own four-step validation chain [packages/core/src/service/services/order.service.ts:L675-L679], and the affected line resolves to an `outcome` of `ADDED_AT_REDUCED_QUANTITY` or `NOT_ADDED_OUT_OF_STOCK` whose `errorCode` names `InsufficientStockError` with the `quantityAvailable` integer it carries [packages/core/src/api/schema/common/common-error-results.graphql:L53] — never a request-level failure and never a retry loop. **Prevalidation does not close this window and is not meant to:** it reads the same saleable quantity the commit will read, moments earlier, and where the two disagree the commit wins. A read that showed a line as addable confers no entitlement to add it, because **availability is read point-in-time and nothing in this story reserves stock** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.10 A Point-In-Time Read Is Not A Reservation]

* Scenario: Category — a channel, currency or language mismatch between the list and the reorder context.
   * Given a `ReorderList` created under one channel `token` [packages/core/src/entity/channel/channel.entity.ts:L62] while the reorder request carries a different token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L58]; or the resolved channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differs from the currency the buyer saw when curating the list; or the request resolves to a language other than that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When `applyReorderToActiveOrder` is executed with a `source` whose `reorderListId` names that list
   * Then the outcome is deterministic in all three limbs. A list stored against another channel **does not resolve at all** and returns `ReorderListNotFoundError`, identically to an absent list, because a list is readable only under the token it was created against and that is a hard boundary rather than a filter a caller may widen [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping]. A currency difference **does not block the reorder**: the request proceeds, every line is priced in the target cart's currency by the core call's own adjustment pass, both codes are reported through `sourceCurrencyCode` and `targetCurrencyCode`, **no conversion is attempted and no line is skipped for currency alone** — which is safe here precisely because a list line carries no monetary value for this story to convert [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. A language difference changes only the translated variant-derived fields the existing catalogue read path resolves, because the outcome report's own fields are identifiers, integer quantities and enum members, none of which is language-varying, and a buyer-supplied list name is returned as the buyer entered it in every language code [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping]

## 8. Dependencies

Stated in the epic's dependency form — the required thing, then why it is required and where it belongs — with every entry classified as a **data dependency** or a **shared code path**, because a prerequisite without a classification cannot be sequenced. The two sub-sections are kept apart deliberately: the first is what has to be brought into existence before this work can run, and the second is what already ships and is consumed as it stands.

### 8.1 The Minimum Prerequisite Set — Five Entries, Three Of Them Stories

**True independence is impossible for this story and the fact is documented rather than dressed up.** It is the one story in its feature that reaches across a feature boundary for its source, and the parent feature classifies the edge in the same terms from its own side: a data dependency on one populated reorder list, plus the same shared code path the feature's other stories share [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§4.3 Intra-Feature Story Order]. The set below is the **minimum** and nothing is listed that this work can run without.

- **Story `STORY-001-01-01` — shared code path:** the `ReorderList` and `ReorderListLine` tables, together with the single additive migration that creates them, so there is a row shape to project from. Both tables and that migration belong to that story and to FEATURE-001-01, and neither is created or altered here [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched].
- **Story `STORY-001-01-02` — shared code path:** `addItemToReorderList`, the operation that puts a `ReorderListLine` row with its stored integer quantity in place. Without it a list can exist and hold nothing, so the table alone is not enough for this story to have a source; that operation belongs to that story [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces].
- **Story `STORY-001-02-01` — shared code path:** the `applyReorderToActiveOrder` mutation itself, its resolver, the plugin service, the prevalidation pass, the single core call and the correlation contract. This story adds a source-resolution branch to all of that and publishes no operation of its own [tickets/EPIC-001-reorder-and-replenishment.md:§9.2.1 Every Published Operation Has Exactly One Owning Story].
- **Configuration, the project bootstrap — shared code path:** the plugin module must exist and be registered in the dev-server `plugins` array before the mutation is reachable at all [packages/dev-server/dev-config.ts:L121-L155]. **It does not belong to this piece of work:** the epic declares it a prerequisite of the whole epic, performed once and owned and priced by no story [tickets/EPIC-001-reorder-and-replenishment.md:§7.9 Project Bootstrap]. That array is one of only two files a future implementation may touch outside the plugin package; naming it here is a documentation act and licenses no edit by this ticket [tickets/EPIC-001-reorder-and-replenishment.md:§11.7 The Two Permitted Configuration Exceptions].
- **Data, one populated list owned by the authenticated customer — data dependency:** one `ReorderList` row owned by that customer in the active channel holding at least one `ReorderListLine`. The list path has no source without it, and a list holding zero lines is a required edge case rather than an untested state, asserted by AC-3 and by the first scenario in section 7.

**Two things a reader might expect in that set are deliberately absent, and each absence is a claim this story is willing to be held to.** `STORY-001-01-04` owns the buyer-facing read of lists — `activeCustomerReorderLists` and `activeCustomerReorderList` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces] — and **is not a prerequisite of this story**, because the plugin resolves its source rows through FEATURE-001-01's list service inside the request rather than through a public query [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.5 Named Services], and the list identifier reaches a caller from the create mutation's own response. And **a pre-existing active order is not a prerequisite either**, because on a default-strategy deployment this mutation creates the cart rather than requiring one [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling]; where a criterion asserts an exact resulting quantity it states the cart's prior state as a **precondition of that criterion**, which is a different thing from a dependency of the work.
