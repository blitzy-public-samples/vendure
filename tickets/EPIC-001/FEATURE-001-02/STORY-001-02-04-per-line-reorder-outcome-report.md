## 1. Story Title

**Return a per-line outcome report for every reorder attempt, mirroring the platform's published bulk-add result, so that a returning buyer sees which lines were added, at what quantity and at what price, and which were not.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Report per-line reorder outcomes** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

**The single most important sentence in this file is the one that says what this story does not build.** A bulk add that accumulates a per-item error and still adds the successful items **already exists, and it already exists in public**. The mutation is `addItemsToOrder(inputs: [AddItemInput!]!): UpdateMultipleOrderItemsResult!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L74], its own published description states that it returns a list of errors for each item that failed to add and will still add the successful items [packages/core/src/api/schema/shop-api/shop.api.graphql:L73], and its result type is two fields and no more — `order: Order!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L299] and `errorResults: [UpdateOrderItemErrorResult!]!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L300] on `type UpdateMultipleOrderItemsResult` [packages/core/src/api/schema/shop-api/shop.api.graphql:L298]. At the service layer the same semantics are already implemented: a per-item validation failure is pushed onto an accumulator and the loop continues to the next item rather than abandoning the batch [packages/core/src/service/services/order.service.ts:L680-L683]. **This story therefore mirrors that contract and never reinvents it. Inventing a second partial-success payload shape alongside a published one is a defect, not a design choice**, and the parent feature states the same prohibition once for all four of its stories [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds].

**So the unit of work is correlation, not invention.** Three properties of the shipped accumulator are what leave anything to build, and all three were read out of the method body rather than inferred from its description. The accumulator is a flat array carrying no index and no variant identifier [packages/core/src/service/services/order.service.ts:L665], so two lines failing the same way are indistinguishable in it. A clean item pushes nothing onto it, so it is shorter than the item list and its *n*-th entry is not the *n*-th requested line. And an unresolvable variant is not accumulated at all: the variant is loaded through a throwing accessor requiring `enabled: true` and a null `deletedAt` [packages/core/src/service/services/order.service.ts:L684-L689], with a disabled parent product raising an explicit throw [packages/core/src/service/services/order.service.ts:L692-L693], and there is no `try` and no `catch` anywhere in the method. **That third property is the strongest single justification for this story existing at all**, because it is the one outcome class the platform cannot report: one line whose variant was disabled or soft-deleted since the buyer bought it would end the whole batch instead of producing one failed entry among many.

**This story adds no operation and no table.** The epic's operation-ownership map assigns it none: it closes the outcome contract on `applyReorderToActiveOrder` and publishes no second mutation, no query and no row [tickets/EPIC-001-reorder-and-replenishment.md:§9.2.1 Every Published Operation Has Exactly One Owning Story]. Four things that could be mistaken for part of it are not, and each belongs to a named neighbour:

- **Reporting a price or availability delta *before* the commit** is FEATURE-001-03 and its `reorderPreview` query. That is a read taken ahead of the write; this story reports what the write actually did. No preview is described anywhere below.
- **Offering the buyer a choice about a line that could not be added** — skip, reduce quantity, substitute or abort — is FEATURE-001-04 and its story STORY-001-04-01, which sources the figure a reduce is submitted at from the pre-commit read and uses `InsufficientStockError.quantityAvailable` only to reconcile what the commit then did [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.8 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds]. **That story is the downstream consumer of this report**: it can only offer a choice about a line the report has already named.
- **Persisting an attempt and its per-line outcomes, and publishing the typed events** is FEATURE-001-07, through the `ReorderAttempt` and `ReorderAttemptLine` rows it owns. This story returns the report **in the response only**, which is what keeps this feature's no-new-table ruling true [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.14 Constraints This Feature Is Built Under].
- **The three source forms themselves** are STORY-001-02-01, STORY-001-02-02 and STORY-001-02-03. This story adds no fourth source and no new data; it closes one contract over the three that exist.

**One side effect is referenced rather than restated.** Declaring a new error result grows the published `ErrorCode` enum automatically, which is a widening the epic records as a collision and STORY-001-01-04 asserts against [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions]. **This story declares no new error result**, so it contributes no member to that growth; the side effect is named here in one line so that it is neither treated as new nor accepted silently.

## 2. Source Traceability

The label is a **quoted objective clause**, not `Inferred`. The clause is C3 [tickets/EPIC-001-reorder-and-replenishment.md:§10.2 Objective-Clause Map], reproduced verbatim:

> "and so that buyers are made aware of price and availability changes"

Twelve of the twenty-five stories in this set carry an `Inferred` label naming the requirements block they derive from, and that count is reported at its true value rather than flattered [tickets/EPIC-001-reorder-and-replenishment.md:§10.1 The Headline Number, Reported At Its True Value]. This story is one of the thirteen that does not need one, and it is one of only two stories the clause map assigns to C3.

**Where the clause stops, and what that boundary decides.** The objective sentence continues "before they commit to a reorder", and that remainder is clause C4, which the map assigns to STORY-001-03-02 and STORY-001-04-01 rather than here [tickets/EPIC-001-reorder-and-replenishment.md:§10.2 Objective-Clause Map]. **This story is the awareness that arrives *with* the attempt, not before it:** a buyer who committed a reorder of four lines is told, per line, what quantity landed and at what integer price, and which lines did not land and why. Awareness taken ahead of the commit is FEATURE-001-03's work and is not described below.

**What the clause makes observable, and what it does not.** Awareness is a **shape** claim rather than a timing or conversion claim: the response names each requested line, so no outcome has to be inferred from what is missing. It is not a claim that a buyer notices, and it is not a claim about how long anything takes. This repository declares no numeric business target and the epic reports that absence as a finding rather than filling it in [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers]. No figure is supplied here either. The single numeric target anywhere in this file is the coverage figure in section 10, which the requirements supply rather than this story inventing.

**Why the clause needs this story rather than being satisfied by the platform.** The published bulk result already carries an error collection, so a storefront can already learn that *something* failed. What it cannot learn from that collection is *which* of the buyer's lines failed, because the collection carries no key of any kind [packages/core/src/service/services/order.service.ts:L665]. A buyer told that one of four items was short of stock, without being told which, has been made aware of nothing they can act on.

## 3. Precedent In This Repository

**PRECEDENT:** partial — the overlap here is the strongest in this feature, it is stated first and without softening, and it is the reason the section is longer than a formality.

**What is precedented, and it is a great deal.** The partial-success contract is already published on this platform's Shop API. `addItemsToOrder(inputs: [AddItemInput!]!): UpdateMultipleOrderItemsResult!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L74] returns per-item errors while still adding the successful items, which its own description says in as many words [packages/core/src/api/schema/shop-api/shop.api.graphql:L73]. Its payload is concrete rather than abstract — `type UpdateMultipleOrderItemsResult` [packages/core/src/api/schema/shop-api/shop.api.graphql:L298] with `order: Order!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L299] and `errorResults: [UpdateOrderItemErrorResult!]!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L300] — and its input type is exactly what a projected source line reduces to, `productVariantId` and `quantity` [packages/core/src/api/schema/shop-api/shop.api.graphql:L303-L305]. Underneath it, `OrderService.addItemsToOrder` [packages/core/src/service/services/order.service.ts:L654] already accumulates a per-item error and continues to the next item [packages/core/src/service/services/order.service.ts:L680-L683], already reports a clamped quantity by pushing an error after writing the shortened line [packages/core/src/service/services/order.service.ts:L743-L746], and already returns the two-field object the API type mirrors [packages/core/src/service/services/order.service.ts:L663]. **Saying that this story introduces partial-success reporting to this platform would be false**, and the honest consequence is that its payload is a mirror rather than an invention.

**And there is a shipped in-repo consumer of that bulk add, which is the sharpest piece of evidence in this section.** The `product-bundles` example plugin is the only place in the searched set that calls the method: it builds an item array from the bundle's lines and calls the bulk add [packages/dev-server/example-plugins/product-bundles/services/product-bundle.service.ts:L99], and then, when the returned collection holds anything at all, it **rolls the transaction back and returns the first entry** [packages/dev-server/example-plugins/product-bundles/services/product-bundle.service.ts:L114-L117], discarding every other entry and converting a partial success into an all-or-nothing failure. The same shape appears a second time in the same file [packages/dev-server/example-plugins/product-bundles/services/product-bundle.service.ts:L153-L155]. **That is precedent for calling the bulk add and precedent against reporting it per line**, and it is exactly the outcome this story replaces: a buyer whose four-line reorder contained one short item would be told nothing about the other three.

**What is not precedented, stated as narrowly as it holds.** Two things, and no more.

- **Correlating each outcome back to a source line of a placed order or of a saved list.** The shipped collection is unkeyed [packages/core/src/service/services/order.service.ts:L665], a clean item contributes no entry to it so it is shorter than the item list, and not one of the five member types of its union carries a variant identifier, a source-line identifier or an input index — `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80], `OrderLimitError` with only `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L40], `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44], `InsufficientStockError` with only `quantityAvailable` and `order` [packages/core/src/api/schema/common/common-error-results.graphql:L53-L54] and `OrderInterceptorError` with only `interceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L106]. The correlation therefore has to be **constructed**, and constructing it is this story's contribution [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract].
- **Reporting the one outcome class the platform never reports at all.** A source line whose variant has been disabled or soft-deleted since it was bought is not accumulated: the variant load requires `enabled: true` and a null `deletedAt` and throws otherwise [packages/core/src/service/services/order.service.ts:L684-L689], a disabled parent product throws explicitly [packages/core/src/service/services/order.service.ts:L692-L693], and with no `try` and no `catch` in the method one such line ends the batch. A reorder reads historical data, so this is the ordinary case for the buyers the feature is built for rather than an exotic one.

**The value is chosen on that evidence and defended in one sentence:** `partial` rather than `none` because the reporting contract, its two-field shape and its five error types are all shipped and are all mirrored rather than devised, and `partial` rather than `near-identical` because neither the source-line correlation nor the excluded-variant outcome class exists anywhere in this checkout, and the only shipped consumer of the bulk add throws the per-item report away.

**The searched set, named so the claim is checkable rather than asserted:** the whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. That is the same set the epic and the parent feature searched, and the finding above is an addition to their result rather than a re-run of it [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.12 Precedent In This Repository]. The closest shipped saved-list example remains the wishlist plugin, whose entire Shop API surface is three operations [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L12-L19] with no bulk projection and no per-line outcome of any kind. What this story borrows from it is one idiom and nothing more: `extend type Mutation` for adding a field without touching an existing operation.

**The overlap with the three sibling stories is a dependency, not repository precedent, and it is disclosed in section 8 rather than here.** Precedent means shipped work in this checkout that a story re-applies; a sibling ticket in this same set is a prerequisite to be sequenced, which is a different thing with a different remedy.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when the file is pasted into an external tracker. Every story file in this set uses that same convention, so a reader comparing two stories compares like with like.

```text
As a Returning Buyer,
I want to be told, line by line, what my reorder actually did — which items went into my cart, at what quantity, at what price, and which ones did not go in and why,
So that a reorder that only partly worked is something I can see and act on instead of a cart I have to audit against the order I was reordering.
```

### 4.1 INVEST Criteria

- **Independent** — **this criterion does not hold unqualified, and the honest form is stated rather than the flattering one.** All three sibling stories are prerequisites, classified as one shared code path: STORY-001-02-01 supplies the mutation, the resolver, the source predicate, the prevalidation pass and the single core call; STORY-001-02-02 supplies the line selection that narrows a source; STORY-001-02-03 supplies the saved-list source. The parent feature records the same edge with the same direction and says plainly that a contract cannot be closed over outcomes that do not yet exist [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§4.3 Intra-Feature Story Order]. **What still makes this a story rather than a sub-task of the three is that it delivers value on its own terms once they are merged:** it turns a partially successful reorder from silent into legible, which is the difference between a buyer who knows one of four items was short and a buyer who has to compare their cart against the order they reordered. No story outside this feature is a prerequisite of it, and section 8 gives the whole prerequisite set as exactly three entries.
- **Negotiable** — **the payload shape is not open, and saying so is the point of the story rather than a limit on it.** The parent feature publishes `ReorderResult`, `ReorderLineOutcome`, `ReorderSourceLineRef`, `ReorderRequestOutcome` and `ReorderLineOutcomeCode` in full and final form, and that schema is the only normative statement of the payload [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. This story may not add a field to it, may not rename one, and may not introduce a parallel errors collection: **there is no `errorResults` field on `ReorderResult`, and a story that describes one has described a different contract** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.1 Operation Ownership And Test Matrix]. It may not widen the public payload for the audit's benefit either, because the audit consumes a plugin-internal mapped outcome instead [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.3 The Internal Mapped-Outcome DTO]. What remains genuinely negotiable is nothing in the schema at all: it is how the reconciliation and the attribution are expressed inside the service method the first sibling story already owns.
- **Valuable** — it is the point at which a reorder stops being all-or-nothing in the way the only shipped caller of the bulk add makes it [packages/dev-server/example-plugins/product-bundles/services/product-bundle.service.ts:L114-L117]. A buyer whose four-line repeat purchase contained one item short of stock keeps the other three, is told the exact quantity that landed on the short one, and is told which line it was.
- **Estimable** — the surface is bounded and countable: no new table, no new migration, no new operation, no new error result, one reconciliation step and one attribution step over a payload whose every field is already published. The nearest shipped analogue for the collection being mirrored exists with a declared shape [packages/core/src/api/schema/shop-api/shop.api.graphql:L298-L301]. Section 9 carries the numbers.
- **Sized Appropriately** — one reconciliation rule, one attribution rule, one degradation branch and one outcome-code mapping, over zero new tables and zero migrations. It sits at three points on the epic's rubric and is not a candidate for splitting: the reconciliation and the attribution are two halves of one report, and separating them would leave a story that returns quantities nobody can explain beside a story that returns error codes attached to nothing.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact entry count with its ordering, an exact integer quantity, an exact integer money value with its currency code, or an exact error type name. Nothing below has to be judged, and the closed error vocabulary is what makes that possible: a per-line error is one of five named types and no other.

## 5. Acceptance Criteria

Eight criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria name operations, their arguments, and entity and column names as database preconditions; none names a resolver class, a file path or an internal method name. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

Three preconditions hold for every criterion without being repeated in each, because they are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]: an authenticated session, a channel resolved from the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L56-L59], and a language resolved from the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. The mutation's gate is `@Allow(Permission.Owner)`, which no session holds, so the control is the service-layer ownership and channel predicate rather than the gate; that model is established by STORY-001-02-01 and inherited here rather than re-asserted, and the parent feature's matrix records the inheritance [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.1 Operation Ownership And Test Matrix]. **No criterion below re-tests authorisation**, because this story adds no authorisation surface; what it adds is what the response says once a request is admitted.

**How the eight map onto the five required coverage classes.** Valid input is AC-1, and it is the criterion this story exists for. An error naming the exact type returned is AC-2 and AC-3, one type each. Invalid or incomplete input is AC-4 — a source line whose variant no longer resolves, which is input the platform cannot process at all. Edge cases are AC-5 and AC-8, both deliberately distinct from every scenario in section 7. An existing operation asserted unchanged is AC-6 and AC-7, one operation each.

**The error vocabulary a per-line outcome may name is closed, and that bound is what makes this report testable rather than open-ended.** An entry's `errorCode` is drawn from the five members of the existing `union UpdateOrderItemErrorResult` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], listed here as bullets rather than in the schema's own union form:

- `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80]

**One cardinality statement governs every criterion below, and it is the parent's rather than this story's.** `lineOutcomes` holds one entry per **distinct projected variant key**, ordered by ascending `requestIndex`, that index being the **lowest source index among the key's own contributors**, so the published set is drawn from the source numbering and skips a value wherever two source lines collapsed onto one key, with every requested source line named inside exactly one entry's `contributors` collection as a `ReorderSourceLineRef` carrying that line's own `requestedQuantity` [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract]. Every criterion except AC-5 uses a fixture in which each source line names a distinct variant, so the entry count and the requested-line count coincide there and the indices run 0 upward without a gap — but each states the guarantee in the parent's terms rather than in the coincidence's, and AC-5 exercises the case where the two counts differ. **AC-5's own indices are 0 and 1 rather than 0 and 2**, because the shared key's lowest contributor is the source's first line, so no criterion in this file happens to observe a skipped value even though the definition permits one. **The guarantee holds for a settled request only**, because a variant that stops resolving between prevalidation and the core call ends the request instead of producing an entry [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6b The Request-Level Outcome], and section 7 asserts that branch.

**The grain is settled in one place and this story receives it rather than reporting a disagreement about it.** The parent feature's normative schema section, its keyed line-result contract and its correlation contract — which assigns `requestIndex` to the projected key rather than to a source line [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract] and [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract] — and every item of its definition of done now state the same grain: one entry per distinct projected variant key, with a `contributors` collection naming every source line that fed it [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§5. Definition of Done (Feature-Level)]. **An earlier revision of that feature carried two definition-of-done items describing a withdrawn per-requested-line grain with a singular identifier field, and this story reported the disagreement rather than being able to build against it; the disagreement is resolved in the parent and the report is replaced by this statement.** Reintroducing the withdrawn grain is named here for one reason only: reintroducing it would require an apportionment rule dividing one key's applied quantity between two source lines, and no such per-source-line quantity exists in order state to report — so a criterion below that named a singular source-line identifier on an outcome entry would be asserting a field the schema does not declare.

**Two further readings apply to every criterion and are stated once.** The target cart's prior state is part of the contract, because the platform's write path is additive rather than idempotent — it sums the requested quantity with the quantity already on the line before clamping [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133] and counts quantities held in other lines of the same variant [packages/core/src/service/services/order.service.ts:L695-L702] — so every criterion asserting an exact resulting quantity states the cart's prior state. That distinction is the point of the criterion and it is testable rather than interpretive: that member covers a source that resolved to **zero requested lines** — an empty source, a list holding no lines, or a selection matching nothing — whereas four lines that resolved and then could not be added is a settled report of four refusals [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]. `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] is not the result either, because the cart was determined without difficulty and swapping the two is a defect a test catches [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling]. **A report of four refusals is a success carrying bad news, not a failed request**, which is the whole reason per-line outcomes sit inside a returned result rather than replacing it

## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story reads availability and reports across a request scope. Each is labelled with its category inline, so the category matrix never appears as a table in a story file. All five are distinct from every criterion in section 5.

* Scenario: Category — zero, null or empty collection. The source resolves to no requested line at all.
   * Given an authenticated Returning Buyer whose active cart holds **exactly one line at `quantity` 3** [packages/core/src/entity/order-line/order-line.entity.ts:L97], and a source that resolves under all four conjuncts of the source predicate yet holds **zero** reorderable lines — a placed order with no lines, a saved list with no lines, or an explicitly empty `lineSelections` collection against a source that has them
   * When `applyReorderToActiveOrder` is executed with that source
   * Then the mutation returns **`NoReorderableLinesError`** with its `resolvedSourceLineCount` reporting what the source held, **no `ReorderResult` is returned and therefore no report exists at all**, no line is written, and the active cart still holds exactly one line at `quantity` 3 carrying the same `OrderLine` id. This is the boundary of this story's own subject: **an empty report is not a report of nothing, it is the absence of one**, and the request-level result is what says so. It is deliberately different from AC-8, where four lines resolved and all four were refused, and the two are asserted separately because an implementation that returned this member for AC-8 would be telling a buyer their source was empty when it was not [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. The variant stops resolving in the window between prevalidation and the write.
   * Given a source resolving to four requested lines on distinct variants, all four passing the enabled-and-not-deleted prevalidation read, and one of the four variants then being disabled, soft-deleted, or having its parent product disabled **after** that read and **before** the single core call
   * When `applyReorderToActiveOrder` is executed against that source
   * Then the response carries the request-level outcome **`ABORTED_UNRESOLVABLE_SOURCE_LINE`**, names the aborting variant and the source-line identifiers that projected into it, and carries **zero** per-line entries — the specified shape rather than a degenerate one [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6b The Request-Level Outcome]. **This is the residual race and it is stated rather than designed away.** The variant load throws on `enabled: true` and null-`deletedAt` failure [packages/core/src/service/services/order.service.ts:L684-L689] and on a disabled parent product [packages/core/src/service/services/order.service.ts:L692-L693], nothing catches it, and the exception identifies a variant rather than a source line — so translating it into a per-line outcome would mean guessing which requested line it belonged to, and this story attributes nothing on a guess. **Every statement of the per-line guarantee in this file therefore carries its settled-request precondition**, and the ordinary unavailable-variant case, where the failure is known before delegating, is AC-4's per-line outcome instead

* Scenario: Category — a price changed since the last purchase. The variant now prices at a different integer than the source line recorded.
   * Given a source line whose `listPrice` at placement was 129900 [packages/core/src/entity/order-line/order-line.entity.ts:L120-L121] and whose variant now prices at 134900, both integers in the smallest unit of the currency named by the source order's `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142], with the line's `listPriceIncludesTax` flag [packages/core/src/entity/order-line/order-line.entity.ts:L128] recording which of gross or net that integer was, and with `initialListPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L112-L113] holding the figure the line was first added at
   * When `applyReorderToActiveOrder` is executed with a source naming that line
   * Then the price the buyer reads back is the one **actually applied**, carried on the returned `order` as an integer in the smallest unit of the target's currency stated alongside that currency's code, priced from the current catalogue by the single adjustment pass the platform performs at the end of the call [packages/core/src/service/services/order.service.ts:L751], and **no historical price is copied onto the new line**. This story computes no delta and performs no arithmetic on money, so there is no place in it where a conversion or a rounding rule could be applied, and **no monetary value appears on an outcome entry at all** — the entry carries counts, and prices live on the returned order. Reporting a delta **before** the commit is FEATURE-001-03's work, and reporting one **after** the add is already done by the platform's existing calculated getters `unitPriceChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L168] and `unitPriceWithTaxChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L181], which this story must not duplicate [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]: this report covers the reorder attempt, not the subsequent life of the cart

* Scenario: Category — a point-in-time read gone stale between check and commit. Another order allocated the stock after prevalidation read it.
   * Given a source resolving to two requested lines on distinct variants, both of which prevalidation read as addable at their requested quantities, and another order allocating the stock behind one of the two between that read and the write
   * When `applyReorderToActiveOrder` is executed against that source
   * Then **the report states the outcome that was actually applied and never the one that was predicted**: the affected entry's `addedQuantity` comes from the target order's own per-variant quantity delta, its `outcome` is `ADDED_AT_REDUCED_QUANTITY` or `NOT_ADDED_OUT_OF_STOCK`, and its `errorCode` names `InsufficientStockError` with the `quantityAvailable` integer the platform returned [packages/core/src/api/schema/common/common-error-results.graphql:L53] — never a request-level failure, never a retry, and never a number this story chose. The prevalidation read does not close this window and is not meant to: it reads moments before the commit through the same saleable computation the commit reaches when it clamps a quantity [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133], so the two agree except where the stock moved in between, **and where they disagree the commit wins**. A read that showed a line as addable confers no entitlement to add it, and nothing in this story reserves stock [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.10 A Point-In-Time Read Is Not A Reservation]

* Scenario: Category — a channel, currency or language mismatch between the original order and the reorder context.
   * Given the source order was placed under one channel `token` [packages/core/src/entity/channel/channel.entity.ts:L62] while the reorder request carries a different token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L56-L59]; or the active channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differs from the source order's own `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142]; or the request resolves to a language other than the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When `applyReorderToActiveOrder` is executed against that source
   * Then each of the three has one stated outcome and none is left to an implementation. A source order belonging to **another channel does not resolve at all**, so there is no report to produce and the request is reported as an unresolvable source — a hard boundary, not a filter a caller may widen. A **currency difference lets the reorder proceed**, with both codes reported through `sourceCurrencyCode` and `targetCurrencyCode`, every line priced in the target's currency by the platform's own adjustment pass, no conversion attempted, no line refused for currency alone and no error returned; the report is therefore the surface on which a mismatch becomes observable rather than hidden [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. A **language difference changes nothing in the report**, because its own fields are identifiers, integer counts, outcome codes and error type names, none of which is language-varying — an outcome code is machine-readable rather than a localised sentence, precisely so that this report never becomes a translation surface
