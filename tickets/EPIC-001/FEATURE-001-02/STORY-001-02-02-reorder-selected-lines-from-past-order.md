## 1. Story Title

**Narrow a past order to a chosen subset of its lines and apply that subset to the active cart, so that a returning buyer repurchases only the lines they choose with an exact resulting line count in a stated order.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Reorder selected lines from a past order** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work is one optional input field and the determinism it has to deliver. The field is `lineSelections` on the mutation input the parent feature publishes in full, and its semantics are already fixed there: omitted or null means every line of the source, while an empty list is **not** the same as omitted [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. This story implements the narrowing, the per-selection quantity override, the ordering of the resulting report, and the ruling for a selection that resolves to nothing.

**This story adds no operation.** The epic's operation-ownership map assigns it none: it extends `applyReorderToActiveOrder` with line selection and publishes no second mutation, no query and no table [tickets/EPIC-001-reorder-and-replenishment.md:§9.2.1 Every Published Operation Has Exactly One Owning Story]. Four things that could be mistaken for part of it are not:

- **Reading the whole of a past order** is STORY-001-02-01, whose resolution predicate and single core call this story reuses unchanged.
- **A saved reorder list as the source** is STORY-001-02-03. This story's source is a placed order only.
- **Closing the outcome contract across all three source paths** is STORY-001-02-04.
- **Offering the buyer a choice about a line that cannot be added** — skip, reduce quantity, substitute or abort — is FEATURE-001-04 and its story 04-01. This story reports an outcome and offers no resolution choice, and the `lineResolutions` input field that will carry those choices is declared from the outset yet inert until that feature ships [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. Reporting a price or availability delta **before** the commit is FEATURE-001-03's `reorderPreview`, named here and defined there.

**Why determinism is the whole of this story rather than a quality attached to it.** A subset selection is only worth having if the buyer can predict what comes back. The parent feature already fixes the mechanism: source lines are ordered by ascending `OrderLine.id` for the order path and projected onto distinct variant keys, each key carrying a `requestIndex` equal to the lowest index among its own contributors in that zero-based source numbering, and `lineOutcomes` holds exactly one entry per projected key in ascending `requestIndex` order — a set that skips a value wherever two selected lines collapsed onto one key — with every contributing source line named inside the entry it fed [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract]. Because every criterion in section 5 selects distinct variants, one entry per key and one entry per selected line are the same count there — but the guarantee is stated in the parent's terms rather than in the coincidence's. Every assertion in section 5 is therefore an exact count with a stated order, an exact integer quantity, or an exact error type name. No assertion is a judgement, because a subset whose size and order have to be judged is not testable.

## 2. Source Traceability

The label is a **quoted objective clause**, not `Inferred`. The clause is C2 [tickets/EPIC-001-reorder-and-replenishment.md:§10.2 Objective-Clause Map], reproduced verbatim:

> "so that repeat purchasing on the marketplace requires materially less effort than rebuilding an order from scratch"

Twelve of the twenty-five stories in this set carry an `Inferred` label naming the requirements block they derive from, and that count is reported at its true value rather than flattered [tickets/EPIC-001-reorder-and-replenishment.md:§10.1 The Headline Number, Reported At Its True Value]. This story is one of the thirteen that does not need one.

**What the clause decides about this story, and what it does not.** The clause measures effort against rebuilding an order from scratch, so the observable claim is a **countable** one: one call carrying a selection of two lines in place of one add-to-cart call per line, plus the re-selection of each variant from the catalogue. It is not a timing claim and not a conversion claim. This repository declares no numeric business target and the epic reports that absence as a finding rather than filling it in [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers]. No figure is supplied here either, and the single numeric target that does appear in this file is the coverage figure in section 10, which the requirements supply.

The clause also explains why the subset case exists at all rather than being a refinement of the whole-order case. A buyer who wants three of the eight lines they bought last month gets no help from a whole-order reorder: they would add three lines by hand, or reorder eight and remove five. Both are the rebuild the clause is measured against.

## 3. Precedent In This Repository

**PRECEDENT:** partial — the overlap is real, it is disclosed here rather than discovered later, and it is narrower than it first looks.

**What is precedented.** The Shop API already publishes a bulk add that accepts an arbitrary selection of variant-and-quantity pairs in one call: `addItemsToOrder(inputs: [AddItemInput!]!): UpdateMultipleOrderItemsResult!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L74], whose input type carries exactly a `productVariantId` and a `quantity` [packages/core/src/api/schema/shop-api/shop.api.graphql:L303-L305], and whose own docstring states that it returns a list of errors for each item that failed to add and will still add the successful items [packages/core/src/api/schema/shop-api/shop.api.graphql:L73]. A storefront can therefore already send two of a past order's three variants in one call today. Saying otherwise would be false, and the honest consequence is that **this story does not introduce selective bulk adding to this platform.**

**What is not precedented, stated as narrowly as it holds.** Nothing in this checkout correlates a selection to the recorded lines of a *placed* order and reports outcomes back against those source lines. The existing bulk add takes variant identifiers, not source-line identifiers; its error collection carries no key of any kind [packages/core/src/service/services/order.service.ts:L665]; a clean item contributes nothing to that collection, so it is shorter than the item list; and it therefore cannot say which of the buyer's chosen lines was refused. The selection this story accepts is expressed in `sourceOrderLineId` values, the quantity it defaults to is the line's `orderPlacedQuantity` [packages/core/src/entity/order-line/order-line.entity.ts:L104] rather than a figure the caller supplies, and the report it returns names each source line back to the buyer. That construction is the contribution [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract].

**The searched set, named so the claim is checkable rather than asserted:** the whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. That is the same set the epic and the parent feature searched, and this story cites them rather than re-running the search [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.12 Precedent In This Repository]. The closest shipped example plugin is the wishlist, and the evidence of non-overlap is its own schema extension: its entire Shop API surface is three operations — `activeCustomerWishlist`, `addToWishlist(productVariantId: ID!)` and `removeFromWishlist(itemId: ID!)` [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L12-L19]. It has no order-history path, no subset selection and no per-line report. What this story borrows from it is one idiom and nothing more: `extend type Mutation` for adding a field without touching an existing operation.

**The overlap with STORY-001-02-01 is a dependency, not repository precedent, and it is disclosed in section 8 rather than here.** Precedent means shipped work in this checkout that a story re-applies. A sibling ticket in this same set is a prerequisite to be sequenced, which is a different thing with a different remedy: precedent is disclosed so that novelty is not overclaimed, while a prerequisite is classified so that the two pieces of work can be ordered.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when the file is pasted into an external tracker. Every story file in this set uses that same convention, so a reader comparing two stories compares like with like.

```text
As a Returning Buyer,
I want to pick out only the lines I want from one of my past orders and put just those on my current cart,
So that a partial repeat purchase costs me one call instead of one add-to-cart call per line, and the cart holds exactly the lines I picked and nothing else.
```

### 4.1 INVEST Criteria

- **Independent** — **this criterion does not hold unqualified, and the honest form is stated rather than the flattering one.** STORY-001-02-01 is a prerequisite, classified as a shared code path: the mutation, its resolver, the four-conjunct source resolution and the projection step all arrive with that story, and the parent feature records the same edge with the same direction [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§4.3 Intra-Feature Story Order]. What still makes this a story rather than a sub-task of that one is that it delivers value on its own terms once the prerequisite is merged: a buyer who wants two of the eight lines they bought last month can have them, which the whole-order path cannot give them. **No other story in the set is a prerequisite of it** — in particular no story of FEATURE-001-01, since the order-history path touches no reorder list — and section 8 gives the whole prerequisite set as exactly three entries, only one of which is a story.
- **Negotiable** — **the shape of a selection entry is not open, and saying so is a correction rather than a narrowing of ambition.** The parent feature publishes `ReorderLineSelectionInput` with exactly three fields — `sourceOrderLineId`, `reorderListLineId` and an optional `quantity` — and this story may not add a fourth: a storefront addresses a source line by that line's identifier and **not** by naming the variant, because a variant selector would be a field added to an input the prerequisite story already published, which is the silent widening this feature's frozen-input rule exists to prevent [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. The seven validation rules that govern a selection are likewise settled there rather than here — entry addressing, uniqueness, array size, quantity range, membership, and the omitted-versus-empty distinction — so this story implements them and asserts them instead of choosing them. **A per-entry `quantity` override may exceed the source line's own `orderPlacedQuantity`** [packages/core/src/entity/order-line/order-line.entity.ts:L104], because nothing about a repeat purchase caps it at what was bought before; what bounds it is the configured `maxQuantityPerLine` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency], and the per-key sum is checked against that same ceiling after projection. What remains genuinely negotiable is nothing in the input at all: it is how the filter is expressed inside the service method the prerequisite story already owns.
- **Valuable** — it is the point at which a repeat purchase stops being all-or-nothing. A buyer whose past order mixes a monthly consumable with a one-off purchase can take the consumable and leave the rest, which is the clause C2 promise in section 2 applied to the ordinary shape of a real order history.
- **Estimable** — the surface is bounded and countable: one optional input field, one filter step inside an existing projection, no new table, no new operation and no new error result. The nearest shipped analogue for the bulk call it delegates to already exists with a declared return shape [packages/core/src/service/services/order.service.ts:L663]. Section 9 carries the numbers.
- **Sized Appropriately** — one input field, one filter over source lines already resolved by the prerequisite story, one quantity-override rule and one ruling for an empty selection, over zero new tables and zero migrations [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.3 Named Entities Touched]. It sits at three points on the epic's rubric and is not a candidate for splitting: the empty-selection ruling and the count-and-ordering assertions are the same unit of work seen from two sides, and separating them would leave a story that returns a report nobody has specified the shape of.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact line count with its ordering, an exact integer quantity, or an exact error type name. Nothing below has to be judged.

**Step 4 — build and place a source order of exactly three lines at quantities 2, 1 and 4**, following the sibling story's sequence for the catalogue read, the three `addItemToOrder` calls [packages/core/src/api/schema/shop-api/shop.api.graphql:L72] and the transition that places the order. **Step 5 — run one mutation with a selection of exactly two of those three lines, listing them in reverse id order on purpose.** The shape below is what this feature proposes; it does not exist in this checkout and is written here as a target rather than as a citation [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces].

```graphql
mutation {
  applyReorderToActiveOrder(
    input: {
      source: { sourceOrderId: "<the placed order id>" }
      lineSelections: [
        { sourceOrderLineId: "<L3, the line at quantity 4>" }
        { sourceOrderLineId: "<L1, the line at quantity 2>" }
      ]
    }
  ) {
    ... on ReorderResult {
      requestOutcome
      order { id totalQuantity lines { id quantity } }
      lineOutcomes {
        requestIndex
        contributors { sourceOrderLineId reorderListLineId requestedQuantity }
        productVariantId
        requestedQuantity
        addedQuantity
        orderLineId
        outcome
        errorCode
      }
      unattributedErrorCodes
      sourceCurrencyCode
      targetCurrencyCode
    }
    ... on NoReorderableLinesError { errorCode message }
    ... on NoActiveOrderError { errorCode message }
    ... on OrderModificationError { errorCode message }
    ... on ReorderListNotFoundError { errorCode message }
  }
}
```

**The expected response, stated as an exact observable.** `requestOutcome` is `SETTLED`. The `order` carries **exactly two lines**, at `quantity` 2 and 4, with a `totalQuantity` of 6 [packages/core/src/entity/order/order.entity.ts:L286]. `lineOutcomes` holds **exactly two entries** — two distinct variants, so two projected keys, each with exactly one entry in `contributors` — with `requestIndex` 0 whose single contributor is L1 and `requestIndex` 1 whose single contributor is L3 — **ascending `OrderLine.id`, which is the reverse of the order the input listed them in**, and that inversion is the point of the step rather than a curiosity. Each entry reports an `addedQuantity` equal to its `requestedQuantity`, an `outcome` of `ADDED` and a null `errorCode`; `unattributedErrorCodes` holds zero entries; and `sourceCurrencyCode` equals `targetCurrencyCode`. The middle line L2 has no entry anywhere in the response and its variant appears on no cart line. A non-coder can read that against the source order's three lines and see that two came back, in a stated order, and that the one left behind stayed behind.

Those five are the closed membership of `union UpdateOrderItemErrorResult` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], which is declared in core and cannot gain a member without editing `packages/core` — the reason the plugin owns its own union. **This story declares no new error result of its own**, so it contributes nothing to the automatic `ErrorCode` enum growth that the epic's collision section and STORY-001-01-04 own between them; that side-effect widening is referenced in this one line and is not accepted silently [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

**A third level exists, and assigning each condition to exactly one of the three is what an earlier revision of this section got wrong.** Beside the two levels above sits the **input-contract level**, which is neither a union member nor a line outcome: a violation of the parent feature's shared selection contract — two source fields set, an entry naming the wrong id form for the source, a duplicate id, an over-size `lineSelections` array, a `quantity` outside the permitted range, or an id that names no line of the resolved source — is refused by throwing the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] with the plugin-owned key that rule names, **before any projection, any variant load and any stock read** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces], which is the epic's ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. Two consequences are asserted rather than assumed in the criteria below. **The request-level source-size bound is an input-contract refusal and not `OrderLimitError`**: that type is core's *per-item* error [packages/core/src/service/services/order.service.ts:L2286-L2290] and appears in this story only as the line-level outcome `NOT_ADDED_LIMIT_REACHED` carrying its code. **And no condition appears at two levels**: a selection entry that cannot be resolved is an input-contract refusal, while a selected line that resolves and then cannot be added is a line-level outcome, and nothing is both.

One further reading applies to every criterion below and is stated once: `lineOutcomes` holds one entry per **distinct projected variant** — never one per requested line, though the two counts coincide in every criterion here because each selects distinct variants — and it holds that shape only **for a settled request**, which is the only form of that guarantee this set permits, because a variant that stops resolving between prevalidation and the core call ends the request instead of producing an entry [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6b The Request-Level Outcome]. Every entry names the source lines that fed it in its own `contributors` collection [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces].

## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story reads availability and copies lines across a request scope. Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

* Scenario: Category — zero, null or empty collection. The selection is present and holds no entry.
   * Given an authenticated Returning Buyer whose active cart holds exactly one line at `quantity` 3 [packages/core/src/entity/order-line/order-line.entity.ts:L97], and one source order resolving under all four conjuncts and carrying three `OrderLine` rows that are all addable
   * When `applyReorderToActiveOrder` is executed with a `source` naming that order and a `lineSelections` collection holding **zero entries**
   * Then the mutation returns `NoReorderableLinesError`, no line is written, and the active cart still holds exactly one line at `quantity` 3. **An empty selection is not the same as an omitted selection and must not be treated as one:** omitted or null means every line of the source, and an empty collection means the request resolved to zero requested lines [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. An implementation that coerced the empty collection to "all" would reorder three lines a buyer asked nothing of, which is the single most damaging defect available to this story. `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] is **not** what this returns, because that member means the cart could not be determined or created rather than that the source held nothing, and swapping the two is a defect a test catches [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.8 The No-Active-Order Ruling]

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. One selected line's variant no longer resolves.
   * Given a source order carrying three `OrderLine` rows of which the buyer selects all three, and one of the selected lines references a variant that no longer satisfies the `enabled: true` and null `deletedAt` predicate the bulk add loads each variant with [packages/core/src/service/services/order.service.ts:L684-L689], or whose parent product has since been disabled, which raises a thrown error [packages/core/src/service/services/order.service.ts:L692-L693]
   * When `applyReorderToActiveOrder` is executed with that three-entry selection
   * Then **the other two selected lines are written and the third is reported as `NOT_ADDED_VARIANT_UNAVAILABLE` with an `addedQuantity` of 0 against its own `requestIndex`**, because the plugin service evaluates that same predicate for every retained selection entry and withholds the failing entry from the core call, so the throw is never reached [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract]. **Excluding the entry before delegating is a requirement of this story and not an optimisation.** There is no `try` and no `catch` anywhere in the bulk-add method [packages/core/src/service/services/order.service.ts:L654], so an implementation that withheld nothing would let one stale variant end the entire call and roll back every line already written — and a selection of three lines in which one variant was disabled would then return nothing at all, which is the outcome this scenario exists to forbid. What remains out of scope here is the buyer's *choice* about the withheld line, which is FEATURE-001-04 and its story 04-01; this story reports the outcome and offers no resolution choice. Where a variant instead stops resolving between that prevalidation read and the core call, the response carries the request-level outcome `ABORTED_UNRESOLVABLE_SOURCE_LINE`, names the variant that ended the request and carries zero per-line entries — the residual race the parent feature specifies rather than designs away [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6b The Request-Level Outcome]

* Scenario: Category — a price changed since the last purchase. A selected variant now prices at a different integer than the source line recorded.
   * Given a selected source line whose `listPrice` at placement was 129900 [packages/core/src/entity/order-line/order-line.entity.ts:L120-L121] and whose variant now prices at 134900, both integers in the smallest unit of the currency named by the source order's `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142], with the line's `listPriceIncludesTax` flag [packages/core/src/entity/order-line/order-line.entity.ts:L128] recording which of gross or net that figure was, and with `initialListPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L112-L113] holding the figure the line was first added at
   * When `applyReorderToActiveOrder` is executed with a selection naming that line
   * Then the new cart line is priced from the current catalogue by the bulk add's own single adjustment pass at the end of the call [packages/core/src/service/services/order.service.ts:L751] and **no historical price is copied onto it**; this story computes no delta and performs no arithmetic on money, so there is no place in it where a conversion or a rounding rule could be applied. Reporting a delta **before** the commit is FEATURE-001-03's `reorderPreview`, and reporting one **after** the add is already done by the platform's existing calculated getters `unitPriceChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L168] and `unitPriceWithTaxChangeSinceAdded` [packages/core/src/entity/order-line/order-line.entity.ts:L181], which this story must not duplicate [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]

* Scenario: Category — a point-in-time read gone stale between check and commit. Another order allocated the stock after the buyer chose their lines.
   * Given a storefront read the source order, the buyer chose two of its lines while every chosen line appeared addable, and between that read and the commit another order allocated the stock behind one of the two variants
   * When `applyReorderToActiveOrder` is executed with that two-entry selection
   * Then the authoritative decision is the one the bulk add makes at write time through its own per-item validation chain [packages/core/src/service/services/order.service.ts:L675-L679], and the affected entry resolves to an `outcome` of `ADDED_AT_REDUCED_QUANTITY` or `NOT_ADDED_OUT_OF_STOCK` whose `errorCode` names `InsufficientStockError` with its `quantityAvailable` integer [packages/core/src/api/schema/common/common-error-results.graphql:L53] — never a request-level failure and never a retry, and never a number this story chose. **The prevalidation pass does not close this window and is not meant to:** it reads moments earlier than the commit, using the same saleable computation the commit reaches when it clamps a quantity [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133], so the two agree except when the stock moved in between, and when they disagree the commit wins. A read that showed a line as addable confers no entitlement to add it, and **nothing in this story reserves stock** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.10 A Point-In-Time Read Is Not A Reservation]

* Scenario: Category — a channel, currency or language mismatch between the original order and the reorder context.
   * Given the source order was placed under one channel `token` [packages/core/src/entity/channel/channel.entity.ts:L62] while the reorder request carries a different token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L56-L59]; or the active channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differs from the source order's `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142]; or the request resolves to a language other than the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]

   * Then a source order belonging to another channel does not resolve at all, so neither selection entry resolves either and the request is reported as an unresolvable source rather than read across the boundary — a hard boundary and not a filter a caller may widen; a currency difference lets the reorder **proceed** with both codes reported through `sourceCurrencyCode` and `targetCurrencyCode`, every line priced in the target's currency by the core call's own adjustment pass, no conversion attempted, no line skipped for currency alone and no error returned [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract]; and a language difference changes only the translated variant-derived fields the existing catalogue read path resolves, because the report's own fields are identifiers, integer quantities and error type names, none of which is language-varying
