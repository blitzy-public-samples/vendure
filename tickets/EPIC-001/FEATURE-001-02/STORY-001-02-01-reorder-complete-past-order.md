## 1. Story Title

**Reorder a complete past order into the active cart through one permission-gated mutation, so that a returning buyer receives every line of a repeat purchase in a single call with a named outcome per line.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Reorder a complete past order** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work the title names is one finished slice. The new mutation exists, it accepts a reference to one placed order, it enforces ownership and channel scope from the authenticated session, it **prevalidates every source line before writing anything**, it calls the platform's existing bulk add exactly once, and it returns one outcome for every line it requested — keyed by a `requestIndex` the plugin assigns, because the core call returns no key of its own [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.13 The Outcome Correlation Contract]. Three things that could be mistaken for part of it are not: narrowing the source to a chosen subset of lines is STORY-001-02-02, the saved-list source path is STORY-001-02-03, and closing the outcome contract over all three source paths is STORY-001-02-04.

**The per-line promise in the title is load-bearing and it is deliverable, but not by the route it first appears to take.** The platform's bulk add accumulates an error per failed item and adds the successful ones, which reads like a per-line report already. It is not one: its error collection carries no per-item key [packages/core/src/service/services/order.service.ts:L665], a successful item contributes nothing to it, and an unresolvable variant *throws* rather than accumulating [packages/core/src/service/services/order.service.ts:L684]. This story therefore owns the correlation itself, and the prevalidation pass is what keeps a single stale line from rolling back the whole reorder.

**Step 0 — the preflight.** It checks five prerequisites and **the fifth is the one this path cannot survive without**: the seed imports its catalogue from a path that is a build-time copy rather than a checked-in file [packages/dev-server/populate-dev-server.ts:L41] and [packages/create/build.ts:L17], and without it there is no variant to order and therefore no order to reorder. It is read-only, it aggregates every failure rather than stopping at the first, it **compares** the installed Bun version against the pinned one [.github/actions/setup/action.yml:L11-L12] rather than printing it, and it is a function returning a status rather than a block of bare `exit` statements — so pasting it into a live terminal cannot close that terminal. An earlier revision of this story did both the printing and the exiting.

```bash
# Run from the repository root. Read-only: nothing below installs, builds or writes.
reorder_preflight() {
    local problems=0
    local expected_bun='1.3.10'

    if ! command -v bun >/dev/null 2>&1; then
        echo 'MISSING: bun is not on PATH. See the contribution guide prerequisites.'
        problems=$((problems + 1))
    else
        local actual_bun
        actual_bun=$(bun --version 2>/dev/null | tr -d '[:space:]')
        # Compared, not merely printed: a version echoed to the terminal asserts nothing, and the
        # reader who is going to notice a mismatch is exactly the reader who did not need the check.
        if [ "$actual_bun" != "$expected_bun" ]; then
            echo "VERSION: bun is $actual_bun, but continuous integration pins $expected_bun."
            problems=$((problems + 1))
        fi
    fi

    [ -d node_modules ] || {
        echo 'MISSING: root node_modules. Run the documented install step first.'
        problems=$((problems + 1)); }
    [ -x node_modules/.bin/ts-node ] || {
        echo 'MISSING: node_modules/.bin/ts-node, which the populate script loads as a require hook.'
        problems=$((problems + 1)); }
    [ -f packages/cli/dist/cli.js ] || {
        echo 'MISSING: packages/cli/dist/cli.js, which the dev script executes. Run the build step.'
        problems=$((problems + 1)); }
    [ -f packages/create/assets/products.csv ] || {
        echo 'MISSING: packages/create/assets/products.csv, which the seed imports its catalogue from.'
        problems=$((problems + 1)); }

    if [ "$problems" -ne 0 ]; then
        echo "PREFLIGHT FAILED: $problems prerequisite problem(s). Nothing was started."
        return 1
    fi
    echo 'PREFLIGHT OK'
    return 0
}
reorder_preflight
```

So the cart is asserted by content — three lines, this variant at this quantity — and **ordering is asserted only where it is promised**, on `lineOutcomes`, whose `requestIndex` the plugin assigns itself and whose ordering the parent feature publishes as part of the payload contract.

## 5. Acceptance Criteria

Eight criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria name operations, their arguments, and entity and column names as database preconditions; none names a resolver class, a file path or an internal method name. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

Three preconditions hold for every criterion without being repeated in each, because they are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]: an authenticated session, a channel resolved from the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L56-L59], and a language resolved from the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. Where an outcome varies with them, the criterion names the token and the language code. **AC-4 is the deliberate exception to the first of the three**: it removes the authenticated session on purpose, because an operation whose every criterion assumes a session has never tested what happens without one.

**How the eight map onto the five required coverage classes, and why two of them are authorisation criteria.** Valid input is AC-1. Invalid or incomplete input is AC-2, which covers every source reference failing the placed-order predicate — including the foreign-owner reference, whose response it asserts byte-identical to the other three so that the non-disclosure is a tested property rather than a described intention. Unauthenticated access is AC-3. An error naming the exact type returned is AC-4, which names `InsufficientStockError` with its `quantityAvailable`, and AC-6, which names `OrderLimitError` through the `NOT_ADDED_LIMIT_REACHED` outcome. Edge cases are AC-5, the two-keys-one-cause correlation case, and AC-8, the retry. An existing operation asserted unchanged is AC-7, which covers the single-item add and the line adjustment together. **The mapping names the exact criterion numbers rather than gesturing at them**, because an earlier version of this paragraph described eight criteria while seven were published and pointed three of its five classes at the wrong numbers — which makes a coverage claim unverifiable at exactly the moment a reviewer wants to verify it. **AC-2 and AC-3 are two criteria where one used to stand**: a single criterion covering "a reference that matches no row *or* an order belonging to another customer" is satisfied by a test of either branch, and the branch a test author naturally reaches for is the harmless one — so the foreign-owner case, which is the one that leaks another customer's purchase history if it is wrong, could be skipped without failing anything. Unauthenticated access had no criterion at all. Separating them is the fix.

The error vocabulary these criteria may name is closed, and it is split across **two levels** rather than one — a distinction the parent feature fixes and this story asserts on both sides [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. **Request level** is the four members of the plugin-owned `ApplyReorderResult` union: `NoReorderableLinesError`, `ReorderListNotFoundError`, `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] and `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80]. A request-level result means nothing was added at all. **Line level** is a `ReorderLineOutcomeCode` on each entry of `lineOutcomes`, optionally carrying the `errorCode` of one of the existing types below; a line-level outcome sits inside a **successful** response, because a reorder in which one line of eight failed is a success carrying a report. The plugin-owned union is necessary rather than stylistic: `union UpdateOrderItemErrorResult` is declared in core [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117] and cannot gain a member without editing `packages/core`, which the zero-edit boundary forbids.

The existing types whose codes may appear at line level are the five members of that core union, listed as bullets here rather than in the schema's own union form:

- `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80]
- `OrderLimitError`, carrying `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L37]
- `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44]
- `InsufficientStockError`, carrying `quantityAvailable` and `order` [packages/core/src/api/schema/common/common-error-results.graphql:L50]
- `OrderInterceptorError`, carrying `interceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103]

The single new `NoReorderableLinesError` this feature declares is a request-level member only [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]. Declaring one new error result grows the published Shop `ErrorCode` enum automatically, because that enum's members are derived from every type implementing the `ErrorResult` interface [packages/core/src/api/config/generate-error-code-enum.ts:L9]. That side-effect widening is owned by the epic's collision section and by STORY-001-01-04, is referenced here in this one line, and is **not** accepted silently [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

**A note on the boundary case where every line clamps to zero.** A source order in which no line has any addable quantity writes no line at all: each entry in `lineOutcomes` carries `NOT_ADDED_OUT_OF_STOCK` with an `addedQuantity` of 0, the active order's line count is exactly what it was before the call, and the mutation still resolves to `ReorderResult` rather than to an error member — a request that was understood and produced no cart change is not a failed request. `NoReorderableLinesError` is reserved for a source that resolves to zero requested lines in the first place, which is a different condition and is asserted separately.

Stated in the epic's dependency form — the required thing, then why it is required and where it belongs — with each entry classified as a **data dependency** or a **shared code path**, because a prerequisite without a classification cannot be sequenced. The two sub-sections are kept apart deliberately: the first is what has to be brought into existence before this work can run, and the second is what already ships and is consumed as it stands.

### 8.1 The Minimum Prerequisite Set — Exactly Two Entries, Neither Of Them A Story

- **Configuration, the project bootstrap — shared code path:** the plugin module must exist and be registered in the dev-server `plugins` array before the new mutation is reachable at all [packages/dev-server/dev-config.ts:L121-L155]. **It does not belong to this piece of work.** The epic declares it a prerequisite of the whole epic, performed once by the implementation run, owned and priced by no story and claimed by none [tickets/EPIC-001-reorder-and-replenishment.md:§7.9 Project Bootstrap] — which is what keeps this story and the harness-proving run in FEATURE-001-01 from each presenting the same wiring as their own first step, and what leaves the "no prerequisite story" claim below literally true. That array is one of only two files a future implementation may touch outside the plugin package [tickets/EPIC-001-reorder-and-replenishment.md:§11.7 The Two Permitted Configuration Exceptions]; naming it here is a documentation act and licenses no edit by this ticket.
- **Data, one placed order for the authenticated customer — data dependency:** the source path has no source without it, the row is obtainable end to end through operations that already ship, and it is then readable through `Customer.orders(options: OrderListOptions): OrderList!` [packages/core/src/api/schema/common/customer.type.graphql:L11]; it belongs to the request prerequisites the epic states for every piece of work in this set rather than to any single one [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]. A customer with no placed order is a required edge case rather than an untested state.

**That set is non-empty, it has exactly two entries, and it contains no story.** One is the epic-level project bootstrap and one is a row of data a buyer can create for themselves. That is what makes this piece of work demonstrable on its own the moment the bootstrap exists, and it is **demonstration-slice condition (iv)** [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination]. The claim is about *stories*: this work waits on none, and the bootstrap it does wait on is priced by none.

### 8.2 Existing Platform Surfaces Consumed As They Stand

These are not prerequisites to be built. Each already ships in this checkout, each is read or called without modification, and each sits on the hard zero-edit boundary for the two protected packages. - **Service `OrderService` — shared code path:** supplies the bulk add this work is built around [packages/core/src/service/services/order.service.ts:L654] and the active-cart read for the authenticated user [packages/core/src/service/services/order.service.ts:L429]; it belongs to `packages/core`, consumed and never modified.

- **Test harness `@vendure/testing` — shared code path:** the end-to-end sub-task is written against it and no alternative harness is introduced [packages/testing/src/index.ts:L1-L14]; it belongs to `packages/testing` and is consumed as published.

## 9. Story Estimation Guidance

Estimation Factors:
* Effort: Medium — one mutation field, one resolver, one service method, one pre-filter step, one projection step and one error-correlation step, over zero new tables and zero migrations.
* Complexity: Medium — the logic is thin, but it consumes a core call whose per-item outcomes must be mapped back to the lines the buyer asked for, and one class of unavailability has to be filtered out before that call because the core raises it as a throw rather than as an accumulated entry, which the acceptance criteria have to keep separate from the clamping cases.

* Estimated Lines of Code to Generate: 600, split as 340 production / 260 test
* Estimated Autonomous Generation Time: 4.0 hours
* Estimated Human Review Time: 2.0 hours
