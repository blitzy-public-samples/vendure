## 1. Feature Title

**Resolve a past order or a saved reorder list into active-cart lines through one permission-gated mutation that reports a per-line outcome, so that a returning buyer stops rebuilding a repeat purchase variant by variant.**

Short name, used verbatim wherever this feature is referred to in one phrase, and identical to the label the epic's features index gives it: **Reorder from Order History and Saved Lists** [tickets/EPIC-001-reorder-and-replenishment.md:§4. The epic classifies this feature's deviation from its originally suggested area as **expanded**, and the rationale is mechanical rather than editorial: the suggested area covered reorder from order history only, and this feature absorbs list-to-cart materialisation as well **because both paths converge on the same core call, `OrderService.addItemsToOrder` [packages/core/src/service/services/order.service.ts:L654], so splitting them across two features would duplicate the per-line partial-failure contract in both** [tickets/EPIC-001-reorder-and-replenishment.md:§4. Delivery is part of the single self-contained plugin package the epic describes — `packages/reorder-plugin/`, exporting `ReorderPlugin`. No file under `packages/core` or `packages/admin-ui` is edited to deliver it.

## 2. Feature Summary

### 2.1 The Capability

A returning buyer takes one past order, a chosen subset of that order's lines, or one saved reorder list, and turns it into lines on their active cart through a single Shop API mutation. **For a request that settles, that mutation returns an outcome for every requested line** — applied at the requested quantity, partially applied at a reduced quantity, or not applied with a named error type — rather than succeeding or failing as a whole. Section 2.6a specifies how each outcome is keyed back to the source lines that produced it; section 2.6b specifies the single request-level outcome a request that does **not** settle returns instead, because one class of unavailability ends the platform call outright and cannot be reported per line.

### 2.2 Contribution To The Epic

This feature is the epic's batch B2, "Reorder execution" [tickets/EPIC-001-reorder-and-replenishment.md:§9.4 Run Batches]. It owns three steps of the returning-buyer journey: opening a past order through the existing history read path, applying a reorder to the active order, and producing the per-line outcome report [tickets/EPIC-001-reorder-and-replenishment.md:§2.5 The Returning-Buyer Journey This Epic Builds]. It is the feature that discharges the objective's central promise — that a repeat purchase costs materially less effort than rebuilding an order from scratch — and the epic nominates this feature's first story as the one demonstrable slice a non-coder can be shown, on the ground that its traceability label is a quoted objective clause rather than an inference [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination].

Read the contribution precisely, because this feature is a *write* path and nothing more:

- **It does not decide what a buyer should be warned about before committing.** The pre-commit price and availability delta read belongs to FEATURE-001-03, which consumes the commit path this feature builds.
- **It does not decide what happens to a line that cannot be added.** Skip, reduce, substitute and abort belong to FEATURE-001-04. This feature reports the outcome; it does not offer the buyer a resolution choice.
- **It does not own the list tables.** `ReorderList` and `ReorderListLine` are FEATURE-001-01's, and this feature only reads them [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched].
- **It does not record the attempt or publish the event.** The audit rows and the typed events belong to FEATURE-001-07, which depends on this feature for the outcome it records.

### 2.3 Named Entities Touched

**This feature introduces no new table.** That is a deliberate design outcome and not an omission: every row it needs already exists, either in the platform's own order tables or in FEATURE-001-01's list tables, so the feature reads and never owns. The consequence is stated plainly in section 5 — there is no additive migration in this feature, and the only migration evidence it carries is that it added none.

Existing platform entities, read and never altered:

- **`Order`** [packages/core/src/entity/order/order.entity.ts:L44], declared as implementing `ChannelAware` and `HasCustomFields`. Seven of its columns are load-bearing here. `code` is the uniquely indexed buyer-facing reference [packages/core/src/entity/order/order.entity.ts:L70], and its own JSDoc states it is the reference to show a customer rather than the id — which is why a reorder input may address a source order by either. `state` [packages/core/src/entity/order/order.entity.ts:L72] and `active` [packages/core/src/entity/order/order.entity.ts:L82], the latter defaulting to true, are what separate a *past* order from the cart being written to. `orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] is the indexed timestamp that makes "the order I placed last" orderable, and `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142] is what makes a currency mismatch between source and target detectable rather than silent. Ownership is read from `customerId` [packages/core/src/entity/order/order.entity.ts:L99], and the target cart's lines from `lines` [packages/core/src/entity/order/order.entity.ts:L102].
- **`OrderLine`**. Two columns define what a reorder actually copies. `quantity` is the live quantity [packages/core/src/entity/order-line/order-line.entity.ts:L97]; `orderPlacedQuantity` is the quantity as at placement [packages/core/src/entity/order-line/order-line.entity.ts:L104]. **The distinction is not cosmetic and a story that picks the wrong one is wrong:** a source line's reorder quantity is taken from `orderPlacedQuantity`, because that is what the buyer actually bought, whereas `quantity` on a historical order can have been altered by an administrative modification after placement. The line's price columns — `initialListPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L113], `listPrice` [packages/core/src/entity/order-line/order-line.entity.ts:L121] and `listPriceIncludesTax` [packages/core/src/entity/order-line/order-line.entity.ts:L128] — are read by FEATURE-001-03 and are named here only so that no story in *this* feature copies a historical price onto a new line.
- **`ProductVariant`**. The target of every projected line. This feature reads the variant identifier and nothing else; the variant's `enabled` state is asserted by the core call described in section 2.6, not by plugin code.
- **`Channel`**. Supplies the request scope described in section 2.9.

Existing plugin-owned entities from FEATURE-001-01, read and never altered:

- **`ReorderList`** and **`ReorderListLine`**, the latter carrying the parent list id, a `ProductVariant` id and an integer quantity [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]. The list path projects one requested line per `ReorderListLine` row, taking the quantity from the row rather than from history. This is the only part of this feature that depends on FEATURE-001-01 at all, which is what section 4.1's qualifier means.

### 2.4 Named Services

- **`OrderService` — existing, in `packages/core`, consumed and never modified.** Four members are named, and the distinction between the one this feature calls and the ones it must leave alone is the point of naming them:

Both are also the two operations the epic's first collision would widen as a side effect if this epic declared a custom field on `OrderLine`, which is why they are the specific pair section 5 requires evidence for [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].
  - `applyPriceAdjustments` [packages/core/src/service/services/order.service.ts:L2311] — named so that no plugin code calls it directly. The bulk add already performs the adjustment pass, as section 2.6 records.

- **`ReorderListService` — existing after FEATURE-001-01, plugin-owned, read only.** The list path resolves its source rows through it rather than querying the list tables directly, so the ownership rule that feature already implements is not reimplemented here [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.5 Named Services].
- **`TransactionalConnection` — existing, consumed.** This feature writes no plugin-owned row, so its use here is confined to reading within the request's transaction [tickets/EPIC-001-reorder-and-replenishment.md:§7.4 Existing Entities And Services The Work Depends On].

### 2.5 Named API Surfaces — One New Mutation, Zero Existing Signatures Changed

**Existing read paths this feature consumes and does not extend:**

- `Customer.orders(options: OrderListOptions): OrderList!` [packages/core/src/api/schema/common/customer.type.graphql:L11] — the order-history read path, reachable through the `activeCustomer` root query [packages/core/src/api/schema/shop-api/shop.api.graphql:L5] and already paginated, sortable and filterable. Section 2.6 records the prohibition attached to it.
- `activeOrder: Order` [packages/core/src/api/schema/shop-api/shop.api.graphql:L11] — the cart read. Its own docstring is directly relevant to section 2.8: it states that the value is null until an Order is created via `addItemToOrder`.
- `order(id: ID!): Order` [packages/core/src/api/schema/shop-api/shop.api.graphql:L34] — a single order by id, whose docstring records that in the Shop API only orders belonging to the currently-authenticated User may be queried. A storefront reads a candidate source order through this or through `orderByCode` [packages/core/src/api/schema/shop-api/shop.api.graphql:L41]; neither is altered.

**The one new operation**, added through the plugin's `shopApiExtensions` using `extend type Mutation` — the mechanism the shipped wishlist example already demonstrates [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L16-L19]:

- `applyReorderToActiveOrder` — accepts **either** a source order reference **or** a reorder-list reference, optionally narrowed to a subset of source lines, optionally carrying the resolution policy declared below, and returns a per-line outcome report. One mutation rather than two is a direct consequence of the expanded scope in section 1: two mutations would need two copies of the outcome contract.

**The whole input shape is fixed here, including the fields only a later feature gives behaviour to. This is deliberate and it is the point of this paragraph.** A published GraphQL input is a contract; adding a field to it later is additive for a client but it *does* reshape an operation this feature already shipped, and a reader tracking the epic's promise that no published surface is redefined would be entitled to call that a breach. So the fields FEATURE-001-04 needs are declared in the initial version of the input, with the default behaviour this feature implements, rather than appearing in a second batch:

- **A per-line resolution choice**, optional, naming for a given source line one of `skip`, `reduce quantity`, `substitute` or `abort` — the four labels FEATURE-001-04 fixes and this feature does not rename [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.3 The Four Resolution Outcomes]. **Under this feature, supplying any value other than the default is rejected as an unsupported argument value rather than silently ignored**, because a silently ignored resolution choice is worse than an absent field: a buyer would believe they had chosen.
- **A request-level default policy**, optional, with exactly one value published by this feature — the abort-on-unresolvable-line behaviour section 2.6b rules. FEATURE-001-04 adds the further values and the behaviour behind them.
- **A substitution acceptance reference**, optional, unused by this feature and reserved for the candidate a buyer accepts. It is declared nullable and is documented as reserved, so that adding its behaviour later changes no signature.

**What FEATURE-001-04 therefore contributes is behaviour, not shape**, and that feature records the same division from its own side [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces]. The epic's operation count is unaffected: this remains one new mutation, and the resolution work adds none.

**The published contract, in full and final form.** Every argument, input field, payload field, enum member, union member and nullability is fixed here rather than left to a story, and it is fixed **including the fields later features need** — `lineResolutions` is declared now even though FEATURE-001-04 is the feature that gives its values meaning. That is deliberate and is explained under the third reading below. Every name was collision-checked against both checked-in introspection snapshots and none exists in either [schema-shop.json:data.__schema.types] and [schema-admin.json:data.__schema.types].

Six readings of that contract are load-bearing:
- **`ReorderPermissionDeniedError` is a member, and it is DECLARED here — this feature is its single SDL authority.** The declaration sits in section 2.11 field for field, and the reason it sits here rather than in the feature that returns it is a build requirement rather than a preference: this union names the member from its **first published version**, and a union member's type must exist for the merged schema to build, so the declaration cannot wait for a later batch [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.11 The Error Vocabulary This Feature Introduces]. **FEATURE-001-06 is the only feature that ever RETURNS it** and consumes this declaration in its own two unions rather than redeclaring it [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.12 The Error Vocabulary This Feature Introduces], which is what makes STORY-001-06-03's refusal representable without a second, rival declaration — a plugin-owned type declared twice in one merged schema document is a build failure, not a merge. **The `ErrorCode` growth therefore lands in THIS feature's batch, B2, not in B5**, because the enum is generated from every type implementing the error interface [packages/core/src/api/config/generate-error-code-enum.ts:L9] and the type exists from the moment this document merges; section 6.5's ledger carries the resulting stage totals [tickets/EPIC-001-reorder-and-replenishment.md:§6.5 The Cumulative Published-Surface Ledger — One Authority, Not Eight Snapshots]. **An earlier revision of this bullet said the type belonged to FEATURE-001-06 and was consumed rather than declared here**, while this file's own section 2.11 declared it and the epic's inventory assigned it here — two declaring authorities for one type, which is the defect this correction closes.
- **A plugin-owned union is mandatory, because the core union cannot be extended.** `union UpdateOrderItemErrorResult` is declared in core [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117] and a plugin cannot add a member to it without editing `packages/core`, which the epic's zero-edit boundary forbids. `ApplyReorderResult` is therefore plugin-owned, and it needs its own `__resolveType` field resolver registered in the plugin's resolvers array — ruling R8 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. Mirroring the published payload, which mechanism two requires, means matching its *shape*, not reusing its union.
- **Per-line failures are not top-level union members, and the separation between the two levels is total.** A line that could not be added is reported inside `lineOutcomes` with its own `outcome` code and `errorCode`, because a reorder in which one line of eight failed is a **success carrying a report**, not a failure. `InsufficientStockError`, `NegativeQuantityError`, `OrderInterceptorError` and `OrderLimitError` therefore never appear as top-level results of this mutation; their codes appear on individual outcomes. **`OrderLimitError` is not an exception to that rule, and settling which of the two bounds it names is what closes a contradiction three files carried.** Two bounds that one type name, and they are now separated by *mechanism* rather than by level-of-the-same-type. *The plugin's own source-size bound* is checked **before** the core call and is **not a member of this union at all**: an over-bound source is refused by throwing the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30], so the client observes `USER_INPUT_ERROR` in `extensions.code` [packages/core/src/common/error/errors.ts:L29] and the message key `error.reorder-selection-above-maximum`: **nothing is written**, the field the operation would have returned is null, and there is no `lineOutcomes` array at all. *The deployment's order-items limit* is core's, enforced per item during the write [packages/core/src/service/services/order.service.ts:L675-L679], returned into the accumulated collection rather than thrown [packages/core/src/service/services/order.service.ts:L2286-L2290] and [packages/core/src/service/services/order.service.ts:L2298-L2302], and reported **line-level** as `NOT_ADDED_LIMIT_REACHED` with `errorCode` naming `OrderLimitError` [packages/core/src/api/schema/common/common-error-results.graphql:L37], because the lines that fit are written and the buyer needs to know which ones were not. **One bound, one mechanism; two bounds, two mechanisms.** An earlier revision of this reading put `OrderLimitError` in the union as a request-level member *and* on the line, which left a client unable to tell a plugin refusal from a core rejection except by inspecting whether a payload came back, and left three child stories listing a four-member union against a five-member declaration [tickets/EPIC-001/FEATURE-001-02/STORY-001-02-03-add-reorder-list-to-active-cart.md:§5. Acceptance Criteria]. **A core error type is now used only for the condition its own description names — and `OrderLimitError` describes the maximum order size the *server configuration* permits rather than a bound a plugin invented**, which is ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory].
  - **Request level — the plugin's own source-size bound, checked before any core call, and refused by throwing.** A source resolving to more projected lines than `ReorderPluginOptions.maxProjectedSourceLines` is refused whole with `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] under the plugin message key `error.reorder-selection-above-maximum`, which is the single key this feature uses for that one configured bound whichever surface it is checked on: **no `ReorderResult` is returned, no `lineOutcomes` array exists and not one `OrderLine` row is written**. **The request-error shape is therefore one shape and it is stated once:** `data.applyReorderToActiveOrder` is null, `errors[0].extensions.code` reads `USER_INPUT_ERROR` [packages/core/src/common/error/errors.ts:L29], and `errors[0].message` carries the plugin message key named above. `OrderLimitError` is **not** a member of `ApplyReorderResult` and does not appear here. **An earlier revision of this sentence spliced two clauses into one** — it began "`OrderLimitError` is not a member of" and continued straight into "the client reads `USER_INPUT_ERROR`", naming no union and leaving the reader to guess where one statement ended and the next began. Reporting it per line instead would emit N identical failures with no successful line among them, which a client cannot tell apart from a partial success; reporting it as a union member would reuse a core type for a condition its own description does not name.
  - **Line level — the cart's own item and line-item limits, reached during the core call.** `addItemsToOrder` produces `OrderLimitError` **per item** from the cart-level item check [packages/core/src/service/services/order.service.ts:L2288-L2290] and the per-line-quantity check [packages/core/src/service/services/order.service.ts:L2300-L2302], accumulating it into its returned error array and continuing rather than aborting [packages/core/src/service/services/order.service.ts:L676-L683]. Earlier lines have therefore already been written, so the truthful report is per line: the outcome is `NOT_ADDED_LIMIT_REACHED` and `errorCode` carries that type's code. **A top-level refusal here would be a lie about the cart's state.**
  - **A client distinguishes the two by shape, and neither shape is a union member of this mutation**: the request-level condition returns a null `data.applyReorderToActiveOrder` with `USER_INPUT_ERROR` in `extensions.code` and no payload at all, while the line-level condition **returns a populated `ReorderResult`** *containing* that code on one `lineOutcomes` entry beside the entries that succeeded. **An earlier revision of this clause omitted its verb**, leaving the second half of the contrast without a predicate. No third possibility is published, no core error type other than `NoActiveOrderError` and `OrderModificationError` is permitted at the top level of this mutation, and `OrderLimitError` is **not** a member of `ApplyReorderResult`.
- **`lineResolutions` is declared now so that FEATURE-001-04 changes nothing later.** F4 adds the resolution behaviour; if it also had to add the input field, it would be modifying an input this feature had already published — which is the silent redefinition the epic's fifth collision exists to prevent [tickets/EPIC-001-reorder-and-replenishment.md:§6.2 Research-Discovered Collisions]. Until F4 ships, a non-empty `lineResolutions` is a request-level input failure rather than a silently ignored field, and that too is a declared behaviour rather than an accident. The same applies to `SKIPPED_BY_RESOLUTION` and `SUBSTITUTED`: both members exist in the enum from the outset and are unreachable until F4, because adding an enum member later is a published-schema change while an unreachable member is not.
- **`errorCode` is typed as the platform's own `ErrorCode` enum**, whose members are generated from every type implementing the error interface [packages/core/src/api/config/generate-error-code-enum.ts:L9], so the outcome report names exact existing error types rather than a parallel vocabulary. Every consuming example that switches on it carries a default branch, per ruling R9.
- **Both currency codes are on the payload, which is what makes a mismatch a reported outcome rather than a hidden one.** Section 2.9 fixes the behaviour; these two fields are how a client observes it.
**The single-vocabulary rule, which every story in this feature is held to.** The schema above is the only normative statement of the payload, and every story uses these type and field names verbatim rather than paraphrasing them. Three consequences are stated so no story re-derives them differently. **There is no separate "errors" or "failures" collection, and no story may describe one** — a reorder that fully succeeds returns `lineOutcomes` in which every entry carries an `ADDED` outcome and a null error, and the phrase "an empty failure list" is not the contract. **One vocabulary correlates the report across both source paths**: an outcome entry names every source line that fed it inside `contributors`, and each `ReorderSourceLineRef` there carries the same pair of nullable identifier fields the selection input uses, `sourceOrderLineId` and `reorderListLineId`, exactly one of which is set and which one being fixed by the source form, so a consumer reads the report and the input it sent in the same terms rather than in two vocabularies. **The report is keyed by projected variant and not by source line**, and section 2.6a states why: the core sums same-variant quantities, so a per-source-line applied quantity would require an apportionment rule this feature declines to invent. **Quantities are integers and no monetary value appears in the outcome at all** — `requestedQuantity` and `addedQuantity` are counts, and prices live on the returned `order`, where the platform already expresses money as an integer in the smallest currency unit.
**The source-size bound, carried by one named option of its own.** The number of source lines one call accepts is bounded by **`ReorderPluginOptions.maxProjectedSourceLines`**, typed `number` and constrained to a finite integer of at least 1, **required with no value declared anywhere in this ticket set**, and **validated at plugin initialisation** so that an absent, zero, negative, fractional or non-finite value fails startup with the option named rather than admitting an unbounded public mutation [tickets/EPIC-001-reorder-and-replenishment.md:§7.10 The Plugin Option Ledger — One Authority For Every Configured Key]. The value is the epic's fourth product decision and is not a figure this feature invents [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions], under the rule that binds every collection and every collection-scale workload in this epic [tickets/EPIC-001-reorder-and-replenishment.md:§7.7 Bounded Collections].

**Why this is its own key and not FEATURE-001-01's `maxLinesPerList`, stated because an earlier revision of this paragraph said it was that maximum for a list source and "the same configured maximum" for an order source — which named no key at all and, read literally, bounded an order source by a list's limit.** Three reasons, each of which alone settles it. An **order** source has no list bound to borrow: an order's line count is bounded by the deployment's order-items limit [packages/core/src/service/services/order.service.ts:L2286-L2290], a different quantity under different ownership, so borrowing `maxLinesPerList` for it would apply a bound the source was never written under. The **projection is not the source**: a multi-line selection can merge several source lines onto one variant key and can span two sources, so the count this bound applies to is produced by the projection and is neither source's stored line count. And the two bounds guard **different costs** — `maxLinesPerList` guards how large a stored list may grow, while this one guards how much variant loading and stock reading one public request may provoke, which is the cost the epic's fourth decision was raised about. The two therefore interact rather than coincide: for a list source the write is additionally subject to whatever bounds the list, so the effective ceiling is the lesser of the two, and **a story that configures one and asserts the other has tested nothing**. Two consequences are stated rather than implied: a request whose source resolves to more lines than the bound is refused **at request level** with the platform's `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] and the plugin-owned key `error.reorder-selection-above-maximum` rather than truncated silently — and **not** with `OrderLimitError` [packages/core/src/api/schema/common/common-error-results.graphql:L37-L41], which is core's *per-item* error and is therefore reported only as a line-level outcome, per the epic's ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. **The outcome collection is bounded by construction** because it holds one entry per distinct projected variant, which is at most the number of requested lines, and the requested lines are bounded. The bound is what makes the maximum-source benchmark scenario in the epic a defined measurement rather than an open-ended one [tickets/EPIC-001-reorder-and-replenishment.md:§7.6 Data-Volume Assumptions And The Benchmark Workflow].

**The shared selection contract, declared once here and imported by every feature that projects source lines.** FEATURE-001-03's preview and FEATURE-001-04's resolution round both accept these two input types rather than mirroring them [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces], so a rule stated here is a rule everywhere and a rule left unstated is a hole everywhere. **An earlier revision of this feature left five of the seven rules below undefined**, which meant a story could not write a deterministic validation criterion and two stories wrote different ones. Every violation is refused **before any projection, any variant load and any stock read**, as a request-level input failure carrying the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] — `extensions.code` of `USER_INPUT_ERROR` and a plugin-owned message key — rather than as a union member, per the epic's ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]:

- **Source addressing.** Exactly one of `sourceOrderId`, `sourceOrderCode` and `reorderListId` is set. Zero or two set is refused with `error.reorder-source-not-addressable`. A code and an id naming the same order is still two fields set and is still refused, because accepting it would require deciding which wins.
- **Selection entry addressing.** Exactly one of `sourceOrderLineId` and `reorderListLineId` is set on every entry, and the one that is set must match the source form — a `reorderListLineId` against an order source is refused with `error.reorder-selection-wrong-source-form`, not silently ignored.
- **Uniqueness.** No line id appears twice in `lineSelections`. A duplicate is refused with `error.reorder-selection-duplicate`, and the offending id is named in the error's variables. **Deduplicating silently is not an option**: two entries for one line with two different quantity overrides have no defined resulting quantity, and picking one would be an invented rule.
- **Array size.** `lineSelections` holds no more entries than the configured source-size maximum this paragraph's predecessor names. Over-size is refused with `error.reorder-selection-above-maximum`. This is the *request* bound and it is checked on the array itself, so a caller cannot make the server resolve a thousand ids to be told the source has ten lines.
- **Quantity override range.** A supplied `quantity` is an integer of at least one and no greater than the configured `maxQuantityPerLine` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency]. Zero, negative and over-maximum are refused with `error.reorder-selection-quantity-out-of-range`. **The ceiling exists because the value is a 32-bit integer in the schema and in the column**, and because the per-key sum of several contributors can exceed either even when no single entry does — so the sum is checked against the same ceiling after projection and refused the same way.
- **Membership.** Every id names a line of the *resolved* source. An id that names a line of another order, another list, or nothing at all is refused with `error.reorder-selection-unknown-line`, and the error names how many ids failed rather than which, so the operation cannot be used to probe another buyer's line ids.
- **Omitted versus empty.** An omitted or null `lineSelections` means every line of the source. An explicitly empty array is **not** the same request: it selects nothing, and the operation returns `NoReorderableLinesError` with `resolvedSourceLineCount` reporting what the source held. The two are never conflated, which is why the input's own description says so.

**SETTLED — what the over-bound refusal actually is, because there are two different limits in play and an earlier version of this file conflated them.** That version refused an over-bound source with `OrderLimitError` [packages/core/src/api/schema/common/common-error-results.graphql:L37-L41] at request level, which cannot be expressed: `OrderLimitError` is **not a member of `ApplyReorderResult`**, so a resolver returning it would not type-check against the union this feature publishes, and adding it would put a core order-items limit in the same position as a plugin source-size limit. The two limits are therefore separated by mechanism — a thrown input error for the plugin's bound, a line-level code for core's — and every story in this feature uses this separation verbatim.
- **The plugin's own source-size bound is a request-level refusal by the platform's own `UserInputError`** [packages/core/src/common/error/errors.ts:L27], carrying the code `USER_INPUT_ERROR` in `extensions.code` [packages/core/src/common/error/errors.ts:L29] because that class extends `I18nError` which extends `GraphQLError` [packages/core/src/i18n/i18n-error.ts:L18] and [packages/core/src/i18n/i18n-error.ts:L25-L27]. `data.applyReorderToActiveOrder` is null, no `ReorderResult` is returned, and the refusal happens **before the source lines are projected, before any variant is loaded, before any availability read and before `OrderService.addItemsToOrder` is called** — which is what makes the bound a guard on work rather than a label on it. No Admin API operation is added by this feature. No query is added by this feature at all — the history read path already exists, and adding a reorder-specific one is explicitly prohibited in section 2.6.

### 2.5.2 Replay Safety — The Idempotency Key, And Why An Additive Mutation Needs One

**This mutation adds quantities, so a retry is not free, and an earlier version of this file had no answer to that.** Every other guarantee in this feature concerns what happens *within* one call. This section concerns what happens when one call is made twice, which is the ordinary case rather than the exotic one: a storefront issues `applyReorderToActiveOrder`, the write commits, the response is lost to a dropped connection or a closed tab, and the client — or the buyer pressing the button again — issues the same request a second time. **Without a replay identity the second call is indistinguishable from a buyer who genuinely wants the items twice, so the quantities double, a second audit attempt is recorded and the three events fire again.** That is a correctness defect in a buyer-facing write path, not a hardening nicety, and it is worse here than on a single-item add because one call can double an entire order.

**The mechanism, stated as the contract rather than as advice.**

- **The key is caller-minted, opaque and optional.** `ApplyReorderInput.idempotencyKey` is a `String` of at most sixty-four characters. The plugin never generates it and never parses it, and it **never persists it either**: it is digested into the claim identity below, compared as a digest, by digest and never stored in cleartext, nothing more. **It is also never logged, never projected onto any Admin field and never carried in any event payload**, because its content is whatever the client chose to put in it. Omitting it is legal and means the caller has accepted that a retry adds again — which is the honest default for a client that does not want the guarantee, and is why the field is nullable rather than required.
- **The scope is the tuple, never the key alone — and what is stored is one digest OF that tuple rather than the key, in one column, under one plain unique index.** The claim identity is the tuple of the acting customer, the channel, the operation and the caller's key. **It is stored as `ReorderAttempt.replayClaimDigest`, a fixed-width non-null column carrying the plain unique index `UQ_reorder_attempt_replay_claim`, and FEATURE-001-07 is its authority** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **Two earlier forms are withdrawn rather than left standing beside it, because between them they described a schema no migration could produce:** a partial unique index named `UQ_reorder_attempt_idempotency` over `(actingCustomerId, channelId, idempotencyKeyDigest)`, qualified by a "where the key is not null" predicate that is not part of the index grammar every engine this set is evidenced against accepts [.github/workflows/build_and_test.yml:jobs]; and a separate nullable `idempotencyKeyDigest` column beside the claim digest, which made the claim two columns in one file and one in another. **The portable form is the settled one: one non-null digest, one plain index, no row predicate.** A request that supplies no key still fills the column, with the digest taken over the attempt's own `correlationId`, which is unique per attempt by construction — so keyless requests never collide and the index needs no predicate. **The digest substitution changes nothing a caller can observe**: a keyed hash under a configured secret is stable and equality-preserving, so the same key always claims the same row, and a caller neither supplies nor reads the digest. What it changes is that the caller's arbitrary text is never persisted in a customer-linked table a support surface reads, which is why that feature stores it that way [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. Scoping to the customer and channel means one buyer's key cannot collide with another's, and a key replayed under a second channel token is a *different* request rather than a replay — which follows from ruling R16 rather than being a separate choice [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory]. **One column rather than a composite over three, because the whole tuple is inside the digest and the operation element is constant for this one mutation.** **What keys that hash is settled configuration rather than an open question**: the epic's option ledger declares `replayClaimHmacKey` and the `replayClaimKeyId` recorded beside each digest, and is the single authority for both [tickets/EPIC-001-reorder-and-replenishment.md:§7.10 The Plugin Option Ledger — One Authority For Every Configured Key].
- **The claim is one insert, and it is the same insert the audit trail makes — written once, after the core call, inside the reorder's own transaction.** This is the ordering rule, and it replaces an earlier revision of this bullet that required the attempt row to be inserted as the request's *first* write while FEATURE-001-07 required exactly one append-only insert *after* the core work [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.5.1 The Write Shape And Its Transaction Boundary]. **Both could not hold, and the resolution is that the insert's position inside the transaction does not matter**, so the later position wins and there is no pending state, no second write and no status transition anywhere in this design. **What makes the claim atomic is the unique index rather than the ordering**, and the reasoning is worth stating because it is the whole of the guarantee: the resolver is decorated `@Transaction()`, so the cart write and the attempt insert are one unit of work [packages/core/src/connection/transaction-wrapper.ts:L64]. Two concurrent calls carrying the same key both reach the core call and both attempt the insert; one succeeds and commits, the other violates the constraint and **its entire transaction rolls back — including its cart write** [packages/core/src/connection/transactional-connection.ts:L176-L177]. So exactly one application survives, which is exactly the guarantee an insert-first design would have bought, and the only cost of the later position is work done and discarded on the losing request rather than a wrong cart.
- **The loser reads the committed row in a new transaction, because its own is no longer usable.** A failed statement leaves the enclosing transaction unusable on some engines, so the recorded result is read *after* the rollback, in a fresh transaction, and only then returned with `replayed` true [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.5.1 The Write Shape And Its Transaction Boundary]. **A story asserting the race asserts that fresh read**, not a read inside the failed transaction, because a read inside it passes against sql.js and fails against a real engine. A cheap pre-call probe for an already-committed row is permitted and is the ordinary path — it costs one indexed read and spares the duplicate work — but it is an optimisation and never the guarantee, because two calls that both probe before either commits both miss.
- **A request that fails for any other reason burns no key, and that follows from the same ordering rather than from a rule of its own.** The claim commits with the reorder, so a request that rolls back leaves no row and therefore no claim: a client whose call failed may retry with the same key and have it treated as new work. **A refused request records no key at all**, because every refusal branch returns before the core call and the column is written only where the request reached it — which is what keeps a client from being locked out of retrying a request that was rejected for bad input, and what confines a replay to the one branch section 2.5.2a proves is reconstructible.
- **A second request reusing one key with a different payload is REFUSED, not silently replayed, and that is a correction rather than a refinement.** The attempt row stores a second digest beside the claim: a **request fingerprint** over the canonical request — the resolved source reference, the ordered selection entries with their quantities, and the ordered resolution entries — so a collision on the claim index is followed by loading the claimed row and comparing fingerprints. **Equal is a replay** and returns the recorded result. **Unequal is a conflicting reuse of one key**, refused with the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] under the message key `error.reorder-idempotency-key-payload-mismatch`, writing nothing. An earlier revision of this section compared the key alone, so a client that reused a key while changing its selection received the *first* request's result and a cart that did not match what it had just asked for — a wrong answer returned confidently. FEATURE-001-01 states the identical rule for its own claim, so one contract governs both surfaces [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency — The Rules That Make The Contract Deterministic].
- **The field is published by this feature and made effective by FEATURE-001-07, and a key supplied before then is refused rather than accepted.** The row the claim is written to is `ReorderAttempt`, which story 07-01 creates in batch B5 [tickets/EPIC-001-reorder-and-replenishment.md:§9.4 Run Batches], whereas this feature ships in B2. **So there is an interval in which the field is declared and the storage is not there, and the behaviour in that interval is stated rather than left to be discovered:** a request carrying a non-null `idempotencyKey` is refused as an unsupported input, exactly as a non-empty `lineResolutions` is refused until FEATURE-001-04 ships. **Refusing is the whole point of naming this**: silently ignoring the key would hand a client a guarantee it does not have, which is worse than not offering the guarantee at all, and a client that receives a refusal knows to retry without the key and accept the consequence. The field is nonetheless declared here rather than added later because adding an input field later is a published-schema change, which is the widening this feature's frozen-input rule exists to prevent. **The same refusal covers a second, permanent case rather than only the sequencing one:** FEATURE-001-07 exposes a plugin option that suppresses recording, and a deployment that sets it has no attempt row and therefore no claim store, so a keyed request under that configuration is refused on the same path and with the same shape [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11.3 How "Disabled" Is Achieved — Because Unregistering The Plugin Is Not It]. **One condition, one refusal, two causes** — and in neither case is a key accepted and then quietly ignored, because a client that believes it holds this guarantee and does not is worse off than a client told it cannot have it.
- **An eighth plugin-owned table for the claim was considered and rejected, and the reasoning is recorded so it is not reopened as an oversight.** A dedicated idempotency table would make the guarantee effective from B2, but it would add a table to the epic's seven-table inventory [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory], a second additive migration and a second row lifecycle to govern under the erasure decision — and it would store, per claim, the same customer, channel and outcome the attempt row already stores. **Two tables recording one event is the duplication the do-not-duplicate inventory exists to prevent**, so the claim shares the attempt row and this feature accepts the sequencing consequence above instead. What is *not* accepted is leaving the interval undescribed.
- **A replay returns the recorded result and writes nothing, and exactly which fields "recorded" covers is settled in section 2.5.2a rather than left as an intention.** The loser of that race, and any later call carrying an already-claimed key, reads the recorded attempt and returns a `ReorderResult` rebuilt from it — the same `lineOutcomes` entry for entry, the same `requestOutcome`, the same `unattributedErrorCodes`, the same two currency codes and the same `correlationId` — with `replayed` set to `true`. It adds no quantity to the cart, records no second attempt and publishes no second event. **Two fields differ from the original response and both are named**: `replayed`, which exists so a client can tell the two apart, and `order`, which is re-read live because a cart is not a snapshot. Section 2.5.2a states why and what follows from it.
- **A replay is not a way to read someone else's attempt.** The recorded attempt is addressed by the digest of the full tuple, which includes the acting customer and the channel, so a caller can only ever replay their own key in their own channel. A key belonging to another customer digests to a different value, resolves to no row, and the request proceeds as new work. **The raw key never leaves the plugin**: it is not published on the response, not carried on an event payload and not written to a log line — only the digest is, which is what keeps a caller-chosen string that may encode anything out of the audit and instrumentation surfaces [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7 The Three Events And Their Payload Schemas — This File Is Their Authority].
- **`correlationId` is what a support conversation quotes, and it is deliberately not the idempotency key.** The key is chosen by the client and may encode whatever the client encodes; the correlation identifier is minted by the plugin, opaque, carries no customer identity, and is returned on the payload and persisted on the attempt row so a buyer can quote it and an agent can find the row. Log lines name the correlation identifier and never the customer identifier, which is the data-minimisation rule FEATURE-001-07 states for every diagnostic it emits [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality].
- **What is out of scope, said plainly so nobody builds it.** There is no time-to-live on a claimed key, no explicit key-release operation and no cross-channel key namespace. A claimed key is retained exactly as long as its attempt row is retained, so it is governed by the epic's customer-data-lifecycle decision and by nothing separate [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions] — inventing a keep-period for it here would be inventing the very number that decision exists to hold open.

**Why this is declared now rather than added by a later feature.** The input type publishes its final shape in this feature's first version, so a field a later feature needs must be declared here or be a widening later [tickets/EPIC-001-reorder-and-replenishment.md:§6.2 Research-Discovered Collisions]. FEATURE-001-07 reuses this key as the attempt and publication identity rather than minting its own, which is what makes a replayed reorder produce one audit trail instead of two.

**This creates no dependency of this feature on FEATURE-001-07, and the direction matters.** The epic's graph carries `F2 → F7` and no reverse edge, and that stays true: this feature ships, is accepted and is demonstrable without the attempt table existing, in exactly the way it ships without FEATURE-001-04's resolution behaviour existing. FEATURE-001-07's arrival *activates* a field this feature already published; it is not a prerequisite of this feature's delivery.

**Which stage each acceptance criterion asserts is settled here, because leaving it to the criterion produced a criterion that accepted either outcome.** An earlier revision let three stories' final criterion accept "whichever replay stage happens to be active", which is not an acceptance criterion at all: a test that passes on two different behaviours cannot fail on the wrong one, and it also gave the demonstration-slice nomination a story prerequisite it is not allowed to have [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination]. **So the split is by owner rather than by stage.** Every criterion in **this** feature's four stories asserts the B2 behaviour and only that: a non-null `idempotencyKey` is refused as an unsupported input, the cart's line count is unchanged by the refused call, and `correlationId` is present, non-empty and **different** on two key-less calls of the same input. That is deterministic on the day this feature merges and needs no other story. **The persisted guarantee — the same key twice leaving one attempt row and a second response identical but for `replayed` — is asserted by `STORY-001-07-01`**, which creates the row the claim occupies, and by no story of this feature. Neither assertion is conditional, and no criterion anywhere in this set is written to pass under two behaviours. `correlationId` behaves the same way — it is minted and returned by this feature from the outset, because minting an opaque identifier needs no table, and it becomes *persisted* when the attempt row exists.

### 2.5.2a What A Replay Actually Returns — The Bounded Recorded Response, Field By Field

**A guarantee that a replay returns "the same response" is only true if every field of that response is recoverable, and an earlier revision of this file asserted it without checking.** The audit tables FEATURE-001-07 declares are the only durable record of an attempt [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched], so a field the response carries and those rows do not hold is a field a replay would have to invent, re-derive or omit. This section closes that gap in the only two ways available: it names the fields that must be persisted for the guarantee to hold, and it **weakens the guarantee explicitly** for the one field that cannot be.

**The scope of the guarantee is one branch, and confining it there is what makes it checkable.** A key is recorded only on an attempt that reached the core call and committed — the settled branch, whose attempt outcome is one of fully applied, partially applied, none applied or the degraded unattributed value [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums]. Every refused branch returns before the core call and records no key; the aborted branch rolls its cart write back, so a retry adds nothing that was not added the first time and is treated as new work. **A replay therefore only ever reproduces a `ReorderResult`, never an error member and never an aborted response**, which removes the whole class of question about reconstructing a union member's own fields — `NoReorderableLinesError.resolvedSourceLineCount` among them.

**The ten payload fields of `ReorderResult` and where each comes from on a replay.** Nine are read from the recorded rows or are constants on this branch; one is re-read.

- `requestOutcome` — `SETTLED`, which is a constant on this branch rather than a stored value.
- `lineOutcomes` — one entry per attempt-line row, ordered by that row's `requestIndex`, with `productVariantId` from the recorded requested variant, `requestedQuantity` and `addedQuantity` from the recorded quantities, `outcome` and `errorCode` from the recorded enum members, and `contributors` from the recorded lineage.
- `unattributedErrorCodes` — from the attempt row. **This is one of the three values the attempt row must carry for this section to hold**, because the collection is a request-level fact that no line row encodes: on the degraded branch it holds error codes precisely because they could *not* be attributed to a line.
- `sourceCurrencyCode` and `targetCurrencyCode` — from the attempt row, the second and third of those three values. A line's recorded `currencyCode` is the currency the applied price was expressed in and is null on a line that applied nothing, so it cannot stand in for either.
- `abortingProductVariantId` and `abortingSourceLineIds` — null and empty, which are constants on this branch.
- `correlationId` — from the attempt row, which is why it is minted before the write rather than after it.
- `replayed` — `true`, the one field whose value is *supposed* to differ.
- `order` — **re-read live, and this is the explicit weakening.** A cart is a live aggregate whose totals, taxes, promotions and shipping recalculate on every change, and the attempt row records an order id and code rather than an order [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. Storing a serialised copy was rejected: it would duplicate a core aggregate in a plugin table, go stale the moment the buyer changed the cart, and hand a client a stale cart that looks authoritative. So the replay returns the cart **as it is now**, read through the same active-order path the original request used, and a client that needs the cart as it was at the time of the attempt does not get it from here.

**What this obliges of the audit trail, stated as a requirement on named columns rather than as an expectation.** Three values above are request-level and two are per line, and none of them is derivable from the others, so each must exist as a column on the attempt tables: `unattributedErrorCodes` as a bounded ordered list of closed `ErrorCode` names — bounded because the source size is bounded and the names are drawn from a closed five-member set; `sourceCurrencyCode` and `targetCurrencyCode`; and, per line, both the applied cart-line identifier that `ReorderLineOutcome.orderLineId` reports and the ordered contributor lineage carrying each contributing source line's identifier **and its own requested quantity**. FEATURE-001-07 declares all five [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched], and this feature's mapped-outcome DTO produces every one of them (section 2.5.3) — which is the compile-time check that keeps this section honest rather than aspirational.

**The two properties a story asserts, because a replay is only as good as its evidence.** First, **field equality on the reproducible eight**: the same call issued twice with one key returns two responses that are equal field for field across everything except `order` and `replayed`, asserted by comparing the two responses rather than by re-deriving the expected values. Second, **the weakening is asserted rather than assumed**: between the original call and the replay the test removes a line from the cart through the existing `removeOrderLine` mutation [packages/core/src/api/schema/shop-api/shop.api.graphql:L76], and the replayed response's `order` reflects that removal while its `lineOutcomes` still report what the original attempt did. That second case is what distinguishes a live re-read from a stored snapshot, and it is the case an implementation that stored a snapshot would fail.


### 2.5.3 The Internal Mapped-Outcome DTO — What This Feature Produces For FEATURE-001-07 To Consume

**FEATURE-001-07 records an audit row per projected variant key and states that it copies its values rather than deriving them. That is only true if this feature actually produces them, and the public payload does not.** `ReorderLineOutcome` is deliberately narrow: it carries no monetary value at all, no tax basis, no availability reading and no resolution choice, because a buyer-facing outcome report has no business carrying them. The audit needs all four, and it needs three label snapshots the public payload also omits. Left unstated, the gap would be closed at build time by the audit re-deriving values from the catalogue *after* the write — reading a price that may already have changed, resolving a name in whatever language that later request happened to carry, and recording a number the buyer never saw. **So the producer is named here, in the feature that owns the write path, and the audit consumes it.**

**The DTO is two levels, because the audit is two tables.** `MappedReorderAttempt` is the request-level envelope, carrying the per-key collection plus every request-level value the attempt row records; `MappedReorderOutcome` is one instance per **distinct projected variant key**. Both are **plugin-internal TypeScript and neither is published in any schema.** They are the return value of `ReorderService`'s internal mapping step — the same step 4 projection section 2.6a specifies — and it exists in exactly one grain, **the same grain the public payload uses: one instance per PROJECTED VARIANT KEY**, carrying the same grain that payload carries and the same contributor collection. **An earlier revision of this sub-section said one instance per REQUESTED SOURCE LINE**, which is the defect this paragraph exists to close: the public entry is per projected key, so a per-source-line DTO could not be filled from it without inventing an apportionment of the applied quantity across the lines that collapsed, and the audit written from it could not be lined up against the response the buyer saw. One grain, three consumers — response, DTO and audit row — is ruling R4 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory]. **The two grains in this feature are therefore both named, they are different on purpose, and the derivation between them runs in one direction only — which is the whole of the correlation model and is stated here so no story has to infer it.** The internal collection is at **source-line** grain because that is the grain FEATURE-001-07's audit rows need and the grain that preserves lineage. The published `lineOutcomes` collection is at **projected variant key** grain, as ruling R4 fixes, and it is *derived from* the internal collection by grouping on the projected key: one published entry per key, at the lowest `requestIndex` of the lines that fed it, carrying each of those lines as a `contributors` entry with its own `requestedQuantity`. **The derivation never runs the other way, and no applied quantity is ever divided along it:** `addedQuantity` is a property of the key, taken once from step 4's before-and-after diff, and it appears on the published entry only. The internal instance's `applied` quantity is the same key-level number, recorded against every line of that key rather than split between them, and FEATURE-001-07 stores it that way and says so [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4b The Migration Plan, Its Owner, And The Grain That Every Consumer Reads]. A reader who wants the per-line share will not find one, because there is none to find. **That is the same grain as the public report and as the audit row, and the agreement is the point rather than a coincidence**: FEATURE-001-07 states that it copies these values rather than deriving them, which a per-source-line instance would make impossible, because the audit would have to re-project duplicate lines onto one key and would be deriving after the write exactly what this step already computed before it. **An earlier revision declared this type per requested source line, and that reading is withdrawn**: it left `requestIndex` undefined for two source lines naming one variant and it gave one write three grains — report, DTO and audit — where the projection produces one [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract]. Every contributing source line is still named, inside the identity field below. Per instance:

**The request-level envelope, `MappedReorderAttempt`.** Every field is a value this feature already holds at the moment the mapping runs, and none is re-read afterwards:

- **Identity and routing** — the `correlationId` this feature mints, the acting customer's id from the authenticated session, the active channel's id, and the request's `languageCode` as resolved for the request rather than translated to anything.
- **Source** — the source discriminator as a closed value of **order, list, or unresolved**; the source order's id and its `code` [packages/core/src/entity/order/order.entity.ts:L68] for the order path, or the source list's id for the list path, exactly one pair populated on each of those two and **neither populated on the third**. **The third member is not a widening of this DTO but a shape it already had to produce and could not name**: a request refused for naming no source or two has no resolvable source, so a two-member discriminator has no value that is true of it, and the consuming table's own discriminator carries the same three members for the same reason [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. Where the source was a list the caller does not own, that list's owner customer id together with the authorisation basis, the share id and the capability as it stood at the moment of the request, which FEATURE-001-06 supplies to this feature's service [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.6 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds].
- **Target** — the target cart's id and its `code`, both null where no cart was resolved.
- **Outcome** — the request-level outcome, the aborting variant id where section 2.6b's abort branch was taken, and the five counts section 2.5's payload does not carry: requested keys, fully applied, partially applied, rejected and not evaluated.
- **Response reconstruction** — `sourceCurrencyCode`, `targetCurrencyCode`, the `unattributedErrorCodes` collection exactly as the response reported it, and the caller's `idempotencyKey` where one was supplied — carried on the DTO because the recording step needs it to compute the claim digest, and **never persisted as itself**: the column FEATURE-001-07 writes is `replayClaimDigest`, a keyed digest of the whole claim tuple [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. These four are here because section 2.5.2's replay returns a recorded response rather than a re-computed one, and a value the mapping never produced is a value no table can store.

**The per-key instance, `MappedReorderOutcome`.** One per distinct projected variant key, carrying the same `requestIndex` the public payload carries. Per instance:

- **Identity and lineage** — `requestIndex`, which is the lowest contributing index for this key; the projected `productVariantId` that *is* the key; and the ordered `contributors` collection — one entry per source line that projected into this key, each carrying that line's own identifier in the same form the public `ReorderSourceLineRef` carries it, together with that line's own requested quantity. **The collection is the lineage and it is never flattened to one identifier**, because a key fed by two source lines has two of them and a single-identifier field would have to discard one.
- **Variants and the cart line the units landed on** — the requested variant id; the *applied* variant id, which differs only where FEATURE-001-04 substituted one for another and is equal otherwise; and the **applied order-line id**, which is the identifier `ReorderLineOutcome.orderLineId` reports on the public payload and is null exactly where the applied quantity is zero. Two variant fields rather than one, because an audit that stores only the applied variant cannot answer what the buyer originally asked for. The order-line id is named here rather than left to the consuming table to find, because section 2.5.2's obligation list already requires it per line and a field that obligation names but this enumeration omits is exactly the mapping hole the compile-time totality rule below exists to catch.
- **Quantities** — requested and applied, both integers. The requested value is the sum over `contributors`; the applied value is the key's own before-and-after order-state delta from step 2, recorded identically against every line of that key and never divided between them, **never a share of it apportioned to a source line**, because no per-source-line applied quantity exists in order state to take one from.
- **Label snapshots, captured once and never re-resolved** — the requested variant's `name` and `sku` [packages/core/src/entity/product-variant/product-variant.entity.ts:L50] and [packages/core/src/entity/product-variant/product-variant.entity.ts:L56], and the applied variant's `name` where anything was applied. Three rules make them recordable rather than merely desirable. **They are captured from the variants step 2 already loaded**, in the one bulk load section 2.13 specifies, so they cost no extra read and cannot disagree with the row the write path used. **They are resolved in the request's own `languageCode`, and that code travels with them** on the request-level envelope, so a reader knows which language a stored name is in rather than assuming the deployment's default — `name` is a `LocaleString` resolved from the variant's own translation rows [packages/core/src/entity/product-variant/product-variant.entity.ts:L50] and [packages/core/src/entity/product-variant/product-variant.entity.ts:L129], so a name without its language is a string of unknown provenance, whereas `sku` is a plain column and carries no language at all [packages/core/src/entity/product-variant/product-variant.entity.ts:L56]. **The requested pair is always present on a mapped key and the applied name is present exactly where the applied quantity is above zero**, which is what lets the consuming table declare the first two as `NOT NULL` and the third as nullable rather than guessing [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. The snapshot is what makes a report of a since-deleted item readable, and taking it here rather than at read time is the whole reason it is honest.
- **Resolution** — the resolution choice that governed this key, drawn from the four members of `ReorderLineResolutionAction` and **null where the caller supplied none**, which is every line until FEATURE-001-04 ships. There is no fifth `DEFAULT` member: absence is expressed as absence, per ruling R4.
- **Availability at read** — the availability reading the pre-commit computation produced for this line, in FEATURE-001-03's published vocabulary [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces — One New Query, Zero Existing Signatures Changed], and the `quantityAvailable` integer where the attributed error carried one [packages/core/src/api/schema/common/common-error-results.graphql:L53].
- **Outcome** — the `ReorderLineOutcomeCode` member and the attributed `ErrorCode` member, both exactly as the public payload reports them.
- **Money, and never without its basis** — the unit price applied to this line as an integer in the smallest currency unit, its `currencyCode`, and a **tax-basis boolean** recording whether that integer includes tax. **The three are named `unitPrice`, `currencyCode` and `listPriceIncludesTax`** — that third name being the platform's own for the flag [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128] rather than the `unitPriceIncludesTax` an earlier revision of this bullet wrote, and being the name FEATURE-001-07 declares on the column [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched] and FEATURE-001-08 projects [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces]. **A different name here would be the mapping layer this section claims does not exist**, so the mapping across the three files is by name rather than by description — and the third name is a **correction**, because an earlier revision of this bullet called it `unitPriceIncludesTax` while claiming in the same sentence that the three names matched the other two files, which they did not; the producing column and the platform's own per-line declaration both spell it `listPriceIncludesTax` [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. The three travel together as one unit and are null together: an integer amount without its currency and its basis is not a smaller record of the price, it is an ambiguous one, and the platform itself keeps the basis beside the amount on every order line [packages/core/src/entity/order-line/order-line.entity.ts:L128].
- **Correlation** — the attempt's `correlationId` and, where the caller supplied one, the idempotency key, so the audit row and the response name the same attempt.

**Three rules keep this from becoming a second public contract.** First, **the public projection stays narrower and that is intentional**: `ReorderLineOutcome` is a strict subset of the per-key fields above, and no story may add a field to the public payload because the audit needs it. Second, **the mapping is total in both directions and is checked at compile time**: FEATURE-001-07's recording method accepts these two types and every column it writes is assigned from a named field of one of them, so a field added here without a home there fails to compile rather than being silently dropped, and **a column added there with no field here has no source and is a defect in that feature rather than a gap in this one** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **"Assigned from" covers four columns that are computed from a named field rather than copied from one, and they are enumerated here so that totality means what it says instead of being quietly approximate.** Each names its single source field, so each is still checkable: the attempt's `replayClaimDigest` is the keyed hash of the claim tuple this envelope carries — the acting customer, the channel, the operation and either this envelope's `idempotencyKey` or, where the caller supplied none, the attempt's own `correlationId` — so it is **non-null on every row** and never null [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]; the line's `contributors` column is the canonical serialisation of the per-key `contributors` collection and is empty for no key, since every key has at least one contributor; the line's `channelId` is denormalised from **this envelope's** channel id rather than from the per-key instance, which has none; and the attempt's own `outcome` is **derived** from the envelope's request-level outcome together with its five counts and its refusal branch, because the two vocabularies differ deliberately — this feature publishes a two-branch request outcome to a buyer while the audit records the **eleven-member** `ReorderAttemptOutcome` disposition FEATURE-001-07 declares — the same eleven that feature's check constraint enumerates, not a count restated here, and that derivation is a named total function whose branches the consuming feature owns [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums, And The Counting Rule That Makes Them Add Up]. **Nothing outside those four is computed, and in particular no column is filled from a catalogue, price or stock read performed after the write.** Third, **the grain is one across all three surfaces rather than one per surface, and this is the sentence a review found self-refuting when it was two.** The envelope is **per request** and the outcome is **per projected variant key**, and those are the grains of the published response, of this internal mapped DTO **and** of FEATURE-001-07's two audit tables alike — one attempt row per request and one attempt-line row per projected variant key, which is exactly what that feature's `UQ_reorder_attempt_line_attempt_variant` constraint enforces rather than trusts [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4.1 The Index Contract — Named Here Because Every Consumer Of These Tables Reads Them By Predicate]. **No consumer may read any of the three at a per-source-line grain** — source-line identity is reached only through `contributors`, whose entries carry `sourceOrderLineId` or `reorderListLineId`. **And the request-level identity is single-valued for the same reason:** the attempt is identified by its `correlationId` and claimed by its one non-null `replayClaimDigest`, so a keyless request is as identifiable as a keyed one and no branch of this contract depends on a caller having supplied a key.

### 2.6 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds

The epic's do-not-duplicate inventory assigns this feature three mechanisms, each with a prohibition attached [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. **This is the section that answers the question this file exists to answer, and the most consequential finding in the whole feature is in it: a per-item error-accumulating bulk add already exists at both the service layer and the API layer.** A ticket that re-specified it would be duplicating shipped work. A ticket that ignored it would ship a second, incompatible partial-success contract alongside a published one. Neither is acceptable, so the new mutation is positioned as a *caller* of the first and a *mirror* of the second.

#### Mechanism one — `OrderService.addItemsToOrder`, the service-layer bulk add

`addItemsToOrder` [packages/core/src/service/services/order.service.ts:L654] was added to the public service surface as `@since 3.1.0` [packages/core/src/service/services/order.service.ts:L652]. Its own JSDoc is the specification this feature builds against, and it makes two mechanical claims [packages/core/src/service/services/order.service.ts:L643-L650]: the method **fetches the entire Order once** and **performs price adjustments once at the end**, and because it can return more than one error result, a caller is directed to inspect the `errorResults` array to determine whether any errors occurred. Its declared return type states the same thing in the type system — a resolved object carrying both an `order` and an `errorResults` array [packages/core/src/service/services/order.service.ts:L663].

Its per-item behaviour is what makes it the right call for a reorder, and it was read rather than assumed:

- **Each item is validated through a four-step chain** — `assertQuantityIsPositive`, `assertAddingItemsState`, `assertNotOverOrderItemsLimit` and `assertNotOverOrderLineItemsLimit` [packages/core/src/service/services/order.service.ts:L675-L679]. The second of those is why the target must be an order still accepting items, and the third and fourth are why a large reorder can partially fail on limits rather than on stock.
- **On a validation failure it accumulates the error and continues to the next item** rather than aborting the batch [packages/core/src/service/services/order.service.ts:L680-L683]. Partial success is therefore the core method's existing semantics for *this class of failure*, not something the plugin adds on top.
- **But the accumulation is partial in three specific ways, and every one of them constrains this feature.** They are read from the method body rather than from its docstring, and the epic records them as collision C8 [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions]:
  - **The accumulator carries no key.** `errorResults` is a flat array of error results with no index and no variant identifier [packages/core/src/service/services/order.service.ts:L665]. Two lines failing with the same error type are indistinguishable in the return value.
  - **A successful item pushes nothing onto it.** The array's length and ordering therefore carry no positional relationship to the requested items, so the *n*-th error result is not the *n*-th requested line.
  - **An unresolvable variant throws instead of accumulating.** The variant is loaded with a throwing accessor requiring `enabled: true` and a null `deletedAt` [packages/core/src/service/services/order.service.ts:L684-L689], and a disabled parent product raises an explicit throw [packages/core/src/service/services/order.service.ts:L692-L693]. There is no `try` and no `catch` in the method, so either case abandons the loop — and under the `@Transaction()` decorator the surrounding transaction is rolled back [packages/core/src/connection/transaction-wrapper.ts:L67-L70], discarding **every line already written**. One item disabled since the last purchase would abort the whole reorder.
- **The pre-filter is not a duplication of the core's check, and it is not a second partial-success contract.** It is the price of the core's check being a throw. The prohibition attached to this mechanism forbids a per-variant *add loop* and an invented partial-success *payload* [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]; reading each source line's variant once to decide whether it is addable is neither. The single bulk call remains exactly one call.
- **Reordering a past order is the case that makes this unavoidable.** A source order is historical data, so its lines routinely point at variants that have since been disabled or deleted — that is the second of the three edge-case categories every story in this set must cover. A contract in which one such line discards the entire reorder would make the feature fail for exactly the buyers it is built for, and it would contradict the resolution decision tree FEATURE-001-04 draws, whose disabled-or-deleted branch is a per-line outcome offered a choice of `skip`, `substitute` or `abort` rather than a request-level failure [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.9 Figure F4-FLOW — The Unavailable-Line Resolution Decision Tree]. That feature reaches the same conclusion from the same evidence and names the division of labour between the two files explicitly [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.4 What The Commit Path Already Does Today — The Question This File Exists To Answer].
- **What remains a request-level failure is a source that cannot be resolved at all** — an unresolvable order or list reference, a reference belonging to another customer, or a source in a foreign channel — and a source resolving to zero requested lines, which is `NoReorderableLinesError`. Those are properties of the *source*, not of one line within it.
**One deliberate ordering consequence.** Because the pre-filter reads each source line's variant, the availability state it records is read *before* the core call rather than during it, so it is a point-in-time read in the sense section 2.10 describes: a variant disabled in the moment between the filter and the write produces a thrown error from the core rather than a skip. That residual race is stated rather than designed away, and the correct behaviour is to surface it as a request-level failure and let the caller retry — the alternative, wrapping the core call to translate a throw into an outcome, would mean guessing which line threw, because the exception identifies a variant and not a source line. **Section 2.6b turns that residual race into an explicit request-level outcome rather than leaving it as a warning**, and it is the reason the per-line guarantee in this feature is always stated with "for a settled request" attached.

**This reverses an instruction an earlier version of this section gave.** It said plugin code does not pre-filter disabled or deleted variants "because the core call already does". The core call does not filter them — it throws on them, which is not the same thing and is precisely why the epic's ruling R4 puts prevalidation in the plugin. Section 2.13 sets out the five-step contract that replaces the earlier instruction.

*The prohibition, quoted in substance from the epic:* do not write a per-variant add loop, and do not invent a second partial-success mechanism inside the platform's write path [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. **The prohibition is narrower than "map the errorResults into the report", and the difference matters:** the plugin calls the service exactly once per reorder, and it derives each line's applied quantity from the target order's own per-variant line quantities rather than from the unkeyed error array.

**What "one call" does and does not buy, stated precisely, because the honest version is weaker than the flattering one.** A single call avoids what a per-variant loop would repeat *outside* the item work: one active-order resolution, one order fetch, and one price-adjustment pass over the finished order [packages/core/src/service/services/order.service.ts:L751]. **It does not make the work constant.** The method's own body iterates the input array and, per item, runs the four-step validation chain [packages/core/src/service/services/order.service.ts:L675-L679], resolves the variant with its `enabled` and `deletedAt` predicate [packages/core/src/service/services/order.service.ts:L684-L689], and performs the line write. The cost therefore scales with the number of source lines whichever way it is called, and three obligations follow:

- **No ticket in this feature or its stories may present the single call as evidence of a constant query count.** What it is evidence of is a constant number of *order-level* operations. A story that wants to claim a query count claims it as a measurement, not as an inference from the call site.
- **The source size is bounded** as section 2.5 states, so the per-item work has a stated ceiling rather than an open one.
- **The comparison is measured, not asserted.** The epic's commit-path benchmark scenario runs this mutation at the maximum source size against the same line count added one at a time through the existing single-item mutation, and reports both measurements and their difference [tickets/EPIC-001-reorder-and-replenishment.md:§7.6 Data-Volume Assumptions And The Benchmark Workflow]. If the bulk path does not win, the number says so.

#### Mechanism two — the already-published API-layer bulk contract

This is the half that is easiest to miss and most expensive to get wrong, so it is stated in as many words: **the partial-success contract is already public. This feature and story 02-04 must consume or mirror that contract, and must not invent a competing one.**

The published mutation is `addItemsToOrder(inputs: [AddItemInput!]!): UpdateMultipleOrderItemsResult!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L74], and its own SDL docstring states that it returns a list of errors for each item that failed to add and will still add the successful items [packages/core/src/api/schema/shop-api/shop.api.graphql:L73]. The payload it returns is defined in the same file and is not abstract — it is two fields:

```graphql
"""
Returned when multiple items are added to an Order.
The errorResults array contains the errors that occurred for each item, if any.
"""
type UpdateMultipleOrderItemsResult  {
    order: Order!
    errorResults: [UpdateOrderItemErrorResult!]!
}
```

That type is declared at [packages/core/src/api/schema/shop-api/shop.api.graphql:L298], with `order: Order!` at [packages/core/src/api/schema/shop-api/shop.api.graphql:L299] and `errorResults: [UpdateOrderItemErrorResult!]!` at [packages/core/src/api/schema/shop-api/shop.api.graphql:L300], above its own docstring [packages/core/src/api/schema/shop-api/shop.api.graphql:L294-L297]. Its input type is equally concrete — `input AddItemInput` carrying `productVariantId: ID!` and `quantity: Int!` [packages/core/src/api/schema/shop-api/shop.api.graphql:L303-L305] — which is exactly the shape a reorder's projected source line reduces to, and is why section 2.7 shows the projection step explicitly.

The error union in that payload is closed and its membership was read rather than inferred: `union UpdateOrderItemErrorResult` names exactly `OrderModificationError`, `OrderLimitError`, `NegativeQuantityError`, `InsufficientStockError` and `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117]. Three design rules follow directly from that membership:

- **The reorder outcome report's error position reuses those five types rather than restating them.** Each already exists: `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80-L83], `OrderLimitError` with its `maxItems` field [packages/core/src/api/schema/common/common-error-results.graphql:L37-L41], `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44-L47], `InsufficientStockError` [packages/core/src/api/schema/common/common-error-results.graphql:L50-L55] and `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103-L107].
- **`InsufficientStockError` is how a shortfall is named, and its `quantityAvailable` field is a precedent rather than an input.** It carries `quantityAvailable: Int!` [packages/core/src/api/schema/common/common-error-results.graphql:L53] alongside `order: Order!` [packages/core/src/api/schema/common/common-error-results.graphql:L54], and this feature consumes its *presence* to set a line's outcome code while taking the applied quantity from the target cart's own line delta, per section 2.13. **Two precise limits on that field, because an earlier draft of this bullet overstated it.** First, it arrives only after the platform has already written the shortened line [packages/core/src/service/services/order.service.ts:L736-L749], so it cannot be the input to a decision taken beforehand — which is why FEATURE-001-04 sources the figure a `reduce quantity` resolution is submitted at from the pre-commit preview instead, and uses this error only to reconcile what the commit then did [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.8 The Existing Mechanisms This Feature Consumes Rather Than Rebuilds]. Second, the error is not per-line addressable, so it is the correlation contract and not this payload that says which requested line was short. What the field does establish is that an obtainable-quantity integer is **already public** on this platform's Shop API, which is what makes the preview's request-bounded figure a smaller disclosure rather than a new one [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings].
- **The outcome report adds a per-line *position*, not a per-line *error vocabulary* — and the plugin, not core, is what supplies the position.** The core `errorResults` array is flat and unkeyed, so the correlation cannot be read out of it: it has to be *constructed*. What the reorder report contributes is that construction, so a buyer sees which of their lines failed rather than that some line did. Section 2.13 is the contract for how it is constructed, and it is the single most consequential design decision in this feature. The array carries no key of any kind: **not one of the five member types carries a variant id, a source-line id or an input index**, as their declarations show — `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80-L83], `OrderLimitError` with only `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L37-L41], `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44-L47], `InsufficientStockError` with only `quantityAvailable` and `order` [packages/core/src/api/schema/common/common-error-results.graphql:L53] and [packages/core/src/api/schema/common/common-error-results.graphql:L54] and `OrderInterceptorError` with only `interceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103-L107]. The array is also **shorter than the item list**, because a clean add pushes nothing. Section 2.6a specifies the construction and section 2.13 states the five steps it is implemented as.

*The prohibition:* the epic records that partial-success semantics exist at *both* layers and that a story must therefore state which layer it consumes [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. This feature states it once, here, for all four stories: **the plugin service consumes the service layer, and the plugin's published payload mirrors the API layer.** No story in this feature calls the `addItemsToOrder` mutation from inside the server, and no story invents a payload shape that diverges from the two-field form above.

### 2.6a The Keyed Line-Result Contract — How Identity Is Constructed, Not Assumed

**This section exists because the obvious reading of mechanism two is wrong in a way that would ship a report attributing failures to the wrong lines.** The core returns an order and a flat error array; a plugin that zipped that array against its own item list index-for-index would be inferring identity from error order, and the array is not index-aligned — a clean item contributes no entry, so every entry after the first success is off by one. The contract below never performs that zip. It is built from three steps, each of which is independently checkable, plus one assertion that fails loudly rather than guessing.

**Step 1 — the projection makes the variant id a key, and the key is what everything downstream is reported against.** Source lines are projected into the item array the core call accepts, `productVariantId` and `quantity` [packages/core/src/api/schema/shop-api/shop.api.graphql:L303-L305], with **one item per distinct variant**: where two source lines reference the same variant, their quantities are summed into a single item. **The projection is not the report, and that distinction is what this paragraph exists to make — but the core call and the report share that one cardinality, and this paragraph is the authority for it.** One item per distinct variant goes to the core; one entry per distinct variant comes back to the client, with every contributing source line named inside that entry's `contributors` collection [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. **An earlier revision of this step published the opposite rule** — one entry per requested source line, with each entry naming a single source line and the key's applied quantity divided across the entries in ascending index order, each capped at that entry's requested quantity. **That rule is withdrawn in full, and no story, definition-of-done item or sibling feature may reinstate it**, for the reason step 4 states: the division has no measurable source, so every number it produced would be a fabrication in the shape of a measurement. What the entry reports instead is derivable, and step 4 lists it field by field. The projection is not a convenience either. The core resolves an existing line per variant [packages/core/src/service/services/order.service.ts:L669-L674] and additionally sums the quantity already present on other lines of the same variant [packages/core/src/service/services/order.service.ts:L695-L702], so two items naming one variant do not behave independently and could not be reported on independently. **Aggregating first is what makes the variant id a genuine key rather than a label that repeats.** No plugin code sends the same variant twice.

**`requestIndex` has exactly one definition in this feature, it is the epic's ruling R4, and it is this one.** The source lines are first ordered deterministically as section 2.13 step 1 fixes and are numbered `0` to `n-1` in that order; each projected variant key then takes as its `requestIndex` **the LOWEST of the numbers its contributing source lines carry** [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory].

**The index set is therefore drawn from the source numbering and is SPARSE wherever duplicates collapsed, and that is the property the definition exists for.** It is single-valued, because a set of numbers has one minimum; it is injective, because each source number belongs to exactly one key, so the lowest number of one key cannot be the lowest of another; and it therefore *identifies* the entry as well as ordering it, which a rank cannot do.

**A non-contiguous example, worked, because a dense example cannot distinguish the two candidate algorithms.** A source whose four ordered lines name variants A, B, A, C is numbered A=0, B=1, A=2, C=3 and projects onto three keys: A with contributors {0, 2}, B with {1}, C with {3}. The published entries carry `requestIndex` **0, 1 and 3** — there is no entry at 2, and 3 appears even though only three entries exist. **An earlier revision of this paragraph specified a dense `0` to `k-1` sequence with no gap and no repeat**, which on this same input would have published 0, 1 and 2; that form is withdrawn, because a rank recomputed per response is not stable against a source whose lines are re-ordered and carries no information about which source line began the key. A test asserts this exact example rather than a duplicate-free one, since a duplicate-free source makes the two algorithms agree.

**What `requestIndex` is not:** it is never the position of *the* source line in the request, because a key may have several; where a client needs to name a source line it reads that line's own identifier inside `contributors`, which is the field that exists for it.

**Step 2 — a before-and-after quantity diff yields the applied quantity per key, with no reference to the error array at all.** The plugin records, for each projected variant, the total quantity that variant already holds on the target order before the call — the sum over `quantity` [packages/core/src/entity/order-line/order-line.entity.ts:L97] of every line of the returned order's `lines` collection [packages/core/src/entity/order/order.entity.ts:L102] naming that variant. The same sum is taken from the order the call returns [packages/core/src/service/services/order.service.ts:L663]. **The difference is the applied quantity for that key**, and it is derived from order state rather than from a diagnostic array, which is what makes it authoritative. Each key then classifies into exactly one of three positions:

- applied equals requested — **fully applied**;
- applied is greater than zero and less than requested — **partially applied**;
- applied is zero — **not applied**.

**Step 3 — the error type is attributed by a join over an independently-computed key set, and the join is proven rather than assumed.** The core's per-item loop pushes **at most one** error for an item and then continues to the next: a validation failure pushes and continues [packages/core/src/service/services/order.service.ts:L680-L683], a clamp to zero pushes and continues [packages/core/src/service/services/order.service.ts:L710-L715], an interceptor rejection pushes and continues to the labelled outer statement [packages/core/src/service/services/order.service.ts:L724-L727], and a downward-adjusted quantity pushes after the line is written [packages/core/src/service/services/order.service.ts:L743-L749]. A clean item pushes nothing. The post-loop pass that re-wraps stock errors with the final order preserves their positions [packages/core/src/service/services/order.service.ts:L754-L761]. **Two properties follow, and together they make the join sound:** the entries appear in item order, and the set of items that produced one is exactly the set of keys step 2 did **not** classify as fully applied. So the plugin orders its own non-fully-applied keys by their position in the item array and pairs them with the error entries in order. **The pairing is over a key set derived from order state, not over the array's own contents — which is the difference between a join and a guess.**

**The assertion that keeps step 3 honest.** Before the pairing is used, the plugin asserts that the count of non-fully-applied keys equals the length of the returned error array. **If it does not, the plugin does not guess.** Every entry projected from a non-fully-applied key is reported with its applied and requested quantities and the outcome `UNATTRIBUTED_ERROR`, the whole error array is reported once at request level in `unattributedErrorCodes` rather than per line, and the condition is logged as a contract violation against the core version in use. This branch exists because the properties above are properties of a version of a method this feature does not own; if a future release makes them false, the report degrades to something visibly incomplete instead of quietly wrong. **A story must include a unit test that forces the mismatch and asserts the degraded shape**, because a defensive branch nothing exercises is a comment.

**Step 4 — the key-level result *is* the reported entry, and the source lines that fed it are carried inside it.** Steps 1 to 3 compute a result per *key*, and section 2.5 publishes exactly that: one `ReorderLineOutcome` per **distinct projected variant**, in ascending `requestIndex` order — a set drawn from the source numbering and therefore sparse wherever duplicates collapsed onto one key, per the definition in section 2.6a — with every contributing source line named in that entry's `contributors` collection as a `ReorderSourceLineRef` carrying its own `requestedQuantity`. **An earlier revision of this section projected the key result back onto one entry per source line and had to invent an allocation rule to divide one applied quantity between two contributors. That rule is withdrawn, and no story may reintroduce it**: an apportionment across contributors is unobservable — the core writes one order line per variant [packages/core/src/service/services/order.service.ts:L669-L674] and sums same-variant quantities across lines [packages/core/src/service/services/order.service.ts:L695-L702], so there is no per-source-line applied quantity in order state to report, and any split would be a fabricated number wearing the shape of a measured one. What the entry reports instead is exact and derivable: `requestedQuantity` is the sum over its contributors, `addedQuantity` is the key's applied quantity from step 2, and each contributor's own `requestedQuantity` is what that source line asked for. Where a key carries exactly one contributor — the ordinary case, since a source order holds one line per variant — `contributors` has length one and the entry reads as a per-line outcome.

**What the report therefore carries per entry**, in the published field names of section 2.5, and every value derivable from steps 1 to 4 without reading the error array for identity:

- `requestIndex`, the zero-based position of this projected key in the request, identical to the index `reorderPreview` assigns the same key for the same input;
- `contributors`, never empty, holding one `ReorderSourceLineRef` per source line that projected into this key, in source order, each naming its line through `sourceOrderLineId` or `reorderListLineId` — exactly one of which is set, fixed by the source form — and carrying that line's own `requestedQuantity`;
- `productVariantId`, the key itself, and `requestedQuantity` as an integer equal to the sum over `contributors`;
- `addedQuantity` as an integer, taken from step 2 and never apportioned;
- `outcome`, one member of `ReorderLineOutcomeCode`: `ADDED` where the key is fully applied, `ADDED_AT_REDUCED_QUANTITY` where it is partially applied, the matching `NOT_ADDED_*` member where it is not applied and step 3 attributed the reason, and `UNATTRIBUTED_ERROR` where the assertion below fails;
- `errorCode`, where step 3 attributed one: the exact `ErrorCode` member of the error type from the five members of the closed union [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117]. Where that type is `InsufficientStockError`, the `quantityAvailable` integer it carried [packages/core/src/api/schema/common/common-error-results.graphql:L53] is what the reduced `addedQuantity` is reconciled against.

**The guarantee, stated at the strength it actually holds.** Where the request settles — that is, where the core call returns rather than throwing — **every distinct projected variant receives exactly one outcome entry, the count of entries equals the count of distinct projected variants, every requested source line appears in exactly one entry's `contributors`, and the sum of the entries' `addedQuantity` equals the sum of the applied quantities over those keys**. The count of entries is therefore at most, and is often below, the count of requested lines; a text that states the two counts are equal is stating something this feature does not guarantee. Section 2.6b states what happens when the request does not settle, and it is deliberately a different guarantee rather than the same one restated. Story 02-04 formalises this contract in the published payload; every other story in this feature consumes it as specified here.

**The cross-feature correlation contract, which is what makes a preview joinable to its commit.** Step 4's grain is not an internal detail: FEATURE-001-03's `reorderPreview` and this mutation are two reads of the *same requested-line list*, and a storefront that shows a preview and then commits has to be able to say which preview line became which outcome. **That join is exact, and it is exact because both payloads use one grain and one index.** Three rules fix it, and this section is their authority.

- **One grain, both sides: one entry per projected variant key.** Both payloads project two requested lines that name one variant onto a single entry, so neither ever reports one variant twice, and neither needs an apportionment rule to divide a key-level result between two entries. Source-line identity survives inside `contributors` on both sides — each contributor carrying its own requested quantity — which is what makes a preview entry and a commit entry joinable over the same request at the same `requestIndex`. The variant key is therefore the entry’s identity as well as a field on it.
- **One index, computed the same way: `requestIndex` is the zero-based position of the projected variant key**, as step 1 defines it and as neither payload redefines it. The plugin assigns it from the ordered key sequence, and the same projection over the same source with the same `lineSelections` produces the same indices in the preview and in the commit. Where a caller previews and then commits with an *unchanged* input, `requestIndex` n names the same **variant key** in both responses — and therefore the same set of contributing source lines, since the projection is deterministic.
- **The variant key and the contributor identifiers are the join keys that survive a changed input, and that is why the index alone is not the contract.** A caller that previews a whole order and then commits a narrowed selection gets a *different* index set, and joining on the index would silently pair the wrong entries. So both payloads carry the entry's own `productVariantId` and, inside `contributors`, each contributing source line's identifier — `sourceOrderLineId` or `reorderListLineId`, exactly one set per contributor, in the same field names on both sides — and **a client joining across the two operations joins on the `productVariantId`, or on a contributor identifier where it tracks source lines, using `requestIndex` only for ordering within one response.** Stated the other way: `requestIndex` is stable within a response and across responses to identical inputs; the variant key and the contributor identifiers are stable unconditionally.

**No separate projection identity is published, and that is a consequence of the two grains agreeing rather than an omission.** An earlier reading of these two features had the preview keyed per distinct projected variant while the commit was keyed per requested line, and under those grains a join would have needed a synthesised projection key plus a list of contributing source lines on both sides. Unifying the grain removes the need for both. A story may not introduce such a key, because it would be a second vocabulary for an identity the payloads already carry.

### 2.6b The Request-Level Outcome — What Happens When The Core Call Throws

**Mechanism one records that a disabled or deleted variant, or a disabled parent product, raises a thrown error rather than an accumulated one. This section states the consequence as a contract instead of leaving it as a warning, because the per-line guarantee in section 2.6a cannot cover a call that never returns.**

The mechanics are not in doubt. The bulk add resolves each variant through a call requiring `enabled: true` and a null `deletedAt` [packages/core/src/service/services/order.service.ts:L684-L689], and throws when the parent product is disabled [packages/core/src/service/services/order.service.ts:L692-L693]. There is no `try` and no `catch` anywhere in the method. So one such line ends the whole call, and the lines already written before it are **not** rolled back by the method itself — the plugin's own transaction boundary is what determines whether they survive.

**The ruling, in three parts.**

- **A reorder request has exactly one request-level outcome, always, and it is a field of the response rather than an inference from what is missing.** Its value is `SETTLED` where the core call returned, or `ABORTED_UNRESOLVABLE_SOURCE_LINE` where it threw because a projected variant no longer resolves. A response carrying the second value carries **zero** per-line outcome entries, and that is the specified shape rather than a degenerate one.
- **The per-line guarantee is stated with its precondition attached, everywhere it appears.** "One outcome per projected variant key, with every requested source line named inside it" holds **for a settled request**. Neither this feature nor any story in it may state the unconditional form, because the unconditional form is false against this platform. Naming the precondition is what makes the guarantee testable: a story asserts the entry count for a settled request and asserts the request-level value plus an empty entry collection for an aborted one.
- **The aborting line is named, and naming it is what makes the outcome actionable rather than opaque.** Before the core call, the plugin already holds the projected key set from section 2.6a's step 1; the thrown error identifies the variant that failed to resolve. The request-level outcome therefore carries that variant id and the source-line identifiers that projected into it, so a buyer is told *which* item ended the request. That is a report about the request, not a per-line outcome entry, and it is deliberately kept in a different position in the payload so the two are never conflated.

**Why the abort is not smoothed away here, and where the remedy lives.** Pre-filtering unresolvable variants out of the item array would convert this into a per-line outcome — and that is exactly what FEATURE-001-04's `skip` resolution does, deliberately, as its own fourth finding records [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.4 What The Commit Path Already Does Today]. **This feature does not silently drop a line**, for one reason stated plainly: dropping a line the buyer asked for is a decision about their order, and the resolution-policy input this feature publishes in section 2.5 is where a buyer takes that decision explicitly. **What this feature does do is prevalidate**, so that a line already known to be unresolvable is reported as a per-line outcome rather than ending the request — which is why the ordinary unavailable-line case is a per-line outcome and not an abort. The abort branch is therefore the residual race: a variant that passes prevalidation and is disabled, deleted or has its parent product disabled between that read and the core call. It is narrow, it is not eliminable without a lock the platform does not offer, and it has a specified shape rather than an undefined one. **The consequence is recorded rather than minimised: on the default policy, one line whose variant was disabled since the last purchase prevents the whole reorder**, and that is the sharpest limitation of this feature.

**The obligation this places on the audit trail, stated here because the contract is this feature's.** An aborted request is still an attempt. FEATURE-001-07 records one attempt row per request with the request-level outcome above, whichever value it takes, which means its recording path cannot sit only on the settled branch [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.10 Asynchronous Delivery]. This feature states the requirement; that feature owns the mechanism.

#### Mechanism three — the `Customer.orders` order-history read path

The history read already exists as `Customer.orders(options: OrderListOptions): OrderList!` [packages/core/src/api/schema/common/customer.type.graphql:L11] and is already paginated, sortable and filterable through the generated list options.

*The prohibition:* do not add a reorder-specific order-history query [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. This feature reads history through that field and adds only the reorder write path. Concretely, that means a storefront selects the source order itself — sorting on `orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] through the existing list options — and passes an identifier to the new mutation. The mutation does not accept "my most recent order" as a concept, because resolving that would require the query this prohibition forbids.

**A correction that changes what the plugin's own source query must do: `Customer.orders` is not a placed-order-only field.** It resolves through `findByCustomerId`, whose predicate excludes exactly one state — `order.state != 'Draft'` — alongside the customer and channel filters [packages/core/src/service/services/order.service.ts:L336-L357] and specifically [packages/core/src/service/services/order.service.ts:L348]. An in-progress cart is in the `AddingItems` state, not `Draft`, so **the buyer's own active cart is among the rows that field returns.** An earlier reading of this section treated the field as a history read and left the source query to inherit its predicate, which would have let a buyer reorder their current cart into itself — every line doubling, with no error to show for it.

*The rule that follows, and it applies to the plugin's service query rather than to the storefront's read:* the source order is resolved by a predicate of **four** conjuncts — `customerId` equals the session's customer, `channelId` is the active channel, **`orderPlacedAt` is not null**, and `active` is false [packages/core/src/entity/order/order.entity.ts:L82] and [packages/core/src/entity/order/order.entity.ts:L92]. The last two are what make it a *placed* order; the first two are the ownership and scoping predicate ruling R3 requires. A source reference that fails any of the four does not resolve, and the mutation reports it identically to one that matches no row at all — the non-disclosure rule ruling R3 carries. The storefront remains free to read history through `Customer.orders`; what it may not do is rely on that field having filtered the cart out.

- **The core call happens exactly once per reorder, not once per line.** The single `addItemsToOrder` arrow is the design, and the loop that would replace it is the thing mechanism one prohibits. **The arrow is not a claim about query count**, and the figure deliberately draws the per-item work as a self-loop inside the core participant for that reason: the method iterates its input internally, so one arrow at this boundary sits above N validations, N variant resolutions and N line writes beneath it. - **Ownership is enforced before the source is read, not after.** A request authenticated as a different customer is refused at the resolver, so no history row and no list row is read on its behalf.
- **The three steps between the projection and the report are drawn separately because they are separate sources of truth.** The snapshot and the diff establish *what happened* from order state; the join establishes *what the platform called it* from the error array. Collapsing them into one "correlate the errors" arrow is precisely the design section 2.6a rejects, because the error array cannot identify a line.
- **The `alt` branch is a contract, not an error path.** The upper branch is section 2.6b's request-level outcome; it returns a shape, it is asserted by a story, and it is recorded by the audit trail exactly as the lower branch is.
- **The constructed identity is this feature's actual contribution.** The core returns an order and a flat `errorResults` array; deriving one keyed outcome per distinct projected variant, each naming its contributing source lines, from those two things is what section 2.6a specifies and what story 02-04 formalises in the published payload.

### 2.8 The No-Active-Order Ruling — Stated, Not Left Implicit

A reorder writes into an active order. What happens when the session has none is a decision, not a detail, so it is taken here rather than left to a story to guess.

**The ruling, in two halves: `applyReorderToActiveOrder` creates the active order through the existing mechanism on a default-strategy deployment — and where the deployment's configured strategy cannot resolve or create a cart, the mutation returns the existing `NoActiveOrderError` rather than letting a thrown error escape. `NoActiveOrderError` is therefore a member of its result union.**

**The second half of that ruling reverses an earlier version of this section, which excluded `NoActiveOrderError` outright. The exclusion was unsafe, and the reason is in this checkout.** The mechanism is `ActiveOrderService.getActiveOrder` invoked with `createIfNotExists` set to `true`, whose overload returns a non-optional `Order` [packages/core/src/service/helpers/active-order/active-order.service.ts:L84-L88]. But *how* it returns one is delegated: it iterates the configured `ActiveOrderStrategy` set, calling `determineActiveOrder` on each with the input for that strategy's name and then `createActiveOrder` where the strategy defines one [packages/core/src/service/helpers/active-order/active-order.service.ts:L96-L112]. When no strategy resolves an order and none defines a create method, **it throws** `UserInputError('error.order-could-not-be-determined-or-created')` [packages/core/src/service/helpers/active-order/active-order.service.ts:L114-L120]. A published mutation whose result union omits that outcome does not thereby prevent it; it merely leaves it undeclared, surfacing as a raw GraphQL error a client has no typed handling for.

**And a plugin mutation cannot be given the strategy's input, which is the constraint that makes the mapping necessary rather than optional.** The generator that injects the `ActiveOrderInput` argument into operations does so for a **fixed list of nineteen core operations named in its source** [packages/core/src/api/config/generate-active-order-types.ts:L58-L78], adding the argument to each [packages/core/src/api/config/generate-active-order-types.ts:L97-L106]. `applyReorderToActiveOrder` is not and cannot be on that list, so no `activeOrderInput` argument is generated for it and it has no way to carry a custom strategy's input. Declaring a plugin-owned imitation of that argument was considered and rejected: the input type is built from the strategies' own `defineInputType` output at boot [packages/core/src/api/config/generate-active-order-types.ts:L41-L47], so a hand-written copy would drift from the deployment's actual configuration the moment a strategy changed.

*The resulting contract, stated as behaviour a test can assert:* the plugin calls `getActiveOrder(ctx, undefined, true)` — an **empty** strategy input — and catches the failure. **Supported without qualification** is any deployment whose configured strategy set can determine or create a cart from an empty input, which includes the default strategy and therefore every unmodified deployment. **Declared and typed** is the other case: the throw is caught and returned as `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95], so a storefront on a custom-strategy deployment receives a typed result naming exactly what happened instead of an untyped server error. What the plugin does *not* do is guess at a strategy input.

Three pieces of evidence make creation-on-add the platform-consistent behaviour for the ordinary case:

- **The platform already treats "add an item" as the operation that creates the cart.** The `activeOrder` query's own docstring states the value is null until an Order is created via `addItemToOrder` [packages/core/src/api/schema/shop-api/shop.api.graphql:L7-L11]. A reorder is an add, so it creates. The creation itself runs through `OrderService.create` [packages/core/src/service/services/order.service.ts:L455] when the session has no order [packages/core/src/service/helpers/active-order/active-order.service.ts:L63-L64].
- **The result union of the existing add operations excludes `NoActiveOrderError`.** `union UpdateOrderItemsResult` names `Order` and five error types and does not include it [packages/core/src/api/schema/common/common-types.graphql:L273-L279]. Those operations can afford the omission because the generator gives *them* the strategy input; this mutation cannot, which is exactly why mirroring the published shape stops short of mirroring that omission.
- **The platform has a separate union for operations that genuinely require a pre-existing order.** `union ActiveOrderResult = Order | NoActiveOrderError` [packages/core/src/api/schema/shop-api/shop.api.graphql:L292] is what `NoActiveOrderError` primarily serves. This mutation does not *require* a pre-existing order — it creates one where it can — so it borrows the member without borrowing that union.

**What covers the empty case, which is a different condition and must not be conflated with it.** "There was nothing here to reorder" — zero requested lines, from an empty source order, a list with no lines, or a selected subset that resolved to nothing — is `NoReorderableLinesError`, which section 2.11 introduces. `NoActiveOrderError` means "the cart could not be determined or created"; `NoReorderableLinesError` means "the source held nothing". A story that returns the first for an empty list, or the second for a strategy failure, has swapped them, and both mistakes are testable rather than matters of interpretation.

### 2.9 Channel Scoping, Language Scoping And Monetary Values

The one new mutation is channel-scoped and language-scoped. This is a property of the request rather than an argument a caller may omit, so it holds without being restated per story [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites].

- **Channel.** The active channel is identified by a unique token read from the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L58], carried as a unique column on `Channel` [packages/core/src/entity/channel/channel.entity.ts:L62]. **A past order placed under one channel token cannot be reordered into a cart on another.** The source order is resolved within the active channel, so an order belonging to a different channel does not resolve at all and the mutation reports it as an unresolvable source rather than reading across the boundary. The same holds for the list path: `ReorderList` stores the id of the channel it was created under, so a list created under one token is not readable under another [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping]. This is a hard boundary, not a filter a caller may widen.
- **Language.** Translated output resolves against the request's `languageCode`, which defaults to the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. This feature stores no string of its own and translates nothing: the outcome report's own fields are identifiers, integer quantities and error type names, none of which is language-varying, while every variant-derived field a report exposes is translated by the existing catalogue read path. A skipped-line *reason* is a machine-readable code, not a localised sentence, precisely so that the report does not become a translation surface this feature would then have to own.
- **Money.** Every monetary value in this feature's payloads is an **integer in the smallest unit of its currency, stated alongside its currency code**, which defaults to `Channel.defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]. A decimal monetary value is a defect, not a formatting preference. Whether a quoted price is gross or net is governed by `Channel.pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113] and by the line's own `listPriceIncludesTax` [packages/core/src/entity/order-line/order-line.entity.ts:L128], so a payload that reports a price without saying which it is has reported nothing. By way of illustration rather than specification: a source line placed at a `listPrice` of 129900 whose variant now prices at 134900, both integers in the smallest unit of the currency named by the accompanying currency code, is a reportable delta — and reporting it is FEATURE-001-03's work, not this feature's.
- **A currency mismatch is a reported outcome, never a silent conversion — and section 2.13 fixes it to exactly one behaviour rather than leaving it to a story.** The source order carries its own `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142]. Where that differs from the currency the reorder context resolves to, **the reorder proceeds, both codes are reported on the payload through `sourceCurrencyCode` and `targetCurrencyCode`, every line is priced in the target's currency by the core call's own adjustment pass, and no conversion is attempted.** No line is skipped for currency alone and no error is returned for it. This feature performs no arithmetic on money at all: it projects variant identifiers and integer quantities, and the target order prices those lines itself through the core call's own adjustment pass. There is consequently no place in this feature where a rate could be applied, which is the strongest form the constraint can take.

### 2.10 A Point-In-Time Read Is Not A Reservation

Availability checked while a reorder is being assembled can change before the reorder is committed, and **nothing in this feature reserves stock**. It is stated at feature level because three of this feature's four stories inherit it and because the mistake it prevents is a natural one.

The sequence is unavoidable: a storefront reads a source order, the buyer decides, and the mutation runs. Between the read and the write, another order can allocate the stock. `addItemsToOrder` performs its own validation at write time [packages/core/src/service/services/order.service.ts:L675-L679], so the authoritative availability decision is the one the core call makes, not the one a preview reported earlier. Two consequences are carried into the stories:

- **A preview that showed a line as addable does not entitle it to be added.** The outcome report is the record of what actually happened; a preview is advisory. A story that asserts a preview and a commit always agree is asserting something this platform does not guarantee.
- **A stale point-in-time read is a required edge case, not a defect to design away.** The correct behaviour is a per-line outcome naming `InsufficientStockError` with its `quantityAvailable` [packages/core/src/api/schema/common/common-error-results.graphql:L53], not a request-level failure and not a retry loop.

FEATURE-001-03 owns the pre-commit read and repeats the same staleness note in its own figure; this feature owns the commit and is the place the staleness actually resolves.

### 2.11 The Error Vocabulary This Feature Introduces

**Two** of the six error results the whole ticket set declares are declared by this feature: `NoReorderableLinesError`, which this feature also returns, and `ReorderPermissionDeniedError`, which **only FEATURE-001-06 ever returns** and which is declared here because it is a member of a union this feature freezes in its first version — a member's type must exist for the schema to build, so the declaration cannot wait for the feature that uses it. The remaining four belong to FEATURE-001-01, and that sibling records the same split from its side [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10 The Error Vocabulary This Feature Introduces]. **The set-wide total is unchanged at six**; what moved is which file declares one of them, and the consuming feature records the move from its own side too [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.12 The Error Vocabulary This Feature Introduces]. **The `ErrorCode` consequence is stated here rather than left to be derived**: both of this feature's declarations land in batch B2, taking the enum from thirty-six members to thirty-eight, and no batch after B2 grows it — the stage figures being the epic ledger's and cited rather than recomputed [tickets/EPIC-001-reorder-and-replenishment.md:§6.5 The Cumulative Published-Surface Ledger — One Authority, Not Eight Snapshots].

`NoReorderableLinesError` is returned when a reorder resolves to zero requested lines — an empty source order, a list holding no lines, or a selected subset that matched nothing. Section 2.8 explains why this rather than `NoActiveOrderError` covers the empty case.

**The reachable sets are stated positively, at both levels, and neither is stated as a negation.** **An earlier revision of this paragraph opened by asserting that no existing core error type is reachable from this feature at all and then listed three of them** — which cannot both hold, and which left a reader unable to tell which sentence to implement against; the negation is withdrawn and what follows is the enumeration.

**Request level — the five error members of `ApplyReorderResult`, each named with its declaring file and its single reachable condition.** `NoReorderableLinesError` is this feature's own declaration, returned where an explicitly empty selection was supplied. `ReorderListNotFoundError` is FEATURE-001-01's declaration, returned where a list source is addressed by an id that does not resolve for the caller. `ReorderPermissionDeniedError` is **this feature's own declaration** in section 2.11, returned only on the shared-list path FEATURE-001-06 introduces. `NoActiveOrderError` [packages/core/src/api/schema/common/common-error-results.graphql:L95] is an existing core type, reachable where the configured strategy can neither resolve nor create a cart. `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80] is an existing core type, reachable where the cart can no longer be modified. **So two of the five request-level members are existing core types and three are plugin-declared**, which is the count a story asserts against the union.

**Line level — one existing core type, and one only.** `OrderLimitError` [packages/core/src/api/schema/common/common-error-results.graphql:L37] appears as the `errorCode` on an entry whose `outcome` is `NOT_ADDED_LIMIT_REACHED`, which is the condition its own description names, the maximum order size the server configuration permits [packages/core/src/api/schema/common/common-error-results.graphql:L36]. **It is never a member of `ApplyReorderResult`**, because the plugin's own source-size bound is an input-contract violation refused by a thrown `UserInputError` rather than by a union member, per section 2.14 and the epic's ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory]. A line-level entry carries no other existing core type.

Every other error this feature can report already exists. No text in this feature or in its four stories names an error outside the six declared by this ticket set and the **thirty-one** types that already implement the `ErrorResult` interface in this checkout — fifteen in [packages/core/src/api/schema/common/common-error-results.graphql:L2] through [packages/core/src/api/schema/common/common-error-results.graphql:L103-L107], and sixteen more in [packages/core/src/api/schema/shop-api/shop-error-results.graphql:L2] through [packages/core/src/api/schema/shop-api/shop-error-results.graphql:L130].

### 2.13 The Outcome Correlation Contract, The Prevalidation Pass And The Transaction Boundary

This section exists because section 2.6 establishes that the core call **cannot** tell the plugin which requested line an error belongs to, and cannot be handed a stale line without aborting. Everything the feature promises about per-line outcomes rests on what follows, so it is specified as an ordered algorithm rather than described. The epic settles the same contract as ruling R4 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]; this is its feature-level statement, and all four stories implement exactly this.

**Step 1 — Resolve, order, project, and index the projected keys.** The source is resolved by the four-conjunct predicate in section 2.6 for the order path, or through `ReorderListService` for the list path. The resolved source lines are ordered deterministically — ascending `OrderLine.id` for the order path, ascending `ReorderListLine.id` for the list path — and are then projected onto **distinct `productVariantId` keys** exactly as section 2.6a's step 1 specifies. **`requestIndex` is assigned to the projected key, not to the source line**, as the lowest of the deterministic source numbers its contributors carry — so the published entries appear in ascending `requestIndex` order and that order is sparse wherever duplicates collapsed, exactly as section 2.6a's worked A, B, A, C example shows — and each key's `contributors` collection preserves the source order; a key's `requestedQuantity` is the sum over its contributors. That assignment is what makes the index reproducible across `reorderPreview` and `applyReorderToActiveOrder` for the same input. Each contributor's own quantity is `orderPlacedQuantity` for the order path [packages/core/src/entity/order-line/order-line.entity.ts:L104] and the list line's own quantity for the list path, unless `lineSelections` overrode it. `requestIndex` is the key every outcome is reported against and the key `lineResolutions` addresses; **it is the plugin's own invention, because core supplies no key.**

**Step 2 — Prevalidate once per distinct projected key, before any write.** This is the step that keeps a stale line off the core call rather than discovering it there, and every read in it is per key rather than per requested line. Prevalidation runs per key because every predicate below is a property of the variant or of the summed quantity, and because the core itself resolves one line per variant [packages/core/src/service/services/order.service.ts:L669-L674]. For each projected key the plugin evaluates, in order:

- **Does the variant resolve under the same predicate the core call uses** — `enabled: true` and a null `deletedAt`, with the parent product enabled [packages/core/src/service/services/order.service.ts:L684-L689] and [packages/core/src/service/services/order.service.ts:L692-L693]? A failure yields `NOT_ADDED_VARIANT_UNAVAILABLE` for **every requested line that contributed to that key**, and the key is **not passed to the core call**. This is the difference between a reorder that reports one lost line and a reorder that fails entirely.
- **Is the key's summed requested quantity a positive integer within the configured per-line maximum?** A failure yields `NOT_ADDED_INVALID_QUANTITY` where it arises from the source's own stored quantities; where it arises from a supplied `lineSelections` quantity it was already refused at request level by the shared selection contract in section 2.5 before any projection took place, so the two paths never both report the same violation.
- **What is the addable quantity?** It is read through `ProductVariantService.getSaleableStockLevel` [packages/core/src/service/services/product-variant.service.ts:L323] — the same method the core write path reaches when it clamps a quantity [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L125] — and clamped into `[0, requestedQuantity]` for the key's summed quantity. Zero yields `NOT_ADDED_OUT_OF_STOCK`; a value below the request yields a key that will land reduced. **Using the same method as the commit path is what makes prevalidation and commit agree by construction**, and it is why ruling R6 forbids reimplementing the calculation.

**Step 3 — Call once with the projected keys.** The admitted keys are passed as the item array — one entry per `productVariantId` with the contributors' quantities already summed by step 1 — and `OrderService.addItemsToOrder` is called **exactly once**. Projecting before calling is not an optimisation: it is what makes step 4 unambiguous, because the target order holds at most one line per variant and a per-variant reading could not be divided between two source lines. **Where two source lines share a variant there is one outcome entry, one `orderLineId` and one `addedQuantity`, with both source lines named in that entry's `contributors`. No apportionment is performed and none may be specified**, per section 2.6a's step 4.

The variants for the whole key set are hydrated by **exactly one call** to `ProductVariantService.findByIds` [packages/core/src/service/services/product-variant.service.ts:L150] — not one call per key and never one per requested line. **That is a service-call claim and not a statement claim, and the distinction is deliberate:** it is one **call**, not one statement: that method loads six relation paths [packages/core/src/service/services/product-variant.service.ts:L152-L161] and then applies channel pricing and translation to what it loaded [packages/core/src/service/services/product-variant.service.ts:L162], so its statement count is the platform's rather than this plugin's [tickets/EPIC-001-reorder-and-replenishment.md:§7.7.1a Three Observation Boundaries, Because "One Query" Is Three Different Claims]. The assertion is therefore one call, zero per-line calls, and a whole-request statement count that does not grow with the number of keys. The availability read is taken **at most once per key** and its result is held for the duration of the request, so that step 4's reconciliation and any later clamp reuse the same number rather than re-reading it. Admitted keys are then passed to `OrderService.addItemsToOrder` in **exactly one** call.

**The cost of steps 2 and 3 is a stated number rather than a hope, and section 5 requires it to be asserted.** For a request of *n* requested lines collapsing to *k* distinct keys, the reads before the core call are: one source read, one bulk variant load, one request-scoped global-settings read — the settings are cached per request by the platform [packages/core/src/service/services/global-settings.service.ts:L63-L64], so this does not become one read per key — and at most *k* availability reads. **The count therefore scales with *k* and not with *n*, and it is asserted that way**: the same *k* keys submitted first as *k* lines and then as *n* lines with duplicates issue the same number of statements before the core call. Nothing in this paragraph is a claim about the statements `addItemsToOrder` itself issues, which section 2.6 states are proportional to the item count and are measured rather than inferred.

**Step 4 — Reconcile by quantity delta, not by error position.** The target order's line quantity per variant is captured before the call and after it. Each admitted key's `addedQuantity` is that delta, reported whole. The outcome code follows from the delta and the key's summed request: equal yields `ADDED`, a positive value below the request yields `ADDED_AT_REDUCED_QUANTITY`, and zero yields the code prevalidation predicted or `NOT_ADDED_LIMIT_REACHED` where the core call reported a limit. **The delta is authoritative and needs no key, which is the whole reason this design works.**

**Step 5 — Attribute error codes honestly, or not at all.** A returned error result is attached to an outcome entry's `errorCode` only where it can be attributed to exactly one variant — an `InsufficientStockError` whose `quantityAvailable` [packages/core/src/api/schema/common/common-error-results.graphql:L53] matches a single reduced line, or a case in which exactly one key failed. Anything else goes to `unattributedErrorCodes` on the payload. **No error result is ever attached to an outcome entry on a guess**, because a report that names the wrong line is worse than one that names none: a buyer would go and change the wrong item.

**The transaction boundary, stated rather than implied.** The resolver is decorated `@Transaction()`, so the source read, the core call and — once FEATURE-001-07 ships — the audit write are one unit of work that commits or rolls back together [packages/core/src/connection/transaction-wrapper.ts:L64] and [packages/core/src/connection/transaction-wrapper.ts:L67-L70]. Two consequences are load-bearing and are what the stories assert:

- **A request-level failure is all-or-nothing, and it arrives in one of two response locations rather than one.** An unresolvable or unowned source, a strategy failure or a source resolving to zero lines returns one of the **five** error members of `ApplyReorderResult` — four of them, plus the permission refusal FEATURE-001-06 declares for a shared-list source — and writes nothing; a cart that could not be determined, a target order that is not modifiable and a share that does not authorise the caller each return one of the **five** error members of `ApplyReorderResult`. A malformed request and a source resolving to more lines than the configured maximum, or any other violation of the shared selection contract, is refused by a thrown `UserInputError` that puts one entry in the top-level `errors` array and nulls the field, again writing nothing. In both cases the cart's line count is exactly what it was. Section 2.5's second reading fixes which condition takes which route, and section 2.14 is the authority for the source-size bound.
- **A per-line rejection is not a failure and does not roll anything back.** The transaction commits, the successful lines are in the cart, and the rejected lines are reported in `lineOutcomes`. This is the case the feature exists to serve, and it is only reachable because step 3 keeps the throwing cases out of the core call.

**The target cart's prior state is part of the contract, because `addItemsToOrder` is additive rather than idempotent.** A reorder into a cart that already holds a variant *adds to* that line: the core method sums the existing quantity with the new one before clamping [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L124] and counts quantities in other lines for the same variant [packages/core/src/service/services/order.service.ts:L695-L703]. Two rules follow. **A story asserting an exact resulting quantity states the target cart's prior quantity for that variant as a precondition** — an empty cart being the simplest such statement, and the one the acceptance criteria use. And **the addable quantity computed in step 2 shifts with the cart's existing contents**, which is a second reason it is recomputed at commit time by the core call rather than trusted from a preview.

**Currency: one fixed result rather than a family of behaviours.** Where the source order's `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142] differs from the target cart's, the reorder **proceeds**, every line is priced from the current catalogue in the target's currency by the core call's own adjustment pass, and the payload reports both codes through `sourceCurrencyCode` and `targetCurrencyCode`. No conversion is attempted, no line is skipped for currency alone, and no error is returned. That is the single defined behaviour; a story may not choose a different one. It is safe precisely because this feature copies no monetary value at all — it projects a variant identifier and an integer quantity.
