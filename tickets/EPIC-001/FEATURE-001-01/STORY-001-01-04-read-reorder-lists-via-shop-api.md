## 3. Precedent In This Repository

**PRECEDENT:** near-identical

**A complete saved-list plugin already ships in this repository, and its read operation is the direct analogue of one of this story's two queries.** `packages/dev-server/example-plugins/wishlist-plugin/` is not a sketch: its own README states that it is the complete plugin described in the platform's "Writing your first plugin" tutorial [packages/dev-server/example-plugins/wishlist-plugin/README.md:L3]. Its read is `activeCustomerWishlist` [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L13], declared inside an `extend type Query` block [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L12] — the same mechanism this story uses — and gated on the resolver with the owner permission [packages/dev-server/example-plugins/wishlist-plugin/api/wishlist.resolver.ts:L12] beneath a query decorator [packages/dev-server/example-plugins/wishlist-plugin/api/wishlist.resolver.ts:L11], which is the same gate this story uses.

**The delta is stated precisely, because the verdict turns on it rather than on the resemblance.** `activeCustomerWishlist` returns a single flat collection of items and nothing else. Reading its declaration and its item entity together fixes four differences that are structural rather than incidental:

- **No list identity and no name.** The shipped plugin's saved collection hangs off the customer, so there is exactly one of them, it has no name, and there is nothing to address by identifier. This story returns **multiple named lists**, each with its own row and its own stored name.
- **No quantity.** The item entity carries a variant relation [packages/dev-server/example-plugins/wishlist-plugin/entities/wishlist-item.entity.ts:L10] and a variant id column [packages/dev-server/example-plugins/wishlist-plugin/entities/wishlist-item.entity.ts:L13] and [packages/dev-server/example-plugins/wishlist-plugin/entities/wishlist-item.entity.ts:L14] and no third column at all, so there is no per-line quantity for a read to return. Every line this story returns carries an integer quantity.
- **No single-item read.** The shipped plugin publishes one query and two mutations [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L16], so there is no analogue anywhere in it for `activeCustomerReorderList`, which addresses one list by identifier and must decide what to return when that identifier is not the caller's.
- **No bound.** `activeCustomerWishlist` returns an unbounded collection. Every collection this story returns is bounded, and the epic's rule allows exactly two ways to bound one — the platform's configured limit through a paginated return type, or a decided cap with the choice stated [tickets/EPIC-001-reorder-and-replenishment.md:§7.7 Bounded Collections]. This story uses both: the collection read and the nested `lines` collection are paginated, each through a return type implementing that interface with its `options` argument supplied by the generator, and the number of lines a list may hold is additionally capped at the write by `ReorderPluginOptions.maxLinesPerList` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces].

**The verdict is near-identical rather than partial**, and the reason is the reviewer rather than the arithmetic: the closest match in the searched set is close enough that a reviewer must be told about it before reading a line of the criteria. The *shape* of the work — a permission-gated Shop API query resolving a customer-owned collection through a plugin service, declared through `extend type Query` — is shipped, taught in a tutorial and reused throughout this repository. What is new is named and multiple lists, a per-line quantity, a single-list read that must not disclose another customer's rows, and a bounded page.

**Two consequences of the verdict, stated plainly.** Because the precedent is near-identical, this story is disqualified from the epic's demonstration-slice nomination: demonstrating a read of a customer's own saved collection would demonstrate a shape the platform already ships and teaches. That nomination belongs to `STORY-001-02-01` [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination]. Nor does this story hold the harness-proving nomination, which belongs to `STORY-001-01-01` because that story owns the first additive migration and has no prerequisite story, neither of which is true here.

**The searched set that produced the verdict.** The whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. Nothing in that set publishes a *named* saved list, a per-line quantity, a single-list read addressed by identifier, or a saved-collection read that returns a paginated type.

**One name-collision check, run rather than assumed, because this story publishes types.** The literal string `ReorderList` occurs zero times in the checked-in Shop API introspection snapshot, and neither `ReorderList`, `ReorderListLine` nor `ReorderListList` appears anywhere in that snapshot's type map [schema-shop.json:data.__schema.types], so every type name this story publishes is free. The epic carries the same check across the whole published-symbol inventory rather than leaving it to a story [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. The reusable scaffolding this story leans on is present in that same snapshot rather than proposed: the paginated-list interface is declared in source [packages/core/src/api/schema/common/common-types.graphql:L9] and the node interface and the existing catalogue variant type are both published, which is why no plugin-owned pagination wrapper and no plugin-owned variant projection is invented here.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line when the file is read on any renderer and when it is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Storefront Developer (Shop API consumer),
I want two published Shop API queries that return the authenticated customer's named reorder lists and, for one list addressed by identifier, that list's lines with their integer quantities,
So that a storefront build that already compiles against the published schema still compiles after the plugin is installed, and the saved lists become readable through two named operations rather than through a shape I have to guess at.
```

**The benefit is a verifiable state rather than a figure.** No number in that WHY clause and no number anywhere in this file describes how fast, how often or how much: this repository declares no such target and none is invented here [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value]. What is verifiable is that the nineteen pre-existing root queries are unchanged in number and in signature after the plugin is registered, that no existing type loses or retypes a field, and that the two new queries return the shapes the parent feature publishes.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract, and between them both of this story's queries are exercised — `activeCustomerReorderLists` in AC-1, AC-3, AC-5, AC-6 and AC-8, `activeCustomerReorderList` in AC-2 and AC-4, and the existing `activeCustomer` query in AC-7. The five required coverage classes map onto them as follows: valid input is AC-1, AC-2 and AC-6; invalid or incomplete input is AC-3 and AC-4; an error naming the exact type returned is AC-3; an edge case is AC-4; and the assertion that an existing operation is unchanged is AC-7, with AC-8 carrying the one side-effect widening that could not be avoided.

**Four rulings govern every criterion below. Each is settled elsewhere and is transcribed here rather than re-decided, so that no criterion invents a shape.**

**Ruling one — the payload carries no price and no stock field, and that is a boundary rather than an omission.** A `ReorderListLine` stores a variant reference and an integer quantity and no monetary column at all, so no criterion below asserts an amount of money and none asserts an availability state [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. Where a storefront needs either, it reads the existing catalogue fields on the variant these lines reference, which already pair an integer money value with its currency code [packages/core/src/api/schema/common/product.type.graphql:L53] and [packages/core/src/api/schema/common/product.type.graphql:L54] and already express availability as a string rather than a number [packages/core/src/api/schema/common/product.type.graphql:L56]. **Duplicating either onto a list line would be a defect twice over:** it would copy a value that goes stale the moment the catalogue moves, and it would rebuild the pre-commit delta read that FEATURE-001-03 owns and that the epic's do-not-duplicate inventory forbids reproducing [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated].

**Ruling two — the collection read is paginated, the single-list read is not a collection at all, and every collection either read returns is bounded by a mechanism named here rather than by a figure this story chose.** The collection read returns a type implementing the paginated-list interface [packages/core/src/api/schema/common/common-types.graphql:L9], which is what makes the platform generate its sort-and-filter options input rather than the plugin hand-writing one [packages/core/src/api/config/generate-list-options.ts:L32] and [packages/core/src/api/config/generate-list-options.ts:L34], with that generator running inside the schema build after plugin extensions have been merged [packages/core/src/api/config/get-final-vendure-schema.ts:L100]. **`activeCustomerReorderList` returns one object rather than a page**, so pagination does not apply to the query itself; what it carries is bounded in two different ways the parent feature fixes and this story asserts — the nested `lines` collection returns `ReorderListLineList!`, a paginated-list implementor whose `options` argument the generator supplies because it walks the fields of every object type rather than only the root query's [packages/core/src/api/config/generate-list-options.ts:L41-L48] and appends the argument wherever such a field does not already declare one [packages/core/src/api/config/generate-list-options.ts:L87-L99], and the number of lines a list may hold is capped separately at the write by `ReorderPluginOptions.maxLinesPerList`. **The two are distinct guarantees and neither substitutes for the other**: pagination bounds what one read returns, the option bounds what may be stored. **An earlier revision of this ruling said the nested collection was a plain array and that the owner-only grant collection was read here**, and both are withdrawn — the array contradicted the published contract, and the grant roster is returned by FEATURE-001-06 on its own mutation payload rather than anywhere in this story's read path [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.5 Named API Surfaces]. **Declaring the arguments is not the bound, though — applying them is**, so every paginated read resolves its items through the platform's list-query builder [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L209] rather than through an unbounded repository read. The parent feature fixes this shape in its published contract and the epic makes it a rule for every collection surface in the set [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces] and [tickets/EPIC-001-reorder-and-replenishment.md:§7.7 Bounded Collections]. **The parent feature file governs the shape, and where its wording and this file's ever diverge, the feature file wins and this paragraph is the thing to amend.**

**Ruling three — the single-list read resolves to null for every inaccessible case and never to an error result, and this is a security decision rather than a style one.** The parent feature's published contract declares that query's return type as a nullable list object rather than as a result union, so it is not capable of carrying an error result at all, and the same section states the reason: with the platform's default auto-increment identifier strategy [packages/core/src/config/default-config.ts:L101] a list identifier is guessable, so distinguishing "no such list" from "not yours" would confirm another customer's row to anyone who counts. The platform makes the identical choice on its own single-order read, throwing the same result whether the order is absent or forbidden precisely to close an enumeration channel [packages/core/src/api/resolvers/shop/shop-order.resolver.ts:L141] and [packages/core/src/api/resolvers/shop/shop-order.resolver.ts:L143]. **`ReorderListNotFoundError` is therefore named in this story but is not returned by either of its queries:** it is the normalizing result on the four list-addressing mutations `STORY-001-01-03` owns, where a union return type can carry it and where a caller who asked to write genuinely needs a reason. **The parent feature said both things at once and now says one:** its operation matrix previously described this read as returning `ReorderListNotFoundError` while its own published contract declared a nullable object type, and a nullable object type cannot express a union member. The matrix row is corrected to assert `null` for every inaccessible case [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6.1 Operation Ownership And Test Matrix], and the epic settles the general rule once so no sibling can diverge from it again: a single-entity read by id answers `null` for both absent and non-owned, and the not-found result lives only in mutation unions [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. AC-4 asserts the null.

**Ruling four — the gate is not the control, so every criterion that refuses a request names what actually refused it.** All eight of this feature's operations are gated with the owner permission and this feature registers **zero** custom permission definitions, because a custom permission cannot be granted to the Customer Role at all [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.7 The Existing Mechanism This Feature Consumes Rather Than Rebuilds]. The platform's own source states that a resolver relying on ownership **must** include logic enforcing that only the owner of the resource has access, and that without it the effect is the same as public access [packages/core/src/api/config/generate-permissions.ts:L32]; the owner permission is additionally declared unassignable and internal [packages/core/src/common/constants.ts:L28], so no deployment-side configuration could make ownership hold on the resolver's behalf, and the guard admits a session that does not hold the permission it lists [packages/core/src/service/helpers/request-context/request-context.service.ts:L109]. **The control is the in-service predicate** — the row's owning customer equals the customer resolved from the authenticated session, the row's channel equals the active channel resolved from the token header, and the session carries an active user at all, which is the minimal guard the shipped precedent already demonstrates [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L74]. `CrudPermissionDefinition` [packages/core/src/common/permission-definition.ts:L146], whose read member is exposed as a getter [packages/core/src/common/permission-definition.ts:L181] and which is registered through the authentication options [packages/core/src/common/permission-definition.ts:L125], remains the right helper for this epic's *administrative* operations, which FEATURE-001-04 and FEATURE-001-08 register — and it is named here only to record that this story does not use it.

**Two properties of both queries are stated once here rather than repeated in every criterion.** Each is a single synchronous read: neither enqueues a job and neither schedules a task, so no criterion names an asynchronous trigger or a completion signal. And each is **point-in-time**: a list's membership and a line's quantity can change between the read and any later use of what was read, and neither query reserves anything, holds anything or locks anything. AC-2 states that on the payload and the fourth scenario in section 7 exercises it.

**The four authorisation assertions the parent feature makes mandatory in every story of this feature are carried by AC-1, AC-4 and AC-5 between them:** a session holding no custom permission **succeeds** (AC-1), a request carrying a foreign channel token reads nothing (AC-1 and AC-4), a request authenticated as a different customer is refused (AC-4 and AC-5), and an unauthenticated request receives an empty page rather than an error (AC-5). The first of those is written as a positive assertion because its absence is what would let the design fault the epic records as collision C7 reach production [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

* Given a Storefront Developer has authenticated a client as one seeded customer in the active channel, and that customer owns a `ReorderList` named `Monthly Cleaning` in that channel holding exactly two lines, the first referencing one enabled variant [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] at a `quantity` of exactly 2 and the second referencing a different enabled variant at a `quantity` of exactly 3, both lines carrying the inherited creation and update timestamps [packages/core/src/entity/base/base.entity.ts:L31] and [packages/core/src/entity/base/base.entity.ts:L33]
* When the client executes the `activeCustomerReorderList` query supplying that list's identifier
* Then the query returns that list and not a null, its `name` being exactly `Monthly Cleaning`, its `lineCount` exactly 2, its `viewerAccess.access` exactly `OWNED` and its `viewerAccess.grantedCapabilities` an empty collection — both read through the nested object the parent feature publishes, because a per-requester value may not sit as a bare scalar on a row type the list generator inspects [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces]; the `lines` collection, which is itself a paginated list whose `options` argument the generator supplies [packages/core/src/api/config/generate-list-options.ts:L87-L99], returns `totalItems` of exactly 2 and holds exactly two entries in ascending order of their inherited creation timestamp, the first carrying a `quantity` of exactly 2 and the second exactly 3, each entry naming the identifier of the variant it references and each variant's translated `name` resolving against the request's language code [packages/core/src/api/schema/common/product.type.graphql:L48]; no entry carries a price field, a currency field or a stock field of its own; `lineCount` equals the number of `ReorderListLine` rows stored for that list rather than the number of entries a page happened to return; and the response is a point-in-time read that reserves nothing, so a line removed by another session immediately afterwards does not invalidate what was returned and does not entitle the caller to add it later

**Two notes on AC-2.**

*Why `lineCount` is asserted separately from `lines.totalItems` and from the length of `lines.items`.* **Three different facts are in play and a client needs all three.** `lineCount` lets a storefront render a summary without fetching any line at all; `lines.totalItems` is how many lines the list holds in total; and the length of `lines.items` is how many arrived in *this page*, which is bounded by the platform's Shop-side list limit and may be smaller than either of the other two. Asserting only one of them would let an implementation that returned a page of lines and reported that page's size as the total pass — and a buyer would then be told a list holds fewer items than it does. **Three near-duplicate paragraphs stood here, each describing the nested collection's bound differently, and they are merged into the two statements below** — a bound described three ways is three bounds to a reader.

*What the parent feature actually declares.* `lineCount` is a stored column and the single authority for that number, published for exactly this summary purpose, so it equals the number of `ReorderListLine` rows stored for the list and not the size of any page [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6.2 The Read Shape Of A Page Of Lists]. `lines` is a paginated field whose `totalItems` equals `lineCount` when one page carries the whole set and is smaller when it does not.

*The two bounds that are routinely conflated, kept distinct.* The **read** bound is the `lines` field's own generated options argument clamped by the platform maximum — requested through the argument on the field itself rather than through a second argument on the query, because the generator injects one into any field whose type implements `PaginatedList` [packages/core/src/api/config/generate-list-options.ts:L42-L48], so there is exactly one way to page this collection and asserting that there is only one is part of what this story delivers. The **write** bound is the configured maximum number of lines a list may hold, whose value is an open product decision — which is why the nested collection is paginated rather than plain-and-capped, a cap needing to be decided before it can bound anything [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency].


*Why the staleness clause is in a criterion rather than only in an edge case.* A read that returns a quantity looks like a promise about that quantity, and it is not one. Naming the point-in-time property inside the acceptance criteria makes it part of what a reviewer signs off rather than a caveat a reader may skip: nothing in either query allocates stock, holds a row or takes a lock, and the resolution of a line that can no longer be added belongs to FEATURE-001-04 rather than to this read [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values].

**Three notes on AC-3, because this is the one criterion in this story that names an error, the one that proves the bound is enforced rather than declared, and the one whose sibling read is asserted separately.**

*The nested collection's own bound is asserted by its own criterion rather than folded into this one.* Exactly one GraphQL operation is named per criterion, so `activeCustomerReorderList` and the field-level options argument on its nested `lines` collection are exercised by that query's own criteria and by the definition-of-done item that counts the statements a page of lists costs. The obligation itself is unchanged and is stated here so it cannot be lost: an over-limit nested `take` is refused with the same platform `UserInputError` and the same message key with `data.activeCustomerReorderList` null and no partial nested page returned, and an omitted nested options argument returns at most the configured limit of `items` while reporting a `totalItems` equal to the list's stored line total rather than to the returned page length. **The nested collection is bounded by its own field-level argument and not by the outer one**, so an implementation that clamps the outer page while resolving `lines` through an unbounded relation load satisfies this criterion and still fails that obligation [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces].

*The error is the platform's, and that is the point.* This story declares no error result of its own — neither of its queries can return one — so the exact error a reviewer can assert against is the one the platform already raises, and it is asserted by its message key rather than by a driver message or a prose description. Naming a plugin-defined limit error here would have meant reimplementing a check the platform performs before the query runs, which is precisely what the epic's do-not-duplicate inventory forbids [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated].

*Why the omitted-page-size halves exist at all.* A resolver may accept `skip` and `take` and then ignore them, in which case the query is unbounded in every respect that matters while looking bounded in the schema. The omitted-page-size assertions are what catch that: if the resolver never reaches the builder, an omitted page size returns every row and the assertion fails. **The nested pair is asserted because the nested collection is a separate resolution path**, and a `lines` field resolved by loading the relation is exactly the unbounded inner collection a paginated outer query is often mistaken for having ruled out. **No figure is quoted in this criterion.** The limit is named as the configured value and asserted against, which is why this criterion is writable today even though the per-surface default page size beneath the platform maximum is still an open architectural decision [tickets/EPIC-001-reorder-and-replenishment.md:§8.2 Architectural Decisions].

**Four notes on AC-8, which is the second of this story's two feature-wide obligations and the one that reads least like a read-path criterion.**

*Why the two client fixtures and their two commands are named in the criterion rather than left to an implementer.* An earlier version of this criterion ended by asserting that "a client that switches exhaustively on `ErrorCode` without a default branch fails to compile against the rebuilt schema, while the same client carrying a default branch compiles unchanged" — **and named no client, no generator and no type checker, so there was nothing for a test to run and nothing for a reviewer to inspect.** A promise about a compilation outcome is only testable when the artefact compiled, the tool that compiles it and the expected exit status are all named. Declaring the two runs as package scripts in the shape a shipped package already uses [packages/dashboard/package.json:L17] keeps them runnable by name, reviewable in a diff, and pinned to the workspace compiler.

*The mechanism is cited rather than asserted.* The enum's members are generated from the names of every type implementing the error interface [packages/core/src/api/config/generate-error-code-enum.ts:L9], matched against the interface-name constant declared in the same file [packages/core/src/api/config/generate-error-code-enum.ts:L3] by a filter over each type's declared interfaces [packages/core/src/api/config/generate-error-code-enum.ts:L17]. *Why this criterion belongs to a read story that declares no error at all.* That is the sharpest thing about it. The epic requires the growth to be declared with a number rather than with the word additive [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings], so the number is stated for both scopes: this feature's four error results take the Shop enum from thirty-two members to thirty-six [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§5. *What the enum members are, described without a separator that a table would need.* The four this feature adds derive by upper-snake conversion from `ReorderListNotFoundError`, `ReorderListNameConflictError`, `ReorderListLimitError` and `ReorderListLineNotFoundError` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10 The Error Vocabulary This Feature Introduces]. ## 7. Edge Cases

Five scenarios. The three unconditionally required categories are covered by the first three, and the last two cover conditional categories that genuinely apply to a channel-scoped, point-in-time read. **Two of the required three resolve to *proceed* rather than to a block**, and that is stated honestly rather than force-fitted into a failure a read cannot have.

* Scenario: Zero, null or empty collection — the customer holds no lists at all, and a list they do hold holds no lines
   * Given one seeded customer is authenticated in the active channel and owns exactly zero `ReorderList` rows in it, while a second seeded customer in the same channel owns exactly one `ReorderList` row holding exactly zero `ReorderListLine` rows
   * When the first customer executes `activeCustomerReorderLists`, and then the second customer executes `activeCustomerReorderLists` followed by `activeCustomerReorderList` supplying their own empty list's identifier
   * Then proceed on all three, with no warning and no error. The first customer's call returns `totalItems` of exactly 0 and an empty `items` collection rather than a null and rather than an error result, because holding no lists is an ordinary state for a customer who has never created one and this feature's curation paths work for a customer who has never placed an order at all [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]. The second customer's collection call returns `totalItems` of exactly 1. The single-list call returns that list rather than a null, with its stored `name` intact, its `lineCount` exactly 0 and its `lines` reporting a `totalItems` of exactly 0 with an empty `items` collection — **so an empty list is returned rather than omitted**, because a buyer who created a list and has not filled it needs to see that the list exists in order to fill it

* Scenario: An item unavailable, deleted or disabled since the last purchase — the variant behind a line is disabled, or its row has been soft-deleted
   * Given a customer is authenticated in the active channel and owns a `ReorderList` in it holding exactly two lines, the first referencing a variant whose `enabled` flag has been set to false since the line was added [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] and the second referencing a variant whose row has since been soft-deleted, which sets a deletion timestamp rather than removing the row [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When that customer executes `activeCustomerReorderList` supplying that list's identifier
   * Then proceed, with no warning and no audit record: the list is returned with a `lineCount` of exactly 2 and a `lines` connection whose `totalItems` is exactly 2 and whose `items` collection holds exactly two entries, **both lines still present so the buyer sees what they saved**, each carrying its non-null `productVariantId` and its integer quantity unchanged. **The soft-deleted line's `productVariant` object resolves to `null` while its `productVariantId` remains populated, and the entry itself is still returned** — which is exactly why the parent feature declares that relation nullable and its identifier non-null: a non-null relation could only have exposed a withdrawn catalogue object or removed the whole line from the page [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces — Eight Shop API Operations, Zero Existing Signatures Changed]. The disabled line's variant object still resolves, because a disabled variant is still resolvable in the channel, and its `enabled` value is readable on the variant type the platform already publishes. Neither the disabled flag nor the deletion timestamp is read as a precondition by this query and neither is projected onto the plugin's own payload as a field of its own, because **a saved list records intent rather than availability** and this payload carries no availability field at all. The disabled and deleted states are surfaced at preview time by FEATURE-001-03 and resolved at commit time by FEATURE-001-04, which is where the parent feature places them [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. Note that a *hard* variant deletion is a different case and is out of this scenario's scope: it would take the line with it through the on-delete action declared on the line's variant relation, so the list would then hold exactly 1 line rather than 2 — and because that cascade runs underneath the plugin, the stored `lineCount` is corrected by the compare-and-set repair the next time the list is read singly rather than being left to disagree with its rows, which this story asserts separately [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6.2.1 The One Path That Can Drift The Counter]. If the parent feature file is ever amended to omit or flag a stale line instead, the feature file governs and this scenario follows it

* Scenario: A price changed since the last purchase — the catalogue price of a variant behind a line has moved
   * Given the price of the variant behind a line has changed since the buyer last purchased it, and a customer is authenticated in the active channel owning a `ReorderList` in it holding exactly one line for that variant at a `quantity` of exactly 2
   * When that customer executes `activeCustomerReorderList` supplying that list's identifier, and then executes `activeCustomerReorderLists`
   * Then proceed on both, with **no observable difference of any kind**, and the reason is structural rather than a policy choice: the line table stores no price, so there is no stored value for a price change to invalidate and no field on either payload whose value could differ before and after the change [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. Both responses return the same identifiers, the same stored name and the same integer quantity of exactly 2 as they would have returned before the change. A price delta is computed at preview time by FEATURE-001-03 against the live variant price, and the in-cart counterpart of that comparison already exists in the platform and must not be rebuilt anywhere [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. **A reader must not infer a price column on a list line from anything in this story**

* Scenario: A point-in-time read gone stale between the read and a later use — a second session amends the list after the response was returned
   * Given a customer is authenticated in the active channel owning a `ReorderList` in it holding exactly two lines, and a second session for that same customer is open concurrently
   * When the first session executes `activeCustomerReorderList` and records the response, the second session then removes one of the two lines through the mutation that owns removal, and the first session re-executes the same query with the same identifier
   * Then proceed on both reads, with the discrepancy reported by whoever acts on the stale response rather than by this query. The first response remains exactly what was read — two entries, each with its recorded quantity — because a returned payload is a snapshot and **this read reserved nothing, held nothing and locked nothing**. The second response returns a `lineCount` of exactly 1 and a `lines` connection whose `totalItems` is exactly 1 and whose `items` collection holds exactly one entry, that entry being the line the second session did not remove, identified by its identifier rather than by its position. Neither read fails, neither read is retried by the server, and no error result is returned by either, because a list changing between two reads is the ordinary behaviour of a mutable collection rather than a fault. Where a caller then applies a stale snapshot to a cart, the reporting obligation sits on that path and not here: the per-line outcome report belongs to FEATURE-001-02 and the resolution of a line that can no longer be added belongs to FEATURE-001-04

* Scenario: A channel, currency or language mismatch — the list is requested under a channel token it was not created under, and then under a second language code
   * Given a customer is authenticated and owns exactly two `ReorderList` rows created under a first channel's token, a second channel exists with its own distinct token [packages/core/src/entity/channel/channel.entity.ts:L62], each channel declares its own default language code [packages/core/src/entity/channel/channel.entity.ts:L74], and one of the lists holds exactly one line whose variant has a translated name in both of those languages
   * When that customer executes `activeCustomerReorderLists` sending the second channel's token, then `activeCustomerReorderList` with a known list identifier while sending that same second token, and then `activeCustomerReorderList` twice under the first channel's token with two different language codes
   * Then block the first two and proceed on the last two. Sending the second channel's token returns `totalItems` of exactly 0 with an empty `items` collection, and the single-list call under that token resolves to exactly null — indistinguishable from an absent row, per the non-disclosure ruling AC-4 asserts — because every read filters on the channel the token resolved to and a row without a matching channel is unreachable by design rather than global by default [tickets/EPIC-001-reorder-and-replenishment.md:§7.8 The Seven Plugin-Owned Tables]. The two calls under the first token both return the same list with the same `lineCount` of exactly 1 and the same line identifier, the variant's translated name differing between them while **the stored list name is byte-identical in both**, because this feature stores exactly one string of its own and does not translate it. **The currency dimension of this category does not apply and the reason is stated rather than skipped:** no monetary value appears anywhere in either payload, so the channel's default currency code [packages/core/src/entity/channel/channel.entity.ts:L88] has no effect on either response, and there is no currency mismatch a criterion here could assert

**The one remaining conditional category is not force-fitted.** A concurrent modification or race between two writers does not apply to this story, because neither of its operations writes: the concurrency this story does have is a read observing a concurrent write, which the fourth scenario covers as staleness rather than as a race. The write-side races belong to the stories that write — a duplicate name resolved by a database constraint in `STORY-001-01-01`, and an adjustment losing to a removal in `STORY-001-01-03` [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency].
