## 2. Source Traceability

> "Make it effortless for returning buyers to reorder the items they purchase regularly"

That sentence is clause C1 of the objective statement, and the epic maps it to five of the twenty-five stories with this one first [tickets/EPIC-001-reorder-and-replenishment.md:§10.2 Objective-Clause Map]. The label on this story is therefore a quoted clause of the objective statement rather than a derived one.

How this story serves the clause: a buyer cannot reorder a regularly purchased set with less effort than rebuilding it until that set exists as a durable, named, owned object, and this story is the one that brings that object into being. Everything the rest of the epic does to a list — adding a line, materialising it into a cart, previewing a delta, sharing it across seats — reads a row that this story writes.

**Why this story is the epic's harness-proving run.** Four pieces of evidence, each independent of the others, transcribed from the nomination rather than re-argued [tickets/EPIC-001-reorder-and-replenishment.md:§9.5 Nomination]:

- **It is the first story in dependency order that requires a new plugin-owned table**, and therefore the first additive migration in the set. Nothing upstream of it needs to exist.
- **It exercises the entire toolchain in a single pass** — new plugin-owned entities, an additive migration through the existing lifecycle [packages/core/src/migrate.ts:L118], an `extend type Mutation` schema extension of the shape the shipped wishlist plugin already demonstrates [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L16], a permission-gated resolver, and an end-to-end specification driven by the existing harness, whose whole published surface is the fourteen re-exports of a single index [packages/testing/src/index.ts:L1-L14]. A misconfiguration in any link of that chain fails this story.
- **It has no prerequisite story**, so a red result isolates to the environment rather than to the reorder design. That property is what makes it a proving run.
- **It runs on the four per-engine jobs that already exist** [.github/workflows/build_and_test.yml:L174] with no new infrastructure, so the first additive migration is evidenced on MariaDB, MySQL, PostgreSQL and sql.js on its first merge.

### 2.1 Detection Is Not Isolation — The Staged Checkpoints That Make This A Proving Run

**Having no prerequisite story is not the same as isolating a failure, and conflating the two is what this sub-section exists to disentangle.** A single specification that boots a server, runs a migration, loads a schema extension, authenticates a session and then asserts a domain outcome fails as one red result. That result proves *something* is wrong across five layers; it does not say which, and a proving run whose output is "the chain is broken somewhere" has detected a problem without isolating it. The absence of an upstream story removes one candidate cause out of six, not five.

The remedy is ordering rather than more assertions: **four staged checkpoints run before the first domain assertion, each with its own diagnostic and each depending only on the layers below it.** Every checkpoint uses a surface that already ships, so none of them can fail for a reason this story introduced.

- **Checkpoint one — the plugin module loads and the server boots with it registered.** The assertion is that the harness's server initialisation completes with `ReorderPlugin` present in the configuration, in the shape the exemplar benchmark and every end-to-end specification already use [packages/core/e2e/default-search-plugin.bench.ts:L42-L47]. **Diagnostic on failure: the plugin's own metadata, providers or imports are wrong.** Nothing about migrations, schema or authentication has been touched yet.
- **Checkpoint two — the migration applies and reverts against a known-good baseline.** Generated through the existing lifecycle [packages/core/src/migrate.ts:L118], applied [packages/core/src/migrate.ts:L40] and reverted once [packages/core/src/migrate.ts:L89], with the cached seed data deleted first because a schema change invalidates it [AGENTS.md:L19]. **Diagnostic on failure: the entity definitions or the generated data-definition statements are wrong on this engine** — and because this checkpoint runs per engine, a failure on one engine and a pass on the other three localises the defect to that engine rather than to the plugin.
- **Checkpoint three — the schema extension is present and nothing existing moved.** Two assertions against the generated schema and no database work at all: `createReorderList` exists on the root `Mutation` type [packages/core/src/api/schema/shop-api/shop.api.graphql:L70], and the root `Query` type still declares exactly nineteen root queries [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52]. **Diagnostic on failure: the `shopApiExtensions` wiring is wrong, or a generator widened something** — the second case being the epic's first collision showing up in practice [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].
- **Checkpoint four — a session authenticates and carries the permission, using only shipped operations.** A Shop API sign-in as a seeded customer, followed by `activeCustomer` [packages/core/src/api/schema/shop-api/shop.api.graphql:L5] returning that customer, and one call to the new mutation observed only for *not* being refused by the gate. **Diagnostic on failure: the seed, the credential, the channel token or the permission registration is wrong** — never the list-creation logic, which no assertion has reached yet.

**Only then do the eight criteria in section 5 run.** The ordering is the whole mechanism: a failure at checkpoint N with checkpoints one through N-1 green names the layer, and the four checkpoints together are what turn "this story detects a broken toolchain" into "this story says which link broke". A red result at checkpoint four with the first three green is an environment failure; a red result in section 5 with all four checkpoints green is a defect in this story's own logic, and that is the distinction the nomination depends on.

This story is **not** the epic's demonstration slice. That nomination belongs to `STORY-001-02-01` [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination], and section 3 states the disqualifying reason outright rather than leaving it implicit.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. The five required coverage classes map onto them as follows: valid input is AC-1, invalid or incomplete input is AC-2, an error naming the exact type returned is AC-3 and AC-4, an edge case is AC-7, and the assertion that an existing operation is unchanged is AC-8. AC-5, AC-6 and AC-7 between them carry the three authorisation assertions the parent feature makes mandatory in every story of this feature — an unauthenticated request writes nothing, **a session holding no custom permission succeeds**, a request authenticated as a different customer cannot produce that customer's row, and a foreign channel token does not reach another channel's data [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.7 The Existing Mechanism This Feature Consumes Rather Than Rebuilds]. The middle one of those is the criterion whose absence would let the design fault the epic records as collision C7 reach production, which is why it is written as a positive assertion rather than left implicit in AC-1.

Two properties of the operation are stated once here rather than repeated in every criterion. `createReorderList` is a single synchronous write: it enqueues no job and schedules no task, so there is no asynchronous trigger and no observable completion signal to name. And it reads no price and no stock level, so no criterion below is a point-in-time availability read that can go stale between check and commit; that class of read belongs to FEATURE-001-03 and FEATURE-001-04.

AC-1: A named list is created for the authenticated customer in the active channel

**A note on AC-6, and the reason it now asserts a success where an earlier draft asserted a permission.** An earlier version of this criterion required the session to hold a `CreateReorderList` permission produced by a `CrudPermissionDefinition`. **A customer session can never hold it.** The customer role is created with `Permission.Authenticated` and nothing else [packages/core/src/service/services/role.service.ts:L433-L444], a customer's user is assigned exactly that role [packages/core/src/service/services/user.service.ts:L99-L107], and the role cannot be edited to hold more because the update path refuses to modify it [packages/core/src/service/services/role.service.ts:L290]. The control is the service-layer predicate asserted above, and with `Permission.Owner` it is not the load-bearing half but the whole of it: the platform states that a resolver relying on ownership **must** enforce it, and that without that logic the effect is the same as public access [packages/core/src/api/config/generate-permissions.ts:L32-L34].
**A note on AC-6, because the gate alone is not the control and the obvious gate would refuse every buyer.** The gate this mutation declares is `Permission.Owner`, applied to the resolver with the `@Allow` decorator [packages/core/src/common/permission-definition.ts:L134], which is the pattern the shipped wishlist plugin uses on all three of its customer-facing operations [packages/dev-server/example-plugins/wishlist-plugin/api/wishlist.resolver.ts:L11-L12]. **A `CrudPermissionDefinition` permission [packages/core/src/common/permission-definition.ts:L146] is deliberately not used here, and the reason is a platform constraint rather than a preference:** the Customer Role ships holding `Permission.Authenticated` alone [packages/core/src/service/services/role.service.ts:L443], it is the role every customer user is given [packages/core/src/service/services/user.service.ts:L106-L107], and `RoleService.update` throws when asked to amend it [packages/core/src/service/services/role.service.ts:L290-L291] — so a registered permission can never be granted to a customer and a mutation gated on one is refused for every buyer in every channel. This story therefore registers no permission definition and contributes no member to the published `Permission` enum [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.7 The Existing Mechanism This Feature Consumes Rather Than Rebuilds]. The control is the in-resolver logic asserted above, and it is mandatory rather than defensive: `Permission.Owner` is declared `assignable: false` and `internal: true` [packages/core/src/common/constants.ts:L28-L31] and the guard admits a request that merely lists it [packages/core/src/service/helpers/request-context/request-context.service.ts:L109], which is why the platform states that a resolver relying on it **must** include logic enforcing that only the owner of the resource has access and that without that logic the effect is the same as public access [packages/core/src/api/config/generate-permissions.ts:L32-L34]. That determination is recorded as settled in the epic's third collision rather than left as an open decision [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

## 7. Edge Cases

Five scenarios. The three unconditionally required categories are covered by the first three, the fourth covers a conditional category that applies to a create-a-list operation, and the fifth covers the customer-data lifecycle the epic leaves open, because a soft-deleted buyer leaves this story’s rows behind. Two of the required three resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure the operation cannot have. **A further scenario used to sit here and no longer does:** the concurrent duplicate-name race was promoted to AC-7, because a scenario in this section is not covered by the automation gate that section 10 applies to the criteria, and that race is the one defect in this story a sequential test cannot find.

* Scenario: Zero, null or empty collection — the customer owns no reorder list at all
   * Given a Returning Buyer is authenticated in the active channel and owns zero `ReorderList` rows in that channel
   * When that customer executes `createReorderList` with the name `Weekly grocery restock`
   * Then proceed: the mutation returns a `ReorderList` whose line count is exactly zero and whose name equals the input name, and the number of lists that customer owns in that channel becomes exactly one — an empty starting state is the normal first call rather than an error path

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant the buyer previously bought is now disabled
   * Given a Returning Buyer previously purchased a variant whose `enabled` flag is now false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53]
   * When that customer executes `createReorderList` with a name they do not already hold
   * Then proceed, with no warning and no audit record: this operation reads no variant at all, because a list is created empty and lines arrive in `STORY-001-01-02`. A disabled variant cannot affect list creation, and its effect on a reorder is evaluated later — at preview time by FEATURE-001-03 and at resolution time by FEATURE-001-04

* Scenario: A price changed since the last purchase — the catalogue price of a previously purchased variant has moved
   * Given the price of a variant the buyer previously purchased has changed since that purchase
   * When that customer executes `createReorderList` with a name they do not already hold
   * Then proceed, with no warning: the `ReorderList` table stores no monetary column, so this story holds no price that could go stale, and a price delta is computed at preview time by FEATURE-001-03 [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. Copying a price onto a list row would be a defect rather than an optimisation

* Scenario: Concurrent modification or race — two requests create the same list name for the same customer at the same moment
   * Given a Returning Buyer owns no list named `Weekly grocery restock` in the active channel, and two requests carrying that name are in flight together for that customer and that channel
   * When both executions of `createReorderList` reach the write
   * Then block one of the two: exactly one execution returns a `ReorderList` and the other returns `ReorderListNameConflictError`, and the number of lists that customer owns in that channel ends at exactly one more than its starting value. A service-layer pre-check cannot produce that outcome on its own, because both requests may read before either writes; the named unique index `UQ_reorder_list_customer_channel_name_key` is what makes exactly one of them fail [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]. **The translation of that failure is narrow and is part of this scenario rather than a separate concern:** the caught exception is matched against that one constraint name and only that name maps to `ReorderListNameConflictError`, every other database error is re-raised as an internal error, and the API-visible message on either path contains no driver text, no SQL fragment and no constraint name — a raw driver message can disclose the schema, the column list and sometimes the conflicting value itself, none of which belongs in a buyer-facing response [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency] The uniqueness rule is scoped to the owning customer **and** the active channel, so the same name submitted under a second channel token proceeds rather than colliding: it writes a new row carrying the second channel's id, and the count of that customer's rows in the first channel is unchanged.


* Scenario: The named customer is soft-deleted after owning a list — the row outlives the buyer
   * Given a Returning Buyer owns exactly one `ReorderList` named `Weekly grocery restock` in the active channel, and that customer is subsequently soft-deleted, `Customer` being declared soft-deletable [packages/core/src/entity/customer/customer.entity.ts:L28-L29]
   * When `createReorderList` is executed again with that same name, first by a session for the soft-deleted customer and then by a second customer in the same channel
   * Then proceed with an audit-free record of the present state rather than a new behaviour: the soft-deleted customer's row is still present and still carries that `customerId`, so the first execution returns `ReorderListNameConflictError` on the unchanged per-customer-and-channel uniqueness rule, the second customer's execution returns a new `ReorderList` because uniqueness is scoped to the owning customer, and **this story implements no deletion, anonymisation or purge behaviour on either table** — the epic's customer-data-lifecycle decision selects that behaviour and a story that shipped one first would have to unship it [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]

The two remaining conditional categories do not apply here and are not force-fitted. A point-in-time read gone stale between check and commit does not apply because this operation reads no availability and makes no reservation. A channel, currency or language mismatch between an original order and a reorder context does not apply because this operation reads no order and carries no monetary value; the channel dimension it does have is asserted as AC-7 instead. The concurrent-modification category, which does apply, was **promoted out of this section into AC-7** rather than dropped, for the reason the note under that criterion gives: while it sat here it fell outside the automation gate, and a duplicate-name race is the one defect in this story that only a concurrent test can find.
