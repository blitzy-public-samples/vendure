### 2.1 Detection Is Not Isolation — The Staged Checkpoints That Make This A Proving Run

**Having no prerequisite story is not the same as isolating a failure, and conflating the two is what this sub-section exists to disentangle.** A single specification that boots a server, runs a migration, loads a schema extension, authenticates a session and then asserts a domain outcome fails as one red result. That result proves *something* is wrong across five layers; it does not say which, and a proving run whose output is "the chain is broken somewhere" has detected a problem without isolating it. The absence of an upstream story removes one candidate cause out of six, not five.

The remedy is ordering rather than more assertions: **four staged checkpoints run before the first domain assertion, each with its own diagnostic and each depending only on the layers below it.** Every checkpoint uses a surface that already ships, so none of them can fail for a reason this story introduced.

- **Checkpoint one — the plugin module loads and the server boots with it registered.** The assertion is that the harness's server initialisation completes with `ReorderPlugin` present in the configuration, in the shape the exemplar benchmark and every end-to-end specification already use [packages/core/e2e/default-search-plugin.bench.ts:L42-L47]. **Diagnostic on failure: the plugin's own metadata, providers or imports are wrong.** Nothing about migrations, schema or authentication has been touched yet.
- **Checkpoint two — the migration applies and reverts against a known-good baseline.** Generated through the existing lifecycle [packages/core/src/migrate.ts:L118], applied [packages/core/src/migrate.ts:L40] and reverted once [packages/core/src/migrate.ts:L89], with the cached seed data deleted first because a schema change invalidates it [AGENTS.md:L19]. **Diagnostic on failure: the entity definitions or the generated data-definition statements are wrong on this engine** — and because this checkpoint runs per engine, a failure on one engine and a pass on the other three localises the defect to that engine rather than to the plugin.
- **Checkpoint three — the schema extension is present and nothing existing moved.** Two assertions against the generated schema and no database work at all: `createReorderList` exists on the root `Mutation` type [packages/core/src/api/schema/shop-api/shop.api.graphql:L70], and **each of the nineteen baseline root queries is still present and byte-identical** in name, argument list, argument types, return type and nullability [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52], **this story adding none of its own** — the baseline-plus-owned-additions form the epic requires, never an absolute post-plugin total, because a total stops being true the moment a query-adding sibling merges [tickets/EPIC-001-reorder-and-replenishment.md:§2.4 Scope Boundaries — Explicit In-Or-Out Rulings]. **Diagnostic on failure: the `shopApiExtensions` wiring is wrong, or a generator widened something** — the second case being the epic's first collision showing up in practice [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].
- **Checkpoint four — a session authenticates and passes the gate, using only shipped operations.** A Shop API sign-in as a seeded customer, followed by `activeCustomer` [packages/core/src/api/schema/shop-api/shop.api.graphql:L5] returning that customer, and one call to the new mutation observed only for *not* being refused by the gate. **The checkpoint asserts what the platform can actually produce, and an earlier version of this line asserted what it cannot:** it said the session "carries the permission" and named a permission registration among its diagnostics, while this story registers none and while `Permission.Owner` is declared `assignable: false` and so is in no session's permission set [packages/core/src/common/constants.ts:L27-L31]. What is asserted instead is the pair the gate does produce: the session holds `Permission.Authenticated` and nothing else [packages/core/src/service/services/role.service.ts:L443], and the request context on that call carries `authorizedAsOwnerOnly` true, which is what the guard sets when the caller lacks the listed permission and the listed permission is `Owner` [packages/core/src/service/helpers/request-context/request-context.service.ts:L104-L110], and which the shipped shop-order resolver reads before applying its own owner comparison [packages/core/src/api/resolvers/shop/shop-order.resolver.ts:L88-L95]. **Diagnostic on failure: the seed, the credential, the channel token or the `@Allow` wiring is wrong** — never the list-creation logic, which no assertion has reached yet, and never a permission registration, of which this story has none.

**Only then do the eight criteria in section 5 run.** The ordering is the whole mechanism: a failure at checkpoint N with checkpoints one through N-1 green names the layer, and the four checkpoints together are what turn "this story detects a broken toolchain" into "this story says which link broke". A red result at checkpoint four with the first three green is an environment failure; a red result in section 5 with all four checkpoints green is a defect in this story's own logic, and that is the distinction the nomination depends on.

This story is **not** the epic's demonstration slice. That nomination belongs to `STORY-001-02-01` [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination], and section 3 states the disqualifying reason outright rather than leaving it implicit.

### 4.2 Demonstration Requirement

One path, runnable end to end from this file alone, in two numbered terminals because one step occupies its terminal for as long as the demonstration lasts. **The steps are numbered 0 to 6 with no gap and no repetition** — an earlier revision of this section carried two steps numbered 0 and then jumped to 2, which is a sequence a reader cannot follow and cannot tell is complete. This block is a verbatim copy of the epic's canonical form and is kept byte-identical to it [tickets/EPIC-001-reorder-and-replenishment.md:§11.11.1 Step 0 — Preflight]; a copy that has drifted from it is defective rather than a variant.

```bash
# Run from the repository root. Read-only: nothing below installs, builds or writes.
reorder_preflight() {
    local problems=0
    local expected_bun='1.3.10'
    local expected_node_range='^20.19.0 || >=22.12.0'

    if ! command -v bun >/dev/null 2>&1; then
        echo 'MISSING: bun is not on PATH. See the contribution guide prerequisites.'
        problems=$((problems + 1))
    else
        local actual_bun
        actual_bun=$(bun --version 2>/dev/null | tr -d '[:space:]')
        # Compared, not merely printed: a version echoed to the terminal asserts nothing, and the
        # reader who is going to notice a mismatch is exactly the reader who did not need the check.
        if [ "$actual_bun" != "$expected_bun" ]; then
            echo "VERSION: bun is $actual_bun, but continuous integration pins $expected_bun."
            problems=$((problems + 1))
        fi
    fi

    # The declared Node range is TESTED, not printed: printing `node --version` beside a comment
    # naming the range asserts nothing, because any version at all satisfies it — a checkout on an
    # unsupported line produces a clean preflight and then fails later, inside a build, for a reason
    # this check has the information to state up front.
    if ! grep -qF "$expected_node_range" package.json 2>/dev/null; then
        echo "STALE: package.json no longer declares engines.node as '$expected_node_range', so this"
        echo '       preflight is checking a range the repository has moved off.'
        problems=$((problems + 1))
    fi
    if ! command -v node >/dev/null 2>&1; then
        echo 'MISSING: node is not on PATH.'
        problems=$((problems + 1))
    else
        local actual_node major minor patch
        actual_node=$(node --version 2>/dev/null | tr -d 'v[:space:]')
        major=${actual_node%%.*}
        minor=${actual_node#*.}; minor=${minor%%.*}
        patch=${actual_node##*.}
        case "$major$minor$patch" in
            *[!0-9]*|'') echo "VERSION: node reported an unparsable version '$actual_node'."
                         problems=$((problems + 1)) ;;
            *) if ! { [ "$major" -eq 20 ] && [ "$minor" -ge 19 ]; } &&
                 ! { [ "$major" -eq 22 ] && [ "$minor" -ge 12 ]; } &&
                 ! [ "$major" -ge 23 ]; then
                   echo "VERSION: node is $actual_node, outside the declared range $expected_node_range."
                   problems=$((problems + 1))
               fi ;;
        esac
    fi

    # Compose is INVOKED rather than assumed: quoting `docker compose up -d mariadb` as step 1 and
    # checking nothing leaves a reader without the Compose plugin — or with only the end-of-life
    # hyphenated binary — meeting a command-not-found in the middle of a demonstration.
    if ! command -v docker >/dev/null 2>&1; then
        echo 'MISSING: docker is not on PATH, so the disposable database cannot be started.'
        problems=$((problems + 1))
    elif ! docker compose version >/dev/null 2>&1; then
        echo 'MISSING: the docker compose plugin. Every Compose command in this set is the v2'
        echo '       subcommand form; the hyphenated docker-compose binary is end-of-life and is'
        echo '       not what these tickets quote.'
        problems=$((problems + 1))
    fi
    if [ ! -f docker-compose.yml ]; then
        echo 'MISSING: docker-compose.yml, which declares the disposable database service.'
        problems=$((problems + 1))
    elif ! grep -qE '^[[:space:]]+mariadb:' docker-compose.yml; then
        echo 'MISSING: a mariadb service in docker-compose.yml, which every demonstration in this'
        echo '       set points its seed at by default.'
        problems=$((problems + 1))
    fi

    [ -d node_modules ] || {
        echo 'MISSING: root node_modules. Run the documented install step first.'
        problems=$((problems + 1)); }
    [ -x node_modules/.bin/ts-node ] || {
        echo 'MISSING: node_modules/.bin/ts-node, which the populate script loads as a require hook.'
        problems=$((problems + 1)); }
    [ -f packages/cli/dist/cli.js ] || {
        echo 'MISSING: packages/cli/dist/cli.js, which the dev script executes. Run the build step.'
        problems=$((problems + 1)); }
    [ -f packages/create/assets/products.csv ] || {
        echo 'MISSING: packages/create/assets/products.csv, which the seed imports its catalogue from.'
        problems=$((problems + 1)); }

    if [ "$problems" -ne 0 ]; then
        echo "PREFLIGHT FAILED: $problems prerequisite problem(s). Nothing was started."
        return 1
    fi
    echo 'PREFLIGHT OK'
    return 0
}
```

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. The five required coverage classes map onto them as follows: valid input is AC-1, invalid or incomplete input is AC-2, an error naming the exact type returned is AC-3 and AC-4, an edge case is AC-7, and the assertion that an existing operation is unchanged is AC-8. AC-5, AC-6 and AC-7 between them carry the three authorisation assertions the parent feature makes mandatory in every story of this feature — an unauthenticated request writes nothing, **a session holding no custom permission succeeds**, a request authenticated as a different customer cannot produce that customer's row, and a foreign channel token does not reach another channel's data [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.7 The Existing Mechanism This Feature Consumes Rather Than Rebuilds]. The middle one of those is the criterion whose absence would let the design fault the epic records as collision C7 reach production, which is why it is written as a positive assertion rather than left implicit in AC-1.

Two properties of the operation are stated once here rather than repeated in every criterion. `createReorderList` is a single synchronous write: it enqueues no job and schedules no task, so there is no asynchronous trigger and no observable completion signal to name. And it reads no price and no stock level, so no criterion below is a point-in-time availability read that can go stale between check and commit; that class of read belongs to FEATURE-001-03 and FEATURE-001-04.

AC-1: A named list is created for the authenticated customer in the active channel
* Given a Returning Buyer is authenticated against the Shop API in the channel identified by the token sent in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L62], the request resolves its language from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74], and that customer owns no `ReorderList` row named `Weekly grocery restock` in that channel
* When that customer executes the `createReorderList` mutation with the name `Weekly grocery restock`
* Then the mutation returns a `ReorderList` whose `name` equals `Weekly grocery restock` character for character and whose line count is exactly zero, the stored row carries the authenticated customer as its `customerId` and the token's channel as its `channelId`, the same `name` string is returned under every `languageCode` because a list name is stored as the buyer entered it and is not a translated string [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10.1 The Buyer-Supplied List Name], and a second list created in the same way with the name `<b>Tools</b> &amp; spares` is returned in the `name` field byte-for-byte as it was submitted — neither escaped, nor stripped, nor interpreted as markup — because the field carries data and every consumer renders it as text, and the stored row carries exactly five data columns beyond the inherited identifier and timestamps — `customerId`, `channelId`, `name`, the canonical `nameKey`, the denormalised `lineCount` at exactly zero, and nothing else — with no contact detail, no free-text note beyond the name the buyer supplied and no serialised request context, which is the minimisation the epic's customer-data-lifecycle decision requires of every plugin-owned customer-linked table while that decision is open [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]

AC-2: A name failing the input contract is rejected, writes no row, and is neither truncated nor silently altered
* Given a Returning Buyer is authenticated in the active channel; the list-name length bound is the fixed constant 191 characters and the `name` column was created at that same width, there being no plugin option for it [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency — The Rules That Make The Contract Deterministic]; and the number of `ReorderList` rows that customer owns in that channel is recorded before each call
* When that customer executes the `createReorderList` mutation once for each of these four names in turn — a name consisting only of space characters, a name one character longer than the fixed 191-character bound, namely 192 characters, a name containing the C0 control character `U+0007`, and a name containing the zero-width character `U+200B` — each evaluated by the trim-collapse-normalise-lower-case canonicalization the parent feature fixes [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency]
* Then each of the four calls writes no `ReorderList` row, leaves the recorded number unchanged at its exact prior value, and returns **exactly one entry in the response's top-level `errors` array whose `extensions.code` is exactly `USER_INPUT_ERROR`** — the code the platform's `UserInputError` carries [packages/core/src/common/error/errors.ts:L27] and [packages/core/src/common/error/errors.ts:L29], surfaced through `extensions.code` because that class extends `I18nError` which extends `GraphQLError` [packages/core/src/i18n/i18n-error.ts:L18] and [packages/core/src/i18n/i18n-error.ts:L25-L27] — with `data.createReorderList` exactly null and no other entry in `errors`; **no call stores a shortened, stripped or otherwise altered version of the submitted name**, so a fifth call submitting the over-long name minus its final character is the way to obtain a stored row rather than the fourth call having quietly stored a truncated one

**A note on AC-2, because it carries the whole input contract and one half of it is still open while the other is now fixed.** The four rejections above are one criterion because they share one operation, one Then and one table-driven test; splitting them would spend three of this story's eight criteria on the same contract.

*Which parts are asserted against a configured value, and which against a constant.* The length case asserts the boundary against the **fixed constant 191** and not against a configured value, because there is no name-length option and the number is forced by the `name` column's width [tickets/EPIC-001-reorder-and-replenishment.md:§7.10 The Plugin Option Ledger — One Authority For Every Configured Key]. The list-count case in AC-4 is the one asserted against a configured value — `ReorderPluginOptions.maxListsPerCustomer` — and it names no figure, because that value is an open decision the epic records as blocking this story [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. An earlier revision of this paragraph asserted the length "against whatever the plugin option holds", which named an option that does not exist. The normalisation applied before the uniqueness comparison is the other configured half, and it is asserted by AC-3 rather than here: whichever of exact, trimmed, case-insensitive or Unicode-normalised comparison is chosen, AC-3's second call has to collide under it.

*Why the rejection is a request-level error rather than a result-union member, and why the criterion names the exact error rather than the class of error.* None of the six error results this ticket set declares covers an invalid name, and this story declines to invent a seventh [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10 The Error Vocabulary This Feature Introduces]. The nearest shipped analogue is the precedent service raising the platform's input-error class when a variant id does not resolve [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L37-L39], so the error raised is `UserInputError` [packages/core/src/common/error/errors.ts:L27] and the code observable on the wire is `USER_INPUT_ERROR` [packages/core/src/common/error/errors.ts:L29]. **The criterion names both, and that is ruling R17 rather than a preference** [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]: an earlier version asserted only "a request-level error entry and no payload", which an internal server error, a resolver crash and a genuine input rejection all satisfy identically — so it could not fail when the behaviour under test was absent. A *missing* `name` argument is a different case again and is not written as a criterion at all, because a non-nullable input argument fails GraphQL schema validation before any resolver executes.

*Why an over-long name must be refused by validation and not by the database.* If the validated bound and the column width disagree, the over-long case surfaces as a driver-level write failure whose message and type vary by engine, which is neither testable across the four engine jobs nor useful to a buyer. The feature-level definition of done therefore requires the two numbers to be equal [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§5. Definition of Done (Feature-Level)].

AC-3: A name the same customer already holds returns ReorderListNameConflictError, under the configured comparison
* Given a Returning Buyer is authenticated in the active channel and already owns a `ReorderList` named `Weekly grocery restock` in that channel, where the name is unique per owning customer and channel [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched] and the comparison that decides sameness is the one the plugin configures [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.10.1 The Buyer-Supplied List Name], enforced on the canonical `nameKey` column by the named index `UQ_reorder_list_customer_channel_name_key` over owning customer, channel and canonical name
* When that customer executes the `createReorderList` mutation a second time with the name `Weekly grocery restock`, and then a third time with that same name altered only along the dimension the configured comparison collapses — the name carrying one leading and one trailing space where the comparison trims, or the name in upper case where the comparison ignores case, or the decomposed Unicode form of the same characters where the comparison normalises
* Then both the second and the third call return `ReorderListNameConflictError`, neither writes a row, and the number of `ReorderList` rows that customer owns in that channel is exactly one after all three calls, so the normalisation the service applies before comparing is observable from the published operation rather than only from the database's collation

AC-4: A customer holding the configured maximum returns ReorderListLimitError carrying that maximum, and two simultaneous creates cannot exceed it
* Given `ReorderPluginOptions.maxListsPerCustomer` is configured to 2 for the test deployment [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency], a Returning Buyer is authenticated in the active channel, and the bound is enforced by a transaction holding a pessimistic write lock on the owning `Customer` row on the three engines that support one and by a single conditional statement on sql.js, which is the shipped claim idiom [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L284-L336]
* When that customer already owns exactly 2 `ReorderList` rows in that channel and executes the `createReorderList` mutation with a name they do not already hold, and separately, when that customer owns exactly 1 row and two `createReorderList` executions carrying two different unheld names are driven against a deterministic barrier on independent connections and released to write together, on `e2e-mariadb`, `e2e-mysql` and `e2e-postgres` [.github/workflows/build_and_test.yml:jobs], the three jobs that run a database server the suite can open two independent connections against; `e2e-sqljs` runs the same cases **sequentially**, where what they evidence is single-connection correctness, replay idempotency and constraint behaviour rather than interleaving — the platform's own source records that engine as one without pessimistic locking [packages/core/src/plugin/default-scheduler-plugin/default-scheduler-strategy.ts:L267], so a pair of requests there runs one after the other however the test is written
* Then the first call returns `ReorderListLimitError` whose `maxItems` is 2, writes no row, and leaves the row count at exactly 2; and of the two barrier-released calls exactly one returns a `ReorderList` and the other returns `ReorderListLimitError` with `maxItems` of 2, leaving the row count at exactly 2 rather than 3 — which is the assertion a count-before-insert check fails and which only the three server engines can make, since a sequential pair cannot detect it

**A note on AC-4, and on why a number now appears in it.** The **shipped default** for `maxListsPerCustomer` is an open product decision that the epic records as blocking eight stories including this one [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. Configuring 2 for a test deployment is not the same thing as choosing that default, and treating the two as the same is what made an earlier version of this criterion unbuildable: it asserted behaviour "against whatever value is configured" without stating a value, which no test can set up. The distinction the parent feature draws is the one applied here — a criterion written against a *configured* value is writable today, while the *default* cannot be signed off until a maintainer sets it [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency]. No product default is invented by this story. The shape is idiomatic rather than novel: the platform already ships an order-level limit error [packages/core/src/api/schema/common/common-error-results.graphql:L37] that carries its own maximum in its payload [packages/core/src/api/schema/common/common-error-results.graphql:L40], so what is missing here is the value and not the pattern. Both `ReorderListNameConflictError` and `ReorderListLimitError` are declared new by this ticket set, and declaring them grows the published `ErrorCode` enum on every boot, because its members are derived from every type implementing the `ErrorResult` interface [packages/core/src/api/config/generate-error-code-enum.ts:L9] matched against the interface-name constant in the same file [packages/core/src/api/config/generate-error-code-enum.ts:L3] by a filter over each type's declared interfaces [packages/core/src/api/config/generate-error-code-enum.ts:L17]. The epic records that growth as collision C2 and requires any consuming example that switches on `ErrorCode` to carry a default branch [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

AC-5: An unauthenticated request writes nothing
* Given the request carries a valid channel token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L62] and no authenticated session
* When the `createReorderList` mutation is executed with a name
* Then no `ReorderList` row is written and the response carries **exactly one entry in its top-level `errors` array whose `extensions.code` is exactly `FORBIDDEN`** — the code the platform's `ForbiddenError` carries [packages/core/src/common/error/errors.ts:L67] and [packages/core/src/common/error/errors.ts:L69], surfaced through `extensions.code` by the same `I18nError` mechanism [packages/core/src/i18n/i18n-error.ts:L25-L27] — with `data.createReorderList` exactly null; the request is refused by the resolver's own ownership logic rather than by the `@Allow` gate — the gate admits a session that does not hold the permission it lists [packages/core/src/service/helpers/request-context/request-context.service.ts:L109], so an unauthenticated request reaches the resolver and is stopped there, by the session guard the shipped precedent already demonstrates for a request holding no active user [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L74-L76]. **`FORBIDDEN` rather than `UNAUTHORIZED` is the asserted code, and the distinction is the platform's own**: `UnauthorizedError` is raised where credentials do not match [packages/core/src/common/error/errors.ts:L53], whereas an absent session on a permission-gated operation is what the platform's guard reports as forbidden [packages/core/src/api/middleware/auth-guard.ts:L83]. Naming the exact code is ruling R17 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]: "the response carries no payload" alone would be satisfied by a resolver that threw for an unrelated reason

**A note on AC-6, which asserts a success where an earlier draft asserted a permission, because the obvious gate would refuse every buyer and the gate alone is not the control.** This is one note where an earlier revision of this story carried two, together with a duplicated `Given` bullet whose second copy claimed the session holds `Permission.Owner`; the two notes argued the same case in different details, and all three are consolidated here — recorded rather than silently removed, because a criterion whose preconditions are stated twice is a criterion a reader cannot be sure they have read once. **A customer session can never hold a registered permission.** The Customer Role is created with `Permission.Authenticated` and nothing else [packages/core/src/service/services/role.service.ts:L433-L444], a customer's user is assigned exactly that role [packages/core/src/service/services/user.service.ts:L99-L107], and the role cannot be edited to hold more because the update path refuses to modify it [packages/core/src/service/services/role.service.ts:L290-L291]. What the gate does is admit the request and mark the context — the guard sets `authorizedAsOwnerOnly` when the session holds none of the listed permissions [packages/core/src/service/helpers/request-context/request-context.service.ts:L104-L110], which is exactly the state an ordinary customer session arrives in. The gate is `@Allow(Permission.Owner)` applied with the decorator [packages/core/src/common/permission-definition.ts:L134], which is what the shipped saved-list precedent uses on all three of its customer-facing operations [packages/dev-server/example-plugins/wishlist-plugin/api/wishlist.resolver.ts:L11-L12] and what the platform's own customer-owned Shop resolvers use [packages/core/src/api/resolvers/shop/shop-order.resolver.ts:L75]. **This story therefore registers no permission definition and grows the published `Permission` enum by zero members**, and the epic's ledger row is the single authority for how many definitions the set registers and where they live — cited rather than restated here, because a local copy of that arithmetic is how a corrected total came to disagree with itself across files [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. **The control is the service-layer predicate asserted above, and with `Permission.Owner` it is not the load-bearing half but the whole of it:** the guard admits a request that merely lists the member [packages/core/src/service/helpers/request-context/request-context.service.ts:L109], which is why the platform states that a resolver relying on ownership **must** include logic enforcing that only the owner has access, and that without that logic the effect is the same as public access [packages/core/src/api/config/generate-permissions.ts:L32-L34]. AC-7: Two concurrent requests for the same name leave exactly one row and one exact conflict error
* Given a Returning Buyer is authenticated in the active channel and owns no `ReorderList` named `Weekly grocery restock` in that channel, and the uniqueness of name per owning customer and channel is enforced by a database constraint on the `ReorderList` table rather than by a service-level check alone [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]

* Then on each of the three server engines exactly one barrier-released execution returns a `ReorderList` and the other returns `ReorderListNameConflictError`, the number of `ReorderList` rows that customer owns with that name in that channel is exactly one, and neither execution returns a database-level failure to the caller because the violation on `UQ_reorder_list_customer_channel_name_key` is caught and mapped to that error result; and on all four engines the direct duplicate write is refused by the database naming that same constraint, with the row count still exactly one — **`e2e-sqljs` carrying the constraint-shape half only, and not being offered as concurrency evidence**, per the epic's race-evidence rule [tickets/EPIC-001-reorder-and-replenishment.md:§7.8 The Seven Plugin-Owned Tables]

**A note on AC-7, which is a criterion rather than an edge case for a stated reason.** A duplicate-name race is the only defect in this story that a service-level check cannot prevent and that a sequential test cannot detect: two requests both read "no such name", both pass the check, and both write. While it sat in the edge-case section it was outside the automation gate — the unit tests cover the service check and the end-to-end specification covers the criteria, so a race described only as a scenario could be, and would be, skipped. It is a criterion now, and it is asserted **per engine** because the constraint that makes it safe is a database constraint and engines differ in how they report a violation. This is also the assertion that proves the uniqueness rule is where the parent feature's entity mapping says it is [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]: **if the rule were only in the service, this criterion fails and no other criterion in this story would notice.**

*And a second correction, which is why the criterion above now reads as two assertions rather than one.* An earlier version said the two executions were "issued concurrently, both reaching the write, on each of the four database engines". **Neither half of that survives scrutiny.** "Issued concurrently" is not an instruction a test can be written against: two calls fired from one process are routinely serialised by the client, the pool or the transaction, so the test passes having proved sequencing rather than interleaving — which is the worst kind of green, because it is green for the wrong reason and would stay green if the constraint were dropped. And **"each of the four engines" overstates what one of the four can observe**: `e2e-sqljs` runs the WebAssembly SQLite build that `@vendure/testing` ships as an in-process initializer [packages/testing/src/index.ts:L12], so two transactions there execute in one process against one in-memory database and cannot be made to interleave at all. The criterion therefore separates the two properties the epic's race-evidence rule separates [tickets/EPIC-001-reorder-and-replenishment.md:§7.8 The Seven Plugin-Owned Tables]: **the barrier** proves the interleaving, on the three engines that can hold two concurrent transactions, and **the direct duplicate write** proves the constraint is the database's rather than the service's, on all four. Neither substitutes for the other, and the sql.js exclusion is stated rather than left for a reader to infer from a passing job.

## 7. Edge Cases

Five scenarios. The three unconditionally required categories are covered by the first three, the fourth covers a conditional category that applies to a create-a-list operation, and the fifth covers the customer-data lifecycle the epic leaves open, because a soft-deleted buyer leaves this story’s rows behind. Two of the required three resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure the operation cannot have. **A further scenario used to sit here and no longer does:** the concurrent duplicate-name race was promoted to AC-7, because a scenario in this section is not covered by the automation gate that section 10 applies to the criteria, and that race is the one defect in this story a sequential test cannot find.

* Scenario: Zero, null or empty collection — the customer owns no reorder list at all
   * Given a Returning Buyer is authenticated in the active channel and owns zero `ReorderList` rows in that channel
   * When that customer executes `createReorderList` with the name `Weekly grocery restock`
   * Then proceed: the mutation returns a `ReorderList` whose line count is exactly zero and whose name equals the input name, and the number of lists that customer owns in that channel becomes exactly one — an empty starting state is the normal first call rather than an error path

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant the buyer previously bought is now disabled
   * Given a Returning Buyer previously purchased a variant whose `enabled` flag is now false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53]
   * When that customer executes `createReorderList` with a name they do not already hold
   * Then proceed, with no warning and no audit record: this operation reads no variant at all, because a list is created empty and lines arrive in `STORY-001-01-02`. A disabled variant cannot affect list creation, and its effect on a reorder is evaluated later — at preview time by FEATURE-001-03 and at resolution time by FEATURE-001-04

* Scenario: A price changed since the last purchase — the catalogue price of a previously purchased variant has moved
   * Given the price of a variant the buyer previously purchased has changed since that purchase
   * When that customer executes `createReorderList` with a name they do not already hold
   * Then proceed, with no warning: the `ReorderList` table stores no monetary column, so this story holds no price that could go stale, and a price delta is computed at preview time by FEATURE-001-03 [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.9 Channel Scoping, Language Scoping And Monetary Values]. Copying a price onto a list row would be a defect rather than an optimisation

* Scenario: Concurrent modification or race — two requests create the same list name for the same customer at the same moment
   * Given a Returning Buyer owns no list named `Weekly grocery restock` in the active channel, and two requests carrying that name are in flight together for that customer and that channel
   * When both executions of `createReorderList` reach the write
   * Then block one of the two: exactly one execution returns a `ReorderList` and the other returns `ReorderListNameConflictError`, and the number of lists that customer owns in that channel ends at exactly one more than its starting value. A service-layer pre-check cannot produce that outcome on its own, because both requests may read before either writes; the named unique index `UQ_reorder_list_customer_channel_name_key` is what makes exactly one of them fail [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.4 Named Entities Touched]. **The translation of that failure is narrow and is part of this scenario rather than a separate concern:** the caught exception is matched against that one constraint name and only that name maps to `ReorderListNameConflictError`, every other database error is re-raised as an internal error, and the API-visible message on either path contains no driver text, no SQL fragment and no constraint name — a raw driver message can disclose the schema, the column list and sometimes the conflicting value itself, none of which belongs in a buyer-facing response [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.11 Names, Bounds And Concurrency]. The uniqueness rule is scoped to the owning customer **and** the active channel, so the same name submitted under a second channel token proceeds rather than colliding: it writes a new row carrying the second channel's id, and the count of that customer's rows in the first channel is unchanged.

* Scenario: The named customer is soft-deleted after owning a list — the row outlives the buyer
   * Given a Returning Buyer owns exactly one `ReorderList` named `Weekly grocery restock` in the active channel, and that customer is subsequently soft-deleted, `Customer` being declared soft-deletable [packages/core/src/entity/customer/customer.entity.ts:L28-L29]
   * When `createReorderList` is executed again with that same name, first by a session for the soft-deleted customer and then by a second customer in the same channel
   * Then proceed with an audit-free record of the present state rather than a new behaviour: the soft-deleted customer's row is still present and still carries that `customerId`, so the first execution returns `ReorderListNameConflictError` on the unchanged per-customer-and-channel uniqueness rule, the second customer's execution returns a new `ReorderList` because uniqueness is scoped to the owning customer, and **this story implements no deletion, anonymisation or purge behaviour on either table** — the behaviour itself is settled by ruling R19, which deletes these two tables' rows outright from a bounded job of the plugin's own queue owned by FEATURE-001-07 and arriving in batch B5 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings], and what this story waits on is the period rather than the rule [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]

The two remaining conditional categories are ruled on here rather than dismissed as a pair, and **the channel, currency and language category is ruled on one dimension at a time, which is a correction: an earlier revision of this paragraph declared the whole category inapplicable in a single sentence and left the language dimension unaddressed.** A point-in-time read gone stale between check and commit does not apply, because this operation reads no availability and makes no reservation. Of the three dimensions in the other category: **the channel dimension does apply and is asserted rather than ruled out** — a list created under one `vendure-token` is invisible under a second real token and a name identical to it is therefore free in that second channel, which is the third call of AC-7 [packages/core/src/entity/channel/channel.entity.ts:L62]. **The currency dimension has no surface at all**, because this operation stores, returns and compares no monetary value of any kind, so there is nothing for a currency to qualify. **The language dimension has no surface either, and the absence is asserted rather than claimed**: a list name is a plugin-owned string on the plugin's own table with no translation entity behind it, so the created row's `name` is returned byte-identical under a request that resolves a second `languageCode` [packages/core/src/entity/channel/channel.entity.ts:L74], and section 10 carries that assertion as an obligation so the ruling is tested instead of asserted. The concurrent-modification category, which does apply, was **promoted out of this section into AC-7** rather than dropped, for the reason the note under that criterion gives: while it sat here it fell outside the automation gate, and a duplicate-name race is the one defect in this story that only a concurrent test can find.
