## 1. Story Title

**Grant and revoke a seat's reorder permission, so that a Buying Account Administrator withdraws a colleague's access to a shared list and the colleague's next request is refused.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Grant and revoke seat reorder permission** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table]. The heading above is the same sentence in action-object-outcome form, measured at 177 characters and so inside the 255-character ceiling this tier sets.

What this story delivers is the second half of the grant lifecycle: the `revokeReorderListShare` mutation, the active-to-revoked transition it performs, the re-grant path that returns a revoked row to active without a third mutation, and the three refusal branches that only exist once a grant can stop conferring access — revoked, seat removed from the account, and seat moved to a different account.

**The permission model is this story's subject, and it is the settled one rather than the obvious one.** Both mutations in this feature are gated `@Allow(Permission.Owner)` [packages/core/src/common/permission-definition.ts:L134] and the feature registers no permission definition at all; the control is the service-layer predicate — **ownership of the list plus the active channel for these two owner-only mutations**, and the four-conjunct ownership-or-live-grant form for a read or a cart write reached through a grant [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.9 Figure F6-AUTH — The Ownership-Plus-Share Authorisation Check]. That is not a choice taken here — the epic settles it as rulings R2 and R3 after finding that a custom permission can never be granted to a customer session, and this story consumes the ruling rather than re-arguing it [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory]. What makes the permission model *this* story's work rather than its sibling's is that a predicate evaluated once per request is only observable when something it depends on changes between two requests, and revocation is the change that makes it observable.

Five things that could be mistaken for part of it are not.

- **Creating the grant** is `shareReorderList`, owned by `STORY-001-06-01` together with the `ReorderListShare` table, its additive migration and its **six** named constraints [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§3. - **Reordering from a shared list** is `STORY-001-06-03`, which invokes FEATURE-001-02's cart write as a customer who is not the list's owner. This story reaches no cart and writes no order line.
- **Administering seat membership** is not built anywhere in this epic. Seats are the platform's existing customer-group relation, maintained through an Admin API operation this feature neither owns nor modifies [packages/core/src/api/schema/admin-api/customer-group.api.graphql:L16]. This story *reads* membership on every request and never writes it.
- **Registering a permission definition.** `CrudPermissionDefinition` [packages/core/src/common/permission-definition.ts:L146] and `RwPermissionDefinition` [packages/core/src/common/permission-definition.ts:L245] are both named in section 6, and both are named as the mechanism this story deliberately does not register — the epic's **four** definitions are all administrative and none belongs to this feature.

The class itself is at [packages/core/src/common/permission-definition.ts:L146], and `RwPermissionDefinition` [packages/core/src/common/permission-definition.ts:L245] is the narrower alternative where only a read and a write member are wanted. **This story registers none of it**, for the reason section 5 gives under AC-3.
- **An end-to-end suite exercising exactly this mechanism already ships.** `packages/core/e2e/custom-permissions.e2e-spec.ts` is 192 lines over three blocks — superadmin holds custom permissions automatically [packages/core/e2e/custom-permissions.e2e-spec.ts:L74], custom permissions prevent unauthorised access [packages/core/e2e/custom-permissions.e2e-spec.ts:L106], and adding permissions enables access [packages/core/e2e/custom-permissions.e2e-spec.ts:L147]. - **The gate this story uses is the shipped one for a buyer-owned resource.** Every customer-facing operation in the wishlist example plugin is declared `@Allow(Permission.Owner)` [packages/dev-server/example-plugins/wishlist-plugin/api/wishlist.resolver.ts:L11-L12], and its service resolves the acting customer from the session, refusing a request with no active user [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L74-L76]. The plugin declares its entity, provider and Shop API extension in plugin metadata [packages/dev-server/example-plugins/wishlist-plugin/wishlist.plugin.ts:L9-L16] and mutates configuration from its own configuration function rather than by editing core [packages/dev-server/example-plugins/wishlist-plugin/wishlist.plugin.ts:L17-L26].

**Half two — nothing in this repository revokes one customer's access to another customer's data, because nothing shares customer-owned data between customers at all. That is the new part.** The search above returns no plugin that grants one customer access to another customer's rows, so there is nothing whose withdrawal could be copied: its only hits under those two trees are shared-constant imports. The Shop API schema tree contains no grant surface and no revocation surface of any kind, and no core entity carries a grant, share or delegation column. The closest shipped analogue is single-owner by construction — the wishlist plugin's whole published surface is three operations, `activeCustomerWishlist` declared through `extend type Query` [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L12-L14] with `addToWishlist` and `removeFromWishlist` declared through `extend type Mutation` [packages/dev-server/example-plugins/wishlist-plugin/api/api-extensions.ts:L16-L19] — and its `removeFromWishlist` is the owner deleting their own row, not one party withdrawing another party's access. Its data hangs off one customer through an internal relation custom field [packages/dev-server/example-plugins/wishlist-plugin/wishlist.plugin.ts:L18-L24], a shape that cannot express a second party at all, so it has no access to withdraw.

**So the verdict is `partial` and not `none`, and not `near-identical` either.** The gate, the decorator, the schema-extension idiom and the end-to-end harness are all re-application of shipped work. Concretely new in this story are the revoked state as a persisted condition rather than a deleted row, the per-request re-evaluation that makes a withdrawal bite on the next request rather than at the next sign-in, the removed-seat and moved-seat refusals in which an untouched grant stops conferring access, and the re-grant path that returns a revoked row to active [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.13 Precedent In This Repository — Partial].

**One deliberate departure from the shipped precedent, stated because a reviewer will look for it.** The wishlist plugin's remove operation deletes the row. This story does not delete. Revocation is a state on the share row with `revokedAt` recording when, because a behaviour asserted against a row that no longer exists cannot be asserted at all — the revoked-mid-session case in AC-5 and the support agent's view of a grant that once existed both need the row to survive [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.8 The Grant Lifecycle, And Why Revocation Is A State Rather Than A Delete].

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when the block is pasted into an external tracker. Every story file in this set uses that same convention.

```text
As a Buying Account Administrator,
I want to withdraw a seat's granted capability on a reorder list I own, and to restore it later without creating a second grant,
So that a colleague who has changed role or left the account stops being able to place the account's repeat order on the very next request they make, and no colleague retains a capability the account no longer intends them to hold.
```

### 4.1 INVEST Criteria

- **Independent:** this story is buildable and demonstrable on its own once `STORY-001-06-01` is merged, and it needs nothing from `STORY-001-06-03` or from any story in FEATURE-001-02 through FEATURE-001-08. Its one story-level prerequisite is a grant to revoke, which the intra-feature order already places ahead of it and never behind it [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§4.3 Intra-Feature Story Order]. Where true independence is impossible — a revocation genuinely cannot be demonstrated without a grant — section 8 names the prerequisite and classifies it rather than leaving it implicit.
- **Negotiable:** open to a maintainer are whether a revoked seat's already-materialised cart lines are retained or removed, whether a cap exists on seats per shared list, and the erasure window for a share row, all three recorded as decisions in section 8.1 rather than answered here [tickets/EPIC-001-reorder-and-replenishment.md:§8. Decisions Required Before Build]. **Not negotiable** is that the authorisation decision is re-evaluated per request rather than cached on the session, that the withdrawal introduces no new session mechanism, and that every refusal a caller without visibility can provoke returns one identical result.
- **Valuable:** a grant that cannot be withdrawn is a grant an account administrator has to think twice before making. This story is what makes `STORY-001-06-01` usable in an account whose membership changes, and it is the story that creates the revoked condition `STORY-001-08-03`'s support view distinguishes from an active one [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§4.2 Downstream — One Feature Depends On This One].
- **Estimable:** the shape is one mutation and one service method over a table that already exists, plus the predicate branches that only become reachable once a grant can lapse — which the epic's rubric prices at exactly eight points as a permission model spanning multiple entities, the entities being the share row, the list, the customer and the customer group [tickets/EPIC-001-reorder-and-replenishment.md:§9.1 The Estimation Rubric, So The Numbers Are Reproducible].
- **Sized Appropriately:** eight points on the epic's Fibonacci scale, sitting exactly on the eight-point line-of-code anchor with no upward adjustment, and the scale deliberately omits thirteen so that an oversized story is split instead of estimated [tickets/EPIC-001-reorder-and-replenishment.md:§9.1 The Estimation Rubric, So The Numbers Are Reproducible].
- **Testable:** every criterion in section 5 names one GraphQL operation and asserts a state a test can read — an exact row count for a named pair, an exact stored column value including a null or non-null `revokedAt`, an exact error result type name observed inside the response data rather than as a top-level entry, an exact entry count returned by a named read, or the authenticated identity a request was refused under.

### 4.2 Demonstration Requirement

It turns on identity more sharply than any other story in this feature, so the two customers are named and it is stated at every step which of them is acting. **Customer A is the list owner and performs the revoke. Run that sequence, confirm its two closing checks — `docker compose version` prints a version, and `packages/cli/dist/cli.js` exists — and then continue here.

It destroys and recreates the contents of whichever database the dev configuration selects, so point it at a disposable development database and nothing else.

**Steps 1 and 2 — seed the disposable database, then start server and worker, as one chained subshell.** Read the destructive-setup warning first — **`bun run populate` destroys and recreates the contents of whichever database the dev configuration selects, with no prompt and no dry run** [tickets/EPIC-001-reorder-and-replenishment.md:§11.11.2 Step 1 — A Disposable Database, And What The Seed Does To It] — and point it at a disposable development database and nothing else. Then take the first two seeded customers by identifier ascending, create a group with `createCustomerGroup` [packages/core/src/api/schema/admin-api/customer-group.api.graphql:L8] and add both to it with `addCustomersToGroup` [packages/core/src/api/schema/admin-api/customer-group.api.graphql:L16]. Record the group identifier as `G`; the first address is customer A and the second is customer B. Then authenticate as customer A over the Shop API with the existing `login` mutation [packages/core/src/api/schema/shop-api/shop.api.graphql:L116], create one list with `createReorderList` from `STORY-001-01-01` and record its identifier as `L`, and grant B a capability over it with `shareReorderList` from `STORY-001-06-01`, using `capability` of `APPLY_TO_ORDER`. **Record the grant's own identifier from that call's payload — `grants.items[0].id` — as `GID`**, because it is the key the operation under test takes and the owner-only mutation payload is the only place it is published [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.5 Named API Surfaces — Two New Mutations, Zero Existing Signatures Changed]. > **Every credential in this demonstration is a disposable development fixture and none is a deployment credential.** The administrative pair `superadmin` / `superadmin` and the seeded customer password are created by `bun run populate` in the throwaway database it clears and reseeds. Neither pair is written into a configuration file, a test fixture that outlives this demonstration, or any deployed environment. **The platform's own guard is narrower than it is usually read to be, so it is stated exactly here rather than leaned on as blanket cover.** It compares only the *superadmin password* against the shipped default [packages/common/src/shared-constants.ts:L12] and returns at once when that password differs [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L26-L29]; the default `superadmin` *identifier* is deliberately permitted [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L16-L17]. It **throws only when `NODE_ENV` is `production`** [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L36-L38], returns in silence when it is `test` [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L40-L42], and otherwise only logs a warning [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L44-L45] — the change itself arriving in 3.7.0 [CHANGELOG.md:L33]. Two consequences follow and both are stated rather than assumed. **A deployment that neglects to set `NODE_ENV=production` starts with the default password and a log line**, so the obligation is to set `NODE_ENV=production` *and* to wire `authOptions.superadminCredentials` from environment variables, which is what the guard's own remediation hint directs [packages/core/src/service/helpers/utils/check-superadmin-credentials.ts:L6-L8]. **And the seeded customer password sits outside the guard entirely** — nothing in the platform refuses to start over it — so its containment rests on the throwaway database and on nothing else.

**Step 4 — as customer B, observe that the access exists.** Authenticate as customer B over the Shop API [packages/core/src/api/schema/shop-api/shop.api.graphql:L116] and call `activeCustomerReorderLists` with `includeShared` set to true. **Expected:** exactly one entry, whose `id` equals `L`, whose `viewerAccess.access` is `SHARED` and whose `viewerAccess.grantedCapabilities` is a collection of exactly one member equal to `APPLY_TO_ORDER`. **Leave customer B's session open** — the next step depends on it still being open, because that is what makes the withdrawal observable within a live session.

**Step 5 — as customer A, execute the operation under test.** Substitute `L`, the list identifier recorded at step 2, and `GID`, the grant identifier recorded at step 3. **Both are required arguments of `RevokeReorderListShareInput` and omitting either one is refused by the platform's own non-null validation before the resolver runs, so a call carrying only `grantId` does not reach the service at all — an earlier revision of this step sent exactly that call and would have failed schema validation rather than demonstrating a revocation.** **The list is named because the resolver authorizes the list first and reads the grant only within that list's scope**, which is what keeps a grant identifier from being usable against a list its holder does not own; and **the grant rather than the grantee's address is the key**, because an address cannot address a grant whose holder has left the account or changed their address, and a grant identifier can [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.5 Named API Surfaces — Two New Mutations, Zero Existing Signatures Changed]. Send no `vendure-token` header: the dev configuration sets no default channel token and the seed creates only the default channel, so channel resolution returns it.

```graphql
mutation {
  revokeReorderListShare(input: { reorderListId: "<L>", grantId: "<GID>" }) {
    ... on ReorderListSharePayload {
      reorderList {
        id
        name
        viewerAccess {
          access
          grantedCapabilities
        }
      }
      grants {
        totalItems
        items {
          id
          capability
          state
          revokedAt
        }
      }
    }
    ... on ReorderPermissionDeniedError {
      errorCode
      message
    }
    ... on ReorderListNotFoundError {
      errorCode
      message
    }
  }
}
```

**Expected:** a `ReorderListSharePayload` whose `reorderList.id` equals `L` and whose `reorderList.viewerAccess.access` is `OWNED`, because customer A is the owner and that field reports what the *calling* customer holds [tickets/EPIC-001/FEATURE-001-01-named-reorder-lists.md:§2.6 Named API Surfaces], and whose `grants.totalItems` is exactly 1 with that single item now carrying `state` of `REVOKED` and a non-null `revokedAt` — **the row is still there, which is the whole point of revocation being a state rather than a delete** [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.8 The Grant Lifecycle, And Why Revocation Is A State Rather Than A Delete]. Its `granteeRef` is byte-identical to the value the grant carried before the revocation, which is what lets an owner see that the same seat was revoked rather than a different one.


**Step 6 — as customer B, on the same session opened at step 4 and with no re-authentication, observe that the access is gone.** Reissue the identical `activeCustomerReorderLists` call with `includeShared` set to true. **Expected:** exactly zero entries. That is the whole point of the story: the refusal arrives on B's next request rather than at B's next sign-in, because the ownership-or-valid-share predicate is evaluated per request and holds nothing on the session [packages/core/src/api/config/generate-permissions.ts:L32-L34].

**Step 7 — as customer A, restore the capability without creating a second grant.** Reissue `shareReorderList` for the same pair with `capability` of `APPLY_TO_ORDER`. **Expected:** success, and exactly one `ReorderListShare` row for the pair of `L` and B with `state` back to `ACTIVE` and `revokedAt` back to null — one row, not two, the guarantee resting on the composite unique key `UQ_reorder_list_share_list_grantee` that `STORY-001-06-01` declares [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.3 Named Entities Touched]. Reissuing B's read from step 6 then returns exactly one entry again.

**No dashboard extension is opened at any point**, and the administrative credential appears at step 3 for one purpose only — creating the seat set that no Shop API surface can create.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract, and each states which customer is authenticated, whether that customer owns the list or holds a grant on it, the channel token the request carries and the `languageCode` it resolves under. The five required coverage classes map onto them as follows: valid input is AC-1, invalid or incomplete input is AC-2, an error naming the exact type returned is AC-3 and AC-4, an edge case is AC-5 and AC-6, and the assertion that an existing operation is unchanged is AC-8.

**AC-3 and AC-4 together are the mandatory negative criterion, split into its two terminal branches so that a failure names one branch rather than two.** AC-3 is the caller with no relationship to the list at all, refused with the normalized result; AC-4 is the caller holding a live grant attempting an operation reserved to the list's owner, refused with the one error result this feature declares. **AC-5 is the mandatory revoked-mid-session criterion** and AC-6 is its sibling for a grant that was never revoked and stops conferring access anyway. **AC-7 is the single criterion permitted to name `shareReorderList`**, because the re-grant path re-invokes the existing grant mutation rather than introducing a third one.

**Four properties of the operation are stated once here rather than repeated in every criterion.**

- **Naming convention used throughout.** Customer **A** owns list **L** and is the only party that may revoke a grant on it. Customer **B** is the grantee seat whose capability is withdrawn. Customer **C** is a third customer who neither owns `L` nor holds a grant on it. Group **G** is the customer group all seats of the account belong to, and **G2** is a second, different account's group. **T** is the channel token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L58-L59] and stored as a unique column on the channel it identifies [packages/core/src/entity/channel/channel.entity.ts:L62]; **T2** is a second channel's token. Unless a criterion says otherwise the request resolves its `languageCode` from the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74], which is `en` [packages/core/src/api/schema/common/language-code.graphql:L72] in the fixture.
- **The revoke is a state transition and never a delete.** `state` moves from `ACTIVE` to `REVOKED` and `revokedAt` records when, so the row survives and every criterion below asserts a row count together with the column values on that row [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.8 The Grant Lifecycle, And Why Revocation Is A State Rather Than A Delete].
- **`revokeReorderListShare` is a single synchronous write.** It enqueues no job, publishes no event and schedules no task, so no criterion below names an asynchronous trigger or an observable completion signal. Event publication in this domain belongs to `STORY-001-07-02`.
- **`ReorderPermissionDeniedError` is returned inside `data` as a member of the operation's result union, and is not a thrown error.** That distinction is asserted rather than assumed, because the two are observed in different places: a thrown `ForbiddenError` [packages/core/src/common/error/errors.ts:L67] or `UserInputError` [packages/core/src/common/error/errors.ts:L27] surfaces as a top-level GraphQL error entry with no `revokeReorderListShare` payload — which is how the shipped precedent reports a variant it cannot resolve [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L38] — whereas every criterion below asserts a **returned** union member, reachable through an inline fragment on the payload. A criterion satisfied by a top-level error entry has not been satisfied.

**A note on AC-3, which is the ruling this whole story rests on and the reason a permission gate is not the control.** The platform states the caveat in its own source: ownership must be enforced by custom logic inside the resolver, and because ownership cannot be defined generally nor statically encoded at build time, any resolver using `Permission.Owner` **must** include logic enforcing that only the owner of the resource has access — and without that logic the effect is the equivalent of using `Permission.Public` [packages/core/src/api/config/generate-permissions.ts:L32-L34], the whole caveat being written out in one block in that file [packages/core/src/api/config/generate-permissions.ts:L12-L33]. **A permission gate alone is not a control.** Two independent reads confirm it rather than restate it: `Permission.Owner` is declared with `assignable: false` [packages/core/src/common/constants.ts:L30] and `internal: true` [packages/core/src/common/constants.ts:L31] on the definition at [packages/core/src/common/constants.ts:L28], so no deployment configuration can make ownership hold; and the guard sets its owner-only flag precisely when the session does **not** hold the listed permission [packages/core/src/service/helpers/request-context/request-context.service.ts:L109], which the access-control strategy then admits [packages/core/src/config/auth/default-entity-access-control-strategy.ts:L56]. So the gate refuses essentially nobody, and `revokeReorderListShare` performs an explicit ownership check of its own. **A `CrudPermissionDefinition` gate [packages/core/src/common/permission-definition.ts:L146] is not the alternative:** the Customer Role is created holding one permission [packages/core/src/service/services/role.service.ts:L433-L444] and cannot be amended, the update path throwing when asked to modify it [packages/core/src/service/services/role.service.ts:L290-L291], so a registered permission would refuse every buyer instead. **And the refusal is `ReorderListNotFoundError` rather than `ReorderPermissionDeniedError`, deliberately**, which is the normalization the parent feature requires for every case in which a caller cannot see a list; the platform's own single-order read makes the same choice and its inline comment names enumeration as the reason [packages/core/src/api/resolvers/shop/shop-order.resolver.ts:L141-L143].

## 7. Edge Cases

Five scenarios, which is the maximum this tier permits, and the five categories this feature requires are covered one apiece in the order below. Two of the five resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure this operation cannot have: withdrawing a capability evaluates neither availability nor price, so the two catalogue-movement categories are genuine non-events here, and the value of recording them is precisely that a reader does not go looking for a check that would be wrong to build.

* Scenario: Zero, null or empty collection — the list has no grants to withdraw, and then the last remaining grant is withdrawn
   * Given customer A owns list L in the channel identified by token T, A is a current member of group G in T's channel, and in the first run L holds exactly zero `ReorderListShare` rows of any state while in the second run L holds exactly one, an `ACTIVE` grant to customer B
   * When customer A executes `revokeReorderListShare` in each run — in the first run with a `grantId` matching no row, since L has no grant to name, and in the second with the `grantId` of L's one active grant
   * Then proceed in both runs rather than blocking either: the first run returns `ReorderListSharePayload` whose `grants.totalItems` is exactly 0 and writes nothing, leaving the count of `ReorderListShare` rows for L at exactly 0 and `activeGrantCount` at 0, because there is nothing to transition and the owner is entitled to see the empty grant set rather than an error; the second run returns the payload with `grants.totalItems` of exactly 1 and leaves exactly 1 row for L, now carrying `state` of `REVOKED` and a non-null `revokedAt`, with `activeGrantCount` back to 0, so **withdrawing the last grant empties the set of effective grants without emptying the table** and the list is left with zero active grants and one historical row. A list with zero active grants is a list only its owner can reach, which is the state FEATURE-001-01 shipped it in

* Scenario: An item unavailable, deleted or disabled since the last purchase — the shared list holds a variant that is now disabled
   * Given customer A owns list L in T's channel, one of L's lines references a product variant whose enabled flag is now false, one `ACTIVE` `ReorderListShare` row exists for the pair of L and B, and A and B are current members of group G in T's channel
   * When customer A executes `revokeReorderListShare` with the `grantId` of B's grant on L
   * Then proceed, with no warning and no audit record: **revocation is independent of variant state and evaluates no availability at all.** This operation reads no variant, no stock level and no catalogue state, so a disabled variant cannot affect the transition and the row moves to `REVOKED` exactly as it would for a list of fully enabled variants. Variant state is evaluated elsewhere and later — at preview time by FEATURE-001-03 and at resolution time by FEATURE-001-04 — and a revocation that pre-checked availability would be reading catalogue state to answer an authorisation question

* Scenario: A price changed since the last purchase — the catalogue price of a variant on the shared list has moved
   * Given the price of a variant on list L has changed since customer A last purchased it, A owns L in T's channel, and one `ACTIVE` `ReorderListShare` row exists for the pair of L and B
   * When customer A executes `revokeReorderListShare` with the `grantId` of B's grant on L
   * Then proceed, with no warning: **a `ReorderListShare` row stores no price and no reservation, so no monetary value in it can go stale and none is rewritten by the transition.** Where a price does surface to a grantee before the withdrawal — reading L's lines, or receiving the cart that `STORY-001-06-03` produces — it is an integer in the smallest unit of its currency stated alongside the currency code, which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]; a grant of a list whose line prices total 129900 in the currency code that channel declares carries neither that integer nor any part of it, before or after revocation. A decimal monetary value anywhere in this story is a defect rather than a formatting preference

* Scenario: Concurrent modification or race — a seat holding a live authenticated session has its grant withdrawn mid-session, and two withdrawals of the same grant are issued together
   * Given customer B holds an open, unexpired session established before any withdrawal and holds one `ACTIVE` `ReorderListShare` row with `capability` of `APPLY_TO_ORDER` on list L, which customer A owns in the channel identified by token T, and B has already issued one successful read on that session which returned exactly 1 entry for L
   * When customer A executes `revokeReorderListShare` with the `grantId` of B's grant while B's session is still open — and, in the second half of this scenario, two such executions carrying that same `grantId` are in flight together — after which customer B reissues its read on that same session
   * Then block B and converge A: **B's very next request on the live session is refused** — reissuing `activeCustomerReorderLists` with `includeShared` set to true returns exactly 0 entries where it previously returned 1, and that count is the named observable signal by which the refusal is detected, requiring no re-authentication, no session invalidation and no new session mechanism; the refusal arrives on the next request rather than at the next sign-in because the predicate is re-evaluated per request and caches nothing on the session, which is the direct consequence of ownership being resolvable neither generically nor at build time [packages/core/src/api/config/generate-permissions.ts:L32-L34]. For the two barrier-released withdrawals, both report success, exactly one `ReorderListShare` row exists for the pair afterwards with `state` of `REVOKED`, and neither caller receives a conflict; the guarantee is the composite unique key over the list and the grantee rather than a service-level pre-check, so this half runs against a real database engine and not a repository test double [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.3 Named Entities Touched]. A barrier-released withdrawal and re-grant settle on that one row in one of the two states and never on two rows

* Scenario: Channel, currency or language mismatch — a grant made under one channel token is withdrawn under another, and the withdrawal leaves no residual access
   * Given customer A owns list L in the channel identified by token T, one `ACTIVE` `ReorderListShare` row exists for the pair of L and B in that channel, a second channel identified by token T2 exists, and both A and B are assigned to both channels
   * When customer A executes `revokeReorderListShare` with the `grantId` of B's grant on L while sending T2 in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L58-L59], and then executes the same mutation under T, after which customer B reads L under each token in turn
   * Then block the first and proceed with the second: **a grant granted under one channel token confers no access under another** [packages/core/src/entity/channel/channel.entity.ts:L62], so A's call under T2 returns `ReorderListNotFoundError` because L belongs to T's channel and not to T2's, and the row count for the pair is unchanged with `state` still `ACTIVE`; A's call under T succeeds and moves that one row to `REVOKED`; and B's reads afterwards return exactly 0 entries under T and exactly 0 entries under T2, so **withdrawing under channel token T leaves no residual access under channel token T2** — there was none to leave, because the grant was only ever effective in T's channel. The name customer B saw for L before the withdrawal was read under the request's `languageCode`, which defaults to the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74] and is `en` [packages/core/src/api/schema/common/language-code.graphql:L72] in the fixture; a capability is an enumerated member carrying no prose to translate, so no part of this transition varies by language code. Any price a grantee saw follows the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] as an integer in the smallest unit, and whether it included tax follows that channel too [packages/core/src/entity/channel/channel.entity.ts:L113]

The remaining conditional category does not apply and is not force-fitted. **A point-in-time read gone stale between check and commit** is not a case this story has: `revokeReorderListShare` reads no availability and makes no reservation, so it holds nothing that can expire between a check and a write. The authorisation decision it invalidates *is* point-in-time, but that is the opposite class of problem — the decision going stale is the intended effect of this story rather than a hazard in it, which is exactly why the revoked-mid-session behaviour is assertable at all [tickets/EPIC-001/FEATURE-001-06-buying-account-list-sharing.md:§2.8 The Grant Lifecycle, And Why Revocation Is A State Rather Than A Delete].
