### 4.2 Demonstration Path

One path, concrete, and observable to a non-coder as one named operation with its input and its expected response, followed by the same set rendered on a dashboard page. **"Via the API" would not be a demonstration, and is not what is written below.** Each command carries its own working directory — as a subshell, or as a function that resolves the repository root itself — so the steps can be pasted in sequence, and the terminals are numbered because Terminal 1 stays occupied for as long as the demonstration lasts, so every step after it is issued from a second one.

**Before step 1 — the shared demonstration prerequisite, referenced rather than restated.** The toolchain check, `bun install --frozen-lockfile`, `bun run build` and the database container are the epic's verified demonstration prerequisite, stated once for all twenty-five stories [tickets/EPIC-001-reorder-and-replenishment.md:§7.9.1 The Verified Demonstration Prerequisite]. **Not one step below runs on a clean checkout without it.** The read-only, fail-closed preflight is the epic's canonical function and is not restated here [tickets/EPIC-001-reorder-and-replenishment.md:§11.11.1 Step 0 — Preflight, Read-Only, Fail-Closed, And Safe To Paste Into A Live Shell].

**Step 1 — clear the stale dashboard build, because this story is the first in its feature to render one. The command is written fail-closed: it resolves the repository root, verifies the checkout is this monorepo, deletes only the one generated directory and refuses to run at all outside a checkout.** Vite does not remove old hashed files, so artefacts accumulate under the dev-server distribution directory and the handbook's instruction to clear them is unconditional [AGENTS.md:L51]. **Under the live-Vite mode this demonstration uses, clearing them is what makes a Vite failure visible rather than what makes a build clean:** the dashboard plugin serves that directory only when nothing is listening on the development port, so an empty directory turns a Vite process that failed to start into a missing page instead of a silently stale one.

**This is the only recursive deletion any demonstration path in this set asks a reader to run, and it is written as a guarded function rather than as a bare command.** A bare `rm -rf packages/dev-server/dist` is resolved against the reader's current directory, so pasted one directory too deep it removes nothing and reports success, and pasted inside a different checkout it removes that checkout's bundle instead — and neither outcome is visible in the output. It would also follow a symlink at the target and delete that link's contents. The block below therefore resolves the repository root with git, compares the resolved parent against the expected path, refuses a symlink and refuses a target that is not a directory, and confirms the removal afterwards; and it is a **function returning a status rather than a script calling `exit`**, so pasting it into a live terminal cannot close that terminal — the same convention the epic's preflight follows [tickets/EPIC-001-reorder-and-replenishment.md:§11.11.1 Step 0 — Preflight, Read-Only, Fail-Closed, And Safe To Paste Into A Live Shell].

```bash
# Terminal 1, before the server is started, and it may be pasted from anywhere inside the
# checkout. The target is resolved from the repository root rather than from the current
# directory, so no working directory a reader is sitting in can redirect the deletion; and the
# resolved path is compared, and refused if it is a symlink or is not the expected directory,
# before anything is removed.
reorder_clear_dashboard_bundle() {
    root=$(git rev-parse --show-toplevel) || {
        echo 'CLEAR FAILED: not inside a git checkout, so the repository root cannot be resolved.'
        return 1
    }
    root=$(cd "$root" && pwd -P) || return 1
    parent=$root/packages/dev-server
    if [ ! -d "$parent" ] || [ -L "$parent" ]; then
        echo "CLEAR FAILED: $parent is not a directory in this checkout."
        return 1
    fi
    resolved_parent=$(cd "$parent" && pwd -P) || return 1
    if [ "$resolved_parent" != "$root/packages/dev-server" ]; then
        echo "CLEAR FAILED: packages/dev-server resolves to $resolved_parent, outside this checkout."
        return 1
    fi
    target=$resolved_parent/dist
    if [ -L "$target" ]; then
        echo "CLEAR FAILED: $target is a symlink; refusing to delete through it."
        return 1
    fi
    if [ ! -e "$target" ]; then
        echo "CLEAR OK: $target is already absent; nothing was removed."
        return 0
    fi
    if [ ! -d "$target" ]; then
        echo "CLEAR FAILED: $target exists and is not a directory; refusing to remove it."
        return 1
    fi
    rm -rf -- "$target" || {
        echo "CLEAR FAILED: rm reported an error on $target."
        return 1
    }
    if [ -e "$target" ]; then
        echo "CLEAR FAILED: $target still exists after the removal."
        return 1
    fi
    echo "CLEAR OK: removed $target"
}

reorder_clear_dashboard_bundle
```

**Expected:** one line beginning `CLEAR OK` naming the absolute path it removed, or naming it as already absent on a checkout that has not built the dashboard yet. Any line beginning `CLEAR FAILED` stops the demonstration here rather than being read past, because the directory this step is responsible for is the one the dashboard plugin falls back to serving, and step 7 depends on it being empty so that a page it does not serve cannot appear as though it did.

The same handbook paragraph names the second trap worth checking before anything else: a stale Vite development server already listening on port 5173, which the dashboard plugin proxies to in preference to serving the built files [AGENTS.md:L51]. **Read that sentence as the fork it is, because the two ways of reaching a dashboard page are different addresses and mixing them is what makes a runbook unfollowable.** Either a Vite development server is listening on 5173 and *it* serves the dashboard, or none is and the dashboard plugin serves the built bundle from the distribution directory under its own route on the API server [packages/dev-server/dev-config.ts:L202-L204]. **This demonstration takes the FIRST of those two and only the first: the `dev` script of steps 2 and 3 leaves a Vite development server listening on 5173, nothing further is built, and every dashboard address in this file is `http://localhost:5173/dashboard/…`.** Step 7 names the built-bundle mode as the alternative it is not using. **Two earlier revisions of this paragraph are withdrawn and both failed in the same way — by naming one mode here and the other in step 7.** The first built a bundle and then opened the Vite port, which is the one address that mode does not serve. The second declared the built-bundle mode here and on port 3000, while step 7 declared the live-Vite server the default and issued no build command at all, so the runbook required both exclusive modes at once and carried two `Navigate to` addresses for one step.

### 4.3 The Curation Contract, And The Five Boundaries Around It

The parent feature publishes the exact Admin schema so that no story has to invent an argument, a payload or an error [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces]. This sub-section restates only what section 5 asserts on, and adds nothing to that contract.

- **Two operations and no third.** `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions): SubstitutionCandidateList!` is the paginated read, and `setSubstitutionCandidates(input: SetSubstitutionCandidatesInput!): SubstitutionCandidateSet!` is the write. Both are new and additive on the Admin API, and no existing operation on either API changes shape.
- **The origin is a required argument, and the filter and sort inputs are generated.** These are different things and conflating them is the error worth naming. The origin argument is what makes a page's order meaningful, because `position` is unique per channel-and-origin pair, so a page interleaving origins would interleave independent orderings. Everything else — the sort parameter, the filter parameter and the pagination parameters — is injected by the platform's own generator for any query field returning a paginated list type, which is what its own documentation states [packages/core/src/api/config/generate-list-options.ts:L31-L33] and what the function does [packages/core/src/api/config/generate-list-options.ts:L34]. **`SubstitutionCandidateListOptions` is therefore declared as an empty run-time-generated stub and never hand-written**, exactly as the shipped precedent declares its own [packages/dev-server/test-plugins/reviews/api/api-extensions.ts:L44-L45]. Hand-writing a filter or a sort input for this read is a defect and not a style choice.
- **The write replaces the whole set for one origin, atomically, and the submitted array is the ordering.** `position` is deliberately absent from the input: the service assigns it from the array index, which makes its contiguity and its uniqueness true by construction rather than by validation. The replacement is a delete-then-insert inside one transaction, the resolver carrying the platform's own decorator [packages/core/src/api/decorators/transaction.decorator.ts:L81] as the shipped precedent's administrative write does [packages/dev-server/test-plugins/reviews/api/product-review-admin.resolver.ts:L68] — **declared at `SERIALIZABLE`, passed as that decorator's second argument [packages/core/src/api/decorators/transaction.decorator.ts:L59-L62] from the set that includes it [packages/core/src/api/decorators/transaction.decorator.ts:L45-L50], because atomicity alone does not stop two curators interleaving their deletes and inserts into a set neither of them submitted [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces — Zero New Buyer-Facing Operations, Two New Admin Operations]**. The permitted end states of two concurrent replacements are exactly two: one submission entire, or the other entire. **An empty `candidates` array is the stated clearing operation** rather than an error, and section 7's first scenario asserts it.
- **A permission gate alone is not an access control in this platform, and that is a published caveat rather than an opinion held here.** The platform's own documentation for ownership-scoped access states that ownership cannot be defined generally nor statically encoded at build time, so a resolver relying on it must include logic to enforce access or it is the equivalent of publishing the data [packages/core/src/api/config/generate-permissions.ts:L32-L34]. The principle carries across: both operations sit behind `RwPermissionDefinition('ReorderSubstitution')` [packages/core/src/common/permission-definition.ts:L245] — the read on `ReadReorderSubstitution` and the write on `WriteReorderSubstitution`, registered through `authOptions.customPermissions` — and **the channel predicate is enforced inside the service on every read and every write**, because the gate only decides who may ask. A definition publishing two members is used rather than one publishing four [packages/core/src/common/permission-definition.ts:L146], since this story has exactly two verbs and two of the four would gate nothing while still appearing in the published enum for every deployment.
- **Curation is per channel, and a candidate curated under one channel token does not surface under another.** This is the one scoping rule a naive implementation would omit: a mapping keyed only on the pair of variants would leak one marketplace channel's curation into every other channel on the deployment. A cross-channel read returning another channel's rows is a defect and not a convenience [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.11 Channel Scoping, Language Scoping And Monetary Values].

**One thing this sub-section deliberately does not state is a number.** The submitted array is bounded by one configured maximum, `ReorderPluginOptions.maxSubstitutionCandidatesPerVariant`, and an array exceeding it is refused with the platform's input error naming the maximum rather than truncated — a truncating replace would silently delete curation the caller believed it had saved. **The value of that maximum is the epic's tenth product decision and remains open** [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions], so this story names no figure for it and asserts the boundary behaviour against whatever value its fixture configures. **There is likewise no relevance target, no candidate-count target and no adoption target anywhere in this story, because this repository declares none** [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value]. Refusing to invent a value is not the same as having no bound, and both halves of that sentence are load-bearing.

### 4.4 The Page Contract — How The Curator Reaches The Page, What It Loads, And What It Refuses To Save

**Why this sub-section exists.** Section 4.3 fixes the two operations; it says nothing about the surface that calls them, and a curation page has three ways of losing a curator's work that no operation contract can prevent: it can save a subset it happens to have on screen, it can save under a channel the curator has since left, and it can overwrite a colleague's set without either of them being told. Each is settled below as a stated behaviour, and each is carried into section 5, section 6's dashboard line and section 10 rather than left as page-level detail.

**What this sub-section is not.** **No design system, component-library version, style guide or design source is named anywhere in this ticket set, and none was supplied to this project** — an absence stated here rather than quietly filled in, following the convention this epic applies to every other absence it found [tickets/EPIC-001-reorder-and-replenishment.md:§11.8 Tooling Findings, Including The Absences]. So **nothing below states a pixel value, a colour, a font, a spacing figure or a contrast ratio** — inventing one would be inventing a specification. Every obligation below is instead a *behaviour* expressed against a dashboard building block that verifiably exists in this checkout and is cited, in the same way the shipped precedent composes its own list surface from published blocks [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9].

#### 4.4.1 Identity And Arrival — The Page Knows Which Origin It Is Curating Because The Route Says So

- **One route, one page identity, one navigation entry.** The extension declares a single dashboard route at the path `/substitution-candidates`, a stable `pageId` on the page it renders — the framework's list page taking that identity as a declared property [packages/dashboard/src/lib/framework/page/list-page.tsx:L48] — and one navigation entry pointing at that route, both declared in the plugin's own dashboard entry as the shipped precedent declares its own [packages/dev-server/test-plugins/reviews/reviews-plugin.ts:L34]. **No second route and no second navigation entry is registered by this story.** The `pageId` is what lets a curator's column-visibility preference persist for this page rather than leaking between pages, the framework keying its default visibility per page [packages/dashboard/src/lib/framework/page/list-page.tsx:L286-L288].
- **The origin identifier lives in the route, not in component state, and this is the defect the earlier revision carried.** An earlier revision of this file described a page listing "the curated candidates for one origin variant" without saying how the page learned which origin that was, which is not implementable. **The origin is a route search parameter**, so the page is deep-linkable, reloadable and shareable, the browser's back and forward actions move between origins, and a reload does not silently return an empty page. When the parameter is absent the page renders its origin selector and no candidate list; when it names an identifier that resolves to no variant in the requesting channel, the page renders the not-found state named in 4.4.4 rather than an empty curated set, because "no such variant" and "no candidates yet" are different facts and a curator must not read one as the other.
- **Two selectors, one existing query behind both — and that query carries an existing permission requirement this story must state.** The origin selector and the add-a-candidate selector are both variant pickers, and both read the platform's existing Admin catalogue list operation `productVariants(options: ProductVariantListOptions)` [packages/core/src/api/schema/admin-api/product.api.graphql:L7] — the very same document the shipped variant picker already issues, returning each variant's identifier, `name` and `sku` [packages/dashboard/src/lib/components/shared/product-variant-selector.tsx:L20-L30]. **No new read operation is added for either selector**, which is why section 1.1's "exactly two operations" count still holds. **A curator's role must therefore hold `Permission.ReadCatalog` [packages/core/src/common/constants.ts:L64] in addition to the two members this story registers, and that is a hard prerequisite rather than a recommendation:** it is the platform's own gate on that operation, so a role holding only `ReadReorderSubstitution` and `WriteReorderSubstitution` reaches this page and finds both pickers refused, which is a broken surface rather than a degraded one. **An earlier revision of this section named no baseline permission at all**, leaving a reader to infer either that the pickers needed none or that the reorder members somehow covered them. Requiring an existing member grows the published `Permission` enum by nothing, and `ReadCatalog` is the narrowest existing member that admits this read — the shipped dashboard precedent gates its own administrative list on exactly it [packages/dev-server/test-plugins/reviews/api/product-review-admin.resolver.ts:L35]. Selecting an origin writes the route parameter; selecting a candidate appends to the draft array and writes nothing to the server until the curator saves.
- **The selectors show `sku` beside `name`, and that is a correctness requirement rather than a nicety.** Two variants of one product commonly share a translated name, so a name-only picker cannot be used to choose between them; the `sku` disambiguates, and the existing picker already reads it [packages/dashboard/src/lib/components/shared/product-variant-selector.tsx:L20-L30].

#### 4.4.2 The Save Is Whole-Set, So The Page Must Hold The Whole Set — Otherwise It Deletes What It Never Loaded

**This is the highest-consequence rule on the page, and it follows from section 4.3 rather than from taste.** The write replaces the entire curated set for one origin; a page that submits the rows it currently has on screen therefore *deletes every row it does not have on screen*. A filtered view, a second page of results, or a still-loading list each produce exactly that outcome, silently and with a success response.

- **The complete set for the selected origin is loaded before the save control is operable, and the page bound that makes that possible is the DASHBOARD's rather than the platform's. This is a correction.** An earlier revision argued completeness from `ReorderPluginOptions.maxSubstitutionCandidatesPerVariant` [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces] being at or below the configured administrative page maximum, whose default is one thousand [packages/core/src/config/vendure-config.ts:L159]. **That is not the limit this page meets.** The dashboard's paginated table always sends a `take` and sends `Math.min(itemsPerPage, 100)` [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L481], with `skip` derived from the current page [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L482] — so **no single request from that primitive can return more than one hundred rows**, and an argument from the thousand-row server limit would have licensed a save composed from the first page of a larger set. **What holds instead:** the candidate maximum is validated at plugin initialisation against one hundred as well as against its finite-integer rule, so the configured bound can never exceed what one request can fetch [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces], the read is scoped to one origin by a required argument, and the page **proves** completeness rather than assuming it by comparing the number of loaded items against the `totalItems` the same response carries.
- **The save control is disabled, with a stated reason rendered beside it, in FIVE cases and not three.** Whenever the loaded item count does not equal `totalItems`; whenever a filter or a search term is applied to the candidate list; whenever the read is in flight or has errored; **whenever any sort other than ascending `position` is applied**; and **whenever more than one page has been visited without the set having been re-read whole**. A disabled control with no explanation is its own defect, so the reason is displayed rather than implied.
- **The `position ASC` guard is not a duplicate of the completeness guard, and it is the one an earlier revision omitted entirely.** The read publishes a generated options input whose sort parameter is derived from every scalar field on the row type [packages/core/src/api/config/generate-list-options.ts:L130], so a curator can legitimately sort the table by `createdAt`, by `candidateProductVariantId` or by any other scalar. **The submitted array IS the curated ordering** — the service assigns `position` from the array index — so saving while an alternate sort is applied would persist that sort as the curation, and the response would confirm it as a success because it returns the set that was actually stored. **The failure is undetectable from the response**, which is precisely why the guard lives on the surface and is asserted there rather than being left to the write's validation, which cannot know what order the curator meant.
- **A paged or filtered subset is never submitted.** If a curator wishes to work with a filter or an alternate sort, clearing it is the precondition for saving; the page does not merge a filtered or re-sorted view back into an unfiltered set, because a merge would need an ordering the curator never expressed.
- **The submitted array is the ordering, and the array is the whole array.** The page sends every loaded row in its on-screen order, and never a delta, because the operation takes no delta.

#### 4.4.3 The Draft Is Bound To One Channel, And A Channel Switch Discards It Rather Than Retargeting It

**The mechanism that makes this necessary is shipped and cited.** Every dashboard request reads the selected channel token from local storage at request time and sends it as the scoping header [packages/dashboard/src/lib/graphql/api.ts:L22] and [packages/dashboard/src/lib/graphql/api.ts:L29-L30]; switching channel rewrites that stored token and invalidates the query cache [packages/dashboard/src/lib/providers/channel-provider.tsx:L177-L193]. **Invalidating queries does not reset a component's local draft.** So without the rule below, a curator who assembles a set under channel A, switches to channel B and presses save sends channel A's array under channel B's token — and section 4.3's channel rule makes that a write into B's curation, which AC-4 asserts must not happen.

- **The draft records the `channelId` the curated set was loaded under**, taken from the read's own response rather than from a client-side guess, every published row and payload in this story carrying that field [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces].
- **On a channel switch with a dirty draft the curator is asked before anything is lost, using the platform's own dirty-navigation block** [packages/dashboard/src/lib/components/shared/navigation-confirmation.tsx:L20-L23]; on confirmation the draft is **discarded and the set is re-read under the new channel**, never retargeted. On a channel switch with a clean draft the page simply re-reads.
- **The save refuses a mismatch on both sides.** The page will not issue a write whose draft `channelId` differs from the channel the header now carries, and the service enforces the same scope independently, because a client-side check is a convenience and the server-side predicate is the control [packages/core/src/api/config/generate-permissions.ts:L32-L34].

#### 4.4.4 Every State The Page Can Be In, Named — Including The Two That Are Failures

Each state below maps onto a mechanism the dashboard already has, so none of this is new machinery.

- **Loading and refetching.** The list renders the loading state the data table already takes as a property [packages/dashboard/src/lib/components/data-table/data-table.tsx:L142], which the shipped paginated list wires from its own fetching flag [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L506]; a refetch is triggerable from the refresh control the same table renders [packages/dashboard/src/lib/components/data-table/data-table.tsx:L452]. **A refetch shows the previous rows while it runs and never blanks the table**, which is what the application-wide query default provides [packages/dashboard/src/app/app-providers.tsx:L12-L19] — and it is safe here precisely because the query is keyed on the origin and the channel, so any previous data belongs to the same subject.
- **Empty.** Zero curated rows for a resolvable origin renders the table's own empty state [packages/dashboard/src/lib/components/data-table/data-table.tsx:L588] with the origin still named at the top of the page and the add-a-candidate selector still operable — never an error, because section 7's first scenario fixes zero rows as a valid answer.
- **Not found.** An origin parameter naming no variant resolvable in the requesting channel renders a distinct not-found state carrying the origin selector, so the curator can choose again without editing a URL.
- **Read failure.** A failed read renders a retry affordance and the safe message of 4.4.6, and **does not** render an empty table, because "the read failed" and "nothing is curated" must not look alike on a page whose save deletes what it did not load.
- **Permission denial, in two distinct shapes, because a role can be refused on this story's own operations or on the platform's catalogue read and the page must not confuse the two.** A curator holding neither published member sees the page's own explanatory denial rather than a blank region. **A curator holding both published members but not `Permission.ReadCatalog` [packages/core/src/common/constants.ts:L64] sees the curated set normally and sees each variant picker rendered in its own explanatory denied state**, naming the missing catalogue capability, because the pickers read the platform's own operation rather than this story's — a state an earlier revision of this section did not define at all, leaving a role the runbook declared complete to produce two silently empty pickers. The platform's guard renders nothing at all when a permission is absent [packages/dashboard/src/lib/components/shared/permission-guard.tsx:L44-L49], which is right for hiding a button and wrong for a whole page, so the guard is used for the save control and an explicit denial state is rendered for the page body. **Neither is an access control:** both operations are gated server-side and the channel predicate is enforced in the service.
- **Saving.** While a save is in flight the save control and the reorder, add and remove affordances are all inoperable, so a second submission cannot be issued from the same draft.
- **Save succeeded.** The page renders the set **the response returned**, not the draft it sent, and reports success. This matters for 4.4.5 and for the empty case, where the write's own payload carries the resulting set [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces].
- **Save failed.** The draft is **kept, not discarded**, the offending identifiers the service named are shown against the rows they belong to, and the save remains retryable — because a refused write left the previously curated ordering intact, which is exactly what AC-3 asserts.
- **Unsaved changes.** A dirty draft blocks navigation away through the platform's own confirmation [packages/dashboard/src/lib/components/shared/navigation-confirmation.tsx:L20-L23].

#### 4.4.5 Two Curators, One Origin — Last Writer Wins, Chosen Explicitly And Tested

**The choice is stated rather than left to the implementation, because "whole-set replacement" plus "no concurrency rule" is a lost update.** Two curators loading the same origin's set, each adding a different candidate, each saving: the second save replaces the first's work in full and the first curator is never told.

- **The rule is last-writer-wins, adopted deliberately.** No version column, no `updatedAt` precondition and no conflict dialogue is introduced. The grounds are that the write is already a single atomic delete-then-insert inside one transaction [packages/core/src/api/decorators/transaction.decorator.ts:L81] so the database is never left in a mixed state; that this story adds no column to a table it does not own [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.5 Named Entities Touched], which rules out a version column; and that curation is a low-contention administrative act on rows scoped to one origin in one channel.
- **What is *not* accepted is the silent part.** Because the page renders the set the response returned rather than the draft it sent, **a curator whose save is followed by a colleague's sees the colleague's set on their next read rather than a stale copy of their own**, and a curator who reorders on top of a set that has since changed is working from what the server last returned.
- **It is asserted rather than asserted-to-be-unlikely.** Section 10 requires a test in which two sessions load one origin's set, both submit a three-element array, and the persisted set afterwards holds exactly three rows equal element for element to the array of the later call, with no duplicate row and no merged fourth row — which is the concurrency behaviour AC-1's idempotence half cannot show, because that half submits the same array twice.

#### 4.4.6 Error Content — What A Curator Is Shown When Something Fails, And What Is Never Shown

**The reason this is a rule and not a preference is that the shipped default is the other way.** The platform's own detail page surfaces a caught error's message directly into a notification [packages/dashboard/src/lib/framework/page/detail-page.tsx:L166-L170], and the same pattern appears elsewhere in the dashboard — copying it here would put whatever a resolver, a driver or a proxy produced onto a curator's screen.

- **Every failure this page renders shows a translated, page-authored explanation naming the operation that failed and the retry available**, drawn from the extension's own catalogues, and **never a raw exception message, a stack frame, a driver error, a SQL fragment, an internal identifier or a file path.**
- **The one class of server-supplied VALUE that is rendered is the offending identifier list the write's validation returns, and it is read from a named structured field rather than parsed out of a message. This is a correction.** An earlier revision of this bullet called it "server-supplied text" and named no field, while the only failure mode the parent feature then defined was a bare thrown `UserInputError` carrying a message and a code and no identifier at all [packages/core/src/common/error/errors.ts:L27-L31] — so the row-level display this page requires had nothing to read. **What the page reads is the `reorderSubstitutionValidation` key on the failed request's top-level error `extensions`**, whose value is a list of `SubstitutionCandidateValidationDetail` [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces — Zero New Buyer-Facing Operations, Two New Admin Operations]. Each entry carries one member of the closed `SubstitutionCandidateRejectionReason` enum, **every** candidate identifier that failed for that reason rather than only the first, and `maxCandidates` on the over-limit reason alone. **The page maps each reason to its own catalogue-supplied explanation** and renders it against the rows whose identifiers that entry names; the reason member itself is never displayed as a raw enum name, and the error's `message` is never displayed at all. Those identifiers are values the curator themselves submitted, which is what makes echoing them safe. **A failed save whose response carries no such extension is rendered as the generic page-authored failure above**, so a missing extension degrades the explanation and never blanks the page.
- **The technical detail is not destroyed, it is relocated:** it belongs in the server's own log, and the epic's own logging constraint on what may be recorded governs there [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality — And The Shipped Mechanism That Would Break It].

#### 4.4.7 Operable Without A Mouse, And Usable On A Narrow Viewport

**Both are contracts on this page's own composition, and both are anchored to shipped behaviour rather than to a guideline recited in the abstract.**

- **Reorder is keyboard-operable, and the platform already supplies the sensor.** The curated order is the whole of the ranking, so a curator who cannot reorder cannot use this page at all. Reordering is implemented through the data table's own reorder callback [packages/dashboard/src/lib/components/data-table/data-table.tsx:L163-L169] with drag-and-drop left enabled rather than switched off through the flag that disables it [packages/dashboard/src/lib/components/data-table/data-table.tsx:L170-L174]; the hook behind it registers a pointer sensor **and a keyboard sensor with sortable keyboard coordinates** [packages/dashboard/src/lib/hooks/use-drag-and-drop.ts:L23-L28]. **The obligation is therefore to assert the keyboard path rather than to build it**: a row is moved from `position` 2 to `position` 0 using only the keyboard, and the resulting array is what the save submits.
- **The move is announced, not merely performed.** A reorder that is visible only as a repaint tells a screen-reader user nothing, so each completed move announces the moved row and its new position through a live region, and the announcement text comes from the extension's own catalogues.
- **Every control has an accessible name and a visible focus indication, and the order of focus follows the order of the page**: origin selector, then the candidate list in `position` order, then the add-a-candidate selector, then save. Each row's remove control names the candidate it removes rather than being an unnamed icon, so a list of identical accessible names cannot occur.
- **The table is a table.** Rows and cells are rendered through the data table's own semantic markup rather than as generic containers [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9], which is what gives assistive technology the row-and-column relationships a curated ordering depends on.
- **The narrow-viewport behaviour is stated because the platform's own column control is not available there.** The data table's column-settings trigger is hidden below the large breakpoint [packages/dashboard/src/lib/components/data-table/data-table-view-options.tsx:L91], so a narrow viewport cannot be repaired by the curator hiding columns. The page therefore declares a column priority: the candidate's `position`, its `name` and its remove control are present at every width; `sku`, the offerability reading of 4.4.8 and any price are the columns that give way first, through horizontal scrolling of the table region rather than through truncation that hides a value with no way to reveal it. **No layout value is stated here** — the requirement is that no required column is unreachable and no value is silently clipped.
- **Reorder remains available at every width.** With the keyboard path required above, a narrow viewport that makes dragging impractical still leaves the ordering operable, which is why the keyboard requirement is a correctness matter rather than an accessibility extra.

#### 4.4.8 Presentation Is Locale-Aware, And The Page Formats Nothing By Hand

- **Money.** Where the surface shows a candidate's price it is the current catalogue price, held as an integer in the smallest unit of the currency the channel resolved [packages/core/src/entity/channel/channel.entity.ts:L88] and rendered through the dashboard's own currency formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L47-L57] or the display component built on it [packages/dashboard/src/lib/components/data-display/money.tsx:L10-L13], which is what converts a minor-unit integer into a locale-aware string carrying the currency symbol and the fraction-digit count that locale and currency imply. **No division by one hundred is performed in page code, no currency symbol is concatenated, and no decimal monetary value is stored or transmitted anywhere.** The gross-or-net basis follows `Channel.pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113] and is stated on the surface rather than left for the reader to assume.
- **Numbers and dates.** A count is rendered through the locale-aware number formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L59-L64] and a timestamp through the locale-aware date formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L66-L71], both from the same hook the dashboard already exposes [packages/dashboard/src/lib/hooks/use-local-format.ts:L27]. **`position` is an ordinal identity rather than a quantity and is rendered as the integer it is.**
- **Every label is a catalogue entry.** No literal user-facing string appears in the surface's source; each is marked up through the translation component the shipped precedent imports [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L2] and extracted into the plugin's own catalogues, which is the obligation section 10's first item checks by command.
- **A candidate's name is the platform's translated value** resolved under the **selected content language** the dashboard client puts on the request as a `languageCode` query parameter [packages/dashboard/src/lib/graphql/api.ts:L38-L44], falling back to the channel's `defaultLanguageCode` where no translation exists in that language [packages/core/src/entity/channel/channel.entity.ts:L74]; the row is rendered with its `sku` beside it so an untranslated name never leaves a row unidentifiable, which is the surface half of section 7's fourth scenario.
- **Offerability is shown as the object the read publishes, not re-derived on the page, and the field vocabulary is the single one the parent feature declares.** Each row renders the four booleans of `SubstitutionCandidateState` — `offerable`, `enabled`, `softDeleted` and `inActiveChannel`, and there is no fifth field and no `deleted` field [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces] — with `offerable` false explained by whichever of the other three is the cause, each explanation a catalogue entry rather than a raw field name. **An earlier revision of this page consumed two different state vocabularies in different places**, one of them naming a `deleted` boolean, because the parent feature declared the type twice with two field sets; that duplicate is withdrawn there and this page consumes the surviving four-boolean shape and nothing else.
- **A row's label comes from the plugin's own minimal display projection and NOT from a `ProductVariant` relation, because no such relation is published.** Each row renders `candidateDisplay.productVariantName` and `candidateDisplay.sku`, and the origin is named from `originDisplay` on the write's returned set [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces]. **Both fields are nullable and the page states what each null means**: a hard-deleted candidate has no name and no SKU left to resolve, so its row renders a catalogue-supplied placeholder beside its identifier rather than an empty cell. **An earlier revision of this page depended on full variant objects being available under this story's own permission**; those relations are withdrawn under the parent feature's reading nine, because publishing them would have exposed raw inventory, per-currency price rows, stock movements and cross-channel assignments to every holder of a curation permission [schema-admin.json:data.__schema.types]. **The catalogue data the pickers need is a separate matter** and arrives through the platform's own `productVariants` query under `Permission.ReadCatalog`, as section 4.4.1 states.

## 7. Edge Cases

**Five scenarios: the three categories required of every story in this set, plus the two conditional categories that genuinely apply — curation is channel-scoped and a candidate's name is a translated value, and two curators can replace one origin's set at the same moment.** Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

**Why five rather than four, which is a change from an earlier revision of this story and the reason is worth stating.** That revision carried four and explained the missing fifth by saying that this story's nearest race — two curators replacing one origin's set at the same moment — was "settled by the transactional delete-then-insert". **It is not settled by that.** A transaction at the engine's default isolation level makes each replacement all-or-nothing without making the pair of them serialisable, so the two can interleave into a stored set neither curator submitted, and the unique index does not forbid it because two disjoint candidate sets violate nothing [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces — Zero New Buyer-Facing Operations, Two New Admin Operations]. The concurrent-modification category therefore **applies to this story and is carried here** as the fifth scenario below, in addition to the sibling case where two commits reach for the same units. **The point-in-time-staleness category remains carried by STORY-001-04-02**, whose candidate offer is read before a write and confers no reservation, and is not duplicated here because this story reserves nothing and executes no Shop API operation [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§4.3 Intra-Feature Story Order]. The allocation across the feature is therefore deliberate rather than an omission.

* Scenario: Category — zero, null or empty collection. Nothing is curated for any variant a Marketplace Category Manager is responsible for, and an explicit clearing submission empties a set that had rows.
   * Given an administrative session on the channel whose token is `e2e-default-channel` [packages/testing/src/config/test-config.ts:L15]; one origin variant with no curated row naming it in any channel; and a second origin variant carrying exactly two curated rows in the requesting channel at `position` 0 and 1
   * When `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions)` is executed for the first origin variant, and `setSubstitutionCandidates(input: SetSubstitutionCandidatesInput!)` is then executed for the second with an empty `candidates` array
   * Then both requests **proceed rather than failing, and each reports**. The read returns exactly zero items with a `totalItems` of exactly 0 — **an empty collection and never a null and never an error result** — so a consumer distinguishes nothing-curated from not-asked without inspecting a null, and the dashboard surface renders its empty state for that origin rather than an error. The write is applied as the stated clearing operation rather than refused: it returns a `candidates` collection holding exactly zero entries, the persisted set for that second origin in that channel then holds exactly zero rows, and no other origin's rows and no other channel's rows are touched. **A clearing submission is a decision a curator is entitled to make**, so it is specified output and not an input failure, and the write reports the resulting empty set rather than a row count so the surface needs no follow-up read to render what it saved

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. Here it is a **curated candidate** that was withdrawn after curation, and the two surfaces answer differently on purpose.
   * Given an administrative session on the channel whose token is `e2e-default-channel` [packages/testing/src/config/test-config.ts:L15]; one origin variant carrying exactly three curated rows in that channel at `position` 0, 1 and 2; the candidate at `position` 0 having had its `enabled` column set to false since it was curated [packages/core/src/entity/product-variant/product-variant.entity.ts:L53]; the candidate at `position` 1 having had its `deletedAt` column set since then [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]; and the candidate at `position` 2 unchanged
   * When `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions)` is executed for that origin variant, and a fresh `setSubstitutionCandidates(input: SetSubstitutionCandidatesInput!)` naming the withdrawn candidate at `position` 0 is then submitted for the same origin
   * Then the administrative read **warns rather than hiding**: all three curated rows are returned, each carrying the `candidateState` object whose `offerable` boolean is false on the first two and true on the third and whose `enabled`, `softDeleted` and `inActiveChannel` booleans say which of the three causes applies to each — four booleans in total and no `deleted` field, that name having belonged to a duplicate declaration now withdrawn [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces], so a Marketplace Category Manager sees which two rows have become unofferable **and why** and can replace them, and the soft-delete state arrives on that plugin-owned field because the Admin `ProductVariant` type publishes no `deletedAt` [schema-admin.json:data.__schema.types], and no curated row is dropped from the surface that maintains it. **The reading comes from that object rather than from a field on the returned variant**, the Admin `ProductVariant` type publishing no deletion timestamp to read one from, and section 4.4.8 requires the page to render each false boolean as a catalogue-supplied explanation rather than as a raw field name. The subsequent submission naming a withdrawn candidate is **blocked** with the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L27] and nothing is written, because the write's validation refuses a disabled or soft-deleted candidate at submission time — curating one afresh would create a row that can never be offered, Figure F4-FLOW's first branch excluding it [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.9 Figure F4-FLOW]. **The two answers are deliberately asymmetric**: an existing row stays visible so it can be repaired, and a new row naming the same variant is refused so the fault is not repeated. Exclusion from a buyer's offer is neither of these and belongs to STORY-001-04-02's shipped default, which excludes withdrawn candidates at read time because a soft delete fires no cascade [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]

* Scenario: Category — a price changed since the last purchase. A candidate has been repriced since it was curated, and curation locks nothing.
   * Given an administrative session on the channel whose token is `e2e-default-channel` [packages/testing/src/config/test-config.ts:L15]; one origin variant carrying exactly two curated rows in that channel; and the candidate at `position` 0 having been repriced since it was curated, so its current catalogue price in the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differs from the price it carried on the day the row was written
   * When `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions)` is executed for that origin variant
   * Then the read **proceeds with the current figure and stores none**: both curated rows are returned unchanged in identity and `position`, because a price movement is not a curation event and no row is invalidated, reordered or removed by one. Where the surface shows a candidate's price it is the **current** catalogue price read through the platform, expressed as an integer in the smallest unit of the currency the channel resolved with its currency code stated alongside, and the gross-or-net basis follows `Channel.pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113]; **a decimal monetary value anywhere is a defect**. **The integer is a transport form and not a display form, and the two were previously conflated here**: the surface renders it through the dashboard's own currency formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L47-L57] or the display component built on it [packages/dashboard/src/lib/components/data-display/money.tsx:L10-L13], which is what applies the fraction-digit count and the symbol the resolved locale and currency imply, so **no page code divides by a hundred, concatenates a symbol or writes a decimal separator**, and the assertion available to a test is the formatter's output for a stated locale rather than a raw integer printed as text. Section 4.4.8 carries the same obligation for counts and timestamps. This story stores no price on any curated row, copies no monetary value, performs no arithmetic on money and applies no rate, so there is no place in it where a stale price could survive. **No price is locked by curating a candidate**, and no comparison between a candidate's price and its origin's is reported here — the two are different variants, so a difference between their prices is not a price change, and reporting the buyer's own price delta belongs to STORY-001-03-01

* Scenario: Category — a channel, currency or language mismatch. Curation performed under one channel token is invisible under another, and a candidate's translated name may be absent for the language a request names.
