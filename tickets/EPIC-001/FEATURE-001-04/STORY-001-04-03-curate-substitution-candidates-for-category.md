### 4.3 The Curation Contract, And The Five Boundaries Around It

The parent feature publishes the exact Admin schema so that no story has to invent an argument, a payload or an error [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces]. This sub-section restates only what section 5 asserts on, and adds nothing to that contract.

- **Two operations and no third.** `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions): SubstitutionCandidateList!` is the paginated read, and `setSubstitutionCandidates(input: SetSubstitutionCandidatesInput!): SubstitutionCandidateSet!` is the write. Both are new and additive on the Admin API, and no existing operation on either API changes shape.
- **The origin is a required argument, and the filter and sort inputs are generated.** These are different things and conflating them is the error worth naming. The origin argument is what makes a page's order meaningful, because `position` is unique per channel-and-origin pair, so a page interleaving origins would interleave independent orderings. Everything else — the sort parameter, the filter parameter and the pagination parameters — is injected by the platform's own generator for any query field returning a paginated list type, which is what its own documentation states [packages/core/src/api/config/generate-list-options.ts:L31-L33] and what the function does [packages/core/src/api/config/generate-list-options.ts:L34]. **`SubstitutionCandidateListOptions` is therefore declared as an empty run-time-generated stub and never hand-written**, exactly as the shipped precedent declares its own [packages/dev-server/test-plugins/reviews/api/api-extensions.ts:L44-L45]. Hand-writing a filter or a sort input for this read is a defect and not a style choice.
- **The write replaces the whole set for one origin, atomically, and the submitted array is the ordering.** `position` is deliberately absent from the input: the service assigns it from the array index, which makes its contiguity and its uniqueness true by construction rather than by validation. The replacement is a delete-then-insert inside one transaction, the resolver carrying the platform's own decorator [packages/core/src/api/decorators/transaction.decorator.ts:L81] as the shipped precedent's administrative write does [packages/dev-server/test-plugins/reviews/api/product-review-admin.resolver.ts:L68]. **An empty `candidates` array is the stated clearing operation** rather than an error, and section 7's first scenario asserts it.
- **A permission gate alone is not an access control in this platform, and that is a published caveat rather than an opinion held here.** The platform's own documentation for ownership-scoped access states that ownership cannot be defined generally nor statically encoded at build time, so a resolver relying on it must include logic to enforce access or it is the equivalent of publishing the data [packages/core/src/api/config/generate-permissions.ts:L32-L34]. The principle carries across: both operations sit behind `RwPermissionDefinition('ReorderSubstitution')` [packages/core/src/common/permission-definition.ts:L245] — the read on `ReadReorderSubstitution` and the write on `WriteReorderSubstitution`, registered through `authOptions.customPermissions` — and **the channel predicate is enforced inside the service on every read and every write**, because the gate only decides who may ask. A definition publishing two members is used rather than one publishing four [packages/core/src/common/permission-definition.ts:L146], since this story has exactly two verbs and two of the four would gate nothing while still appearing in the published enum for every deployment.
- **Curation is per channel, and a candidate curated under one channel token does not surface under another.** This is the one scoping rule a naive implementation would omit: a mapping keyed only on the pair of variants would leak one marketplace channel's curation into every other channel on the deployment. A cross-channel read returning another channel's rows is a defect and not a convenience [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.11 Channel Scoping, Language Scoping And Monetary Values].

**One thing this sub-section deliberately does not state is a number.** The submitted array is bounded by one configured maximum, `ReorderPluginOptions.maxSubstitutionCandidatesPerVariant`, and an array exceeding it is refused with the platform's input error naming the maximum rather than truncated — a truncating replace would silently delete curation the caller believed it had saved. **The value of that maximum is the epic's tenth product decision and remains open** [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions], so this story names no figure for it and asserts the boundary behaviour against whatever value its fixture configures. **There is likewise no relevance target, no candidate-count target and no adoption target anywhere in this story, because this repository declares none** [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value]. Refusing to invent a value is not the same as having no bound, and both halves of that sentence are load-bearing.

## 5. Acceptance Criteria

Six criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria name operations, their arguments and their response fields, together with entity and column names as database preconditions; none names a resolver class, a file path, a React component or an internal method name, because those are not published contracts.
