### 1.2 The Argument For This Story, Which Is An Argument About Where The Answer Comes From

`substitute` is the one outcome of the four that cannot be served from anything already in this checkout. `skip` and `reduce quantity` are shipped behaviours the platform performs unbidden, and `abort` is expressible by declining to call the commit — STORY-001-04-01 sets all three out with the control flow that proves it [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.4 What The Commit Path Already Does Today]. **An alternative variant, by contrast, has to come from somewhere, and nothing in this repository knows what a variant's alternatives are.** Section 3 proves that by search rather than by assertion.

There are three places the answer could come from, and two of them are refused by the constraints rather than by preference.

- **An external recommendation or search service.** This is the path of least resistance and the constraints forbid it: any apparent external need is modelled behind an interface with a database-backed default [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.10 The No-External-Service Discharge, Stated As A Design Ruling]. Section 4.3 states the discharge as a ruling.
- **Inference from purchase history.** Refused because predicting what a buyer would accept instead is a forecasting capability the epic rules out of scope, and because there is no declared target to validate an inference against [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value].
- **A curated mapping a person maintains, read through a replaceable seam.** This is what this story builds. The seam is the interface; the shipped implementation reads one plugin-owned table; a deployment that wants something else replaces the implementation through a plugin option and this epic neither knows nor cares what it does.

**Read those three together and the shape of this story is forced rather than chosen**, which is why section 3 discloses the single precedent value `partial`: strong on the mechanism it borrows, absent on the subject it addresses.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line when the file is read on any renderer and when it is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Returning Buyer,
I want to be offered specific alternative variants for a reorder line that cannot be obtained, drawn from a set a person curated for exactly that variant in the channel I am shopping,
So that a line I cannot have becomes a line I can replace in the same request, instead of a line I can only drop.
```

### 4.1 INVEST Criteria

- **Independent in value, dependent in merge order — and the dependency is named rather than glossed, because true independence is impossible here.** This story depends on STORY-001-04-01, which defines the `substitute` outcome it serves: a source of alternatives has no meaning until something consumes alternatives, and the parent feature records the edge in that direction [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§4.3 Intra-Feature Story Order]. **What it still delivers on its own is observable without the commit path at all:** a configured strategy and a curated candidate set are readable through `reorderPreview`, so the whole of this story's own subject — the interface, the shipped implementation, the table, the plugin option, the ordering, the exclusions and the channel scoping — can be demonstrated and accepted with no resolution instruction ever submitted. Section 4.2's demonstration path does exactly that, and only section 5's second and fourth criteria reach into the commit.
- **Negotiable** — parts of the shape are open and parts are deliberately not. Three choices this story may settle either way: whether a candidate's offer carries the origin line's obtainable quantity or only its own; whether the shipped implementation excludes a candidate the buyer's cart already holds; and whether a substituted line the commit then clamps reports the substitution code or the reduced-quantity code, both of which FEATURE-001-02 already publishes, so either reading is expressible without a new member and section 5's fourth criterion states which one it takes. **What is not negotiable** is that the strategy is one interface with one method, that the method is asked once per resolution round and answers the whole round keyed by origin, that the shipped default reads a plugin-owned table with no outbound call, that the answer carries no score of any kind, that a candidate is described to a buyer with a display token rather than a stock figure, and that the strategy arrives as a plugin option rather than as a new platform configuration property.
- **Valuable** — it is the point at which the fourth resolution outcome becomes reachable in the shipped configuration rather than only in a bespoke one. A default that could only ever return nothing would discharge the no-external-service ruling on paper and defeat it in practice, which is why a working default is part of section 10 rather than an aspiration [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§5. Definition of Done (Feature-Level)].
- **Estimable** — three shipped exemplars fix the interface shape, the parent feature fixes the table column for column with all five of its named constraints [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.5 Named Entities Touched], the availability read is an existing service call [packages/core/src/service/services/stock-level.service.ts:L72], the bulk variant load is an existing method [packages/core/src/service/services/product-variant.service.ts:L150] and the display mapping is an existing composition [packages/core/src/service/services/product-variant.service.ts:L361-L364]. The surface to be written is therefore bounded and countable. Section 9 carries the numbers.
- **Sized Appropriately** — one interface, one shipped implementation, one plugin-owned table with one additive migration, one plugin option and one field on a plugin-owned output type, with **zero new operations, zero new error results, zero permission definitions, zero custom fields and zero asynchronous work**. It is not a candidate for splitting: separating the interface from its shipped default would ship a seam with nothing behind it, and separating the table from the implementation that reads it would ship a migration no code consults.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact candidate count with its ordering, an exact stock token from the three the shipped display strategy returns, an integer monetary value with its currency code, an exact cart line count, an exact error type together with the code a client observes, or the equality of a cart before and after a call. **Step 4 — the one operation, and this is the whole demonstration.** Back in the customer session, execute:

    targetCurrencyCode

### 4.3 The Strategy Seam, The Table Behind It, And The Four Rulings That Fix Them

Everything named in this sub-section that carries no citation is a **target named in ticket text**. `SubstitutionCandidateStrategy`, `SubstitutionCandidateResult`, `DefaultSubstitutionCandidateStrategy`, `ReorderPluginOptions`, `SubstitutionCandidate`, `ReorderSubstitutionCandidateOffer`, `reorderPreview`, `ReorderPreviewLine`, `applyReorderToActiveOrder` and the plugin package do not exist in this checkout, so none of them carries a citation and a downstream reader must not treat any of them as verified. **`ReorderSubstitutionCandidateOffer` is inventoried rather than merely named here:** it is the twenty-first object type in the epic's published-symbol inventory and the one Shop extension that inventory permits a feature to make to a type another feature owns [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings, And The Complete Published-Symbol Inventory], the parent feature declares the extension with its exact shape [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces], and the name was collision-checked absent from both checked-in introspection snapshots [schema-shop.json:data.__schema.types] and [schema-admin.json:data.__schema.types]. **The interface signature and the table mapping are the parent feature's and are inherited rather than re-decided here** [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.6 Named Services And Configurable Strategies] and [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.5 Named Entities Touched].

**Ruling one — the strategy is a plugin option, not a platform configuration property, and this is the sharpest point in the file.** The two shape exemplars are reached through `catalogOptions.stockDisplayStrategy` [packages/core/src/config/catalog/stock-display-strategy.ts:L14] and `orderOptions.changedPriceHandlingStrategy` [packages/core/src/config/order/changed-price-handling-strategy.ts:L17-L18], and both of those live inside `packages/core`. **A new platform configuration property cannot be added without editing that package**, and this work carries an absolute zero-edit boundary on `packages/core` and `packages/admin-ui` [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.14 Constraints This Feature Is Built Under]. So the replacement point is `ReorderPluginOptions.substitutionCandidateStrategy`, supplied on the reorder plugin's own initialisation object and defaulting to the shipped implementation: **the shape of the exemplars is followed and the files that host them are not touched.** The interceptor precedent shows the third possible route — a plugin pushing an implementation onto an array the platform already declares [packages/dev-server/example-plugins/minimum-order-quantity/order-quantity-limits.plugin.ts:L107] — and it is unavailable here for the same reason: no such array exists for this question, and declaring one would be the core edit the boundary forbids.

**Ruling two — the no-external-service constraint is discharged by the interface-plus-database-backed-default shape, and the discharge is stated rather than implied.** A capability that offers a buyer something else is the canonical shape of a hosted recommendation service, and this is the one story in the epic where an implementation would reach for one. The discharge has two halves and both are load-bearing. **The interface is the seam an operator may replace**, so a deployment that wants a hosted recommender is not blocked — it supplies its own implementation through the plugin option, and that choice is the deployment's, taken outside this epic's boundary. **The shipped default resolves candidates from the plugin-owned `SubstitutionCandidate` table with no outbound network call, no vendor credential, no data export and no dependency outside this repository.** Because there is no external service to derive candidates from, and because inferring candidates from purchase history is a forecasting capability the epic rules out of scope, **candidates are curated by a person** — which is what makes STORY-001-04-03 necessary rather than optional [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.10 The No-External-Service Discharge, Stated As A Design Ruling].

**Ruling three — the ordering is deterministic over named columns, and there is no relevance figure anywhere.** **This repository declares no relevance target, no match-quality target, no similarity threshold and no ranking confidence figure of any kind, and this story invents none** [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value]. The order candidates are offered in is therefore the curator's, expressed as data: the shipped implementation reads rows for the active channel and the origin variant and orders them by ascending `position`, which the parent feature makes unique per channel-and-origin pair, so the ordering is total and the read is reproducible rather than an accident of insertion [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.5 Named Entities Touched]. Ascending `candidateProductVariantId` is named as the second sort term so that the emitted ordering is total by the query's own text and not only by a constraint that a later migration could be written without. **A replaced implementation that wants a different order expresses it in the order it returns**, which is the whole reason the returned arrays are ordered and the whole reason no numeric field was published to carry a rank.

**Ruling four — the answer is batched, keyed by origin, and total over the set it was asked about.** The interface takes **one immutable request object** describing the round — the resolved channel id, the `languageCode`, the `currencyCode` and the origins by value — and returns a map keyed by the origin's id whose values are **candidate variant ids** [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.6 Named Services And Configurable Strategies]. Four properties of that answer are this story's to enforce, and section 5 asserts each: **exactly one entry per origin asked about**, with an **empty array** where there is nothing to offer, so "asked and answered none" and "not asked" are distinguishable and the no-candidate path of Figure F4-FLOW is reached by an empty array rather than by a missing key — **a missing key is a contract violation and never a synonym for the empty array**; **no key outside the asked set**; **no array containing its own origin**; and **no array longer than the configured maximum**, an over-long answer being refused rather than trimmed. The key type is the platform's own union of string and number [packages/common/src/shared-types.ts:L79], carried in a map rather than an object literal so a numeric identifier is not stringified.

**Ruling five — what crosses the seam is minimal, and nothing that comes back is trusted. This is the ruling that makes a replaceable seam safe, and two parts of it reverse an earlier draft.**

- **Outbound, the strategy receives a value-only frozen DTO and not a `RequestContext` or an entity.** An earlier draft passed `ctx: RequestContext` together with hydrated `ProductVariant` objects, and argued for the entities on the grounds that an implementation then cannot avoid resolving what it recommends. **Both are withdrawn**, for a reason the interface's own purpose supplies: this seam exists precisely so a deployment may implement it with something that consults another process, and a `RequestContext` carries the cached session [packages/core/src/api/common/request-context.ts:L368], the active user id [packages/core/src/api/common/request-context.ts:L372] and the raw request [packages/core/src/api/common/request-context.ts:L336], while a `ProductVariant` carries lazy relations reaching the catalogue graph and other channels' assignments [packages/core/src/entity/product-variant/product-variant.entity.ts:L177-L179]. **The request names variants, not people** — no customer identifier, no order, no price and no header travels across it — and it is frozen so an adapter cannot mutate the plugin's working set through a shared reference [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.6.2 What Crosses The Strategy Boundary, And What The Wrapper Around It Guarantees].
- **Inbound, every returned id is re-resolved and re-validated by the plugin before a buyer sees it.** An id is a **nomination**, not an assertion that the variant exists, is enabled, is in this channel, is priced or is in stock. The plugin checks all six centrally, in one bulk load, and **drops** a candidate that fails any of them — which it must do rather than delegate, because the platform's own variant resolution applies an `enabled` and `deletedAt` predicate but **no channel predicate** [packages/core/src/service/services/order.service.ts:L684-L689], so a trusted id could pull a variant from another channel into a buyer's offer [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.6.3 Nothing A Strategy Returns Is Trusted — The Central Re-Resolution Rule]. **This is why the interface returns ids rather than entities: an entity a caller must re-verify anyway is just a larger thing to distrust.**
- **The call is wrapped, and the wrapper fails closed.** One invocation per round, bounded by `ReorderPluginOptions.substitutionCandidateTimeoutMs`, **no retry**, a late answer discarded, and any throw, rejection, timeout, malformed return or refused structure yielding **the empty map for the whole round** — never a fall back to the shipped default, never an aborted reorder and never a partially validated answer. Nothing an adapter raises reaches the API, and the one diagnostic per failed round carries a stable failure code, the `correlationId`, the channel id and the origin count, and **nothing else**.

**The field this story populates, transcribed rather than declared.** Both declarations below belong to FEATURE-001-03 and exist in `ReorderPreviewLine`'s first published version [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]; they are reproduced here so a reader does not need two files open, and **a difference between this block and that one is a defect in this block**. What this story adds is the values, not the shape.

Four readings of that block are decisions rather than syntax.

- **The collection is non-null and empty is a real answer.** A nullable collection would give a consumer two ways to express "nothing", and section 5's fifth criterion asserts the empty collection rather than an error or a null. **The field name `substitutionCandidates` also names an Admin query STORY-001-04-03 owns, and the two do not collide**: a field on an object type and a root query field occupy different namespaces, and a plugin's `adminApiExtensions` and `shopApiExtensions` are two separate schema documents, so an Admin operation never shares a namespace with a Shop type's field. The coincidence is named here so a reader does not read it as one symbol declared twice.
- **`stockLevel` is a string and not an enum, and it is the only availability a candidate discloses.** The display strategy exists because directly exposing stock levels over a public API is treated as a leak of sensitive information [packages/core/src/config/catalog/stock-display-strategy.ts:L7-L10], and a deployment may replace it [packages/core/src/config/catalog/stock-display-strategy.ts:L14] — so the field is typed as the contract returns it [packages/core/src/config/catalog/stock-display-strategy.ts:L27] and a criterion asserting one of the three tokens names the shipped default in its Given [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.5.1 The Three Stock Tokens]. **No field here returns `stockOnHand`, `stockAllocated` or an unbounded saleable figure**, which is the epic's ruling R7 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings].
- **`addableQuantity` is bounded by the caller's own request, and the residual disclosure is accepted with its reach stated rather than left unsaid.** Bounding it at the origin line's requested quantity means it can never reveal a saleable level above what the caller already asked for, which is the same acceptance FEATURE-001-03 records for its own figure [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. **What this story widens is the set of variants the bounded figure can be read for**: from variants the caller themselves bought or saved, to those plus the variants a curator mapped to them. That set is finite and administratively controlled rather than the catalogue, and the equivalent figure is already obtainable from this platform for any variant by over-ordering it and reading `quantityAvailable` off the returned error [packages/core/src/api/schema/common/common-error-results.graphql:L53]. **The widening is declared here rather than absorbed.**
- **Money is integer minor units with its currency code, and a decimal monetary value anywhere is a defect.** The basis follows `Channel.pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113] and the code is the response's own target currency, resolved from `Channel.defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88].

**Four boundaries, stated as rules so this story does not annex a neighbour's scope.**

- **It does not detect unavailability.** The availability classification and the obtainable figure are STORY-001-03-02's, consumed here as the input that decides which origins the strategy is asked about [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§4.1 Upstream].
- **It does not define the outcomes.** `skip`, `reduce quantity` and `abort` are STORY-001-04-01's and are not re-specified here; this story supplies what `substitute` needs and nothing else.
- **It does not write the order, and it does not read stock rows.** A resolved line set is handed once to `OrderService.addItemsToOrder` [packages/core/src/service/services/order.service.ts:L654] by the path FEATURE-001-02 already established. Candidate availability is resolved through `StockLevelService.getAvailableStock` [packages/core/src/service/services/stock-level.service.ts:L72], which delegates the multi-location question to the configured strategy [packages/core/src/service/services/stock-level.service.ts:L79]; **no plugin query reads a `StockLevel` row and no plugin code sums `stockOnHand`** — a variant with a negative threshold is obtainable well beyond its on-hand figure, as a shipped specification asserts by writing eight units against a `stockOnHand` of three [packages/core/e2e/stock-control.e2e-spec.ts:L719-L738], so arithmetic in plugin code would offer a substitute for a line that needed none.
- **It does not build the curation surface.** `substitutionCandidates` and `setSubstitutionCandidates`, their permission gate and the dashboard through which a Marketplace Category Manager fills the table are STORY-001-04-03's, which is the one story in this feature owned by a developer working in parallel [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§4.7 Owner Assignment].

**A point-in-time read is not a reservation, and no field or document may suggest otherwise.** Adding to a cart reserves nothing in this platform: a shipped specification has two customers each add one unit of a variant whose `stockOnHand` is one and **both adds succeed** [packages/core/e2e/stock-control.e2e-spec.ts:L1301-L1316], with the allocation recorded only at payment [packages/core/e2e/stock-control.e2e-spec.ts:L1324-L1327]. A candidate read is weaker still: it is taken at the same moment, holds nothing, and the commit re-clamps every line independently [packages/core/src/service/services/order.service.ts:L703]. **No freshness window is stated in any unit**, because this repository declares none and a stated window would imply a guarantee the read does not make [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.12 A Point-In-Time Read Is Not A Reservation].
