## 1. Story Title

**Publish three typed reorder events on the existing event bus, each carrying its request context and a documented payload schema, so that a subscriber reacts to a recorded reorder attempt without polling a table.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Publish reorder events** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work is three event classes, their publish call sites, and the field-by-field documentation of their payloads. **The three names and every payload member are fixed by the parent feature, which declares itself their authority and rules that a divergence between a story and that section is a defect in the story** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7 The Three Events And Their Payload Schemas — This File Is Their Authority]. **This story owns no table and no migration.** `ReorderAttempt` and `ReorderAttemptLine`, and the one additive migration that creates both, belong to `STORY-001-07-01-reorder-attempt-audit-trail.md` [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§3. **Four absences define this story as sharply as its three events, and all four are stated positively rather than left to be inferred from silence** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.6 Named API Surfaces — Three Absences, Stated Plainly]:

**The mechanism is not novel and this story claims no originality for it.** The platform ships a large existing event catalogue under `packages/core/src/event-bus/events/`, exported from the same barrel [packages/core/src/event-bus/index.ts:L6]. The three new events join an established surface.

## 3. Precedent In This Repository

**PRECEDENT:** partial — the publish-and-subscribe idiom is shipped outright and this story re-applies it; three reorder-specific events with documented payload schemas are shipped nowhere.

The searched set is named so the claim is checkable rather than asserted: the whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. That is the same set the epic searched for its nomination reasoning [tickets/EPIC-001-reorder-and-replenishment.md:§9.6 Nomination], and the parent feature reaches the same `partial` verdict from its own side and forbids either of its two stories claiming `none` [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.14 Precedent In This Repository — Partial]. This story does not claim it.

**What is precedented — two shipped things, both read rather than assumed.**

- **The publish-and-subscribe idiom is shipped and documented.** Publication is a single awaited call on the injectable bus, which its own JSDoc gives as the calling form [packages/core/src/event-bus/event-bus.ts:L113] against the method that implements it [packages/core/src/event-bus/event-bus.ts:L116]; subscription is the typed stream filtered to one event class [packages/core/src/event-bus/event-bus.ts:L130]. Nothing about either is being introduced here.
- **The event-shape convention is shipped.** The entity-event shape is exemplified by `OrderEvent`, declared over an order and its input types [packages/core/src/event-bus/events/order-event.ts:L17] and passing a three-member type discriminator through its constructor [packages/core/src/event-bus/events/order-event.ts:L21]. Separately, a shipped test plugin shows a plugin recording its own history-style rows by augmenting the platform's history-data interfaces [packages/dev-server/test-plugins/custom-history-entry/types.ts:L5-L12], which is the nearest analogue in the searched set to a plugin adding its own auditable vocabulary to the platform.

**What is not precedented at all: nothing in this repository publishes reorder events**, because nothing in this repository performs a reorder. There is no reorder event class, no reorder payload shape and no reorder subscriber anywhere in the searched set.

**The unflattering half of the disclosure is required output, so it is stated plainly.** Publishing a typed event from a plugin is re-application of a well-worn pattern over a catalogue that already exists [packages/core/src/event-bus/index.ts:L6]. The bus, the two payload base classes, the transaction-aware delivery and the filtered stream are all shipped, and this story writes none of them.

**What is novel beyond the precedent, stated as three specifics rather than as a claim of novelty:**

- **Three reorder-specific event classes**, named and shaped by the parent feature, joining the shipped catalogue rather than replacing any part of it.
- **A documented payload schema for each**, field by field, including which members are deliberately absent — an omission is part of a schema and this story records it as one.
- **A defined publish moment and a stated publication count per event**, one of which fans out per rejected line while the other two are once per attempt, so a consumer knows how many times it will hear about one reorder rather than inferring it.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when this file is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Seller Operations Manager,
I want the three reorder events published on the platform's existing event bus at the moment a reorder attempt has been recorded, each carrying its request context, the attempt's identity and the routing fields a subscriber needs in order to decide whether the event concerns it,
So that a subscriber of mine is invoked with the attempt already committed and can read that attempt's stored row and its line rows, rather than my having to re-read a table on a timer to discover that a reorder happened.
```

The WHY is a **verifiable state and not a figure**: a subscriber exists, it is invoked, and the rows the event names are readable from inside it. No delay, no delivery share, no throughput and no business effect is claimed, because this repository declares none [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value, Stated Without Invented Numbers].

## 5. Acceptance Criteria

Seven criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria name operations, their arguments, and entity, table and column names as database preconditions; none names a resolver class, a file path or an internal method name. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

Three preconditions hold for every criterion without being repeated in each, because they are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]: an authenticated session, a channel resolved from the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L58-L62], and a language resolved from the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. AC-7 is where those two stop being background and become the assertion.

**The payload contract these criteria assert against, reproduced field by field from the parent feature, which is its authority** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7 The Three Events And Their Payload Schemas — This File Is Their Authority]. Two shipped shapes are followed and neither is invented here: the entity-event shape declares four public readonly members on its base — the entity, a type discriminator, the request context and an optional input [packages/core/src/event-bus/vendure-entity-event.ts:L12-L16] — and is exemplified by `OrderEvent` [packages/core/src/event-bus/events/order-event.ts:L17]; the discrete-occurrence shape is a direct subclass of the common base [packages/core/src/event-bus/vendure-event.ts:L7] declaring its payload as public constructor parameters, exemplified by `OrderLineEvent` [packages/core/src/event-bus/events/order-line-event.ts:L13-L18] and by `OrderPlacedEvent` [packages/core/src/event-bus/events/order-placed-event.ts:L17-L22]. **No timestamp member is invented on any of the three**, because every event inherits a creation timestamp from the common base [packages/core/src/event-bus/vendure-event.ts:L7-L8].

```ts
// The three payloads, member for member. Written as type aliases so each block is valid
// standalone TypeScript rather than a bare property list. `createdAt` is inherited from the
// common event base on all three and is shown for completeness, not re-declared.

// Event one. Entity-event shape, populated with a projection of the attempt row rather than
// with the row. The base declares its entity member over a type parameter, so a projection
// satisfies the shape exactly as a row would.
type ReorderAttemptEventPayload = {
    entity: ReorderAttemptEventSummary; // NOT the ReorderAttempt row. The persisted row is the one
                            // canonical snapshot and it stays in the database; this is a
                            // minimal immutable projection of it, defined immediately below
    type: 'created';        // the base constrains this member to one of three values -- created,
                            // updated or deleted -- and this event only ever carries the created
                            // one, because attempt rows are append-only
    ctx: RequestContext;    // required for transaction-aware delivery; strict use policy below
    createdAt: Date;        // inherited
    // input: DELIBERATELY OMITTED. The base declares it optional, so omitting it is within the
    // shape. Every field it could carry is already a column on the row above or on that row's
    // line rows, and a second copy could disagree with the first.
};

// The projection event one carries. Ten members and no eleventh: two handles, three routing
// fields and the five line counts. Every member is a verbatim copy of a column on an
// append-only row, so none can diverge from its source.
type ReorderAttemptEventSummary = {
    readonly attemptId: ID;         // the durable row, so a subscriber can read the rest
    readonly correlationId: string; // the diagnostic handle, server-minted
    readonly channelId: ID;         // routing field, asserted by AC-4
    readonly sourceType: ReorderSourceType;   // routing field, three members
    readonly outcome: ReorderAttemptOutcome;  // routing field, eleven members; asserted by AC-3
    readonly requestedLineCount: number;
    readonly fullyAppliedLineCount: number;
    readonly partiallyAppliedLineCount: number;
    readonly rejectedLineCount: number;
    readonly notEvaluatedLineCount: number;
};

// WHAT THIS PROJECTION DELIBERATELY OMITS, enumerated so the omission is a contract rather
// than an oversight, and asserted negatively by AC-1: actingCustomerId and every other
// identifier naming a person; sourceOrderId, sourceOrderCode, sourceReorderListId,
// languageCode; idempotencyKeyDigest; targetOrderId;
// targetOrderCode; and all three catalogue label snapshots, which live only on the line
// rows. A subscriber needing any of them reads the durable row by attemptId, under its own
// authorisation -- which is strictly better than a broadcast that reaches every subscriber
// in the process whether or not it should see them.

// Event two. Discrete-occurrence shape. Ids and routing fields only; no row, no collection.
type ReorderAppliedEventPayload = {
    ctx: RequestContext;
    attemptId: ID;            // the attempt row event one carried
    targetOrderId: ID;        // the active order the lines reached
    targetOrderCode: string;  // routing field: the code snapshot, so a subscriber can name the
                              // order without loading it
    appliedLineCount: number; // routing field: the sum of the attempt row's fullyAppliedLineCount
                              // and partiallyAppliedLineCount; always above zero on this event
    createdAt: Date;          // inherited
    // The applied line rows are NOT carried. A subscriber needing them reads ReorderAttemptLine
    // by attemptId.
};

// Event three. Discrete-occurrence shape, modelled on the shipped per-line exemplar.
type ReorderLineRejectedEventPayload = {
    ctx: RequestContext;
    attemptId: ID;                            // the parent attempt row, for correlation
    attemptLineId: ID;                        // the single rejected line row
    requestedVariantId: ID;                   // routing field: the variant the buyer asked for
    finalLineOutcome: ReorderLineOutcomeCode;  // routing field: only ever a member on which the
                                              // line's applied quantity is zero and which is not
                                              // NOT_EVALUATED
    createdAt: Date;                          // inherited
    // The error type name, the available quantity, the applied quantity, the resolution choice
    // and the recorded unit price are NOT carried. All five are columns on the line row, and a
    // subscriber needing any of them reads the row by attemptLineId.
};
```

**There is one payload contract for event three, and a divergence that once stood inside the parent file has been reconciled there, and the report of it is withdrawn.** An earlier revision of this story recorded that the parent's authority section excluded the recorded error type name from event three's payload while one cell of its surface-ownership matrix described that payload as carrying an `errorType` member, and declined to reconcile the two. **The stale cell has been corrected in the parent, so one payload contract now governs** while its authority section excluded it; that cell now asserts the same member set the payload declaration above states, and records the carrying description as withdrawn conditionally [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7.1 Surface Ownership And Test Matrix]. **So the payload above is the whole contract: it carries no recorded error type name, no available quantity, no applied quantity, no resolution choice and no recorded price**, and AC-3 asserts the error name and the available integer where they actually live — as columns on the line row, read by `attemptLineId`. **This story [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7 The Three Events And Their Payload Schemas — This File Is Their Authority], and no error type name**, and AC-3 asserts the recorded name where it actually lives — on the line row, read by the `attemptLineId` the payload carries.

**A consequence worth stating because a reader will look for it: no payload carries a monetary value at all.** The integer-money constraint is therefore discharged here by absence rather than by formatting, and where a price is recorded it is recorded on the line row as an integer in the smallest unit of its currency alongside its `currencyCode` and its tax basis [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128]. A subscriber that needs an amount reads the row.

**Publication and subscription are the platform's mechanisms, consumed as they stand.** Publication is one awaited call on the injectable bus [packages/core/src/event-bus/event-bus.ts:L116], whose own JSDoc gives that calling form [packages/core/src/event-bus/event-bus.ts:L113], declared on the bus class itself [packages/core/src/event-bus/event-bus.ts:L100]. Subscription is the typed stream filtered to one event class [packages/core/src/event-bus/event-bus.ts:L130], with a predicate-based variant available carrying the identical guarantee [packages/core/src/event-bus/event-bus.ts:L142-L148]. **No webhook dispatcher, no polling table and no second message bus is introduced** [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated].

**Every payload carries the request context, and that single fact is what makes this story's completion signal real rather than aspirational.** The typed subscribe's own JSDoc states that where the event contains a request-context object the subscriber is called only after any active database transactions are complete, and that the subscriber can therefore safely access all updated data related to the event [packages/core/src/event-bus/event-bus.ts:L122-L128]. The delivery path finds that context by scanning the event's own properties for one and returns the event untouched when it finds none [packages/core/src/event-bus/event-bus.ts:L311-L316], so **an event without a context is delivered with no transaction awareness and the guarantee simply would not apply to it**. That is the causal chain: the context is on the payload, so the subscriber runs after the commit, so the attempt row the attempt just wrote is readable from inside the subscriber. AC-1 asserts that chain end to end.

**The trigger and the observable completion signal are named once and inherited by every criterion, because "it happens eventually" is never a criterion** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.10 Asynchronous Delivery — The Trigger And The Observable Completion Signal]. The trigger is **one reorder attempt reaching a terminal state** — settled, refused or aborted — and never a timer, a queue drain or an administrator action. The completion signal is **two things of different strengths, and the difference is stated because conflating them is what makes an event look like a guarantee**: the strong signal is the persisted `ReorderAttempt` row and its `ReorderAttemptLine` rows becoming readable, which every criterion below may assert on; the weak signal is a registered subscriber's own observable effect, which holds only for a subscriber in the same process, only where the publishing transaction committed, and only for the one stream that subscriber is attached to.

**The honest limitation, and it is the reason this feature has two stories rather than one.** The event stream is a plain RxJS subject held as a field on the bus instance [packages/core/src/event-bus/event-bus.ts:L101], and subscriptions are torn down when the module is destroyed [packages/core/src/event-bus/event-bus.ts:L102]. **Past events are therefore not replayed**: a subscriber that registers later receives nothing for an event already published, and an event reaches only the subscribers present at publish time. There is no persistence, no retry and no acknowledgement, and where the publishing transaction rolls back the stream drops the event rather than delivering it [packages/core/src/event-bus/event-bus.ts:L337-L343]. **The events are for reaction; the audit rows of `STORY-001-07-01-reorder-attempt-audit-trail.md` are the durable record** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.8a Delivery Semantics — Stated As Absences, Because The Absences Are What Consumers Get Wrong]. No criterion below asserts that an event will arrive.

**Blocking handlers are mentioned and ruled out, because the mechanism that would break neutrality is shipped and documented.** The bus offers a way to register a handler that blocks the code which published the event until the handler has completed [packages/core/src/event-bus/event-bus.ts:L188], and that method's own JSDoc cautions that errors or performance problems in such a handler can cause the associated operation to fail entirely, that a handler which runs long enough logs a warning, that non-trivial work belongs on a background job queue instead, and that the handler executes inside the *same database transaction* as the code which published the event [packages/core/src/event-bus/event-bus.ts:L165-L173]. **This feature registers none**, because instrumentation must be observationally neutral — and that refusal is what makes AC-5 provable rather than merely asserted, since publication pushes onto the stream [packages/core/src/event-bus/event-bus.ts:L117] and then awaits only registered blocking handlers [packages/core/src/event-bus/event-bus.ts:L118].

**A subscriber's use of the context is constrained rather than open, and the constraint is a rule this story documents rather than a preference.** A subscriber may read the channel id, the language code and the active user identifier from it, must pass it onward only to the connection service and only to read, and must not log, serialise, persist or forward it — because the platform ships a serialisation form of a context whose output carries a session token [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11a The Request Context On A Payload — Required, And Strictly Constrained]. Section 6's documentation sub-task puts that policy in the JSDoc of all three classes.

**The prohibition is enforced by an assertion rather than by documentation alone, and two of the members a reader might expect are absent by construction.** The parent enumerates five prohibited member classes — a session or session token, the raw request or a clone of it, the serialised form of a context, an input object of any kind, and any caller-supplied opaque value — and requires a compile-time assertion over each payload type plus one runtime assertion in the publishing path, so a member added later has to pass the same gate. **This story carries that assertion for all three classes**, which is why event one omits the optional `input` member its base offers [packages/core/src/event-bus/vendure-entity-event.ts:L16]. **Neither the raw idempotency key nor either of its digests appears on any payload**, and for two different reasons worth keeping apart: the raw key is not a column on the attempt row at all, so no payload could carry it even by lifting the entity; and the two digest columns are deliberately not lifted, because a digest is neither an id a subscriber correlates on nor a value it can route with — a subscriber telling two attempts apart compares `correlationId`, which every payload reaches through the row or carries directly.

**One member does carry a whole row, and the reason it is retained rather than reduced is the shipped shape.** Event one is an entity event, and that base declares `entity` as a non-optional member [packages/core/src/event-bus/vendure-entity-event.ts:L13], so it cannot carry less and remain one; the platform's own customer event is an entity event over a `Customer` [packages/core/src/event-bus/events/customer-event.ts:L22], which carries an email address [packages/core/src/entity/customer/customer.entity.ts:L42], so the convention is materially more permissive than an attempt row of identifiers, enum members and counts. **Four of its columns are re-identifying and a subscriber treats them under the same rule as the context** — `actingCustomerId`, `sourceListOwnerCustomerId`, `sourceOrderCode` and `targetOrderCode` may be scoped on and read by, and may not be logged, serialised, persisted or forwarded.

**The recorded error vocabulary is closed, and no criterion below names anything outside it.** This story declares no error result, so nothing is added to it. A recorded error name on a line row is the name of an existing type drawn from the five members of the platform's own update-order-item error union [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], listed as bullets here rather than in the schema's own union form:

- `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80-L83]
- `OrderLimitError`, carrying `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L37-L41]
- `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44-L47]
- `InsufficientStockError`, carrying `quantityAvailable` as a non-null integer [packages/core/src/api/schema/common/common-error-results.graphql:L50-L55] and [packages/core/src/api/schema/common/common-error-results.graphql:L53]
- `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103-L107]

Beside a recorded error name sits the plugin's own line outcome member, and the four outcome classes the sibling story fixes are the ones referred to below: applied at the requested quantity as `ADDED`; applied at a reduced quantity as `ADDED_AT_REDUCED_QUANTITY`; not applied naming one of the five types above as one of the `NOT_ADDED_*` members at an applied quantity of zero; and excluded before delegation as `NOT_ADDED_VARIANT_UNAVAILABLE` at an applied quantity of zero with a **null** error name, because the platform supplies no error result for that class at all [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums, And The Counting Rule That Makes Them Add Up].

**Every event assertion below is an exact length and never an existence check, and this is the single most important rule in the section.** An assertion that an event "of type X was received" passes whether one was published or five were, and passes for event two whether it fired or not. **Seven of the counts asserted below are therefore zero — one in AC-1, one in AC-2, two in AC-4 and three in AC-6** — because a zero is precisely what a singular existence assertion cannot see [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7.1 Surface Ownership And Test Matrix]. The figure is given as a count rather than as "some", so a reviewer can check the criteria against it.

**The publication counts are fixed by the parent and are stated here before they are asserted, because one of them is counter-intuitive.** Event one is published exactly once per attempt whatever the outcome. Event two is published exactly once where at least one line reached the target order and **exactly zero where none did**. Event three is published **once per line row in the rejected bucket** — an applied quantity of zero with an outcome other than `NOT_EVALUATED` — so it fans out, and **it is published zero times for a reorder in which every line was applied**. A reduced line is not a rejected line and does not publish it; a line on an aborted attempt carries `NOT_EVALUATED` and does not publish it; a degraded line at zero does publish it, carrying `UNATTRIBUTED_ERROR`. So a fully applied reorder produces two events in total and not three — which is worth writing down because the intuitive reading of "three events" is that all three fire on every success, and a criterion written that way would fail against a faithful implementation.

**How the seven map onto the five required coverage classes, named by criterion number so the claim is checkable.** Valid input is AC-1, which also carries the post-commit read that is this story's strong completion signal. Invalid or incomplete input is AC-2. An error naming the exact type returned is AC-3. An edge case is AC-4, which is the unavailable-variant category from section 7 expressed as a criterion together with the aborted branch. Observational neutrality is AC-5 and AC-6 — the first asserting that a subscriber which throws leaves the reorder response unchanged, the second that an existing operation is unchanged and publishes none of the three. AC-7 discharges the channel-and-language scoping obligation the epic places on every story whose behaviour varies with either.

## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story announces an availability-driven outcome and carries a request scope on every payload. Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

* Scenario: Category — zero, null or empty collection. Every requested line was rejected, so no line was applied and there is nothing for the applied event to announce.
   * Given one subscriber registered per event class through the typed subscribe [packages/core/src/event-bus/event-bus.ts:L130], and a reorder whose source resolves to four requested lines on four distinct variants every one of which has a saleable quantity of 0
   * When the reorder reaches its terminal state and the attempt row and its four line rows are written
   * Then **the attempt event is still published** and is not withheld for having nothing successful to announce: exactly one `ReorderAttemptEvent` is delivered, carrying an attempt row whose `outcome` is `NONE_APPLIED` and whose `fullyAppliedLineCount` and `partiallyAppliedLineCount` are both 0; **exactly zero** `ReorderAppliedEvent` is delivered, because the publication condition for that event is an applied-line count above zero and it is not met; and exactly four `ReorderLineRejectedEvent` are delivered, one per rejected-bucket line. "The buyer tried and got nothing" is the single most useful signal a demand consumer can receive, which is why the unconditional event exists [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.7 The Three Events And Their Payload Schemas — This File Is Their Authority]

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. The excluded-before-delegation outcome reaches the payload, and the aborted branch reports something different again.
   * Given a placed source order carrying a line whose variant was disabled after that order was placed, so the platform's bulk add would throw for it rather than accumulate an error [packages/core/src/service/services/order.service.ts:L693] and the reorder path withholds it from the call instead; and separately a reorder in which a projected variant stops resolving between the prevalidating read and the core call, so the call throws and the request transaction is rolled back
   * When each reorder reaches its terminal state
   * Then in the first case the withheld line is a rejected-bucket line and **one** `ReorderLineRejectedEvent` carries its `attemptLineId` and its `requestedVariantId` with a `finalLineOutcome` of `NOT_ADDED_VARIANT_UNAVAILABLE`, while **the payload carries no error name at all** — not because it was omitted but because none exists for this class, the platform supplying no error result for a variant that fails its own load predicate, so a subscriber reading the line row by `attemptLineId` finds a null recorded error name there too. In the second case **the payload reports the abort at attempt level and not at line level**: exactly one `ReorderAttemptEvent` carries an attempt row whose `outcome` is `ABORTED_UNRESOLVABLE_SOURCE_LINE` and whose `notEvaluatedLineCount` equals its `requestedLineCount`, and **zero rejected events are published**, because a line carrying `NOT_EVALUATED` was never evaluated and announcing it as a rejection would inflate every consumer's rejection count. That the attempt event is delivered at all is what proves it was published from the second transaction opened after the rollback, since the stream discards an event whose transaction did not commit [packages/core/src/event-bus/event-bus.ts:L337-L343]

* Scenario: Category — a price changed since the last purchase. No payload reports the price, and that is the design rather than an omission.
   * Given a source line whose recorded amount at placement was the integer 129900 in the smallest unit of the source order's currency, held on the platform's own declared list price for that line [packages/core/src/entity/order-line/order-line.entity.ts:L120-L121], and whose variant priced at the integer 134900 at the moment of the attempt, with the tax basis recording which of gross or net each figure is [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128]
   * When the reorder reaches its terminal state and its events are published
   * Then **not one of the three payloads carries a monetary value**, by the payload rule that anything beyond an id and a routing field is read from the row: the amount that applied at the attempt is recorded on the `ReorderAttemptLine` row as an **integer in the smallest currency unit** together with its `currencyCode` and its tax basis, all three set together or all three null, and a subscriber that needs the amount reads that row by the `attemptLineId` its payload carried. **No decimal amount and no currency symbol appears anywhere in this story**, no delta is computed here — reporting a change before the commit is FEATURE-001-03's work and reporting one after the add is already done by the platform's own calculated getters, neither of which this story duplicates [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated] — and **no currency conversion happens anywhere in this story**, so there is no place an exchange rate could be applied

* Scenario: Category — a concurrent modification or race. The same buyer has two reorders in flight at once and a subscriber must tell their events apart.
   * Given one authenticated Returning Buyer issuing two reorder requests that overlap in time, each against its own placed source order, neither carrying an `idempotencyKey`, and one subscriber registered per event class
   * When both requests reach their terminal states
   * Then **each attempt publishes its own events and no payload is attributable to the other attempt**, and a subscriber distinguishes them by identity rather than by arrival order: the two `ReorderAttemptEvent` payloads carry two different attempt rows with two different inherited identifiers and two different `correlationId` values [packages/core/src/entity/base/base.entity.ts:L31], and every `ReorderAppliedEvent` and `ReorderLineRejectedEvent` carries the `attemptId` of its own attempt, which is the key a subscriber groups on. **Arrival order across two attempts is not a property a subscriber may rely on**, and the stream guarantees typing and post-commit ordering rather than interleaving [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.8a Delivery Semantics — Stated As Absences, Because The Absences Are What Consumers Get Wrong]. Where the two requests instead carry the same non-null `idempotencyKey`, one attempt row is written rather than two and **one event set is published rather than two**, because a replay records nothing new and therefore announces nothing new

* Scenario: Category — a channel, currency or language mismatch between the original order and the reorder context.
   * Given a source order placed under one channel `token` [packages/core/src/entity/channel/channel.entity.ts:L62] while the reorder request carries a different token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L58-L62]; or the active channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differing from the source order's own currency code; or the request resolving to a language other than the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When the reorder reaches its terminal state and its events are published
   * Then **every payload carries the request context of the attempt, so a subscriber scopes its reaction to the channel the attempt belongs to rather than reacting globally** — which matters because a deployment with per-channel sellers has per-channel consumers — and the attempt row on the attempt event's `entity` records the `channelId` and the `languageCode` **of the attempt** and never those of the source order; a source order belonging to another channel does not resolve at all, so the announced outcome is a refused one rather than a cross-boundary read, and the boundary is hard rather than a filter a caller may widen; a currency difference is carried on the line rows as an integer amount beside its own code with no conversion attempted; and a language difference changes nothing on any payload, because every payload member is an identifier, an integer, a code snapshot or a closed enum member and not one of them is language-varying [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.12 Channel Scoping, Language Scoping And Monetary Values]
