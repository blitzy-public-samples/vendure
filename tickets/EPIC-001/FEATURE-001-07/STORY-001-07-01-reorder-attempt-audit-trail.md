## 1. Story Title

**Record every reorder attempt as one durable audit row with one row per distinct projected variant key, so that a Customer Support Agent can state from a stored record which lines reached the cart, which did not, and why.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Record a reorder attempt audit trail** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work is two plugin-owned tables, the **one** additive migration that creates them, and the service method that writes them. `ReorderAttempt` holds one row per attempt; `ReorderAttemptLine` holds one row per projected variant key, at the lowest `requestIndex` among the source lines that fed it. Both column lists are fixed by the parent feature, which declares its mapping block the only authority for them, and this story adopts them without adding, renaming or widening a column [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched].

**Three absences define this story as sharply as its two tables, and all three are stated positively rather than left to be inferred from silence** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.6 Named API Surfaces]:

- **No Shop API operation.** A buyer neither reads nor writes an audit row.
- **No Admin API operation.** The support-facing read is `reorderAttempts`, published by FEATURE-001-08 and delivered by its story 08-03 [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces]. No read operation and no permission definition is declared here.
- **No new error result.** Six are declared across the whole ticket set and none of them belongs to this feature, so the published `ErrorCode` enum gains nothing on this story's account and the side-effect widening the epic requires be reported rather than absorbed has no surface to arise on [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].

User Stories Index]. **The migration count is settled at ONE in the parent file, and this paragraph records how it got there because a reader of an earlier revision will remember it differently.** That revision had the parent ruling a single additive migration in three places — its named-entities section, its stories-index entry for this story, and its definition of done — while two other passages described a separately reversible migration A and migration B, and this paragraph reported the split as an unreconciled discrepancy for the parent to fix. **It is now reconciled, in favour of one migration, and the parent carries the reasoning** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4b The Migration Plan, Its Owner, And The Grain That Every Consumer Reads]: the generator emits one migration per invocation [packages/core/src/migrate.ts:L118], the child's non-nullable cascading foreign key means no deployment state wants it without the parent so independent revertibility buys nothing, and a per-engine failure is already attributable to a table by the statement that failed. The deciding argument is the child's `NOT NULL` cascading key to the parent: reverting a parent-only migration would leave a child table whose every row violates its own key, so the independent revertibility the two-migration form existed for was never reachable. **This story implements that one migration**, creating `reorder_attempt` before `reorder_attempt_line` and dropping them in the reverse order, and asserts that one revert invocation returns the schema to the state before either table existed.

## 3. Precedent In This Repository

**PRECEDENT:** partial — the recording idiom is shipped, the plugin-owned attempt tables are not.

The searched set is named so the claim is checkable rather than asserted: the whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. That is the same set the epic searched for its nomination reasoning, and the parent feature reaches the same verdict from its own side [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.14 Precedent In This Repository].

**The finding: nothing in this repository records reorder attempts**, because nothing in this repository performs a reorder. There is no attempt table, no per-line audit shape and no outcome-code vocabulary anywhere in the searched set.

**What is precedented, described exactly rather than loosely, because the loose description is wrong in a way that matters.** A shipped test plugin records history-style entries against an order — but it owns no table. It calls the platform's history service from its own resolver [packages/dev-server/test-plugins/custom-history-entry/custom-history-entry-plugin.ts:L28-L33] and writes into the *core* history-entry table, declaring its own entry type by augmenting the platform's history-data interfaces through TypeScript module augmentation [packages/dev-server/test-plugins/custom-history-entry/types.ts:L5-L12]. Its plugin metadata declares imports, an Admin API extension and a configuration function, and **no `entities` array at all** [packages/dev-server/test-plugins/custom-history-entry/custom-history-entry-plugin.ts:L54-L72]. So the precedent is "a plugin can add its own kind of auditable entry to a core table", not "a plugin owns audit tables".

**The unflattering half is required output, so it is stated plainly.** Persisting a row from a plugin service through the platform's connection service is re-application of a pattern this repository uses everywhere, and this story claims no originality for it. The parent forbids either of its two stories claiming `none`, and this story does not [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.14 Precedent In This Repository].

**What is novel beyond the precedent, stated as three specifics rather than as a claim of novelty:**

- **Two plugin-owned tables with a parent-and-child grain.** A history entry is one row against one order; an attempt is one parent row plus one child row per distinct projected variant key, which is a cardinality the core history table cannot express.
- **A per-line outcome-code vocabulary bound to the platform's real error types.** A recorded `errorCode` is drawn only from the five members of the existing `union UpdateOrderItemErrorResult` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], and the eleven-member outcome enum sits beside it to carry the classes for which the platform supplies no error result at all.
- **An attempt record that survives the request.** The reorder response is transient; the row is the system of record that the administrative read in story 08-03 and the recurring-demand aggregate both read afterwards.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when this file is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Customer Support Agent,
I want every reorder attempt written down as one durable row carrying the source order code, the attempt outcome and five line counts, with one child row per projected variant key carrying that key's own requested quantity and its projected key's applied quantity, its outcome code, any error type name and the source lines that fed it,
So that I can state from a stored record which lines a buyer's reorder added, which it did not and why, without asking the buyer to reproduce the attempt and without depending on a log line.
```

### 4.1 INVEST Criteria

- **Independent** — **not unconditionally, and the dependency is stated rather than claimed away.** The write path is triggered by `applyReorderToActiveOrder`, a mutation FEATURE-001-02 owns, and every column on the child row is copied from the internal mapped-outcome object that feature produces [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.3 The Internal Mapped-Outcome DTO]. - **Negotiable** — the column lists, the three closed enums, the nine index names and the twelve check constraints are fixed by the parent and are not open here [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums]. - **Valuable** — it is the first and only point at which a reorder leaves evidence. Without it, a support agent can describe what a buyer says happened and nothing else, and the recurring-demand aggregate has nothing to aggregate.
- **Estimable** — the nearest shipped analogue is a plugin declaring two entities with their relations and a service that persists through the platform's connection service, and the write is two statements over already-computed values. Section 9 carries the numbers, transcribed from the epic.
- **Sized Appropriately** — two entities in one additive migration, one recording service method with two write statements, one derived attempt outcome and five counts, over zero new operations, zero permission definitions and zero dashboard surfaces. It sits at five points on the epic's rubric, the value for a multi-entity write path, and it sits above that band's lines-of-code anchor for one stated reason: it adds a second structural element beyond the base shape, the child table with its own index and constraint set [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table]. Acceptance Criteria]:

- **applied at the requested quantity** — `ADDED`, with `appliedQuantity` equal to `requestedQuantity` and a null `errorCode`. **The equality reads that way because every fixture in this story names distinct variants, so each projected key has exactly one contributor.** Where a request names one variant twice the comparison is made at the key — the applied quantity a row carries is its key's, recorded identically against every line of that key rather than divided between them — and the parent states the rule in that form [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums, And The Counting Rule That Makes Them Add Up].
- **applied at a reduced quantity** — `ADDED_AT_REDUCED_QUANTITY`, carrying the exact integer the platform reported as available on `InsufficientStockError` [packages/core/src/api/schema/common/common-error-results.graphql:L53].
- **not applied, naming exactly one of the five existing types above** — one of the `NOT_ADDED_*` members with an `appliedQuantity` of zero and that type's name in `errorCode`.
- **excluded before delegation** — `NOT_ADDED_VARIANT_UNAVAILABLE` with an `appliedQuantity` of zero and a **null** `errorCode`, because the platform supplies no error result for this class at all: the bulk add loads each variant under an enabled-and-not-deleted predicate [packages/core/src/service/services/order.service.ts:L684-L691] and **throws** for a variant failing it [packages/core/src/service/services/order.service.ts:L693], aborting the batch rather than accumulating. The other three classes originate in the per-item collection that call returns beside the order [packages/core/src/service/services/order.service.ts:L663], which accumulates a validation failure and continues to the next item [packages/core/src/service/services/order.service.ts:L680-L683]. **Without the fourth class the audit trail cannot explain a whole-batch abort**, which is exactly what AC-4 asserts.

**Two fixture conventions apply throughout and are stated once.** First, every fixture below gives each source line a **distinct variant**, so the requested-line count, the projected-key count and the `reorder_attempt_line` row count coincide and every count assertion is exact; the parent fixes the stored grain at one row per projected variant key carrying that key's own zero-based `requestIndex`, and AC-4 is the one criterion that deliberately breaks the distinct-variant convention in order to assert that collapse [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4b The Migration Plan, Its Owner, And The Grain That Every Consumer Reads]. **An earlier revision of this paragraph reported a residual disagreement inside that file, which described the lineage column in one place as a single identifier and in another as a list; that disagreement has been reconciled in the parent and the report is withdrawn** — **the column is `contributors`**, it is a list in every passage that names it, holding each contributing source-line identifier paired with its requested quantity in the order the response reported them, and it is lineage only. **An earlier revision of this paragraph called it `contributingSourceLineIds`, a name no entity in this set declares** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract]. Second, the target cart's prior state is stated wherever a resulting quantity is asserted, because the platform's write path sums the requested quantity with the quantity already on the line before clamping.

**Money, wherever an attempt line records a price, is three values and not one**: an integer in the smallest unit of its currency, the `currencyCode`, and the tax basis copied from the platform's own per-line declaration of whether a list price includes tax [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128], whose JSDoc ties that flag to the settings of the current channel [packages/core/src/entity/order-line/order-line.entity.ts:L125]. ## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story records an availability reading and copies a request scope onto every row. Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

* Scenario: Category — zero, null or empty collection. Every requested line was refused, so nothing was applied.
   * Given an authenticated Returning Buyer whose active cart holds exactly one line before the call, and a placed source order resolving to exactly four requested lines on four distinct variants where every variant resolves under the enabled-and-not-deleted predicate but every one has `stockOnHand` equal to its `stockAllocated` [packages/core/src/entity/stock-level/stock-level.entity.ts:L40] and [packages/core/src/entity/stock-level/stock-level.entity.ts:L43] so every saleable quantity is 0
   * When the reorder is executed against that source
   * Then **the attempt row still exists** and is not omitted for having achieved nothing: it carries the `outcome` `NONE_APPLIED`, a `requestedLineCount` of 4, a `fullyAppliedLineCount` of 0, a `partiallyAppliedLineCount` of 0, a `rejectedLineCount` of 4 and a `notEvaluatedLineCount` of 0; exactly four `reorder_attempt_line` rows exist at `requestIndex` 0 to 3, each carrying `NOT_ADDED_OUT_OF_STOCK` with an `appliedQuantity` of 0 and an `errorCode` naming `InsufficientStockError` [packages/core/src/api/schema/common/common-error-results.graphql:L50]; and the buyer's cart still holds exactly the one line it held before. **Zero applied lines is a recorded fact, not an absent record** — and it is distinct from AC-2, where the source resolved to no line at all and the attempt therefore carries a refused outcome with zero child rows

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. The recorded row must outlive the variant it names.
   * Given a placed source order carrying a line whose variant was disabled after that order was placed, so the attempt records that line as excluded before delegation, and that variant is afterwards removed from the catalogue outright rather than disabled
   * When the removal completes
   * Then the `reorder_attempt_line` row still exists with its `requestIndex`, its `requestedQuantity`, its `appliedQuantity` of 0 and its `outcome` of `NOT_ADDED_VARIANT_UNAVAILABLE` unchanged, and its `requestedProductVariantId` still holds the **exact identifier of the deleted variant**, byte-for-byte unchanged, because that column is an immutable non-null snapshot with no foreign key rather than a relation. **An earlier version of this scenario asserted the opposite** — that the id "becomes null through the nullable set-null relation the parent declares" — and that behaviour is withdrawn in the parent, because nulling it erased the grouping key the administrative aggregate publishes non-null [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]; **and the row still identifies the item, because the label was snapshotted at insert time rather than resolved through that relation** — `requestedProductVariantName` and `requestedProductVariantSku` hold the exact non-null strings they were written with and are byte-for-byte unchanged by the deletion, both being immutable non-null columns on this table rather than projections of the catalogue row [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **Losing the row would delete the evidence about the exact variant a support agent is asked about, and keeping a row whose only identifier has just been nulled would delete the same evidence less visibly** — which is why the relation is nullable rather than cascading *and* why the label does not travel through it. AC-4 asserts what is recorded at the moment of the attempt; this scenario asserts what the row still says afterwards, and the assertion a suite must make here is on the two snapshot strings, not on the nulled identifier alone

* Scenario: Category — a price changed since the last purchase. The row records the amount that applied at the attempt, as an integer.
   * Given a source line whose `listPrice` at placement was the integer 129900 [packages/core/src/entity/order-line/order-line.entity.ts:L120-L121], expressed in the smallest unit of the currency its **order** records — `Order.currencyCode` [packages/core/src/entity/order/order.entity.ts:L142], which is an order-level column that `OrderLine` does not carry, so a recorded line price is meaningless without the code copied alongside it, and whose variant priced at the integer 134900 at the moment of the attempt
   * When the reorder is executed against that source
   * Then the `reorder_attempt_line` row records the amount that applied at the attempt as an **integer in the smallest currency unit**, together with its `currencyCode` and its tax basis, all three set or all three null [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128] — the tax basis being required rather than decorative, because the same integer denotes two different amounts depending on it [packages/core/src/entity/order-line/order-line.entity.ts:L125]. **No decimal amount and no currency symbol appears on either table, no historical price is copied onto the row, and no delta is computed here**: reporting a change before the commit is FEATURE-001-03's work and reporting one after the add is already done by the platform's own calculated getters, neither of which this story duplicates [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. No currency conversion happens anywhere in this story, so there is no place an exchange rate could be applied

* Scenario: Category — a concurrent modification or race. The same buyer has two reorders in flight at once.
   * Given one authenticated Returning Buyer issuing two reorder requests that overlap in time, each against its own placed source order, and neither request carrying an `idempotencyKey`
   * When both requests complete
   * Then **two** `reorder_attempt` rows exist, each with its own `correlationId`, its own inherited creation timestamp [packages/core/src/entity/base/base.entity.ts:L31] and its own child rows, and neither attempt's lines are attributed to the other: they are distinguished by the unique index over the correlation identifier, which is minted before the write is attempted, and each child row is pinned to its parent by the unique key over the attempt identifier together with `requestIndex`, so a double write cannot produce a duplicate line and a count assertion cannot pass by accident [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4.1 The Index Contract]. **Neither keyless request collides with the other on the replay claim, and the reason is the digest rule rather than a null**: each fills `replayClaimDigest` with a digest over its own `correlationId`, which is unique per attempt, so the plain unique index over that column admits both. Where the two requests instead carry the **same** non-null `idempotencyKey`, both digest the same claim tuple, so that same plain unique index refuses the second insert and one attempt row with one set of child rows exists rather than two — which is the mechanism that makes FEATURE-001-02's replay claim atomic rather than a read-then-write [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.2 Replay Safety]. **A unique index qualified by a row predicate is not asserted here and is not used**, because it is not deployable on every engine this story is evidenced against [.github/workflows/build_and_test.yml:jobs]

* Scenario: Category — a channel, currency or language mismatch between the original order and the reorder context.
   * Given a source order placed under one channel `token` [packages/core/src/entity/channel/channel.entity.ts:L62] while the reorder request carries a different token in the `vendure-token` header [packages/core/src/entity/channel/channel.entity.ts:L56-L59]; or the active channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] differing from the source order's `currencyCode` [packages/core/src/entity/order/order.entity.ts:L142]; or the request resolving to a language other than the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * When the reorder is executed against that source
   * Then the attempt row records the channel and the `languageCode` **of the attempt** and never those of the source order, so a row written under one token is not readable under another and the boundary is hard rather than a filter a caller may widen; a source order belonging to another channel does not resolve at all, so the recorded outcome is the refused member of AC-2 with a null code snapshot rather than a cross-boundary read; a currency difference is recorded by keeping each amount beside its own `currencyCode` with no conversion attempted; and a language difference changes nothing else on either table, because every other recorded value is an identifier, an integer or a closed enum member and none of them is language-varying [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.12 Channel Scoping, Language Scoping And Monetary Values]
