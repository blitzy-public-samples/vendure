## 3. PRECEDENT In This Repository

**PRECEDENT:** partial — the recording idiom is shipped, the plugin-owned attempt tables are not.

The searched set is named so the claim is checkable rather than asserted: the whole of `packages/dev-server/example-plugins/`, the whole of `packages/dev-server/test-plugins/`, and `packages/dashboard/test-plans/`. That is the same set the epic searched for its nomination reasoning, and the parent feature reaches the same verdict from its own side [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.14 Precedent In This Repository].

**The finding: nothing in this repository records reorder attempts**, because nothing in this repository performs a reorder. There is no attempt table, no per-line audit shape and no outcome-code vocabulary anywhere in the searched set.

**What is precedented, described exactly rather than loosely, because the loose description is wrong in a way that matters.** A shipped test plugin records history-style entries against an order — but it owns no table. It calls the platform's history service from its own resolver [packages/dev-server/test-plugins/custom-history-entry/custom-history-entry-plugin.ts:L28-L33] and writes into the *core* history-entry table, declaring its own entry type by augmenting the platform's history-data interfaces through TypeScript module augmentation [packages/dev-server/test-plugins/custom-history-entry/types.ts:L5-L12]. Its plugin metadata declares imports, an Admin API extension and a configuration function, and **no `entities` array at all** [packages/dev-server/test-plugins/custom-history-entry/custom-history-entry-plugin.ts:L54-L72]. So the precedent is "a plugin can add its own kind of auditable entry to a core table", not "a plugin owns audit tables".

**The unflattering half is required output, so it is stated plainly.** Persisting a row from a plugin service through the platform's connection service is re-application of a pattern this repository uses everywhere, and this story claims no originality for it. The parent forbids either of its two stories claiming `none`, and this story does not [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.14 Precedent In This Repository].

**What is novel beyond the precedent, stated as three specifics rather than as a claim of novelty:**

- **Two plugin-owned tables with a parent-and-child grain.** A history entry is one row against one order; an attempt is one parent row plus one child row per requested line, which is a cardinality the core history table cannot express.
- **A per-line outcome-code vocabulary bound to the platform's real error types.** A recorded `errorCode` is drawn only from the five members of the existing `union UpdateOrderItemErrorResult` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], and the eleven-member outcome enum sits beside it to carry the classes for which the platform supplies no error result at all.
- **An attempt record that survives the request.** The reorder response is transient; the row is the system of record that the administrative read in story 08-03 and the recurring-demand aggregate both read afterwards.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when this file is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Customer Support Agent,
I want every reorder attempt written down as one durable row carrying the source order code, the attempt outcome and five line counts, with one child row per requested line carrying that line's requested and applied quantity, its outcome code and any error type name,
So that I can state from a stored record which lines a buyer's reorder added, which it did not and why, without asking the buyer to reproduce the attempt and without depending on a log line.
```

### 4.1 INVEST Criteria

- **Independent** — **not unconditionally, and the dependency is stated rather than claimed away.** The write path is triggered by `applyReorderToActiveOrder`, a mutation FEATURE-001-02 owns, and every column on the child row is copied from the internal mapped-outcome object that feature produces [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5.3 The Internal Mapped-Outcome DTO]. What this story *is* independent of is every other story in the set, including its own sibling: it needs no list table, no preview, no cadence and no event. The value it delivers alone is the whole of the system of record — the two tables exist and are populated, which is what makes the administrative read buildable and what makes any later analysis possible at all.
- **Negotiable** — the column lists, the three closed enums, the seven index names and the eleven check constraints are fixed by the parent and are not open here [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4a Three Closed Outcome Enums]. What is genuinely open is the value of the keep period governing how long a customer-linked row survives, which is the epic's third product decision and belongs to a maintainer [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions], and the batch size the data-lifecycle pass uses, which is a configured option rather than a design choice.
- **Valuable** — it is the first and only point at which a reorder leaves evidence. Without it, a support agent can describe what a buyer says happened and nothing else, and the recurring-demand aggregate has nothing to aggregate.
- **Estimable** — the nearest shipped analogue is a plugin declaring two entities with their relations and a service that persists through the platform's connection service, and the write is two statements over already-computed values. Section 9 carries the numbers, transcribed from the epic.
- **Sized Appropriately** — two entities in one additive migration, one recording service method with two write statements, one derived attempt outcome and five counts, over zero new operations, zero permission definitions and zero dashboard surfaces. It sits at five points on the epic's rubric, the value for a multi-entity write path, and it sits above that band's lines-of-code anchor for one stated reason: it adds a second structural element beyond the base shape, the child table with its own index and constraint set [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table]. It is not a candidate for splitting, because a parent table without its child records nothing a support agent can read.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact row count, an exact enum member, an exact integer, or an exact error type name. No criterion asserts a state that has to be judged.

## 5. Acceptance Criteria

Seven criteria. **Each names exactly one published GraphQL operation under test**, so a failure points at a single contract. Criteria name operations, their arguments, and entity, table and column names as database preconditions; none names a resolver class, a file path or an internal method name. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

Three preconditions hold for every criterion without being repeated in each, because they are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites]: an authenticated session, a channel resolved from the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L56-L59], and a language resolved from the channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. **Every recorded row stores both**, so an attempt recorded under one channel token is not readable under another, and the stored `languageCode` is the code the request resolved under rather than a translation of anything [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.12 Channel Scoping, Language Scoping And Monetary Values].

**How the seven map onto the five required coverage classes, named by criterion number so the claim is checkable.** Valid input is AC-1. Invalid or incomplete input is AC-2. An error naming the exact type returned is AC-3. An edge case is AC-4, which is the excluded-before-delegation class from section 7 expressed as a criterion. Observational neutrality is AC-5 and AC-6, the first asserting that the reorder mutation's response is unchanged and the second that an existing operation is unchanged and writes no audit row. AC-7 is the seventh and discharges a separate obligation the epic places on this story by name: each of the five stories blocked by its third product decision carries one assertion of the observable behaviour for a soft-deleted customer [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions].

**The trigger and the observable completion signal are named once and inherited by every criterion, because "it happens eventually" is never a criterion** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.10 Asynchronous Delivery]. The trigger is one reorder attempt reaching a terminal state — settled, refused or aborted. The observable completion signal is the persisted rows becoming readable: after the mutation has returned, a read finds the `reorder_attempt` row together with exactly one `reorder_attempt_line` row per requested line. On the settled branch that is guaranteed by the parent's atomic model, under which the cart lines and the audit rows commit together or the mutation fails [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.5a The Durability Model].

**The recorded error vocabulary is closed, and no criterion below names anything outside it.** A recorded `errorCode` is the name of an existing type drawn from the five members of `union UpdateOrderItemErrorResult` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117], listed as bullets rather than in the schema's own union form:

- `OrderModificationError` [packages/core/src/api/schema/common/common-error-results.graphql:L80]
- `OrderLimitError`, carrying `maxItems` [packages/core/src/api/schema/common/common-error-results.graphql:L37] and [packages/core/src/api/schema/common/common-error-results.graphql:L40]
- `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44]
- `InsufficientStockError`, carrying `quantityAvailable` as a non-null integer [packages/core/src/api/schema/common/common-error-results.graphql:L50] and [packages/core/src/api/schema/common/common-error-results.graphql:L53]
- `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L103]

**This story declares no new error result**, so that set does not grow and the published error-code enum is unchanged. Beside the recorded error name sits the plugin's own outcome code, and the four outcome classes it must express are the ones the sibling story fixes for the response, mirrored here member for member [tickets/EPIC-001/FEATURE-001-02/STORY-001-02-04-per-line-reorder-outcome-report.md:§5. Acceptance Criteria]:

- **applied at the requested quantity** — `ADDED`, with `appliedQuantity` equal to `requestedQuantity` and a null `errorCode`.
- **applied at a reduced quantity** — `ADDED_AT_REDUCED_QUANTITY`, carrying the exact integer the platform reported as available on `InsufficientStockError` [packages/core/src/api/schema/common/common-error-results.graphql:L53].
- **not applied, naming exactly one of the five existing types above** — one of the `NOT_ADDED_*` members with an `appliedQuantity` of zero and that type's name in `errorCode`.
- **excluded before delegation** — `NOT_ADDED_VARIANT_UNAVAILABLE` with an `appliedQuantity` of zero and a **null** `errorCode`, because the platform supplies no error result for this class at all: the bulk add loads each variant under an enabled-and-not-deleted predicate [packages/core/src/service/services/order.service.ts:L684-L691] and **throws** for a variant failing it [packages/core/src/service/services/order.service.ts:L693], aborting the batch rather than accumulating. The other three classes originate in the per-item collection that call returns beside the order [packages/core/src/service/services/order.service.ts:L663], which accumulates a validation failure and continues to the next item [packages/core/src/service/services/order.service.ts:L680-L683]. **Without the fourth class the audit trail cannot explain a whole-batch abort**, which is exactly what AC-4 asserts.

**Two fixture conventions apply throughout and are stated once.** First, every fixture below gives each source line a **distinct variant**, so the requested-line count, the projected-key count and the `reorder_attempt_line` row count coincide and every count assertion is exact; the parent fixes the stored grain at one row per requested source line at its own `requestIndex` [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4b The Migration Plan, Its Owner, And The Grain That Every Consumer Reads], while describing the lineage column in one place as a single identifier and in another as a list — a residual disagreement inside that file which the distinct-variant fixtures leave untouched and which is noted here rather than resolved by this story. Second, the target cart's prior state is stated wherever a resulting quantity is asserted, because the platform's write path sums the requested quantity with the quantity already on the line before clamping.

**Money, wherever an attempt line records a price, is three values and not one**: an integer in the smallest unit of its currency, the `currencyCode`, and the tax basis copied from the platform's own per-line declaration of whether a list price includes tax [packages/core/src/entity/order-line/order-line.entity.ts:L127-L128], whose JSDoc ties that flag to the settings of the current channel [packages/core/src/entity/order-line/order-line.entity.ts:L125]. All three are set together or all three are null. A decimal monetary value in an audit row is a defect rather than a formatting preference.

**A note on the completion signal in AC-1, because it is the one place a reader could substitute a weaker assertion.** The signal asserted is the strong one — the rows are readable once the mutation has returned. ## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus the two conditional categories that apply because this story records an availability reading and copies a request scope onto every row. Each is labelled with its category inline, so the category matrix never appears as a table in a story file.

* Scenario: Category — zero, null or empty collection. Every requested line was refused, so nothing was applied.
   * Given an authenticated Returning Buyer whose active cart holds exactly one line before the call, and a placed source order resolving to exactly four requested lines on four distinct variants where every variant resolves under the enabled-and-not-deleted predicate but every one has `stockOnHand` equal to its `stockAllocated` [packages/core/src/entity/stock-level/stock-level.entity.ts:L40] and [packages/core/src/entity/stock-level/stock-level.entity.ts:L43] so every saleable quantity is 0
   * When the reorder is executed against that source
   * Then **the attempt row still exists** and is not omitted for having achieved nothing: it carries the `outcome` `NONE_APPLIED`, a `requestedLineCount` of 4, a `fullyAppliedLineCount` of 0, a `partiallyAppliedLineCount` of 0, a `rejectedLineCount` of 4 and a `notEvaluatedLineCount` of 0; exactly four `reorder_attempt_line` rows exist at `requestIndex` 0 to 3, each carrying `NOT_ADDED_OUT_OF_STOCK` with an `appliedQuantity` of 0 and an `errorCode` naming `InsufficientStockError` [packages/core/src/api/schema/common/common-error-results.graphql:L50]; and the buyer's cart still holds exactly the one line it held before. **Zero applied lines is a recorded fact, not an absent record** — and it is distinct from AC-2, where the source resolved to no line at all and the attempt therefore carries a refused outcome with zero child rows

* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. The recorded row must outlive the variant it names.
   * Given a placed source order carrying a line whose variant was disabled after that order was placed, so the attempt records that line as excluded before delegation, and that variant is afterwards removed from the catalogue outright rather than disabled
   * When the removal completes
   * Then the `reorder_attempt_line` row still exists with its `requestIndex`, its `requestedQuantity`, its `appliedQuantity` of 0 and its `outcome` of `NOT_ADDED_VARIANT_UNAVAILABLE` unchanged, and its `requestedProductVariantId` becomes null through the nullable set-null relation the parent declares rather than the row being removed with the variant [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **Losing the row would delete the evidence about the exact variant a support agent is asked about**, which is why the relation is nullable rather than cascading. AC-4 asserts what is recorded at the moment of the attempt; this scenario asserts what the row still says afterwards

* Scenario: Category — a price changed since the last purchase. The row records the amount that applied at the attempt, as an integer.
   * Given a source line whose `listPrice` at placement was the integer 129900 in the smallest unit of the source order's `currencyCode` [packages/core/src/entity/order-line/order-line.entity.ts:L120] and [packages/core/src/entity/order/order.entity.ts:L142], and whose variant priced at the integer 134900 at the moment of the attempt
   * When the reorder is executed against that source

Existing Mechanisms That Must Not Be Duplicated]. No currency conversion happens anywhere in this story, so there is no place an exchange rate could be applied

* Scenario: Category — a concurrent modification or race. The same buyer has two reorders in flight at once.
   * Given one authenticated Returning Buyer issuing two reorder requests that overlap in time, each against its own placed source order, and neither request carrying an `idempotencyKey`
   * When both requests complete
   * Then **two** `reorder_attempt` rows exist, each with its own `correlationId`, its own inherited creation timestamp [packages/core/src/entity/base/base.entity.ts:L31] and its own child rows, and neither attempt's lines are attributed to the other: they are distinguished by the unique index over the correlation identifier, which is minted before the write is attempted, and each child row is pinned to its parent by the unique key over the attempt identifier together with `requestIndex`, so a double write cannot produce a duplicate line and a count assertion cannot pass by accident [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4.1 The Index Contract]. * Scenario: Category — a channel, currency or language mismatch between the original order and the reorder context.

## 8. Dependencies

Stated in the epic's dependency form — the required thing, then why it is required and where it belongs — with **each entry classified as a data dependency or a shared code path**, because a prerequisite without a classification cannot be sequenced. Direction is stated for every story-to-story entry, since a dependency without a direction cannot be sequenced either.
