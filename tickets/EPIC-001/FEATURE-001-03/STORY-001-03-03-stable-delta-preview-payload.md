## 4. Prospective Payload Contract

**Everything in this section is a target named in ticket text.** `reorderPreview`, `ReorderPreviewInput`, `ReorderPreview`, `ReorderPreviewSource`, `ReorderPreviewLine`, `ReorderPreviewResult`, `ReorderLineAvailability`, `ReorderList`, `ReorderListLine` and the plugin package do not exist in this checkout, so **none of them carries a citation** and a downstream reader must treat none of them as verified. The shapes are the parent feature's and are inherited rather than re-decided here [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. What this story adds is not a field: it is the set of statements the payload makes **about itself**, and each of the ten sub-sections below is one such statement.

The shape those statements are made over, reproduced so a reader does not have to hold two files open:

```graphql
type ReorderPreview {
  source: ReorderPreviewSource!
  readAt: DateTime!
  currencyCode: CurrencyCode!
  lines: [ReorderPreviewLine!]!
}
type ReorderPreviewLine {
  requestIndex: Int!
  sourceOrderLineId: ID
  reorderListLineId: ID
  productVariant: ProductVariant!
  productVariantId: ID!
  requestedQuantity: Int!
  addableQuantity: Int!
  availability: ReorderLineAvailability!
  stockLevel: String!
  historicalUnitPrice: Money
  historicalUnitPriceWithTax: Money
  currentCataloguePrice: Money!
  currentCataloguePriceWithTax: Money!
  unitPriceDelta: Money
  unitPriceWithTaxDelta: Money
}
```

### 4.1 The Field Set And Its Nullability

**A consumer may rely on the following, and on nothing that is not written here.** Nullability is declared per field rather than described in aggregate, because "some fields may be null" is the statement a consumer cannot code against.

Non-null on the wrapper, present in every response that returns the success member:

- **`source`** — which source the entries were projected from. Non-null. Its own three fields, `sourceOrderId`, `sourceOrderCode` and `reorderListId`, are each individually nullable because exactly one addressing form applies to any one request: an order-sourced preview carries the first two with a null `reorderListId`, and a list-sourced preview carries `reorderListId` with the other two null. **A consumer determines which form it received by testing `reorderListId` for a value rather than by inspecting the input it sent**, so a response is self-describing.
- **`readAt`** — the instant the read was taken, as a `DateTime`. Non-null. Section 4.5 is the reason this field exists at all rather than being an implementation curiosity.
- **`currencyCode`** — one currency code for the whole response, resolved from the requesting channel. Non-null. It is carried once on the wrapper rather than repeated per entry because a single response never mixes currencies: every entry was priced in the one channel the request resolved to.
- **`lines`** — the entry list. Non-null, and **non-null in the empty case too**: a source that projects to no entry returns an empty list, never a null and never an error. Section 7's first scenario asserts it.

Non-null on every entry:

- **`requestIndex`** — a stable per-response index that matches the index the commit mutation assigns to the same projected line, so a storefront joins a preview entry to a commit outcome without guessing at identity.
- **`productVariant`** and **`productVariantId`** — the variant reference in both forms, so a consumer that already holds a variant cache can key on the id without paying for the object.
- **`requestedQuantity`** — the quantity the preview was computed for, as an integer.
- **`addableQuantity`** — the request-specific obtainable quantity, as an integer, **bounded above by `requestedQuantity`** and clamped to zero at the bottom. Section 4.4 states why an integer is publishable here at all.
- **`availability`** — the machine-readable classification, one member of the plugin-owned enumeration.
- **`stockLevel`** — the display string, typed `String!`. Section 4.4 states why it is a string and not an enumeration.
- **`currentCataloguePrice`** and **`currentCataloguePriceWithTax`** — the current catalogue operands as integers. Non-null, because a variant that has no resolvable current price is not reported as a priced entry at all.

Nullable on an entry, and **null together rather than in any mixed combination**:

- **`sourceOrderLineId`** and **`reorderListLineId`** — whichever addressing form does not apply is null, matching the wrapper's `source`.
- **`historicalUnitPrice`**, **`historicalUnitPriceWithTax`**, **`unitPriceDelta`** and **`unitPriceWithTaxDelta`** — all four are absent for a list-sourced entry, because a list line records no price of any kind. **An absent comparison is reported as an absence and never as the integer 0**, since a zero asserts that the price was compared and did not move while an absence asserts that no comparison was possible. The net pair and the gross pair are absent together, because net is subtracted from net and gross from gross and a half-populated pair would invite a mixed-basis subtraction downstream. STORY-001-03-01 fixes the rule; this story publishes it.

**Two guarantees about the set as a whole, and they are the durability half of the contract:**

- **A field is never repurposed.** A published field keeps the meaning its schema description gives it for the life of the field. A changed meaning arrives as a new field with the old one carrying a deprecation, never as the same field returning something else — which is the one failure mode a consumer cannot detect from a schema comparison, because the schema looks identical.
- **A field is never removed without a deprecation first.** Additions are additive by construction; removals are not, and this contract does not perform one.

### 4.2 Entry Count And Ordering

**The entry count is exact and the ordering is stated, because an exact count with its ordering is what replaces a banned adjective here.**

- **One entry per distinct projected variant, not one per source line.** Duplicate source lines naming the same variant are collapsed onto one entry before anything is read, with their quantities summed, against the same variant-keyed projection the commit path defines [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.7a The Preview Is Computed Against The Target Cart]. **A source of *n* lines naming *n* distinct variants therefore returns exactly *n* entries**, and a source of *n* lines naming *m* distinct variants returns exactly *m*.
- **The order is the source's own recorded line order**, taking each distinct variant's position from its first appearance in the source. A list-sourced preview follows the list's own recorded line order on the same rule. **The ordering is published in the schema description rather than left as observed behaviour**, because an ordering a consumer observes and relies on without being promised it is a defect waiting for a query-planner change.
- **`requestIndex` is dense and zero-based across the returned entries**, so a consumer can address an entry by position as well as by variant.

### 4.3 Money

**Every monetary value is an integer in the smallest unit of its currency, always accompanied by the response's `currencyCode`.** A decimal monetary value anywhere in the payload, in a fixture or in a schema description is a defect, not a formatting preference. The platform models money this way: the published scalar is declared as `scalar Money` [packages/core/src/api/schema/common/common-types.graphql:L7], and the catalogue surface a storefront already reads pairs `price: Money!` with `currencyCode: CurrencyCode!` and `priceWithTax: Money!` on the same type [packages/core/src/api/schema/common/product.type.graphql:L53], [packages/core/src/api/schema/common/product.type.graphql:L54] and [packages/core/src/api/schema/common/product.type.graphql:L55].

**The qualification this story owns, and it is the reason this sub-section exists rather than being one line in section 4.1.** The `Money` scalar does **not** itself enforce the integer form. It is based on the native float scalar [packages/core/src/api/config/money-scalar.ts:L29] and its own description states that it supports signed double-precision fractional values [packages/core/src/api/config/money-scalar.ts:L33-L35], deliberately, so that a deployment may configure a different money strategy. **A consumer therefore cannot infer the integer form from the schema's type alone, and this payload's documentation states it explicitly instead** [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.9 Channel Scoping]. That is a published statement rather than a hope: the assertion that every monetary field in a response parses as an integer belongs to AC-1 and to the definition of done, not to a comment.

**And one statement about what the number is.** `currentCataloguePrice` is the variant's current catalogue price on the response's stated tax basis, read at `readAt`. **It is not a quote, not a total, not an expected charge, not a locked price and not a price guarantee**, and no field in this payload is named or described as any of those. Four documented mechanisms can make a committed price differ from it, none of them a race, and the parent feature enumerates all four [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.9a The Reported Price Is The Current Catalogue Price]. The decisive one is that a deployment may configure `orderOptions.changedPriceHandlingStrategy` to hold the earlier price [packages/core/src/config/order/changed-price-handling-strategy.ts:L17-L18], in which case the buyer is charged something this payload never showed — and by default the latest price is used and the resulting change surfaces on the existing in-cart change field instead [packages/core/src/config/order/changed-price-handling-strategy.ts:L12-L13].

### 4.4 Availability

**Two fields carry availability, and the split between them is the whole of the contract.**

- **`stockLevel` is typed `String!` and is whatever the configured display strategy returns.** The published field this mirrors is `ProductVariant.stockLevel: String!` [packages/core/src/api/schema/common/product.type.graphql:L56] on the Shop API's `ProductVariant` type [packages/core/src/api/schema/common/product.type.graphql:L42]. The strategy behind it declares one method returning `string` [packages/core/src/config/catalog/stock-display-strategy.ts:L27] and is deployment-configurable through `catalogOptions.stockDisplayStrategy` [packages/core/src/config/catalog/stock-display-strategy.ts:L14]. **Publishing this field as an enumeration would break a deployment that had supplied its own vocabulary, at schema-serialisation time**, so it is not narrowed. Under the shipped `DefaultStockDisplayStrategy` [packages/core/src/config/catalog/default-stock-display-strategy.ts:L14] the value is exactly one of `OUT_OF_STOCK`, `LOW_STOCK` or `IN_STOCK` [packages/core/src/config/catalog/default-stock-display-strategy.ts:L17-L21], with the low-stock boundary at the constructor's shipped default of 2 [packages/core/src/config/catalog/default-stock-display-strategy.ts:L15] — and **a criterion asserting one of those three names the default strategy in its Given**, per the rule the parent feature fixes for every story in it [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.5.1 The Three Stock Tokens]. STORY-001-03-02 owns the vocabulary; this story owns publishing that it is open rather than closed.
- **The assertion that survives a replaced strategy is an identity, not a literal.** For any variant in any deployment, an entry's `stockLevel` equals what `ProductVariant.stockLevel` [packages/core/src/api/schema/common/product.type.graphql:L56] returns for that same variant in that same request, because both resolve through the one configured strategy. **That is the general form of the guarantee and it is the one this contract publishes**, so a buyer never sees two different answers to "is this in stock" from one deployment.
- **`availability` is the plugin-owned enumeration and is exhaustive**, because the plugin owns it. It is the field a consumer switches on. It describes **the request in this cart** rather than the variant in the abstract, which is why an entry may carry a `stockLevel` of `IN_STOCK` beside an `availability` reporting that the line is not obtainable — the buyer's own active order already holds every obtainable unit. **That pairing is specified output rather than a contradiction**, and STORY-001-03-02 asserts it.

**No raw stock figure appears anywhere in this payload.** No field returns `stockOnHand`, `stockAllocated` or an unbounded saleable level. The prohibition is structural rather than remembered: `StockLevel` is not a Shop API type at all, being absent from the type list of the checked-in introspection snapshot [schema-shop.json:data.__schema.types], and the display strategy exists precisely because directly exposing stock levels over a public API is treated as a leak of sensitive information [packages/core/src/config/catalog/stock-display-strategy.ts:L7-L10].

**The one integer that is published, with its bound as the whole of its justification.** `addableQuantity` never exceeds its own entry's `requestedQuantity`, so asking for two and being told two discloses that at least two exist and nothing more. The disclosure level is no greater than the platform's own, because `InsufficientStockError` already publishes `quantityAvailable: Int!` on a public Shop API mutation [packages/core/src/api/schema/common/common-error-results.graphql:L50] and [packages/core/src/api/schema/common/common-error-results.graphql:L53]; the change is only that a buyer learns it in time to act.

### 4.5 No Reservation, No Price Lock

**The payload is a read taken at `readAt` and nothing more. It holds no stock, locks no price, creates no allocation and confers no entitlement.**

**The statement lives in the operation's own published schema description, not only in this ticket**, and that placement is the deliverable rather than a courtesy: a storefront developer meets the caveat while reading the schema, which is where they are when they decide what to build. Four clauses are published, in these terms:

- the result is a point-in-time read taken at the instant the response reports;
- no stock is held and no price is locked by taking it;
- a commit re-evaluates every line at write time and **is authoritative over the preview**, so the two disagreeing is specified behaviour rather than a defect [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.10 A Point-In-Time Read Is Not A Reservation];
- a consumer that intends to act on the payload re-reads at commit rather than trusting the earlier response.

**No freshness window is stated, in any unit.** This repository declares no such figure, and inventing one would be worse than saying nothing: a stated window implies a guarantee the read does not make. AC-6 asserts the caveat's presence and the re-read behaviour inside a criterion rather than leaving either to prose.

### 4.6 The Error Channel Is Inherited, Not Extended — And The Union Membership This Story Closes

**This story declares no error result.** Its feature declares none of the six the ticket set introduces [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.11 No New Table, No New Error Result], and every error type named anywhere in this file is drawn from the **thirty-one** types that already implement the `ErrorResult` interface in this checkout — fifteen in the common error schema, from its first declaration [packages/core/src/api/schema/common/common-error-results.graphql:L2] to its last [packages/core/src/api/schema/common/common-error-results.graphql:L103], and sixteen more in the shop-specific one, likewise from first [packages/core/src/api/schema/shop-api/shop-error-results.graphql:L2] to last [packages/core/src/api/schema/shop-api/shop-error-results.graphql:L130].

Two paths, both inherited from STORY-001-03-01 and re-decided by neither this story nor STORY-001-03-02:

- **A non-positive per-line quantity override returns `NegativeQuantityError`** [packages/core/src/api/schema/common/common-error-results.graphql:L44], which exists today and is already a member of the core union covering order-item operations [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117]. Naming it invents nothing.
- **An unresolvable, unowned, foreign-channel or empty source returns zero entries and no error type at all.** The precedent is published and exact: `order(id: ID!): Order` is nullable [packages/core/src/api/schema/shop-api/shop.api.graphql:L34] and its own description states that only orders belonging to the currently-authenticated user may be queried [packages/core/src/api/schema/shop-api/shop.api.graphql:L31-L32]. Following it closes an enumeration channel — a caller cannot learn whether another customer's source exists by asking — and keeps this story inside the verified vocabulary.

**The union membership, which STORY-001-03-01 explicitly referred here rather than settling.** That story records the referral in its own words: because the published payload shape is this story's to close, the union-membership question belongs here and to the epic's collision section rather than being settled by widening a sibling's contract. - **`NegativeQuantityError` is added, and the parent's sketch omits it.** It has to be a member, because STORY-001-03-01's own error-path criterion returns it from this operation, and an error a resolver returns without declaring it in the result union is unrepresentable. ### 4.8 Channel And Language Scoping

Both are properties of the request rather than arguments a caller may omit [tickets/EPIC-001-reorder-and-replenishment.md:§7.5 Request Prerequisites], and every criterion in section 5 still names its channel token and its `languageCode`, because a monetary figure is meaningless without the scope that resolved it.

- **Channel.** The active channel is identified by a unique token [packages/core/src/entity/channel/channel.entity.ts:L62] carried in a request header whose key defaults to `vendure-token` [packages/core/src/config/vendure-config.ts:L176-L184] and read from the request at [packages/core/src/service/helpers/request-context/request-context.service.ts:L130-L131]. A source under a different channel token does not resolve.
- **Language.** The `languageCode` comes from a query parameter and otherwise falls back to the channel's `defaultLanguageCode` [packages/core/src/service/helpers/request-context/request-context.service.ts:L136-L145] and [packages/core/src/entity/channel/channel.entity.ts:L74]. **This payload stores and translates no string of its own.** Every field it adds is an identifier, an integer, a currency code, an enum member or one display string from the configured strategy's vocabulary, none of which is language-varying. The only language-varying content reachable through it is the nested variant, whose translated name is language-scoped through `ProductVariant.languageCode` [packages/core/src/api/schema/common/product.type.graphql:L48].
- **Currency.** The response's single `currencyCode` follows the **requesting** channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] and never the source order's, and the tax basis of the current operand follows `Channel.pricesIncludeTax` [packages/core/src/entity/channel/channel.entity.ts:L113] while the historical operand's basis is recorded per source line on `listPriceIncludesTax` [packages/core/src/entity/order-line/order-line.entity.ts:L128]. **Both operands are reconciled onto one basis before subtraction and the payload names the basis it used**, because a delta across two bases is arithmetically well-formed and semantically meaningless.

### 4.9 No Invented Metric

**No number in this contract describes how fast, how fresh, how often or how much.** There is no freshness window in any unit, no service-level commitment, no version-support window in days, no percentage and no business figure. This repository declares none of those, and the epic reports that absence as a finding rather than filling it in [tickets/EPIC-001-reorder-and-replenishment.md:§2.2 Business Value]. **Where no numeric target exists, this file says so rather than supplying a plausible one.**

Every number that does appear is a **verifiable state assertion**: an exact field count, an exact entry count with its ordering, an exact published enum member count, an exact root-query count, an integer money value with its currency code, or the shipped default of the low-stock boundary cited from source [packages/core/src/config/catalog/default-stock-display-strategy.ts:L15]. The single numeric target permitted anywhere in this ticket set is the line-coverage figure in section 10, which is supplied by the requirements rather than invented here.

### 4.10 What A Consumer May Not Rely On

Stated because a contract that lists only its guarantees invites a reader to infer the rest, and an inferred guarantee is the one that breaks.

- **Not the durability of any value.** Every price, every availability string, every classification and every obtainable quantity is as at `readAt` and may differ at the next read. Only the **shape** is stable.
- **Not agreement with a later commit.** The commit re-evaluates each line and is authoritative; a disagreement is specified behaviour [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.10 A Point-In-Time Read Is Not A Reservation].
- **Not the closed-ness of the `stockLevel` vocabulary**, which is the configured strategy's and not the platform's.
- **Not the closed-ness of the `ErrorCode` enum**, which is generated at boot [packages/core/src/api/config/generate-error-code-enum.ts:L9].
- **Not a distinction between an unreadable source and an empty one.** Both return zero entries, deliberately and identically, because a distinguishable difference is an enumeration channel.

- [ ] **Every one of the eight acceptance criteria in section 5 and every one of the five scenarios in section 7 is exercised by an automated test**, with unit tests co-located with the code under test carrying a `.spec.ts` suffix [CONTRIBUTING.md:§Server Unit Tests] and an end-to-end specification under the plugin package's `e2e/` directory written against `@vendure/testing` [packages/testing/src/index.ts:L1-L14] and [CONTRIBUTING.md:§End-to-end Tests]. None is waived, deferred or partially accepted. The three branches of AC-2 are **three separate tests** rather than one parameterised test running a single branch, since the branch a test author reaches for first is the harmless one. Behaviour is evidenced on the four per-engine jobs that already exist [.github/workflows/build_and_test.yml:jobs] with no new infrastructure, and **native SQLite is named as an unverified engine and is not claimed**, because the harness exports initializers for MySQL, PostgreSQL and sql.js only [packages/testing/src/index.ts:L10-L12].
- [ ] **Test coverage over the new plugin code reaches minimum 80% line coverage.** This is the one numeric target this ticket set permits; it is supplied by the requirements rather than invented here, and no service-level, timing, freshness or business figure appears anywhere in this file alongside it.
- [ ] **The two protected packages are evidenced untouched.** `git diff --stat -- packages/core packages/admin-ui` prints nothing, and because a summary diff alone would pass a change already committed on the branch and would never list an untracked path, the epic's boundary gate E1 is run as well and exits zero on both halves — `git diff --quiet "$BASELINE" -- packages/core packages/admin-ui` against the commit this branch diverged from, **and** `git status --porcelain=v1 --untracked-files=all -- packages/core packages/admin-ui` printing nothing [tickets/EPIC-001-reorder-and-replenishment.md:§11.10 The Local Validator Suite]. The dev-server custom-fields object is still empty [packages/dev-server/dev-config.ts:L116], the only file changed outside the plugin package is the dev-server plugin registration array [packages/dev-server/dev-config.ts:L121-L155], and the dashboard bundling configuration [packages/dev-server/vite.config.mts:L1] is **not** touched.
- [ ] **No existing Shop API operation signature changed, and the surface is counted rather than asserted.** The root `Query` type publishes nineteen root queries before this feature and twenty after, every one of the original nineteen byte-identical in name, argument list, argument types, return type and nullability [packages/core/src/api/schema/shop-api/shop.api.graphql:L1-L52]; `product(id: ID, slug: String)` [packages/core/src/api/schema/shop-api/shop.api.graphql:L43], `products(options: ProductListOptions)` [packages/core/src/api/schema/shop-api/shop.api.graphql:L45], `search(input: SearchInput!)` [packages/core/src/api/schema/shop-api/shop.api.graphql:L47], `order(id: ID!)` [packages/core/src/api/schema/shop-api/shop.api.graphql:L34] and `activeOrder` [packages/core/src/api/schema/shop-api/shop.api.graphql:L11] are each evidenced unchanged in signature **and** in behaviour, and no existing type loses a field or has one retyped. **Any widening discovered late is referred to the epic's Feasibility Collisions section rather than accepted in silence** [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions].
- [ ] **The published `ErrorCode` enum member count is unchanged at thirty-two, because this feature declares no new error result.** The figure is stated as a count rather than as the word additive, which is what the epic's ruling on enum growth requires of the story that declares it [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]; the pre-registration count of thirty-two members over thirty-one interface implementors is taken from the checked-in introspection snapshot [schema-shop.json:ErrorCode]; and the number of members this feature contributes is **zero** [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.11 No New Table, No New Error Result]. The published `Permission` enum likewise gains zero members, this story registering no permission definition.
- [ ] **The point-in-time nature of the read, the no-reservation statement and the default-branch guidance are all present in the operation's own published schema description, not only in this ticket.** The JSDoc on the new public API carries the `@since 3.8.0` tag *derived* from the next-minor rule [CONTRIBUTING.md:§New features] applied to this 3.7.0 checkout [packages/core/package.json:L2-L3] and flagged as a derivation [tickets/EPIC-001-reorder-and-replenishment.md:§11.2 Version Tagging], and it states that the result is a read taken at a named instant, that no stock is held and no price is locked, that a commit re-evaluates every line and is authoritative, that a consumer intending to act re-reads at commit, and that an unrecognised `ErrorCode` member is routed through a default branch with the returned `message` field surfaced. **No freshness window is stated in any unit.** No hand-written reference page is produced [tickets/EPIC-001-reorder-and-replenishment.md:§11.5 Public API Documentation Is Generated, Not Hand-Written].
- [ ] **The payload schema is documented field by field, with every field's nullability declared and the entry-count and ordering guarantee stated.** Each of the four nullable entry fields is documented as absent together with its three companions and never as a zero; the entry count is documented as one entry per distinct projected variant in the source's own recorded line order with dense zero-based indices; and no field is described as a quote, a total, an expected charge, a locked price or a price guarantee [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.9a The Reported Price Is The Current Catalogue Price].
- [ ] **Every monetary value in the payload is an integer in the smallest unit of its currency, stated alongside its `currencyCode` and on one named tax basis.** A decimal monetary value anywhere in the payload, in a fixture or in a schema description is a defect. The documentation additionally records that the published `Money` scalar does **not** itself enforce the integer form, being based on the native float scalar [packages/core/src/api/config/money-scalar.ts:L29] and admitting signed fractional values by its own description [packages/core/src/api/config/money-scalar.ts:L33-L35], so a consumer is told the invariant rather than left to infer it from a type. **No raw stock figure is published** and `addableQuantity` never exceeds its own entry's `requestedQuantity`, the disclosure level being no wider than the platform's existing public one [packages/core/src/api/schema/common/common-error-results.graphql:L53].
- [ ] **The result union is closed and the reconciliation against the parent feature's sketch is reported rather than absorbed.** The published union declares the success type and `NegativeQuantityError` [packages/core/src/api/schema/common/common-error-results.graphql:L44] and declares no member that the settled non-disclosure rule makes unreachable; the one member added and the two removed against the parent's three-member sketch are recorded for the epic's collision section [tickets/EPIC-001-reorder-and-replenishment.md:§6.1 Repository-Discovered Collisions]; and every error type named anywhere in this story is drawn from the thirty-one that already implement the interface in this checkout rather than invented [packages/core/src/api/schema/common/common-error-results.graphql:L2] and [packages/core/src/api/schema/shop-api/shop-error-results.graphql:L2].
- [ ] **Migration status is stated as evidence rather than assumed: this story adds no table and no column, so it generates no migration and the additive-migrations-only constraint is satisfied vacuously.** The lifecycle a table-adding story would generate through is named for contrast [packages/core/src/migrate.ts:L40]. The cached end-to-end seed data under the package's `e2e/__data__/` directory is nonetheless deleted before the first run, because a sibling feature's migration precedes this story [AGENTS.md:§Testing]. **And the named regression passes unmodified**: the existing stock-control specification is re-run without edit, including the case asserting the exact display strings against database preconditions [packages/core/e2e/stock-control.e2e-spec.ts:L618-L627], proving the display strategy this payload agrees with still behaves as it did.
