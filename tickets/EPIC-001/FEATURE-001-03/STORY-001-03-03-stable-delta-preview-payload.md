## 1. Story Title

**Publish the reorder preview payload as a documented contract, so that a Storefront Developer (Shop API consumer) codes against a fixed field set, a stated ordering and a staleness caveat while no existing operation changes**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Serve a stable delta preview payload** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

The unit of work the title names is one finished slice, and it is **a contract rather than an operation**: the field set, the nullability of every field, the entry count and its ordering, the money encoding, the availability vocabulary, the error channel and the staleness caveat of the `reorderPreview` query that STORY-001-03-01 introduces and STORY-001-03-02 extends. Nothing in it adds a query, a mutation, a table or a migration.

Three things that could be mistaken for part of it are not:

- **The price computation is STORY-001-03-01's** — which historical operand is used, how the delta is derived, and the read shape that produces it. This story publishes the shape of the answer, not the arithmetic that fills it.
- **The availability computation is STORY-001-03-02's** — the stock preconditions, the strategy call and the classification of a withdrawn variant. This story publishes the fields those computations land in.
- **Resolving a line a preview reports as unobtainable is FEATURE-001-04's**, and this story adds no field for a resolution choice; the commit mutation's input already carries one, declared by FEATURE-001-02 and inert until that feature ships [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces].

**One clarification the title cannot carry, and it is the one that makes this story worth building separately.** A payload that two sibling stories each extend without an owner is a payload whose nullability, entry count and ordering are decided twice — which is how a consumer ends up writing a branch for a combination the resolver cannot produce. This story is the single authority for the shape, and both siblings defer to it by name.

### 3.1 The Do-Not-Duplicate Boundary

The in-cart, post-add price mechanism already exists and this story rebuilds none of it. `OrderLine.unitPriceChangeSinceAdded` and `unitPriceWithTaxChangeSinceAdded` are calculated getters reporting a non-zero delta once a line is in an order [packages/core/src/entity/order-line/order-line.entity.ts:L163-L187], published on the Shop API's `OrderLine` type [packages/core/src/api/schema/common/order.type.graphql:L133] and [packages/core/src/api/schema/common/order.type.graphql:L137]; and `ChangedPriceHandlingStrategy.handlePriceChange` is the deployment-configured decision point for which price wins after an add [packages/core/src/config/order/changed-price-handling-strategy.ts:L32]. The epic's inventory forbids duplicating either [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. **Only the before-commit read is new, and this payload is that read's contract** — so this story publishes a shape, a nullability rule, an ordering and a caveat, and it computes no delta of its own. AC-8 asserts the boundary by reading the existing in-cart fields back unchanged after a preview.

## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line when the file is read on any renderer and when it is pasted into an external tracker. **Every story file in this set uses that same convention**, so a reader comparing two stories compares like with like.

```text
As a Storefront Developer (Shop API consumer),
I want the reorder preview payload published as a fixed field set with a declared nullability per field, a stated entry ordering and a staleness caveat carried in the schema itself,
So that I build the comparison surface against one documented contract instead of inferring its shape from sampled responses, and so that every operation my storefront already calls keeps the signature it has today.
```

### 4.1 INVEST Criteria

- **Independent** — **independence is impossible at the intra-feature scope, and it is named here rather than hidden.** A contract cannot be fixed over fields that do not yet exist, so this story depends on both STORY-001-03-01 and STORY-001-03-02, and the parent feature records the same edge from its own side [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§4.3 Intra-Feature Story Order]. Section 8 classifies each prerequisite rather than leaving it implied. **It still delivers value on its own terms:** a published, documented, regression-asserted payload is what makes the two earlier stories consumable by a storefront rather than merely present, and no third story is needed for that value to land.
- **Negotiable** — parts of the shape are open and parts are deliberately not. Whether the response-level currency code is repeated per entry or carried once on the wrapper is a design choice this story may settle either way, and whether the entry ordering is published as a schema description or as a named directive is likewise open. **What is not negotiable** is that a monetary field is an integer in the smallest unit of a named currency, that an absent comparison is reported as an absence rather than as a zero, that the availability string is whatever the configured display strategy returns rather than a plugin-declared enumeration, that the payload states it confers no reservation and no price lock, and that no field is ever repurposed to carry a different meaning.
- **Valuable** — the value is the difference between a payload a storefront can compile against and a payload a storefront has to reverse-engineer. It lands with the persona the epic assigns it: the Storefront Developer (Shop API consumer) gets a declared field set, a declared nullability rule, a declared ordering, a declared staleness position and a declared obligation to carry a default branch on `ErrorCode` — five statements that are otherwise learned from an incident rather than from a schema.
- **Estimable** — the surface is bounded and countable because the fields already exist after the two sibling stories: this story adds no operand, no source and no data. What it writes is schema descriptions, **no union declaration of any kind**, and an assertion suite over generated schema output — section 4.3.6 removes the union this story once published rather than choosing its members, so there is no union left to declare. The nearest structural analogue in this checkout is a payload type declaring two fields over a pre-existing error union [packages/core/src/api/schema/shop-api/shop.api.graphql:L298-L301], and the analogy is to its per-item shape rather than to its union. Section 9 carries the numbers.
- **Sized Appropriately** — no new table, no migration, no permission definition, no operation, no asynchronous work and no new operand: the whole of it is a published shape plus the tests that hold it still [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.11 No New Table, No New Error Result]. It is not a candidate for splitting either, because removing any one of the five declared statements would leave a contract that is silent on exactly the point a consumer needs it to speak.
- **Testable** — every criterion in section 5 names one published GraphQL operation and asserts an exact field set, an exact entry count with its ordering, an exact integer in the smallest unit of a named currency, an exact error type name, an exact published enum member count, or the equality of two responses taken before and after. No criterion asserts a state that has to be judged, and none states a figure this repository does not declare.

**Step 5 — the one operation, and this is the whole demonstration.** Still in the customer session, execute:

```graphql
query {
  reorderPreview(input: { source: { sourceOrderId: "<the placed order id>" } }) {
    __typename
    sourceState
    readAt
    sourceCurrencyCode
    targetCurrencyCode
    lines {
      requestIndex
      contributors { sourceOrderLineId requestedQuantity historicalProratedUnitPrice }
      productVariantId
      productVariant { id }
      requestedQuantity
      addableQuantity
      availability
      stockLevel
      historicalProratedUnitPrice
      historicalPriceVaries
      currentCataloguePrice
      unitPriceDelta
    }
  }
}
```

**Expected response, and it is exact rather than indicative.** `__typename` is `ReorderPreview`. `lines` holds **exactly two** entries — one per projected variant key, the fixture’s two source lines naming two different variants, in the order the source order’s own lines are recorded — with `requestIndex` values of 0 and 1 and, on each entry’s single `contributors` reference, a distinct `sourceOrderLineId`, which is the join key a client carries into the commit at the same `requestIndex`. Each entry carries every one of the ten remaining selected fields with a value present, `stockLevel` and `currentCataloguePrice` among them, because both source variants are available on this fixture; no field is omitted. Each of `historicalProratedUnitPrice`, `currentCataloguePrice` and `unitPriceDelta` is an **integer** with no decimal point; `sourceCurrencyCode` and `targetCurrencyCode` are both the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88] because the source order was placed in that currency, and every historical figure is read against the first while every current figure is read against the second. Each entry's `contributors` collection holds exactly one reference and `historicalPriceVaries` is false. Each `stockLevel` is one string and each `availability` is one enum member. Each `addableQuantity` is less than or equal to its own entry's `requestedQuantity`. `readAt` carries the instant the read was taken.

**The second half of the demonstration is what did *not* change, and it is the half worth showing a non-coder.** Run a standard introspection query over `__schema` against the now-running Shop API and compare its `ErrorCode` member list and root `Query` field list against the two lists step 1 read out of the snapshot. **What the observed figures are depends on which batches the build carries, and that dependency is stated rather than papered over with a single number**, because `ReorderPlugin` is one plugin, reading the same two things step 1 read out of the checked-in snapshot — the `ErrorCode` enum's member list and the root `Query` type's field list — carrying every feature of this epic rather than one plugin per feature [tickets/EPIC-001-reorder-and-replenishment.md:§9.4 Run Batches]. **Everything in this section is a target named in ticket text.** `reorderPreview`, `ReorderPreviewInput`, `ReorderPreview`, `ReorderPreviewSource`, `ReorderPreviewSourceState`, `ReorderPreviewLine`, `ReorderPreviewContributor`, `ReorderLineAvailability`, `ReorderList`, `ReorderListLine` and the plugin package do not exist in this checkout, so **none of them carries a citation** and a downstream reader must treat none of them as verified. **`ReorderPreviewResult` is deliberately absent from that list**: it is not a prospective symbol of this set at all but a *withdrawn* one, named later in this file only to record that it is never published — see section 4.3.6. What this story adds is not a field: it is the set of statements the payload makes **about itself**, and each of the ten sub-sections below is one such statement.

**Three shape decisions in that block are corrections rather than transcriptions, and this story is where they land because this story owns the payload.** Each replaces something an earlier revision published that could not be satisfied.

- **The operation returns `ReorderPreview!` and there is no result union.** An earlier revision published `union ReorderPreviewResult = ReorderPreview | NegativeQuantityError` while also requiring that an absent source, another customer's source and another channel's source be indistinguishable — two requirements that cannot both hold, because a not-found or forbidden member returned for an id that is not the caller's *is* the enumeration channel the indistinguishability existed to close. **One always-representable payload replaces both**, with `sourceState` carrying `NOT_RESOLVED` and an empty `lines` collection for every unreadable case identically, and the parent feature publishing the same shape [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. **What is gained is not tidiness but representability**: every response a consumer can receive now has a shape declared in the schema.
- **Four fields that were non-null are now nullable, and they fall into two groups rather than one, because the two unavailable states withhold different things.** A variant withdrawn since the purchase is exactly the row the platform's resolution refuses to return [packages/core/src/service/services/order.service.ts:L684-L689], so it withholds the variant object, its availability string **and** its catalogue prices; a variant that resolves but carries no price row for the channel and currency this request resolved to [packages/core/src/config/catalog/default-product-variant-price-selection-strategy.ts:L18-L21] withholds **only** the prices, its variant object and availability string being perfectly readable. **So the VARIANT group — `productVariant` and `stockLevel` — is null on the withdrawn state alone, and the PRICE group — `currentCataloguePrice` and `currentCataloguePriceWithTax` — is null on either state**, which section 4.1 states field by field and the parent feature publishes identically [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. **An earlier revision declared all four one group discriminated by the withdrawn state alone**, which made the unpriced state unrepresentable: it needs a present variant beside two null prices, and a four-field group forbids exactly that combination. `productVariantId` stays non-null because it is read off the source line rather than the catalogue, `availability` stays non-null and carries the reason, and `addableQuantity` stays non-null because zero is representable. **Non-null declarations would have forced the entry to be dropped**, which is the outcome section 4.3.2's entry-count guarantee exists to forbid.
- **Source-line identity lives in `contributors`, and each contributor carries its own recorded prices.** Entries are keyed by distinct projected variant so the `requestIndex` this payload promises to share with the commit is the commit's own index [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract — How Identity Is Constructed, Not Assumed]. A singular `sourceOrderLineId` on the entry, which an earlier revision declared, could not name two source lines of one variant and could not represent the case where those two lines recorded **different** historical prices. Both are now representable: the key-level historical pair is populated only where every contributor agrees, `historicalPriceVaries` says so when they do not, and the per-contributor figures are where the detail lives. **An average is prohibited** — a mean of two prices is a figure the buyer never paid.

#### 4.3.1 The Field Set And Its Nullability

**A consumer may rely on the following, and on nothing that is not written here.** Nullability is declared per field rather than described in aggregate, because "some fields may be null" is the statement a consumer cannot code against.

Non-null on the wrapper, and present in every response the operation returns — including an unresolved one, since the operation declares no union and always returns a payload:

- **`source`** — which source the entries were projected from. Non-null. Its own three fields, `sourceOrderId`, `sourceOrderCode` and `reorderListId`, are each individually nullable because exactly one addressing form applies to any one request: an order-sourced preview carries the first two with a null `reorderListId`, and a list-sourced preview carries `reorderListId` with the other two null. **A consumer determines which form it received by testing `reorderListId` for a value rather than by inspecting the input it sent**, so a response is self-describing.
- **`readAt`** — the instant the read was taken, as a `DateTime`. Non-null. Section 4.3.5 is the reason this field exists at all rather than being an implementation curiosity.
- **`sourceState`** — `RESOLVED` where the source is this buyer's own placed order or reorder list in this channel, `NOT_RESOLVED` for every unreadable case identically. Non-null. **It is the field that replaced the result union**, and a consumer branches on it rather than on `__typename`.
- **`sourceCurrencyCode` and `targetCurrencyCode`** — two currency codes rather than one, both non-null, and the pair is the correction this story makes to an earlier single-code draft. `targetCurrencyCode` is the currency the request resolved to and is the currency of every current catalogue figure; `sourceCurrencyCode` is the code the source order permanently recorded [packages/core/src/entity/order/order.entity.ts:L142] and is the currency of every historical figure. **A single code could not describe a response whose two operands are in different currencies**, which one channel permits because a channel may list more than one code in `availableCurrencyCodes` [packages/core/src/entity/channel/channel.entity.ts:L89-L91] and the platform resolves the request's own code against that list [packages/core/src/service/helpers/request-context/request-context.service.ts:L147-L156]. For a list source, which records no currency, the two codes are equal. **Both deltas are null wherever they differ**, and no conversion is attempted.
- **`lines`** — the entry list. Non-null, and **non-null in the empty case too**: a source that projects to no entry returns an empty list, never a null and never an error. Section 7's first scenario asserts it.

Non-null on every entry:

- **`requestIndex`** — the **lowest index this entry's projected variant key holds among its own contributing source lines**, in the zero-based numbering of the deterministically ordered source, identical to the index the commit mutation assigns the same key. **The set is therefore drawn from the source numbering and skips a value wherever duplicates collapsed**: a source of *n* lines collapsing to *k* keys yields *k* ascending indices drawn from `0` to `n-1`, so the highest may be `n-1` rather than `k-1`, no index repeats because each source number belongs to exactly one key, and two lines naming one variant share one entry and therefore one index — the lower of their two numbers. **Its stability is bounded and the bound is published rather than left to be assumed:** it is stable within one response and across responses to an *identical* input, and it is **not** stable across a changed input, because a caller who previews a whole order and then commits a narrowed selection is sending a different selection, projecting a different key set and getting a different index set. **So `requestIndex` is for ordering and addressing within one response, and the join key across the two operations is `productVariantId` or a contributor identifier beside it.** FEATURE-001-02 is the authority for both the shared grain and the join rule, and this contract transcribes it rather than restating it differently [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract].
- **`productVariantId`** — the identifier of the variant the source line pointed at. **Non-null even when the variant relation beside it is null**, because this identifier is the plugin's own record read from the source line rather than a live catalogue resolution: it is what lets a consumer key an entry, a support agent search for it, and FEATURE-001-04 offer a substitute for it.
- **`contributors`** — non-null and never empty: one entry per source line that projected into this key, in source order, each carrying its own `requestedQuantity` and its own recorded historical prices. **This is where source-line identity survives the variant-keyed projection**, and it is what a consumer joins back to the lines it sent.
- **`requestedQuantity`** — the quantity the preview was computed for, as an integer.
- **`addableQuantity`** — the request-specific obtainable quantity, as an integer, **bounded above by `requestedQuantity`** and clamped to zero at the bottom. Section 4.3.4 states why an integer is publishable here at all.
- **`availability`** — the machine-readable classification, one member of the plugin-owned enumeration. **This is the discriminator for both nullable groups below**, and it is non-null precisely so that a consumer branches on an enum member rather than probing four fields for null.
- **`historicalPriceVaries`** — non-null. True where this key's contributors recorded different historical prices, in which case both key-level historical fields are null, both deltas are null with them, and the per-contributor figures carry the detail.

Nullable on an entry, **discriminated by `availability` and falling into two groups rather than one** — the VARIANT group of two fields, null exactly on the withdrawn state, and the PRICE group of two fields, null on that state **or** on the unpriced-in-channel state. Within each group the fields are null as a set rather than in any mixed combination; across the two groups a present variant beside two null prices is a legitimate response and is exactly what the unpriced state looks like. **This two-group form is the correction that made this contract able to encode both of its own unavailable scenarios**: an earlier version declared all four one group discriminated by the withdrawn state alone, which made the unpriced state unrepresentable, and an earlier version still declared all four non-null while section 7 required a variant withdrawn since purchase to *stay in the response*, which left the implementation two illegal options — dropping the entry and contradicting the one-entry-per-projected-key guarantee, or inventing a catalogue price for a product that no longer has one. Nullability in two groups is the third option and the only truthful one, and the parent feature is the authority this story transcribes [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. **`addableQuantity` is deliberately in neither group**: it is `0` for an unavailable entry, because zero is the true obtainable quantity and is a value rather than an absence.

The VARIANT group, null **if and only if** `availability` is `NOT_ADDABLE_VARIANT_UNAVAILABLE`, and non-null in each of the four other states:

- **`productVariant`** — the variant object. A variant withdrawn since the purchase does not resolve, so there is no object to return; the entry still appears, carrying its `productVariantId`, its `requestedQuantity`, an `addableQuantity` of 0 and this availability state. **This is the rule that lets the payload express its own required edge case**: an earlier version of this contract declared the field non-null while also requiring a story to report a withdrawn variant, which would have forced the server either to invent a variant or to fail the whole response and discard the basket.
- **`stockLevel`** — the display string, typed `String`. Null in the same one state, there being no variant to describe. Section 4.3.4 states why it is a string and not an enumeration.

The PRICE group, null when `availability` is `NOT_ADDABLE_VARIANT_UNAVAILABLE` **or** `NOT_ADDABLE_UNPRICED_IN_CHANNEL`, and non-null in each of the three other states:

- **`currentCataloguePrice`** and **`currentCataloguePriceWithTax`** — the current catalogue operands as integers. Null together in those two states and in no other: a withdrawn variant has no current catalogue price to report, and **a variant that resolves but carries no price row for the channel and currency this request resolved to has none either** — the default selection strategy matching on both [packages/core/src/config/catalog/default-product-variant-price-selection-strategy.ts:L18-L21] while the platform's price applicator raises `error.no-price-found-for-channel` only when its caller asks it to [packages/core/src/service/helpers/product-price-applicator/product-price-applicator.ts:L70-L73], which this feature does not. In that second case `availability` reports `NOT_ADDABLE_UNPRICED_IN_CHANNEL` **with `productVariant` and `stockLevel` both present**, which is precisely the combination a single four-field group could not express. They are integers in the smallest unit of `targetCurrencyCode`, and **null and zero stay distinguishable**: a price of zero is a price and a null is the absence of one. **An earlier revision declared both non-null on the reasoning that such a variant is "not reported as a priced entry at all"**, which contradicted this story’s own withdrawn-variant scenario in section 7 and the sibling story’s retain-and-classify rule — a non-null field with nothing to put in it is a request-level error, so one withdrawn variant would have failed the whole read.

**A consumer therefore needs one test per group and the test is the same enum field**: read `availability`; if it is `NOT_ADDABLE_VARIANT_UNAVAILABLE` expect all four absent, and if it is `NOT_ADDABLE_UNPRICED_IN_CHANNEL` expect the PRICE pair absent and the VARIANT pair present. The parent feature publishes the same two groups and this story restates them field by field rather than differently [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces].

Nullable on an entry for reasons **independent of the variant's availability**, and null together within each group rather than in any mixed combination. The first two groups below are independent of one another and of the two availability-discriminated groups above — a list-sourced entry has null historical operands with its catalogue prices present, and a withdrawn variant has null catalogue prices with its historical operands present — while the third is derived from the others:

- **`sourceOrderLineId`** and **`reorderListLineId`** on each `contributors` entry — whichever addressing form does not apply is null, matching the wrapper's `source`. **The entry itself declares neither field**, source-line identity living in `contributors` because one entry may have two of them.
- **`historicalProratedUnitPrice`** and **`historicalProratedUnitPriceWithTax`** — the one historical pair the parent feature declares [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces — One New Query, Zero Existing Signatures Changed], absent together in **two** declared cases and in no others. **The first is a list-sourced entry**, because a list line records no price of any kind. **The second is contributor disagreement**: where a key's contributors recorded different historical prices, both key-level historical fields are null with `historicalPriceVaries` true, and the figures live per contributor. Both are absent together because net is subtracted from net and gross from gross, and a half-populated pair would invite a mixed-basis subtraction downstream. **A currency mismatch is deliberately not one of the two cases** — the operands the source order permanently recorded are still true figures in `sourceCurrencyCode` and are published, and it is the *deltas* that go null, which is the next bullet's business. STORY-001-03-01 fixes the rule; this story publishes it.
- **There is one historical pair in this payload, not two, and it is the prorated pair.** The differenced operand is `OrderLine.proratedUnitPrice` and `proratedUnitPriceWithTax`, documented as the true economic value of a single unit after order-level discounts are prorated across lines [packages/core/src/entity/order-line/order-line.entity.ts:L213-L229], which is epic ruling R12 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]; `unitPrice`, documented as excluding tax **and discounts** [packages/core/src/entity/order-line/order-line.entity.ts:L146-L152], is never read as the historical operand. **An earlier draft of this story published two pairs and differenced the `unitPrice` one, and both halves of that draft are withdrawn**: a payload offering a consumer two candidate histories is not a stable payload, which is this story's own subject.
- **`unitPriceDelta`** and **`unitPriceWithTaxDelta`** — the delta pair, **null in four declared cases and in no others**, which is what makes it the one nullable group not independent of the rest. **Two are missing operands**: a list-sourced entry or a disagreeing key has no historical operand, and a withdrawn or unpriced-in-channel variant has no catalogue operand. **The third is a currency mismatch**: where `sourceCurrencyCode` differs from `targetCurrencyCode` both deltas are null **even though all four operands are present and published**, because subtracting across currencies would need a rate this repository does not declare — so the response reports what each side recorded and declines only the comparison, which is strictly more information than nulling the operands would leave. **The fourth is the pair rule**: the two deltas are absent together, never one without the other, because a lone gross delta invites a mixed-basis comparison. **In every case the operands that *are* present remain present**, and **an absent comparison is reported as an absence and never as the integer 0**, since a zero asserts that the price was compared and did not move while an absence asserts that no comparison was possible.

**Two guarantees about the set as a whole, and they are the durability half of the contract:**

- **A field is never repurposed.** A published field keeps the meaning its schema description gives it for the life of the field. A changed meaning arrives as a new field with the old one carrying a deprecation, never as the same field returning something else — which is the one failure mode a consumer cannot detect from a schema comparison, because the schema looks identical.
- **A field is never removed without a deprecation first.** Additions are additive by construction; removals are not, and this contract does not perform one.

#### 4.3.2 Entry Count And Ordering

**The entry count is exact and the ordering is stated, because an exact count with its ordering is what replaces a banned adjective here.**

- **Duplicate source lines are collapsed for both the computation and the payload, and the collapse is what makes the two payloads joinable.** Obtainability is computed once per distinct variant against the same variant-keyed projection the commit path defines, with the duplicate lines’ quantities summed for that computation [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.7a The Preview Is Computed Against The Target Cart], **and the key is what the payload reports**: two requested lines naming one variant produce **one** entry at one `requestIndex`, carrying `requestedQuantity` as the sum, `addableQuantity` as the key’s obtainable quantity, and `contributors` naming both source lines with their own requested quantities and recorded prices. **This is the grain the commit mutation publishes, and it is published here identically for one reason: an entry per requested line could not carry a key-level obtainable quantity without an apportionment rule, which the commit contract refuses to invent** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract — How Identity Is Constructed, Not Assumed]. An earlier revision of these two bullets asserted one entry per requested source line, which contradicted both this payload’s own `contributors` collection and the commit payload it must join to.
- **The order is the source's own recorded line order**, one entry per **distinct projected variant key**, ascending by `requestIndex` — which is each key's earliest contributing source line, so a key appears at the position of the first line that fed it. **Worked**: a source recording its lines as A, B, A yields two entries, A at `requestIndex` 0 and B at 1, in that order; a source recording them as A, A, B yields A at 0 and B at 2, so the published indices are 0 and 2 while the order is still A then B. A list-sourced preview follows the list's own recorded line order on the same rule. **An earlier revision of this bullet said one entry per source line, which contradicts the collapse the bullet above requires and is withdrawn.** **The ordering is published in the schema description rather than left as observed behaviour**, because an ordering a consumer observes and relies on without being promised it is a defect waiting for a query-planner change.
- **`requestIndex` is the lowest index a key's own contributors hold in the zero-based source numbering, so the returned set ascends and skips a value wherever duplicates collapsed onto one key** [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.6a The Keyed Line-Result Contract]**, and it is the same value the commit assigns the same key** for the same source and the same selection — which is what lets a storefront join a preview entry to a commit outcome, and lets a buyer's resolution choice reach the line they chose it for.
- **Every requested source line appears in exactly one entry's `contributors` collection**, so the count of contributors summed over all entries equals the count of requested source lines even though the entry count does not. **The two counts are stated separately and neither substitutes for the other**: a consumer that needs "one row per line I sent" builds it from `contributors`, and a consumer that needs "one row per thing the cart will hold" reads the entries.

#### 4.3.3 Money

**Every monetary value is an integer in the smallest unit of its currency, always accompanied by the currency code that value belongs to — `targetCurrencyCode` for a current figure and `sourceCurrencyCode` for a historical one.** A decimal monetary value anywhere in the payload, in a fixture or in a schema description is a defect, not a formatting preference. The platform models money this way: the published scalar is declared as `scalar Money` [packages/core/src/api/schema/common/common-types.graphql:L7], and the catalogue surface a storefront already reads pairs `price: Money!` with `currencyCode: CurrencyCode!` and `priceWithTax: Money!` on the same type [packages/core/src/api/schema/common/product.type.graphql:L53], [packages/core/src/api/schema/common/product.type.graphql:L54] and [packages/core/src/api/schema/common/product.type.graphql:L55].

**The qualification this story owns, and it is the reason this sub-section exists rather than being one line in section 4.3.1.** The `Money` scalar does **not** itself enforce the integer form. It is based on the native float scalar [packages/core/src/api/config/money-scalar.ts:L29] and its own description states that it supports signed double-precision fractional values [packages/core/src/api/config/money-scalar.ts:L33-L35], deliberately, so that a deployment may configure a different money strategy. **A consumer therefore cannot infer the integer form from the schema's type alone, and this payload's documentation states it explicitly instead** [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.9 Channel Scoping]. That is a published statement rather than a hope: the assertion that every monetary field in a response parses as an integer belongs to AC-1 and to the definition of done, not to a comment.

**And one statement about what the number is.** `currentCataloguePrice` is the variant's current catalogue price on the response's stated tax basis, read at `readAt`. **It is not a quote, not a total, not an expected charge, not a locked price and not a price guarantee**, and no field in this payload is named or described as any of those. Four documented mechanisms can make a committed price differ from it, none of them a race, and the parent feature enumerates all four [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.9a The Reported Price Is The Current Catalogue Price]. The decisive one is that a deployment may configure `orderOptions.changedPriceHandlingStrategy` to hold the earlier price [packages/core/src/config/order/changed-price-handling-strategy.ts:L17-L18], in which case the buyer is charged something this payload never showed — and by default the latest price is used and the resulting change surfaces on the existing in-cart change field instead [packages/core/src/config/order/changed-price-handling-strategy.ts:L12-L13].

#### 4.3.4 Availability

**Two fields carry availability, and the split between them is the whole of the contract.**

- **`stockLevel` is typed `String`, nullable, and is whatever the configured display strategy returns for an entry that has one.** The published field this mirrors is non-null because it hangs off a variant that resolved: `ProductVariant.stockLevel: String!` [packages/core/src/api/schema/common/product.type.graphql:L56]. On a preview entry the variant may be the one thing that did *not* resolve, which is why this field is nullable and why it is null exactly when `availability` is `NOT_ADDABLE_VARIANT_UNAVAILABLE` on the Shop API's `ProductVariant` type [packages/core/src/api/schema/common/product.type.graphql:L42]. The strategy behind it declares one method returning `string` [packages/core/src/config/catalog/stock-display-strategy.ts:L27] and is deployment-configurable through `catalogOptions.stockDisplayStrategy` [packages/core/src/config/catalog/stock-display-strategy.ts:L14]. **Publishing this field as an enumeration would break a deployment that had supplied its own vocabulary, at schema-serialisation time**, so it is not narrowed. Under the shipped `DefaultStockDisplayStrategy` [packages/core/src/config/catalog/default-stock-display-strategy.ts:L14] the value is exactly one of `OUT_OF_STOCK`, `LOW_STOCK` or `IN_STOCK` [packages/core/src/config/catalog/default-stock-display-strategy.ts:L17-L21], with the low-stock boundary at the constructor's shipped default of 2 [packages/core/src/config/catalog/default-stock-display-strategy.ts:L15] — and **a criterion asserting one of those three names the default strategy in its Given**, per the rule the parent feature fixes for every story in it [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.5.1 The Three Stock Tokens]. STORY-001-03-02 owns the vocabulary; this story owns publishing that it is open rather than closed.
- **The assertion that survives a replaced strategy is an identity, not a literal.** For any variant in any deployment, an entry's `stockLevel` equals what `ProductVariant.stockLevel` [packages/core/src/api/schema/common/product.type.graphql:L56] returns for that same variant in that same request, because both resolve through the one configured strategy. **That is the general form of the guarantee and it is the one this contract publishes**, so a buyer never sees two different answers to "is this in stock" from one deployment.
- **`availability` is the plugin-owned enumeration and is exhaustive**, because the plugin owns it. It is the field a consumer switches on. It describes **the request in this cart** rather than the variant in the abstract, which is why an entry may carry a `stockLevel` of `IN_STOCK` beside an `availability` reporting that the line is not obtainable — the buyer's own active order already holds every obtainable unit. **That pairing is specified output rather than a contradiction**, and STORY-001-03-02 asserts it.

**No raw stock figure appears anywhere in this payload.** No field returns `stockOnHand`, `stockAllocated` or an unbounded saleable level. The prohibition is structural rather than remembered: `StockLevel` is not a Shop API type at all, being absent from the type list of the checked-in introspection snapshot [schema-shop.json:data.__schema.types], and the display strategy exists precisely because directly exposing stock levels over a public API is treated as a leak of sensitive information [packages/core/src/config/catalog/stock-display-strategy.ts:L7-L10].

**The one integer that is published, with its bound as the whole of its justification.** `addableQuantity` never exceeds its own entry's `requestedQuantity`, so asking for two and being told two discloses that at least two exist and nothing more. The disclosure level is no greater than the platform's own, because `InsufficientStockError` already publishes `quantityAvailable: Int!` on a public Shop API mutation [packages/core/src/api/schema/common/common-error-results.graphql:L50] and [packages/core/src/api/schema/common/common-error-results.graphql:L53]; the change is only that a buyer learns it in time to act. **The formula is one formula and it is the parent's**: `min(requestedQuantity, max(saleable − quantityAlreadyOnTargetCart, 0))`, which is the clamp the commit itself applies [packages/core/src/service/helpers/order-modifier/order-modifier.ts:L117-L133] — a variant of it that omitted the already-held term appeared in an earlier draft of this feature and is withdrawn, because it would have made the preview disagree with the commit deterministically rather than only under a race [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.7a The Preview Is Computed Against The Target Cart]. **And the residual disclosure is accepted explicitly, with its ceiling and its controls, rather than left unremarked.** A caller can vary `requestedQuantity` across calls and read the answer back, which makes the field a request-bounded inventory oracle. The ceiling is the configured per-line maximum, because the shared selection contract refuses a larger override before anything is read [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]; the first control is that an entry exists only for a variant this caller already bought or already saved, so the oracle cannot be aimed at an arbitrary catalogue variant; and the second is that the same figure is already obtainable today by calling the existing `addItemToOrder` with a large quantity and reading `quantityAvailable` off the returned error, which carries the clamped non-zero figure when the quantity was reduced [packages/core/src/service/services/order.service.ts:L743-L748] and zero when nothing could be added [packages/core/src/service/services/order.service.ts:L710-L715]. **What is not published under any circumstances is the unbounded saleable level**, which is why an untracked variant reports `addableQuantity` equal to `requestedQuantity` rather than the maximum safe integer the platform's short-circuit returns internally [packages/core/src/service/services/product-variant.service.ts:L326-L331].

#### 4.3.5 No Reservation, No Price Lock

**The payload is a read taken at `readAt` and nothing more. It holds no stock, locks no price, creates no allocation and confers no entitlement.**

**The statement lives in the operation's own published schema description, not only in this ticket**, and that placement is the deliverable rather than a courtesy: a storefront developer meets the caveat while reading the schema, which is where they are when they decide what to build. Four clauses are published, in these terms:

- the result is a point-in-time read taken at the instant the response reports;
- no stock is held and no price is locked by taking it;
- a commit re-evaluates every line at write time and **is authoritative over the preview**, so the two disagreeing is specified behaviour rather than a defect [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.10 A Point-In-Time Read Is Not A Reservation];
- a consumer that intends to act on the payload re-reads at commit rather than trusting the earlier response.

**No freshness window is stated, in any unit.** This repository declares no such figure, and inventing one would be worse than saying nothing: a stated window implies a guarantee the read does not make. AC-6 asserts the caveat's presence and the re-read behaviour inside a criterion rather than leaving either to prose.

#### 4.3.6 The Error Channel Is Inherited, Not Extended — And The Union Membership This Story Records

**This story declares no error result, and it publishes no result union either.** Its feature declares none of the six the ticket set introduces [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.11 No New Table, No New Error Result], and every error type named anywhere in this file is drawn from the **thirty-one** types that already implement the `ErrorResult` interface in this checkout.

Three paths exist, each belonging to exactly one level, and all three are inherited rather than re-decided here:

- **An input-contract violation throws before a payload exists.** Every rule of FEATURE-001-02's shared selection contract governs this query, because this query reuses that feature's input types rather than mirroring them: exactly one source field set, one id form per entry matching the source form, no duplicate id, no more entries than the configured maximum, a `quantity` override of at least one and no greater than the configured per-line maximum including the per-key sum, and every id naming a line of the resolved source [tickets/EPIC-001/FEATURE-001-02-reorder-from-order-history.md:§2.5 Named API Surfaces]. Each violation throws the platform's own `UserInputError` [packages/core/src/common/error/errors.ts:L26-L30] — `extensions.code` of `USER_INPUT_ERROR` and that rule's plugin-owned message key — before any projection, variant load, price read or stock read, which is the epic's ruling R13 [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]. **The keys are the sibling feature's own and are named here rather than left as "that rule's key", because a consumer branches on them:** `error.reorder-selection-wrong-source-form` for an entry whose id form does not match the source form, `error.reorder-selection-duplicate` for a repeated id, `error.reorder-selection-above-maximum` for more entries than the configured maximum, `error.reorder-selection-quantity-out-of-range` for a `quantity` override below one or above the configured per-line maximum, and `error.reorder-selection-unknown-line` for an id naming no line of the resolved source — which reports **how many** unknown ids were supplied and never which ones, since naming them would be the enumeration channel the second path below exists to close. **None of these five is representable as a payload field or a union member**, which is the other half of why this operation needs no union: an input the contract rejects has no `ReorderPreview` to put an error inside.
- **An unresolvable, unowned, foreign-channel or unauthenticated request returns `sourceState` of `NOT_RESOLVED` with zero entries and no error type at all.** The precedent is published and exact: `order(id: ID!): Order` is nullable [packages/core/src/api/schema/shop-api/shop.api.graphql:L34] and its own description restricts it to orders belonging to the currently-authenticated user [packages/core/src/api/schema/shop-api/shop.api.graphql:L31-L32]. The unauthenticated case joins the other three because this is a **read**, and the shipped read convention normalises rather than refuses — the closest shipped analogue catching the forbidden error on its read [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L22-L29] while letting it propagate on its writes [packages/dev-server/example-plugins/wishlist-plugin/service/wishlist.service.ts:L34-L35], which is ruling R14.
- **A per-entry unavailability is a reported state and not an error.** A withdrawn variant, an out-of-stock variant and a variant unpriced in this channel are all `availability` members with nullable neighbours, per section 4.3.1.

**The union question, which STORY-001-03-01 referred here, is closed by removing the union rather than by choosing its members — and the reasoning is recorded because an earlier revision of this file chose members instead.**

**The referral was resolved by amending the parent rather than by leaving two readings standing:** the field declaration below **is** the parent feature's published contract, a bare `ReorderPreview!` with no union anywhere in it [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces], and this story restates it because a payload-contract story that left its own return type to be inferred would be incomplete.

```graphql
# There is no ReorderPreviewResult. The operation returns the payload directly:
extend type Query {
  reorderPreview(input: ReorderPreviewInput!): ReorderPreview!
}
```

- **The earlier revision published `union ReorderPreviewResult = ReorderPreview | NegativeQuantityError`. Two things were wrong with it, and each is fatal on its own.** First, `NegativeQuantityError` names a condition it does not describe: its own description covers "attempting to set a negative OrderLine quantity" [packages/core/src/api/schema/common/common-error-results.graphql:L43-L47], the platform returns it for `quantity < 0` only [packages/core/src/service/services/order.service.ts:L2267-L2271], and a preview input override of zero is neither negative nor an `OrderLine` quantity. Second, a union whose error member is returned for some failures while every *other* failure must be indistinguishable from success-with-nothing is a contract a consumer cannot branch on coherently.
- **`NoReorderableLinesError` and `ReorderListNotFoundError` are not members, and the parent feature no longer lists them either.** Both are declared by sibling features rather than by this one [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.11 No New Table, No New Error Result], and the settled non-disclosure rule above makes both **unreachable on this read path**: every condition that would produce either — a source that matches no row, a source owned by another customer, a source under a foreign channel token, a source that projects to no entry — returns zero entries and no error type instead. **Publishing an unreachable member obliges every consumer to write a branch it can never enter**, which is a cost with no corresponding disclosure, and it would also make the two branches distinguishable and so reopen the enumeration channel the non-disclosure rule closes.
- **Removing the union removes the incoherence and costs nothing that was load-bearing.** The input violation now throws, so it needs no member; the unreadable cases now return a declared `sourceState`, so they need no member; and the two sibling-declared types this feature never owned — `NoReorderableLinesError` and `ReorderListNotFoundError` — are unreachable on a read path by ruling R14's corollary, which puts a not-found error in the unions of the **mutations** that address a list by id and nowhere else [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings].

- **The reconciliation is recorded in both directions rather than absorbed silently.** The parent feature published a three-member union sketch; this story publishes none, and the parent has been reconciled to the same shape rather than left to contradict its child [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. **Reporting the reconciliation is the deliverable, not evidence of churn**: a payload contract whose parent and child disagree about the return type is the defect this story exists to prevent.


**And the consumer obligation this channel creates, which is the guidance this story publishes.** The `ErrorCode` member set is generated at boot from every type implementing the interface [packages/core/src/api/config/generate-error-code-enum.ts:L9] and [packages/core/src/api/config/generate-error-code-enum.ts:L17], keyed off the literal interface name [packages/core/src/api/config/generate-error-code-enum.ts:L3], over an enum that ships in source with a single literal member [packages/core/src/api/schema/common/common-enums.graphql:L28-L30]. **A consumer therefore cannot switch exhaustively over the members it compiled against.** The published documentation states the obligation in terms: route an unrecognised member through a default branch and surface the returned `message` field rather than failing to parse. Section 7's fifth scenario carries it as an edge case, and section 10 makes its presence in the schema description a completion condition.

#### 4.3.10 What A Consumer May Not Rely On

Stated because a contract that lists only its guarantees invites a reader to infer the rest, and an inferred guarantee is the one that breaks.

- **Not the durability of any value.** Every price, every availability string, every classification and every obtainable quantity is as at `readAt` and may differ at the next read. Only the **shape** is stable.
- **Not agreement with a later commit.** The commit re-evaluates each line and is authoritative; a disagreement is specified behaviour [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.10 A Point-In-Time Read Is Not A Reservation].
- **Not a promise that every field carries a value on the day this story ships — and the one field that does not is named here rather than left to surprise a consumer.** "Only the shape is stable" above means no field this story publishes is removed, renamed, retyped or has its nullability changed. The field set is closed by this story, because the parent feature declares every field of the entry type in its first published version, `substitutionCandidates` included [tickets/EPIC-001/FEATURE-001-03-price-and-availability-delta-preview.md:§2.6 Named API Surfaces]. What is **not** promised is that the collection is non-empty: it is an empty list on every entry until STORY-001-04-02 supplies the values [tickets/EPIC-001/FEATURE-001-04/STORY-001-04-02-substitution-candidate-strategy.md:§4. User Story], and a consumer that reads an empty collection as an error rather than as the no-candidate answer breaks on it while a conforming consumer does not. **The obligation this places on a consumer is the same one the default branch places on it for an enum**: select the fields you use, and treat an empty collection as an answer.
- **Not the closed-ness of the `stockLevel` vocabulary**, which is the configured strategy's and not the platform's.
- **Not the closed-ness of the `ErrorCode` enum**, which is generated at boot [packages/core/src/api/config/generate-error-code-enum.ts:L9].
- **Not a distinction *among* the unreadable cases.** All four — a source that matches no row, one owned by another customer, one under a foreign channel token, and a request with no authenticated customer — return `NOT_RESOLVED` with zero entries, deliberately and identically, because a distinguishable difference among them is an enumeration channel. **What a consumer *may* rely on is the distinction between those four and an owned source that is simply empty**, which returns `RESOLVED` with zero entries: that one is disclosable because a caller who owns a source already knows it exists, so `sourceState` tells an owner "your list is empty" without telling a prober "this id exists". Section 7's first scenario asserts the pair.
