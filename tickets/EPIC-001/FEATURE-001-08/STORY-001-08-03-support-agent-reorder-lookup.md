## 1. Story Title

**Look up a buyer's reorder lists and last recorded attempt through two permission-gated Admin API reads, so that a Customer Support Agent can state which lines reached the cart and which did not from a stored record.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Look up a buyer's lists and last attempt** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

**This story is not free-standing, and presenting it as though it were would misdescribe why it exists.** FEATURE-001-08 was **expanded** from the suggested seller-and-category visibility area to absorb the Customer Support Agent read path, on the ground that all three administrative personas read the same rows over the same plugin-owned tables and a separate support feature would have duplicated the resolver wiring, the permission registration and the pagination contract [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.2 Contribution To The Epic, And The Expanded Rationale]. The support lookup therefore lives beside the demand aggregate rather than in a feature of its own, and it inherits that feature's scoping, pagination and enum contracts instead of restating them.

The unit of work is **two Admin API queries and one permission definition, over zero new tables**. `customerReorderLists` returns the lists a named buyer holds, including those reached through an unrevoked grant. `reorderAttempts` returns recorded attempts with their per-line outcome codes, addressable by the buyer's identity or by the order code recorded on the attempt. Both are gated on a capability separate from the one that reads the demand aggregate, and that separation is a least-privilege requirement rather than an accounting choice [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8 Permission Gating, And The Enum Growth Referenced Rather Than Re-Argued].

**Three absences define this story as sharply as its two operations, and each is stated positively rather than left to be inferred from silence.**

- **No new table and no migration.** Every row read here is created elsewhere: `ReorderList` and `ReorderListLine` by FEATURE-001-01, `ReorderListShare` by FEATURE-001-06, and `ReorderAttempt` with `ReorderAttemptLine` by STORY-001-07-01. Because there is no schema change, the cached seed-data reset under `e2e/__data__/` [AGENTS.md:L19] is **not** triggered by this story, and the repository's classification of a database-schema change as breaking-change work [CONTRIBUTING.md:§Breaking Changes] does not bite on it directly.
- **No new error result.** FEATURE-001-08 declares none of the six this ticket set introduces; all six belong to FEATURE-001-01, FEATURE-001-02 and FEATURE-001-06 [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.14 The Four Absences, Stated Positively]. The published error-code enum therefore gains nothing on this story's account.
- **No forecast.** Visibility over recorded activity is in scope; predicting future stock requirements is out, on the two grounds the epic states rather than asserts — a forecast has no basis in this repository, and there is no declared numeric target to validate one against [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.11 Visibility Is Not Forecasting]. Every value this story returns is a description of something a buyer already did.

**What this story owns that no other file may restate.** STORY-001-07-01 declares no read operation and no permission definition, and delegates the audit-read gate here by name [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.6 Named API Surfaces]. ## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when this file is pasted into an external tracker. Every story file in this set uses that same convention, so a reader comparing two stories compares like with like.

```text
As a Customer Support Agent,
I want to look up a named buyer's reorder lists and that buyer's recorded reorder attempts, each attempt carrying one row per requested line with its requested and applied quantity, its outcome code and any recorded error type name,
So that I can tell the buyer which lines their reorder added, which it did not and why, without asking them to reproduce the attempt and without reading a log file.
```

## 5. Acceptance Criteria

Eight criteria. **Each names exactly one published GraphQL operation under test**, so a failing criterion points at a single contract, and no criterion mentions both of this story's operations. Criteria name operations, their arguments and entity, table and column names as database preconditions; none names a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. The narrative in section 4 is not restated here — the story carries the value and the criteria carry the testable outcomes.

**How the eight map onto the five required coverage classes, named by number so the claim is checkable.** Valid input is AC-1 for `customerReorderLists` and AC-2 for `reorderAttempts`, one per operation. Invalid or incomplete input is AC-3. An error naming the exact type returned is AC-4. An edge case is AC-6. The assertion that an existing operation is unchanged is AC-8. AC-5 carries the cross-capability negative the parent requires of this story by name, and AC-7 carries the do-not-duplicate mandate for the generated list options, which applies to **both** operations because both are paginated.

**Eight properties hold for every criterion below and are stated once here rather than repeated in each.**

- **Both reads are additive and synchronous.** Each arrives through the plugin's `adminApiExtensions` on an `extend type Query` block, which is the mechanism the shipped reviews plugin demonstrates [packages/dev-server/test-plugins/reviews/api/api-extensions.ts:L69-L72], so no existing operation's arguments, return type or nullability changes. Neither enqueues a job nor schedules a task, so neither has an asynchronous trigger or an observable completion signal to name. **Zero Shop API operations are added.**
- **Every request is channel-scoped and language-scoped.** The active channel is identified by the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L61-L62], as that column's own documentation states [packages/core/src/entity/channel/channel.entity.ts:L58-L59], and the request's language resolves from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. The criteria below use the language code `en`. **A row recorded under one channel token is not readable under another, and that bound is applied server-side rather than being a filter a caller may widen** [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. A support agent looking up a buyer who ordered under a second channel is the realistic case, and the answer is that each token returns its own rows and never the other's.
- **One permission definition is registered, and it yields exactly one published member.** It is an instance of the base `PermissionDefinition` [packages/core/src/common/permission-definition.ts:L86], whose `Permission` getter is what the decorator consumes [packages/core/src/common/permission-definition.ts:L107], registered through `authOptions.customPermissions` [packages/core/src/common/permission-definition.ts:L123-L128] and applied with the `@Allow` decorator [packages/core/src/common/permission-definition.ts:L134]. **The four-permission helper is not used** [packages/core/src/common/permission-definition.ts:L146] — it derives a create, read, update and delete member from one name, so a name of 'Wishlist' produces four permissions [packages/core/src/common/permission-definition.ts:L114-L115] — **and neither is the two-permission read-and-write helper** [packages/core/src/common/permission-definition.ts:L245]. The reason is stated rather than left as taste: this story writes nothing, so three of the first helper's four members and one of the second's two would be published members that no operation in this epic ever checks. **That choice is the parent's ruling and is followed here rather than re-derived** [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8 Permission Gating, And The Enum Growth Referenced Rather Than Re-Argued].
- **The gate names exactly one permission, because the decorator is disjunctive.** `@Allow` admits a caller holding any one of the permissions listed, its own documentation stating that with multiple permissions the user needs only one of them under OR logic [packages/core/src/api/decorators/allow.decorator.ts:L11-L12], so a two-argument gate would be **wider** than either permission alone. The conjunction this story requires — its own capability together with the platform's existing `Permission.ReadCustomer` — is therefore enforced inside the resolver ahead of every read with the platform's own AND primitive, `userHasAllPermissions` [packages/core/src/api/common/request-context.ts:L296], which tests each permission rather than intersecting the sets [packages/core/src/api/common/request-context.ts:L303], contrasts itself with the OR-logic sibling in its own documentation [packages/core/src/api/common/request-context.ts:L282-L286] and is available in this line by its own version tag [packages/core/src/api/common/request-context.ts:L294]. **`ReadCustomer` already exists, so the pairing costs zero additional enum members.**
- **A permission gate alone is not a control, and the platform says so about itself.** Ownership must be enforced by custom logic inside the resolver, and because it cannot be defined generally nor statically encoded at build time, a resolver relying on the gate alone is the equivalent of a public one [packages/core/src/api/config/generate-permissions.ts:L32-L34], the whole caveat sitting in one block in that file [packages/core/src/api/config/generate-permissions.ts:L12-L33]. **For a support read that cuts a specific way worth stating: an agent is not the owner of the buyer's data, so ownership is not the control here at all.** What bounds these two reads instead is the capability pairing plus the channel bound plus the addressing rules of AC-3, each applied before any row is fetched. - **Monetary values are integers and are never totalled across currencies.** The only monetary value either operation returns sits on an attempt line, projected as a triple — an integer amount in the smallest unit of its currency, its `currencyCode`, and its tax basis — with all three set together or all three null [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. ## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus two conditional categories that apply because these reads copy a request scope and are paged while rows are still being written. **Each is labelled with its category inline, so the category matrix never appears as a table in a story file.**

* Scenario: Category — zero, null or empty collection. A buyer with nothing recorded, which must be answerable rather than an error.
   * Given an authenticated Administrator holding this story's capability together with `Permission.ReadCustomer` on the channel named by the `vendure-token` header, and one `Customer` [packages/core/src/entity/customer/customer.entity.ts:L23] in that channel who owns zero reorder lists, holds zero unrevoked grants and has zero recorded attempts
   * When each of this story's two lookups is executed in turn, the first addressed by that buyer's identifier and the second by a filter constraining the same identifier
   * Then each returns an **empty paginated list with a `totalItems` of exactly 0 and no error**, because an empty result is a recorded fact rather than a failure; the attempt read still returns its `windowStart` and `windowEnd`, so an agent can see what period was searched rather than inferring completeness from an absence; **and this response is byte-identical to the one an identifier naming no customer row receives**, which is the anti-enumeration rule of AC-6 rather than a coincidence. **The contrast worth stating is with the refusal in AC-3**: an unaddressed call is a request-level failure carrying the platform's input error, while an addressed call over an empty subject is a successful empty page. Those two are different outcomes for different causes, and collapsing either into the other would misreport one of them
* Scenario: Category — an item unavailable, deleted or disabled since the last purchase. The record must outlive the variant it names.
   * Given a recorded attempt whose second requested line named a variant that was already disabled at the moment of the attempt, its `enabled` column being false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53], so that line was recorded as excluded before delegation; and that variant is afterwards removed from the catalogue outright rather than disabled
   * When that attempt is read through this story's attempt lookup after the removal completes
   * Then the line is still returned at its own `requestIndex` with its `requestedQuantity`, its `appliedQuantity` of 0 and its outcome of `NOT_ADDED_VARIANT_UNAVAILABLE` unchanged, and its requested variant identifier and requested variant name come back **null** rather than the line being absent or the whole read failing — those fields being published as nullable precisely so an erased catalogue row cannot fail the response. **This is what lets an agent explain the failure to the buyer**: the outcome member names the class, so the agent can say the item was not orderable at the time and not that the reorder broke, even though the variant it named can no longer be resolved. **Losing the row would delete the evidence about the exact item the buyer is asking about**, which is why the relation is nullable rather than cascading. A variant that was merely disabled or soft-deleted, rather than erased, still resolves its name and is returned with it
* Scenario: Category — a price changed since the last purchase. The record is evidence of what was attempted, not a quotation.
   * Given a recorded attempt line whose amount was stored as an integer in the smallest unit of its currency together with its `currencyCode` and its tax basis, and whose variant is priced differently at the moment the support lookup runs
   * When that attempt is read through this story's attempt lookup
   * Then the line returns the **stored** integer amount with its currency code and its tax basis, all three non-null together, and **no present price, no delta and no recalculated total appears anywhere in the response**; the amount is an integer in the smallest currency unit rather than a decimal, a decimal being a defect rather than a formatting preference; the tax basis is returned rather than omitted because the same integer denotes two different amounts depending on it, so an amount without its basis is ambiguous rather than merely unlabelled; and **the record is explicitly not a quotation** — reporting a price change before a buyer commits is FEATURE-001-03's pre-commit preview surface and is not duplicated here [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. No currency conversion happens anywhere in this story, so there is no place an exchange rate could be applied
* Scenario: Category — a channel, currency or language mismatch between the original order and the lookup context.
   * Given one buyer whose recorded attempts span two channels carrying two distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L61-L62], those two channels declaring different values of `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L87-L88], and an authenticated Administrator holding this story's capability together with `Permission.ReadCustomer`
   * When this story's attempt lookup is executed twice, once carrying each channel token in the `vendure-token` header, with the language resolved from each channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]
   * Then each execution returns only the attempts recorded under the token it carried and **neither result contains the other channel's rows**, the channel being a bound the service applies rather than a filter a caller may widen; **no figure is totalled across the two currency codes** — each recorded amount is returned beside its own currency code and any figure reported is reported per channel, keyed by channel token, because a channel can reach more than one code and "one channel, therefore one currency" is an assumption this platform does not support; every per-line outcome code comes back **untranslated**, being a machine-readable identifier rather than a label; and the only values that follow the requested language code are the dashboard labels rendered around the rows, which live in this story's own plugin-local catalogues rather than in either read's payload
* Scenario: Category — a concurrent modification or race. A row is written while the agent is paging.
   * Given an authenticated Administrator paging through one buyer's recorded attempts with a page size below that buyer's total, and a further attempt for the same buyer being recorded between the first page being returned and the second being requested
   * When the second page is requested with the same sort and the same page size
   * Then the read is **ordered by a declared total tie-break rather than by insertion order**, so the page boundary resolves on a stable key and the observable outcome is stated rather than left to chance: no row already returned on the first page is repeated on the second, and no row that existed when the first page was read is skipped. The newly written row may or may not appear, and **that is reported as the semantics rather than concealed** — each page is a point-in-time read over a table another feature is still writing to, and no lock, snapshot or reservation is taken anywhere in this story. An agent who needs a settled view re-runs the read, which is a cheaper and more honest answer than a consistency guarantee this story does not implement
