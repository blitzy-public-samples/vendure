## 1. Story Title

**Look up a buyer's reorder lists and last recorded attempt through two permission-gated Admin API reads, so that a Customer Support Agent can state which lines reached the cart and which did not from a stored record.**

Short form, transcribed from the epic's story table without rewording so that the two files agree: **Look up a buyer's lists and last attempt** [tickets/EPIC-001-reorder-and-replenishment.md:§9.2 Story Table].

**This story is not free-standing, and presenting it as though it were would misdescribe why it exists.** FEATURE-001-08 was **expanded** from the suggested seller-and-category visibility area to absorb the Customer Support Agent read path, on the ground that all three administrative personas read the same rows over the same plugin-owned tables and a separate support feature would have duplicated the resolver wiring, the permission registration and the pagination contract [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.2 Contribution To The Epic, And The Expanded Rationale]. The support lookup therefore lives beside the demand aggregate rather than in a feature of its own, and it inherits that feature's scoping, pagination and enum contracts instead of restating them.

The unit of work is **two Admin API queries and one permission definition, over zero new tables**. `customerReorderLists` returns the lists a named buyer holds, including those reached through an unrevoked grant. `reorderAttempts` returns recorded attempts with their per-line outcome codes, addressable by the buyer's identity or by the order code recorded on the attempt. Both are gated on a capability separate from the one that reads the demand aggregate, and that separation is a least-privilege requirement rather than an accounting choice [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8 Permission Gating, And The Enum Growth Referenced Rather Than Re-Argued].

**Three absences define this story as sharply as its two operations, and each is stated positively rather than left to be inferred from silence.**

- **No new table and no migration.** Every row read here is created elsewhere: `ReorderList` and `ReorderListLine` by FEATURE-001-01, `ReorderListShare` by FEATURE-001-06, and `ReorderAttempt` with `ReorderAttemptLine` by STORY-001-07-01. Because there is no schema change, the cached seed-data reset under `e2e/__data__/` [AGENTS.md:L19] is **not** triggered by this story, and the repository's classification of a database-schema change as breaking-change work [CONTRIBUTING.md:§Breaking Changes] does not bite on it directly.
- **No new error result.** FEATURE-001-08 declares none of the six this ticket set introduces; all six belong to FEATURE-001-01, FEATURE-001-02 and FEATURE-001-06 [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.14 The Four Absences, Stated Positively]. The published error-code enum therefore gains nothing on this story's account.
- **No forecast.** Visibility over recorded activity is in scope; predicting future stock requirements is out, on the two grounds the epic states rather than asserts — a forecast has no basis in this repository, and there is no declared numeric target to validate one against [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.11 Visibility Is Not Forecasting]. Every value this story returns is a description of something a buyer already did.

**What this story owns that no other file may restate.** STORY-001-07-01 declares no read operation and no permission definition, and delegates the audit-read gate here by name [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.6 Named API Surfaces]. ## 4. User Story

The three mandated lines are rendered as a fenced plain-text block so that each of WHO, WHAT and WHY occupies its own visible line on any renderer and when this file is pasted into an external tracker. Every story file in this set uses that same convention, so a reader comparing two stories compares like with like.

```text
As a Customer Support Agent,
I want to look up a named buyer's reorder lists and that buyer's recorded reorder attempts, each attempt carrying one row per distinct projected variant key with its requested and applied quantity, its outcome code and any recorded error type name,
So that I can tell the buyer which lines their reorder added, which it did not and why, without asking them to reproduce the attempt and without reading a log file.
```

The underlying operations are exercised separately and first by the backend specification of section 10, because a page rendering over a wrong read is worse than a page that does not render.

### 4.3 The Page Contract — Arrival, Subject Binding, States And Presentation

**Why this sub-section exists, and why it carries more weight here than on either sibling page.** Section 5 fixes the two operations; it says nothing about the surface, and this is the one page in the epic that displays **one named person's** activity to somebody who is not that person. That creates a class of defect the operation contract cannot prevent: the page can show buyer A's rows under buyer B's heading, it can render a refusal as an empty result so an agent tells a buyer nothing was recorded when in fact the read was declined, it can print machine outcome identifiers an agent then reads aloud to a customer, and it can leave an erased catalogue item as a blank cell where the story promised the agent could name the exact item. Each is settled below and carried into section 6's dashboard line and section 10.

**What this sub-section is not.** **No design system, component-library version, style guide or design source is named anywhere in this ticket set, and none was supplied to this project** — an absence stated rather than quietly filled in, following the convention this epic applies to every absence it found [tickets/EPIC-001-reorder-and-replenishment.md:§11.8 Tooling Findings, Including The Absences]. So nothing below states a pixel value, a colour, a font, a spacing figure or a contrast ratio. Every obligation is a *behaviour* expressed against a dashboard building block that exists in this checkout and is cited, as the shipped precedent composes its own list surface from published blocks [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9].

#### 4.3.1 One Route, One Page Identity, One Navigation Entry — And It Is This Story's Own

- **This story registers the route `/customer-reorder-activity`, one stable `pageId` on the page it renders — the framework's list page taking that identity as a declared property [packages/dashboard/src/lib/framework/page/list-page.tsx:L48] — and exactly one navigation entry**, in the shape the shipped precedent uses [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L42-L50]. The `pageId` keeps this page's column-visibility preference to itself, the framework keying default visibility per page [packages/dashboard/src/lib/framework/page/list-page.tsx:L286-L288].
- **It is a different route from the recurring-demand page stories 08-01 and 08-02 share**, and deliberately so: a different capability governs it, its subject is one named buyer rather than a channel's trading, and putting it behind the demand entry would present one person's purchasing behaviour as though it were marketplace analytics.
- **The navigation entry carries the same client-side permission hint the precedent uses** [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L48], which **hides a menu item and authorises nothing** — the capability pairing is enforced in the resolver ahead of every read, which AC-4 and AC-5 assert.

#### 4.3.2 The Subject Is Chosen Through A Selector, Not Typed As An Identifier, And It Never Reaches The Route

- **The buyer field is a selector over the platform's existing administrative customer read** `customers(options: CustomerListOptions): CustomerList!` [packages/core/src/api/schema/admin-api/customer.api.graphql:L2], and it is the same debounced search the shipped customer picker already issues, returning each customer's identifier together with `firstName`, `lastName` and `emailAddress` [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L18-L29], debouncing the typed term before it reaches that read [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L45-L65] and rendering the two names above the email address in each row [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L90-L103]. **This is the email-to-identifier mapping the story needs and it is a read that already exists** — an agent knows a buyer's email address, both of this story's lookups are addressed by a `Customer` identifier [packages/core/src/entity/customer/customer.entity.ts:L42], and nothing on this page invents a lookup-by-email operation. **No new read operation is added for it**, which is why this story's operation count stays at two.
- **The selector is gated on the same `Permission.ReadCustomer` the resolver requires**, so the page cannot present a search an agent's own session is not entitled to make. That is presentation aligning with the control rather than becoming it.
- **The chosen buyer's identifier is NOT in the route, and neither is the selected attempt — both live in page state and travel only in the request body.** **This reverses an earlier revision of this bullet, which held both identifiers in route search parameters and presented deep-linking as the benefit**; it is withdrawn on evidence rather than on taste. A `Customer` identifier and an attempt identifier are **sequential auto-increment values by default** [packages/core/src/config/default-config.ts:L101], so a route carrying one is an enumerable pointer to one named person, and once it is in the address bar it is simultaneously in browser history, in the `Referer` header of any request the page originates to another origin, and in any deployment telemetry that records URLs — **three stores this page does not control and cannot clear**, all of which outlive the subject being cleared. The identifiers reach the server as GraphQL variables inside the `POST` body of the two reads, which the transport contract already requires of both [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10.1 The Transport And Credential Contract, Applied To These Three Reads], so nothing is lost from the request and the exposure surface is one place instead of four.
- **Attempt selection is explicit and its own state.** The lists panel and the attempt list are addressed by the buyer; opening one attempt records that attempt's identifier in page state — not in the route — and reveals its per-line rows. **Until a buyer is chosen, both reads are not issued at all** — the page shows its no-subject state rather than firing an unaddressed call, which AC-3 establishes is refused anyway.

#### 4.3.3 The Subject Binding Is A Safety Contract, Not A Convenience — This Is The Highest-Consequence Rule On The Page

**The mechanism that makes this necessary is shipped, global, and points the wrong way for this page.** The dashboard's query client sets `placeholderData: keepPreviousData` as an **application-wide default**, so a query whose key changes keeps rendering the previous key's data while the new request is in flight [packages/dashboard/src/app/app-providers.tsx:L12-L19]. On a list of products that is a considerate touch. **On this page it means an agent who switches from buyer A to buyer B sees buyer A's reorder lists and attempt lines under buyer B's name**, which is a disclosure of one customer's activity to an agent working a different customer's case, and a false record of what the second buyer did.

- **Every query on this page is keyed on the resolved `Customer` identifier and the active channel token**, both as first-class parts of the key rather than as arguments carried alongside it, so no two subjects can ever share a cache entry.
- **This page opts out of the global previous-data default**, using the dashboard's own established idiom for exactly this situation — the shipped selection-keyed inputs set that option to undefined with the reasoning that any "previous" data corresponds to a different selection and showing it would render stale content during the swap [packages/dashboard/src/lib/components/data-input/facet-value-input.tsx:L37-L41]. **The same reasoning applies with more force here, because the stale content is another person's record rather than a stale chip.**
- **On a subject change the rendered rows are cleared before the new request resolves**, and the panel shows its loading state. The same applies to a channel switch, which rewrites the request token beneath the page [packages/dashboard/src/lib/graphql/api.ts:L22] and [packages/dashboard/src/lib/graphql/api.ts:L29-L30] and invalidates queries without resetting anything the page is holding [packages/dashboard/src/lib/providers/channel-provider.tsx:L177-L193].
- **A response that arrives for a subject the page has since left is discarded and never rendered.** Two searches issued before the first has resolved can return out of order, and the later-arriving response is not necessarily the current subject's — so the page renders a response only when its key matches the current buyer and channel.
- **Every rendered row and every panel heading names the subject it belongs to**, so a mismatch is visible rather than silent, which is what 4.3.5 requires.
- **Nothing about the searched buyer is persisted by the page — and making that true requires clearing TWO in-memory stores the shipped selector keeps, which an earlier revision of this bullet asserted past rather than addressed.** The email address an agent typed is not written to local or session storage, is not appended to the route as a display value, and is not retained after the subject is cleared; the route carries the **identifier** the selector resolved, not the address that was searched. A support workstation is frequently shared, and a store that accumulates the addresses of every buyer an agent looked up is a durable record nobody governs.
  - **The shipped `CustomerSelector` retains the searched term in component state.** It holds it in `useState` [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L47] and debounces it [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L48], and nothing in that component clears it when a customer is chosen or when a caller clears its subject. **So this page resets the selector's own state on both events**, which it does by remounting the component under a key derived from the current subject rather than by reaching into it — a remount discards the state a component owns, and this page owns no code inside the shipped selector.
  - **The shipped `CustomerSelector` also retains it, and every matched buyer's email address, in the query cache.** Its search term is part of its TanStack cache key, `['customers', debouncedSearchTerm]` [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L51], the response it caches renders each match's `emailAddress` [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L102], and it sets a one-minute `staleTime` [packages/dashboard/src/lib/components/shared/customer-selector.tsx:L66] while the shared client sets no `gcTime` [packages/dashboard/src/app/app-providers.tsx:L12] — so both the term and the matched addresses survive in memory well past the moment the subject is cleared. **So clearing the subject also removes every cache entry whose key begins `['customers', …]`**, through the exported client [packages/dashboard/src/app/app-providers.tsx:L12], and the same removal runs when the page unmounts. **This is asserted rather than described:** after a search and a subject clear, no cache entry keyed on the searched term remains and the searched string appears in no cache entry's data.
  - **What this does NOT claim.** It does not claim the address never entered memory — it did, because the agent typed it and the server answered — only that it does not outlive the task. A page cannot control what a browser retains in a heap it does not own, and that limit is stated rather than papered over.
- **The route identifier IS a persistence surface, and "nothing is persisted" was too strong without this bullet.** The identifier in the route is written into browser history, is carried in the `Referer` header of any request the page originates to another origin, and is captured verbatim by any deployment-level telemetry that records URLs — **none of which is under this page's control once the value is in the route**, and all three outlive the subject being cleared. **The bullet above is therefore narrowed to what it can honestly claim** — no address and no buyer attribute is persisted anywhere by this page — **and four mitigations are stated as requirements rather than left as reassurance:**
  - **The route value is an opaque identifier and never a contact detail**, so what history retains is a value meaningless without Admin API access under permission, rather than the buyer's email address.
  - **A subject change REPLACES the current history entry instead of appending one**, so the back-stack holds at most one subject rather than accumulating every buyer an agent looked at during a shift; and **clearing the subject removes the identifier from the route** rather than leaving it behind the no-subject state.
  - **The page originates no cross-origin request and embeds no third-party script, image, font or analytics beacon**, so no `Referer` carrying the route leaves the deployment's own origin; any link it renders to another origin carries a no-referrer relationship. **This is asserted by a test that fails on any request to an origin other than the deployment's own** while the page is mounted, rather than by review of the source.
  - **Deployment telemetry that records URLs will record the identifier, and that is the operator's to govern rather than this page's to prevent.** It is stated so an operator can decide, not disclaimed: the identifier is not personal data on its own, and the page adds no telemetry of its own to make it so.
  - **Whether a customer-linked route identifier is acceptable at all is a RULING this story does not have the standing to make, and it is now recorded as an open epic-level decision rather than assumed by these four mitigations.** The four above are the controls; they are not a permission. **An earlier revision of this section carried the mitigations and no ruling**, which read as this page granting itself one. The question — whether an opaque customer identifier may sit in an administrative route, and therefore in browser history and in whatever URL telemetry a deployment runs, or whether the subject must instead be addressed by a short-lived non-linkable handle minted per session — is ranked in the epic's product decisions with this story named among those it blocks [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. **The story is buildable against either answer** — the addressing surface is the route parameter and the mitigations are the same in both cases — and what the ruling gates is sign-off, exactly as the retention window gates story 07-01's.
- **This is asserted rather than assumed.** Section 10 requires a test that resolves buyer A, renders A's rows, switches to buyer B, and asserts that **at no point** does a row belonging to A appear under B — including while B's request is in flight — together with an out-of-order case in which A's response arrives after B has been selected and is discarded.

#### 4.3.4 Every State The Page Can Be In, Named — Including The One That Is A Refusal

- **No subject.** Before a buyer is chosen the page shows the selector and an explanatory no-subject state, and issues neither read.
- **Loading and refetching.** Each panel renders the loading state the data table already takes as a property [packages/dashboard/src/lib/components/data-table/data-table.tsx:L142], which the shipped paginated list wires from its own fetching flag [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L506], with a refetch available through the refresh control the same table renders [packages/dashboard/src/lib/components/data-table/data-table.tsx:L452]. **Because of 4.3.3, a refetch for the *same* subject may keep the previous rows on screen and a change of subject may not.**
- **Empty.** A buyer with nothing recorded renders the table's own empty state [packages/dashboard/src/lib/components/data-table/data-table.tsx:L588] together with the subject and window summary of 4.3.5 — and its wording is identical to the wording an identifier naming no customer produces, because AC-6 requires the two to be indistinguishable and a page that phrased them differently would reintroduce the enumeration oracle the operation closed.
- **Refusal.** A caller holding one half of the capability pairing is refused before any row is read, which AC-4 asserts in both directions. **The page renders that refusal as its own explanatory state, visually distinct from an empty result** — because a refusal shown as an empty table leads an agent to tell a buyer that nothing was recorded, which is a false statement about that buyer's history rather than a cosmetic defect. The platform's permission guard renders nothing at all when a permission is absent [packages/dashboard/src/lib/components/shared/permission-guard.tsx:L44-L49], which is right for hiding the navigation entry and wrong for a whole page, so the guard covers the entry and an explicit refusal state covers the body.
- **Read failure.** A failed read renders a retry affordance and the safe content of 4.3.6, and **never an empty table**.
- **Dependent controls are disabled rather than misleading.** While no buyer is resolved, the attempt list, the paging controls and the attempt-detail region are inoperable; while a subject change is resolving, they are inoperable again rather than operating on the outgoing subject's data.

#### 4.3.5 The Subject, The Channel And The Window Are On The Screen And Bound To The Result

**An agent reads this page aloud to a customer, so an unlabelled panel is an invitation to state the wrong person's record as fact.**

- **Each panel is a plugin-local page region holding its OWN typed query, which is what makes the line below renderable at all.** `windowStart` and `windowEnd` are **sibling fields of the `ReorderAttemptSummaryList` wrapper**, not fields of a row, and the dashboard's shipped paginated table has no route by which a caller receives a wrapper field: its typed contract knows a paginated result as `{ items, totalItems }` and nothing else [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L134] and [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L141]. So this route follows the composition the parent feature declares for all three of its surfaces — **one plugin-local page composing its own typed queries, with the shipped table used beneath each panel as a presentation component receiving `items` and `totalItems`** [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.12a The Dashboard Composition Every Surface In This Feature Uses — A Plugin-Local Typed Query And Page, NOT The Stock `ListPage`]. **An earlier revision of this sub-section bound this line to the stock component's own data**, which that component cannot supply. **Pagination is the page's**: it sends `skip` and `take` explicitly for the attempt panel rather than inheriting the primitive's `take: Math.min(itemsPerPage, 100)` [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L481-L482], which matters here beyond the metadata — the page's chosen `take` is the operand the response-object ceiling of section 4.4 is checked against, so a `take` the page did not choose is a bound it cannot honour, and `ReorderPluginOptions.adminReadDefaultPageSize` governs a caller that omits `take` rather than this surface.
- **A summary line is rendered above each panel on every state including the empty one and the refusal**, naming: the buyer the subject resolved to, by the name the selector resolved rather than by an identifier; the active channel, by the channel label the dashboard already renders; and, for the attempt panel, the searched period as `windowStart` and `windowEnd`, which AC-2 asserts are returned non-null for exactly this purpose.
- **Where an attempt is open, its source handle is shown by BRANCHING ON `sourceType` rather than by printing `sourceOrderCode`, and its `correlationId` is shown unconditionally.** `sourceOrderCode` is nullable and is null in two cases that mean opposite things, so a page that always prints it renders an empty cell for a perfectly ordinary list-sourced attempt [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change]. **Three cases and three renderings, each a catalogue entry:** where `sourceType` names an order source and the code is present, the code is shown as the handle a buyer recognises; where `sourceType` names any other source, that source's own label is shown and no order handle is offered; and where `sourceType` names an order source and the code is null — reachable only after the lifecycle pass has cleared it — the erased-source label is shown. **`correlationId` is non-null on every row and is retained across erasure**, so it is the handle an operator can search on in all three cases, which is what keeps a support conversation possible when no order code exists to quote. **An earlier revision of this bullet displayed the nullable code unconditionally.**
- **On the refusal state the line names what was declined** rather than showing a subject the page did not read.
- **Every part of the line is a catalogue entry with values interpolated**, never an assembled English sentence, and the two window bounds are rendered through the locale-aware date formatter of 4.3.8.

#### 4.3.6 Error Content — What Is Shown, And What Is Never Shown

**The shipped default is the other way, which is why this is a rule.** The platform's own detail page surfaces a caught error's message straight into a notification [packages/dashboard/src/lib/framework/page/detail-page.tsx:L166-L170]; copying that here would put whatever a resolver, a driver or a proxy produced onto a support agent's screen — and on this page such output can carry a customer identifier, a bound parameter naming a person, or a fragment of a statement over customer-linked tables.

- **The two expected refusals are mapped to their own translated copy** — a forbidden response to the capability explanation of 4.3.4, and an input error to the addressing explanation AC-3 fixes — **and everything else renders one generic unexpected-error explanation** carrying a retry and an **opaque support handle** the agent can quote onward. The handle is a value generated for the failed interaction, not a database identifier and not the buyer's.
- **Never rendered: a raw exception message, a stack frame, a driver or SQL fragment, a table or column name, an internal identifier, a file path, or any part of the generated statement.**
- **No third party's data appears in any message**, and no message names a customer other than the resolved subject.
- **The detail is relocated rather than destroyed:** it belongs in the server's own log, under the epic's own constraint on what a log entry may carry [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality — And The Shipped Mechanism That Would Break It].

#### 4.3.7 Machine Identifiers Get A Translated Explanation Beside Them, And The Raw Value Is Kept

**Both reads project machine vocabularies deliberately** — the per-line outcome members and the recorded `errorCode` string, the latter typed as a string rather than as the platform enum so a historical value cannot fail the read. **An agent cannot use either as it stands**: `NOT_ADDED_VARIANT_UNAVAILABLE` and `OrderLimitError` are contracts, not sentences, and reading one to a customer explains nothing.

- **Every outcome member is rendered as a translated label with a translated one-line explanation beside it**, drawn from this story's own catalogues, and **the raw member is kept visible rather than replaced** so an agent can quote it in an internal escalation and a test can assert on it.
- **Every recorded `errorCode` is treated the same way**, with an entry for each of the five names the closed set admits — `OrderModificationError`, `OrderLimitError`, `NegativeQuantityError`, `InsufficientStockError` and `OrderInterceptorError` [packages/core/src/api/schema/common/common-error-results.graphql:L112-L117].
- **An unrecognised value falls back to the raw string rather than to a blank or a guess.** This is required rather than defensive: `errorCode` is a string precisely because a stored value may name a type a later deployment no longer declares, so an unmapped value is an expected input to the page and not an error in it.
- **A null `errorCode` is not rendered as an absence of information.** On the excluded-before-delegation class it is null *by design*, because the platform supplies no error result for it, and the page says so in translated copy rather than leaving an empty cell an agent would read as missing data.
- **The five line counts and the attempt outcome receive the same treatment**, each with a translated label so that the identity between the requested count and the sum of the other four is legible on the screen rather than only in the schema.

#### 4.3.8 Presentation Is Locale-Aware, And Money Carries Its Row's Own Currency And Tax Basis

- **Money.** A line's recorded amount is an integer in the smallest unit of **that row's own** `currencyCode`, and it is rendered through the dashboard's own currency formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L47-L57] or the display component built on it [packages/dashboard/src/lib/components/data-display/money.tsx:L10-L13], which applies the fraction-digit count and the symbol that locale and currency imply. **No page code divides by a hundred, concatenates a symbol or writes a decimal separator, and no amount is rendered in a currency other than the one on its own row** — the page reports per row and never totals, so no figure can span two codes.
- **The tax basis is rendered as a translated label beside the amount, not omitted and not shown as a bare boolean.** The field is `listPriceIncludesTax`, which is the canonical name the producer stores and the parent publishes; **an amount without its basis is ambiguous rather than merely unlabelled**, because the same integer denotes a gross or a net figure depending on it. Where the triple is null the page says the amount was not recorded, in translated copy, rather than rendering zero.
- **Timestamps.** Each attempt's creation timestamp and the two window bounds are rendered through the locale-aware date formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L66-L71] or the display component built on it [packages/dashboard/src/lib/components/data-display/date-time.tsx:L3-L9], never as a raw transport string.
- **Counts** — the five line counts, `totalItems`, `lineCount` and each line's quantities — are rendered through the locale-aware number formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L59-L64] from the hook the dashboard already exposes [packages/dashboard/src/lib/hooks/use-local-format.ts:L27], and **no count is abbreviated, rounded or clipped**; `requestIndex` is an ordinal identity and is rendered as the integer it is.
- **Every label is a catalogue entry.** No literal user-facing string appears in the surface's source; each is marked up through the translation macro the shipped precedent imports [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L2] and extracted into the plugin's own catalogues over a source locale and a second language [packages/dev-server/lingui.config.js:L4-L5] at the path that configuration names [packages/dev-server/lingui.config.js:L8-L9].
- **What is translatable and what is not is stated per value.** A variant's name is a translated platform value; an outcome member, an `errorCode` and a `correlationId` are machine identifiers that are never translated but always **explained**, per 4.3.7; and counts, amounts and timestamps are language-invariant values given a locale-aware presentation.

#### 4.3.9 An Erased Item Is Still Named, Because The Story Promised The Agent Could Name It

**This closes the gap that made the story's own claim unkeepable, and the gap has since been closed a second time at its source.** The earlier design held the requested variant through a nullable set-null relation so that a hard delete could not remove the row — but a row whose only identifier has just been nulled identifies nothing, and an agent asked "which item did not arrive?" could not answer. **That relation is withdrawn at the producer: there is no relation and no foreign key on either variant identifier, and the requested one is `NOT NULL`** [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **So the identifier no longer goes null — which fixes the naming gap and creates a second one this section also closes**: whether the item still exists can no longer be read off the identifier, so it is published as its own state rather than inferred. **Two independent fixes now stand between that question and a blank answer:** the label is snapshotted at insert time, which is what this paragraph goes on to describe, **and the identifier itself is a snapshot column rather than a relation**, so it survives the deletion too [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. The label remains the thing an agent reads; the identifier is what a follow-up query uses.

- **The producer stores an immutable label snapshot at insert time and the parent publishes it as non-null**: `requestedProductVariantName` and `requestedProductVariantSku` are written once when the attempt is recorded and are never re-resolved through the relation [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched]. **This page consumes those two fields as the item's identity** and does not depend on the relation resolving.
- **The identifier is NEVER null, so the page branches on a published existence state instead — and this is the correction that closes the second half of the gap.** `requestedProductVariantId` is `ID!` and stays populated after its catalogue row is hard-deleted [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change], so there is nothing to test for emptiness. **The page reads `requestedProductVariantState.exists`**: where it is true the row shows the item's current translated name with the snapshot beside it, and where it is false the row shows the stored `requestedProductVariantName` and `requestedProductVariantSku` together with a translated deleted-item note saying the catalogue entry no longer exists. **An earlier revision of this bullet said "when the identifier is null"**, which is a branch this contract cannot reach and which would have left a hard-deleted item rendered as though it still existed. The cell is never blank and never shows a bare identifier in either case, and the row's outcome, quantities and recorded amount are unchanged and are shown as they stand.
- **The note is a catalogue entry rather than an English literal**, and it is distinct from the outcome explanation of 4.3.7: the outcome says why the line was not added, and this note says why the item can no longer be opened in the catalogue. Conflating them would tell an agent the line failed because the item was deleted, which may be false — the deletion can have happened long after the attempt.
- **A variant that was merely disabled or soft-deleted still resolves**, so no note is shown for it and its link into the catalogue remains, which is the distinction the second scenario in section 7 asserts.

#### 4.3.10 Operable Without A Mouse, And Usable On A Narrow Viewport

- **Both result regions are tables.** Rows, cells and column headers are rendered through the data table's own semantic markup rather than as generic containers [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9], each sortable header being a control with an accessible name and its current sort direction exposed rather than shown only as an icon. The attempt's per-line rows are a table too, not a list of paragraphs, because `requestIndex`, the quantities and the outcome are columns an agent scans across.
- **The buyer selector is labelled** rather than relying on placeholder text, is reachable and operable from the keyboard, and its results are announced as they narrow — a search field whose result count is silent is unusable without sight.
- **Focus moves in the order the page reads**: buyer selector, then the lists panel, then the attempt list, then the open attempt's lines, then pagination. **Opening an attempt moves focus into that attempt's region** and closing it returns focus to the row that opened it, so an agent working from the keyboard is never dropped at the top of the page.
- **A change of subject or of result set is announced through a live region, naming the resolved buyer** — because the failure this page guards is precisely a silent change of subject, an announcement that omits the buyer would not surface it.
- **Narrow-viewport behaviour is stated because the platform's own column control is not available there.** The data table's column-settings trigger is hidden below the large breakpoint [packages/dashboard/src/lib/components/data-table/data-table-view-options.tsx:L91], so a narrow viewport cannot be repaired by the agent hiding columns. **The two panels stack rather than sitting side by side, in reading order: subject, then lists, then the attempt** — and the subject summary of 4.3.5 stays visible above whichever panel is in view at every width. Column priority on the line table: `requestIndex`, the item's name and the outcome are present at every width; the SKU, the two quantities, `quantityAvailable`, the recorded amount and the `errorCode` give way first, reached by horizontal scrolling of the table region rather than truncated. **Every action reachable at a wide viewport is reachable at a narrow one**, and no value is silently clipped.

### 4.4 The Access-Audit Behaviour — DECLARED BY THE OWNING FEATURE, IMPLEMENTED HERE

**A named-customer support read is the one operation in this epic where the *reader* is worth recording, and an earlier revision of this file never said whether that happens.** Leaving it unstated is the worst of the three options, because a deployment then inherits whichever behaviour the implementation happened to have.

**Where the decision lives has moved, and that move is the correction this section carries.** An earlier revision took the decision *here*, at story level, and introduced with it a durable customer-linked write performed by a read, an on-by-default configuration switch and an error-extension key — none of which the owning feature declared and none of which appeared in the epic's option ledger. **A story may consume a published contract; it may not publish one.** So the behaviour is now declared by FEATURE-001-08, which owns both operations, with its switch ledgered in the epic [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8a The Access-Audit Write On The Two Support Reads, And The Two Error-Extension Keys — Declared HERE Because A Story May Not Introduce Either] and [tickets/EPIC-001-reorder-and-replenishment.md:§7.10 The Plugin Option Ledger — One Authority For Every Configured Key]. **This section is now this story's implementation and test obligation against that declaration rather than the declaration itself**, and every value below — the entry type, the three payload members, `ReorderPluginOptions.recordAdminReorderReadAccess` and its `true` default, the fail-closed posture, the retention path and the history-event side effect — is transcribed from the feature and not decided here.

**The behaviour, restated so this file is readable on its own: this story writes one minimised administrator-attributed access-audit entry per subject-resolving read, and the earlier position that it records none is withdrawn.** That position rested on three grounds, and **the first of them is simply false against this checkout** — which is why the reversal is a correction rather than a change of appetite. The other two survive, and what they now govern is how *small* the entry is rather than whether one exists.

- **WITHDRAWN — "an access log is a table" is not true here, because the platform already ships one.** `HistoryService.createHistoryEntryForCustomer` writes a `CustomerHistoryEntry` against core's own history table [packages/core/src/service/services/history.service.ts:L325-L328], and it **resolves the acting administrator from the request context itself** [packages/core/src/service/services/history.service.ts:L330] and attaches it to the entry [packages/core/src/service/services/history.service.ts:L337], which is precisely the administrator-to-subject attribution an access audit needs. Its `isPublic` parameter defaults to false [packages/core/src/service/services/history.service.ts:L327], so the entry is not a buyer-visible history item. **So this story still owns no table and adds none** — the definition-of-done item it cited is untouched. **What it does add is one member to the existing published `HistoryEntryType` enum**, because the entry carries a plugin-declared type, and that is declared as a schema delta rather than absorbed [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.15 Constraints This Feature Is Built Under]. **The retention question it invoked is answered rather than deflected, and the answer is partly a boundary rather than a guarantee** — a hard delete of the customer removes the entry by cascade, a soft delete does not, and this epic's erasure pass does not reach a core table at all; all three are stated below rather than left to “whatever governs that customer's history”, which was an answer that named no behaviour a reader could check.
- **A durable record of which agent looked up which customer is itself customer-linked personal data.** Adding it without a stated retention period and a stated erasure path would create exactly the kind of ungoverned durable record the epic's own logging constraint exists to prevent [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality — And The Shipped Mechanism That Would Break It].
- **The reads are already narrowly bounded**, which is what keeps the entry small rather than what excused its absence: neither has an unaddressed form, both require a capability pairing evaluated before any row is fetched, both are channel-bound server-side, and the projection carries no email address, no postal address, no telephone number and no payment detail — which AC-1 asserts field by field.

**The other controls this story carries, which are what keep the audit entry minimal rather than what once stood in for it.** An earlier version of this list called them "compensating controls" for the absence of an audit; with the audit present they are no longer compensating anything, and each still holds on its own terms.

- **The projection is minimised at the contract rather than at the page.** An agent cannot exfiltrate what the operation never returns, and AC-1 asserts the omissions as the contract rather than as an oversight.
- **Least privilege is enforced and tested in both directions.** The capability pairing means a demand reader cannot reach a named buyer, which AC-5 asserts, and half the pairing reaches nothing, which AC-4 asserts on both halves.
- **Enumeration is closed.** An empty subject and an unknown identifier are byte-identical, which AC-6 asserts, so the reads cannot be used to discover which buyers exist.
- **Nothing about the searched buyer is persisted client-side**, per 4.3.3, so no durable record accumulates on a shared support workstation either.
- **Sanitised diagnostics only.** Where a failure is logged server-side it carries a stable failure code, a correlation identifier and the channel — and **no customer identifier and no searched address** — the same shape and the same reason the instrumentation feature fixes for its own log entries [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality — And The Shipped Mechanism That Would Break It].
- **"The correlation identifier" needs saying which one, because for these two reads the obvious answer does not exist.** An attempt row's own `correlationId` is minted by the reorder mutation and exists only where an attempt exists [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.4 Named Entities Touched] — so a failure **of the lookup itself** has none, which is precisely the failure an agent needs a handle for. **An earlier version of this list referred to "the correlation identifier" as though one were always available, and it was not.** The gap is closed by a second, differently scoped identifier:
  - **Each of these two queries mints its own request correlation identifier server-side, at the resolver boundary, before any read.** It is opaque, carries no customer identity and no searched address, and is minted whether or not the request succeeds — which is the property an attempt's identifier cannot have.
  - **It travels three ways, each is asserted, and the carrying key is NAMED rather than left to the implementation:** it is the value the sanitised server log entry above carries; it is returned to the client on a failure as **`extensions.reorderSupportCorrelationId`** on the top-level error entry, alongside **`extensions.reorderSupportFailureCode`** carrying one member of the resolver's closed failure vocabulary — both keys declared by the owning feature so that no page picks its own [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8a.2 Two Error-Extension Keys, Named Here So No Page Chooses Its Own]; and **it is rendered beside the generic unexpected-error copy of 4.3.6**, which is what turns "something went wrong" into a sentence an agent can quote to an operator. **An earlier revision of this bullet said only "in the error's own extensions" and named no key**, which made the handle whatever an implementation happened to choose and therefore not a contract the page could be written against. **The page reads the failure code and maps it to its own catalogue copy**, and displays the correlation identifier verbatim as the only server-supplied value it renders.
  - **It is not the same value as an attempt's `correlationId` and the two are never conflated.** Where a row is displayed, that row's own attempt identifier is shown as the handle for *that reorder* [tickets/EPIC-001/FEATURE-001-08/STORY-001-08-03-support-agent-reorder-lookup.md:§4.3.5 The Subject, The Channel And The Window Are On The Screen And Bound To The Result]; the request identifier is the handle for *this lookup*. **A test asserts a failed lookup returns and renders one**, because an identifier that exists only on the success path is an identifier for the case nobody needed it in.

**The audit entry, specified in full, because "write an audit entry" is not a contract.** It is a prerequisite of this story rather than a follow-up, and it is deliberately the smallest record that answers "who looked at whom".

- **When.** One entry per read that resolves a subject, on **both** of this story's operations, **including a read that returns an empty page** — an agent who looked and found nothing still looked. A request refused before a subject is resolved writes none, because there is no subject to attach it to; for that case the record is the sanitised log line and the request correlation identifier specified above. **And because these two reads write, they are the epic's single declared exception to the rule that a plugin query performs no write, which makes the transport contract a control over this write rather than a statement about reads** [tickets/EPIC-001-reorder-and-replenishment.md:§7.5.1 The Transport And Credential Contract]: a `GET` naming either operation is refused before any resolver runs, and a cookie-authenticated cross-origin request carrying a browser-simple content type is refused **and leaves zero entries**. That second assertion is the one that matters here — a refusal that still wrote would have moved the side effect within reach of a cross-site request while the response stayed safely refused.
- **What.** A plugin-declared entry type, **`REORDER_SUPPORT_READ`** — declared as `extend enum HistoryEntryType` on this plugin's own Admin API schema in the shape the shipped precedent uses [packages/dev-server/test-plugins/custom-history-entry/custom-history-entry-plugin.ts:L58-L60], with the payload typed by module augmentation of `CustomerHistoryEntryData` [packages/dev-server/test-plugins/custom-history-entry/types.ts:L10-L12], **which grows that existing published enum by one member and is declared as a schema delta rather than absorbed** [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.15 Constraints This Feature Is Built Under] — `isPublic` left at its default of false [packages/core/src/service/services/history.service.ts:L327], and a data payload of exactly three values: the operation name, the channel identifier, and — for the attempt lookup — which of the two addressing forms was used, as a closed two-member value. **The acting administrator is not stored by this plugin at all**: the platform resolves it from the request context and attaches it [packages/core/src/service/services/history.service.ts:L330] and [packages/core/src/service/services/history.service.ts:L337]. **What is deliberately absent, and asserted as absent: the email address or any other value the agent typed, the resolved row identifiers, the counts returned, the page bounds, and any part of the result.** An access audit records the access, not the answer.
- **Retention, erasure and export — three questions rather than one, and the honest answer to the middle one is a boundary.** **Retention.** The entry is attached to the `Customer` through a cascade-deleting relation [packages/core/src/entity/history-entry/customer-history-entry.entity.ts:L20-L21], so a **hard** delete of that customer removes it in the database with no plugin code involved, and it lives under the platform's own governance rather than under a period this story invents [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. **A SOFT delete does not remove it, and an earlier revision of this bullet implied otherwise by saying the entry “lives and dies with that customer's history”.** The platform's soft delete stamps `deletedAt` and does nothing else [packages/core/src/service/services/customer.service.ts:L800-L802], so the entry outlives a soft-deleted buyer. **Erasure.** This epic's erasure pass governs the plugin's own audit tables and this entry is not one of them [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.13 Privacy And How Long An Audit Row Is Kept — No Policy Is Declared Anywhere]: it lives in a core table, this plugin writes there only through the shipped service and never deletes or rewrites a row in it, so **the pass does not clear it and this story does not claim it does**. What survives is the customer link and the administrator attribution the platform wrote; the payload holds no personal data of its own to clear. **Export.** Exactly one existing surface reaches it and this story adds none: the Admin API's `Customer.history` field, to a caller holding `Permission.ReadCustomer` — the same permission the reads themselves require — because that resolver passes `publicOnly` only for the Shop API [packages/core/src/api/resolvers/entity/customer-entity.resolver.ts:L85] and [packages/core/src/api/resolvers/entity/customer-entity.resolver.ts:L90], which restricts the read to public entries [packages/core/src/service/services/history.service.ts:L313], and this entry is not public [packages/core/src/service/services/history.service.ts:L327]. **Both halves are asserted rather than one**: the Admin read returns the entry and the Shop read does not. **All three answers are written into the operation's own documentation**, so a deployment reads the soft-delete and erasure boundaries before it enables the audit rather than after — and the switch below is how a deployment that will not accept them says so.
- **Failure semantics, stated as a choice with its cost rather than left to an implementer.** The audit write is inside the read's own request, and **if it fails the read fails**: a successful support read with no audit entry is exactly the event the entry exists to capture, so failing closed is the only posture consistent with having the entry at all. **The cost is real and is named: an outage in the history write path blocks support lookups**, which a deployment that would rather have unaudited support than no support must resolve by the switch below rather than by silently swallowing the failure.
- **A deployment may turn it off, and turning it off is visible.** The switch is `ReorderPluginOptions.recordAdminReorderReadAccess`, a boolean defaulting to **true**, **declared by the owning feature and carrying its own row in the epic's option ledger with this story named as its owner** [tickets/EPIC-001-reorder-and-replenishment.md:§7.10 The Plugin Option Ledger — One Authority For Every Configured Key]; a deployment that sets it false is choosing unaudited support reads explicitly, which is a stated configuration rather than an accident. **An earlier revision of this bullet described "a plugin option" with no key name and no ledger row**, which is how an on-by-default durable write came to have no declared switch anywhere above story level.
- **One disclosure, because the shipped mechanism is not silent.** Writing the entry publishes the platform's own history event [packages/core/src/service/services/history.service.ts:L340-L342], so any subscriber in the process observes that a support read occurred. That is a property of the shipped service rather than a choice made here, and it is recorded so it is not discovered later: the payload carries the entry, so a subscriber sees the three values above and the administrator attribution, and nothing the agent typed.

## 7. Edge Cases

Five scenarios: the three categories required of every story in this set, plus two conditional categories that apply because these reads copy a request scope and are paged while rows are still being written. **Each is labelled with its category inline, so the category matrix never appears as a table in a story file.**

* Scenario: Category — zero, null or empty collection. A buyer with nothing recorded, and a buyer whose identity has been erased, both of which must be answerable rather than errors.
   * Given an authenticated Administrator holding this story's capability together with `Permission.ReadCustomer` on the channel named by the `vendure-token` header; one `Customer` [packages/core/src/entity/customer/customer.entity.ts:L23] in that channel who owns zero reorder lists, holds zero unrevoked grants and has zero recorded attempts; and **a second buyer in the same channel who owned one reorder list and carried one recorded attempt with three line rows, was then soft-deleted so that the deletion timestamp is set [packages/core/src/entity/customer/customer.entity.ts:L29], and whose erasure job has since reached a terminal state** — so the settled lifecycle has run against that buyer's rows rather than being pending [tickets/EPIC-001-reorder-and-replenishment.md:§6.4 The Settled Rulings]
* When each of this story's two lookups is executed in turn against the first buyer, the list read addressed by that buyer's identifier in its required `customerId` argument and the attempt read by that same identifier; and then **three further executions are made against the erased buyer — the list read by identifier, the attempt read filtered by that identifier, and the attempt read filtered instead by the `sourceOrderCode` recorded on the attempt** in its required `subject` object, neither being addressed through a caller-supplied filter entry
   * Then for the first buyer each read returns an **empty paginated list with a `totalItems` of exactly 0 and no error**, because an empty result is a recorded fact rather than a failure; the attempt read still returns its `windowStart` and `windowEnd`, so an agent can see what period was searched rather than inferring completeness from an absence; **and this response is byte-identical to the one an identifier naming no customer row receives**, which is the anti-enumeration rule of AC-6 rather than a coincidence. **The contrast worth stating is with the refusal in AC-3**: an unaddressed call is a request-level failure carrying the platform's input error, while an addressed call over an empty subject is a successful empty page. Those two are different outcomes for different causes, and collapsing either into the other would misreport one of them. **And for the erased buyer the settled lifecycle produces three specific outcomes rather than one blanket rule, none of which is an error:** the list read returns an empty page with a `totalItems` of exactly 0, because the saved-list tables for a deleted customer are deleted outright rather than anonymised; the attempt read **filtered by that identifier** also returns an empty page, because the acting-customer column has been nulled and therefore matches no identifier at all; and the attempt read **addressed by the recorded source order code** also returns an empty page with a `totalItems` of exactly 0, **byte-identical to the previous two**, because the erasure pass nulls both order codes as well as both customer references [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.13 Privacy And How Long An Audit Row Is Kept — No Policy Is Declared Anywhere] — so **neither of this read's two addressing forms reaches an erased row**. **An earlier version of this scenario expected that third execution to return the attempt with its three line rows and a null `customerId`, and it is withdrawn as contradicting the very map it relied on**: a projection cannot serve a column the pass has emptied, and a code that still addressed a row would be a route from a buyer-facing order reference to that buyer's purchasing history after erasure. **What the row keeps is what an aggregate reads rather than what a lookup addresses**: it stays counted in FEATURE-001-08's attempt and line counts and stays excluded from its `distinctCustomerCount`, both following from the nulled columns rather than from a rule applied on top of them, and it stays reachable by channel, by variant and by outcome, which is the no-resolution property the producing feature states from its own side. **What no execution does is return the erased buyer's identity, and what none does either is fail** — each is a successful empty page rather than an error. **The cost is stated rather than smoothed over: after the pass this surface can no longer answer “what did that buyer try”, because both ways of asking name the person.** That is the price the epic's erasure rule sets, and it is a price rather than a defect

* Scenario: Category — a concurrent modification or race. A row is written while the agent is paging, and offset paging is promised only what it can keep.
   * Given an authenticated Administrator paging through one buyer's recorded attempts with a page size below that buyer's total, and a further attempt for the same buyer being recorded between the first page being returned and the second being requested
   * When the second page is requested twice under two different addressing forms — once with the same sort and the same page size and **nothing else**, and once with the same sort and page size **plus a filter constraining `createdAt` to `before` the `windowEnd` value the first page returned** [packages/core/src/api/schema/common/common-types.graphql:L131]
   * Then the **unpinned** request repeats a row across the boundary, and that is asserted as the behaviour rather than described as a risk: the declared default orders `createdAt` descending, so the newly written attempt sorts **first**, every later row moves one place later, rather than on an arbitrary one, and the exact row that sat at the end of the first page of this walk is stated rather than softened. **Across a concurrent insert no stronger guarantee is offered, and the reason is the pagination mechanism**: both reads delegate paging to the platform's list-query helper, which parses `skip` and `take` [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L630] and applies them to the query [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L290-L291] over the `skip` and `take` fields the list-options input declares [packages/core/src/common/types/common-types.ts:L69-L70]. **The pagination is by offset**, `skip` becoming the query's row offset [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L640-L641], and an offset addresses a position in the ordering at the moment each page is requested rather than a position in a snapshot taken when the first page was. So with the declared sort placing `createdAt` in **descending** order, the attempt recorded between the two requests sorts ahead of every row already returned, shifting each later row down by exactly one position, and the deterministic consequence is that **the last row of the first page reappears as the first row of the second, exactly once per row inserted ahead of the boundary, while no row that existed at the first request is skipped**. **The newly recorded row appears on neither page of that walk**, having been written after the first page was returned and sorting ahead of the second page's window; it becomes visible only when the walk is restarted. That repetition is asserted by the test as the documented behaviour of an offset walk over a table another feature is still appending to — **an earlier revision of this scenario claimed instead that no row already returned is repeated and that the new row may or may not appear**, and both claims are withdrawn: the first is unachievable with offset pagination under a descending sort, and the second described as indeterminate an outcome that is in fact fixed by the ordering. The symmetric case is stated with it: a row **removed** ahead of the boundary shifts later rows up by one and skips exactly one row per removal, and the only path by which a row of these tables is removed is the customer-lifecycle erasure this story's parent feature owns. **No lock, snapshot, cursor or reservation is taken anywhere in this story**, and a cursor is not adopted rather than merely absent: the generated options input publishes `skip` and `take` and no cursor field, so introducing one would mean hand-writing the pagination this feature is required to delegate [tickets/EPIC-001-reorder-and-replenishment.md:§5. Existing Mechanisms That Must Not Be Duplicated]. An agent who needs a stated reason rather than overlooked: the generated identifier operators are `eq`, `notEq`, `in`, `notIn` and `isNull` and not one of them is ordered [packages/core/src/api/schema/common/common-types.graphql:L93-L99], so the pinned-window form is the strongest contract the published input can express. **The one thing the pin does not cover is stated too**: a deletion inside the pinned window still shifts offsets, and the only thing that deletes these rows is the data-lifecycle pass, which removes the **oldest** rows and therefore perturbs only the pages an agent reaches last
