## 4. User Story

```text
As a Marketplace Category Manager,
I want to read one paginated, sortable, filterable list of the product variants buyers in my channel have reordered, each row naming the variant, the seller it belongs to, how many reorder attempts included it, how many units were reordered, how many distinct buyers reordered it, how many saved lists it appears on, and the first and last times it was reordered,
So that I can name the repeat-purchase behaviour in a category from recorded activity instead of reading individual buyers' orders one at a time.
```

## 5. Acceptance Criteria

Seven criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. Criteria name operations and their arguments and **never** a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. The five required coverage classes map onto them as follows: valid input is AC-1, invalid input is AC-3, an error naming the exact type returned is AC-4, an edge case is AC-5, and the assertion that an existing operation is unchanged is AC-7. AC-2 carries the do-not-duplicate mandate the epic attaches to this feature, and AC-6 carries the currency and channel identity the parent fixes.

Eight properties of the operation are stated once here rather than repeated in every criterion.

- **The read is additive and synchronous.** `recurringDemand` arrives through the plugin's `adminApiExtensions` on an `extend type Query` block, which is the mechanism the shipped reviews plugin demonstrates [packages/dev-server/test-plugins/reviews/api/api-extensions.ts:L69-L72], so no existing operation's arguments, return type or nullability changes. It enqueues no job and schedules no task, so it has no asynchronous trigger and no observable completion signal to name.
- **Authentication and capability are stated in every criterion, and the two are separate.** Every request below is made on an authenticated Administrator session. **A Marketplace Category Manager holds `ReadReorderDemand` together with `ReadReorderDemandAllSellers`**, because the audience for this story is a channel whose `sellerId` is null [packages/core/src/entity/channel/channel.entity.ts:L71-L72] and the parent refuses a seller-unscoped answer to any caller not explicitly entitled to it [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.7.1 The Audience Is A Role Configuration, Not A Persona — And That Is What Makes It Checkable]. The role configuration is itself a precondition this story's fixture asserts before it asserts anything about rows, so the test cannot drift into exercising story 08-02's audience and report a pass.
- **Two permission definitions are registered, and each yields exactly one published member.** Both are instances of the base `PermissionDefinition` [packages/core/src/common/permission-definition.ts:L86], whose metadata method returns a single entry [packages/core/src/common/permission-definition.ts:L90-L100] exposed through the `Permission` getter the decorator consumes [packages/core/src/common/permission-definition.ts:L107], registered through `authOptions.customPermissions` [packages/core/src/common/permission-definition.ts:L66] and applied with the `@Allow` decorator [packages/core/src/common/permission-definition.ts:L75]. **Neither the four-permission helper [packages/core/src/common/permission-definition.ts:L146], which derives a create, read, update and delete member from one name [packages/core/src/common/permission-definition.ts:L114-L115], nor the two-permission helper [packages/core/src/common/permission-definition.ts:L245] is used**, and the reason is stated rather than left as taste: this story writes nothing, so three of the first helper's four members and one of the second's two would be published members that no operation in this epic ever checks. The parent records the same choice with the same reasoning [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8 Permission Gating, And The Enum Growth Referenced Rather Than Re-Argued].
- **The gate names exactly one permission, because the decorator is disjunctive.** `@Allow` admits a caller holding any one of the permissions listed, its own documentation stating that with multiple permissions the user needs only one of them [packages/core/src/api/decorators/allow.decorator.ts:L11-L12], so a two-argument gate would be **wider** than either permission alone. The conjunction this story needs is therefore enforced inside the resolver with the platform's own AND primitive, `userHasAllPermissions` [packages/core/src/api/common/request-context.ts:L296], which tests each permission rather than intersecting the sets [packages/core/src/api/common/request-context.ts:L303] and is available in this line by its own version tag [packages/core/src/api/common/request-context.ts:L294].
- **A permission gate alone is not a control, and the platform says so about itself.** Ownership must be enforced by custom logic inside the resolver, and because it cannot be defined generally nor statically encoded at build time, a resolver relying on the gate alone is the equivalent of a public one [packages/core/src/api/config/generate-permissions.ts:L32-L34], the whole caveat sitting in one block in that file [packages/core/src/api/config/generate-permissions.ts:L12-L33]. So the channel bound and the entitlement check are applied in the service before any row is read, not as a filter on results. A dashboard navigation entry's client-side permission hint [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L48] hides a menu item and **authorises nothing**.
- **Every request is channel-scoped and language-scoped.** The active channel is identified by the unique token carried in the `vendure-token` request header [packages/core/src/entity/channel/channel.entity.ts:L62], as that column's own documentation states [packages/core/src/entity/channel/channel.entity.ts:L56-L60], and the request's language resolves from that channel's `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74]. The criteria below use the language code `en`. A category label is translatable — `Collection.slug` is declared as a locale string [packages/core/src/entity/collection/collection.entity.ts:L58] — so any category label rendered beside these rows follows the requested language code rather than a stored default.
- **The payload carries no monetary field at all**, which is the strongest available discharge of the integer-money constraint: every field on the published row is a count or a timestamp, so there is no amount that could be rendered with a decimal separator and no total that could span two currency codes. Were a monetary aggregate ever added, it would be an integer in the smallest unit of its currency stated alongside its currency code, which defaults to the channel's `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88], and it would re-enter the grouping key [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10 Channel Scoping, Language Scoping And Monetary Values]. A decimal amount anywhere is a defect rather than a formatting preference.
- **The aggregate's input semantics are inherited, not re-derived here.** The `PurchaseCadence` rows this query reads are defined by STORY-001-05-01 as one row per customer, per channel and per product variant, derived from **placed orders only**: the inputs are `Order.orderPlacedAt` [packages/core/src/entity/order/order.entity.ts:L92] and `OrderLine.orderPlacedQuantity` [packages/core/src/entity/order-line/order-line.entity.ts:L104], and rows whose `Order.active` is true [packages/core/src/entity/order/order.entity.ts:L82] are carts and are excluded. That ruling belongs to STORY-001-05-01 and is cited rather than restated as though this story owned it. **No numeric target is asserted anywhere below**: no adoption figure, no demand-growth figure, no query-time budget and no qualifying repeat count, because this repository declares none and the qualifying count is an open decision section 8.1 refers to the epic.

## 7. Edge Cases

Four scenarios, one per required category. The three unconditionally required categories are the first three, and the fourth covers the conditional channel, currency and language category, which applies because the channel is part of every row's grouping key. **Three of the four resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure this read cannot have.** The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — a category in the channel has no recorded reorder activity at all
   * Given an Administrator is authenticated holding both demand permissions on the channel named by the `vendure-token` header, and no `ReorderAttempt`, `ReorderAttemptLine`, `PurchaseCadence` or `ReorderListLine` row exists for any variant of the category being reviewed inside the aggregate window
   * When that Administrator executes the `recurringDemand` query filtered to that category's variants
   * Then proceed with an empty result: `items` is the empty array and `totalItems` equals exactly 0, `windowStart` and `windowEnd` are still returned non-null so the reader knows which window returned nothing, and **no error of any type is returned**. A category with no recorded activity is a specified outcome rather than a failure path, and it is the property that lets this story be accepted before the buyer-facing reorder paths have ever been exercised

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant carrying recorded activity is now disabled or deleted
   * Given an Administrator is authenticated holding both demand permissions on the channel named by the `vendure-token` header, and a variant carrying recorded reorder activity inside the window has since had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] or has been soft-deleted so that its `deletedAt` column carries a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]
   * When that Administrator executes the `recurringDemand` query
   * Then proceed and **return the row rather than omitting it** — this is the deterministic ruling for this operation, stated as a choice between the two available behaviours rather than left open. The aggregate reports historical recorded activity and filters on the channel and the window and on none of `enabled`, `deletedAt`, price or stock, so the row stands with its counts intact and its name and sku resolved. It is labelled by the same `productVariantName` and `sku` fields every other row carries, with no availability field of its own, because the published row declares none and a category manager reading present availability reads it from the catalogue. Where the variant has been **hard**-deleted the row is still returned, with `productVariantName`, `sku` and the relation all null, and where its seller attribution has been erased the row is excluded and the operation's documentation states that the aggregate understates demand for such variants

* Scenario: A price changed since the last purchase — the catalogue price of a variant carrying recorded activity has moved
   * Given the price of a variant carrying recorded reorder activity has changed since the orders that activity was derived from were placed, and an Administrator is authenticated holding both demand permissions on the channel named by the `vendure-token` header
   * When that Administrator executes the `recurringDemand` query
   * Then proceed with no warning and no price field: **this operation reports no monetary value at all, and that boundary is explicit rather than an oversight.** Every field on the published row is a count or a timestamp, so this story holds no price that could go stale and the aggregate is **not a quotation**. Were a monetary aggregate ever added it would be an integer in the smallest unit of its currency stated alongside its currency code [packages/core/src/entity/channel/channel.entity.ts:L88] and never a decimal. A buyer is made aware of a price movement before committing through FEATURE-001-03's `reorderPreview` operation, which owns that comparison; answering the same question here would put two answers to one question in two features

* Scenario: A channel, currency or language mismatch — activity recorded under a different token, a second currency code, or a request in a second language
   * Given a variant carries recorded reorder activity under two distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], inside the first of those channels that variant was purchased under two of the currency codes that channel declares as available [packages/core/src/entity/channel/channel.entity.ts:L90-L91], and the two channels declare different values of `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74] and of `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]
   * When an Administrator holding both demand permissions executes the `recurringDemand` query once under each token, with the language resolved from each channel in turn
   * Then proceed with **one row set per channel and never one summed row across the two**: the channel is part of the grouping key, so each execution returns that channel's rows only and neither result contains the other's. Inside the first channel the two currency codes produce a **single** row whose counts include both, because a count is currency-free and the currency code is deliberately not part of the grouping key — **so nothing is ever summed across currencies here, by construction rather than by rule, since no field on the row is monetary and no exchange rate can be applied anywhere.** Any translatable label rendered beside the rows, a category label among them [packages/core/src/entity/collection/collection.entity.ts:L58], resolves against the requested language code, while the counts and timestamps are language-invariant

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this operation performs no availability check and commits nothing; the staleness it does have is the aggregate's own — it describes the window it names and nothing after it — and it is carried by the second and third scenarios above and by the `windowStart` and `windowEnd` fields AC-1 asserts. A concurrent modification or race is likewise not a separate scenario: two simultaneous reads cannot conflict, and a row written by an upstream feature while a page is being read is observable only as that row appearing in a later page or a later request, which the declared total tie-break on `productVariantId` makes deterministic within one request rather than something this story locks against.
