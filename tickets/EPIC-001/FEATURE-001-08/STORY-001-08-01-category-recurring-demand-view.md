**One name-collision check, run rather than assumed.** A search of both checked-in introspection snapshots for the quoted names `"recurringDemand"`, `"RecurringDemand"` and `"RecurringDemandList"` returns **zero occurrences in each**, so every name this story publishes is free [schema-admin.json:data.__schema.types] and [schema-shop.json:data.__schema.types]. **The reproducible form is the block below rather than a bare count**, because `grep -c` prints `0` and exits 1 when it finds nothing — so the outcome this check wants cannot be told from a failure by exit status — and exits 2 on a missing or unreadable file, which an `if` or a `&&` chain reads as absence. This form separates a match from a read error from a genuine absence, and returns a non-zero status if any name is not free.

```bash
# Run from anywhere inside the checkout. One line per name per snapshot, then one status line.
reorder_names_are_free() {
    root=$(git rev-parse --show-toplevel) || {
        echo 'COLLISION CHECK FAILED: not inside a git checkout.'
        return 1
    }
    problems=0
    for snapshot in schema-admin.json schema-shop.json; do
        if [ ! -f "$root/$snapshot" ] || [ ! -r "$root/$snapshot" ]; then
            echo "COLLISION CHECK FAILED: $snapshot is not a readable regular file, so absence cannot be shown."
            problems=$((problems + 1))
            continue
        fi
        for name in '"recurringDemand"' '"RecurringDemand"' '"RecurringDemandList"'; do
            grep -qF -- "$name" "$root/$snapshot"
            status=$?
            if [ "$status" -eq 0 ]; then
                echo "COLLISION: $name occurs in $snapshot, so that name is not free."
                problems=$((problems + 1))
            elif [ "$status" -ne 1 ]; then
                echo "COLLISION CHECK FAILED: grep exited $status on $snapshot; absence is unproven."
                problems=$((problems + 1))
            else
                echo "free:  $name does not occur in $snapshot"
            fi
        done
    done
    if [ "$problems" -ne 0 ]; then
        echo "COLLISION CHECK FAILED: $problems problem(s). No name here may be treated as free."
        return 1
    fi
    echo 'COLLISION CHECK OK: every name above is free in both snapshots.'
}

reorder_names_are_free
```

**Expected:** six lines beginning `free:` — three names against each of the two snapshots — and a closing `COLLISION CHECK OK`.

## 4. User Story

```text
As a Marketplace Category Manager,
I want to read one paginated, sortable, filterable list of the product variants buyers in my channel have reordered, narrowed to one category I name on every request, each row identifying the variant, identifying the seller it belongs to, and reporting how many reorder attempts included it, how many units were reordered, how many distinct buyers reordered it, how many saved lists it appears on, and the first and last times it was reordered,
So that I can name the repeat-purchase behaviour in a category from recorded activity instead of reading individual buyers' orders one at a time.
```

**Two phrases in that WHAT were imprecise in an earlier revision and are corrected here, because both promised something no published field delivers.** First, **"in a category" is an explicit, **required** narrowing rather than an implication of the story's title**: the read takes `collectionId: ID!` as a required argument applied server-side, and **there is no channel-wide form of this operation** — a request omitting the argument is refused by the platform's own non-null argument validation before any resolver runs, so an unscoped aggregate is unreachable rather than merely undocumented [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change]. **An earlier revision of this bullet described the argument as optional and omission as a channel-wide default, and that description is withdrawn** against the published SDL and against the parent's ruling; a reader wanting demand across a channel issues the operation once per collection. Section 4.3 states how the selection reaches the argument, AC-6 asserts the narrowing and the refusal of an unresolvable identifier, and the first scenario in section 7 asserts the empty case. Second, **"the seller it belongs to" is `sellerId` on the row and a label the page resolves separately**, not a name the row carries: no `sellerName` field exists on `RecurringDemand`, none is added by this story, and section 4.3.3 fixes the one bulk read that turns the identifiers on a page into labels. **Neither correction changes the published schema**, which the parent feature owns.

The session travels as **`Authorization: Bearer <token>`** [packages/dashboard/src/lib/graphql/api.ts:L27] — **not** as `vendure-auth-token`, which is the *response* header the client reads a refreshed token back from [packages/dashboard/src/lib/graphql/api.ts:L58] and never the request credential. And the language travels as the query parameter **`?languageCode=<the selected content language>`**, which the client appends from the operator's own dashboard settings [packages/dashboard/src/lib/graphql/api.ts:L38-L44]. **An earlier revision of this step said only "the bearer token and the channel token"**, which named neither the header nor the language parameter and therefore did not describe the request this surface actually issues.
**And it is issued from a client that holds no session cookie.** That clause is load-bearing rather than tidy: the platform tries the cookie **before** the `Authorization` header and returns as soon as it finds one [packages/core/src/api/common/extract-session-token.ts:L14-L19], so a browser tab or a request tool already signed in to the dashboard executes this call as **that** principal and ignores the token pasted into the header — which silently invalidates the refusal branch above, where the whole point is that the caller holds `ReadReorderDemand` **without** `Permission.ReadSeller`. Use a fresh client or a cleared cookie jar, and confirm the acting principal by executing the existing `me` query [packages/core/src/api/schema/admin-api/auth.api.graphql:L2] immediately before the operation and reading back the identifier and channel permissions it reports. The same rule governs the automated cases [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10.1 The Transport And Credential Contract, Applied To These Three Reads]. **The request is a `POST` carrying `content-type: application/json` and never a `GET`**, which is the transport contract that sub-section states for all three of this feature's operations.

```graphql
# collectionId is REQUIRED: read a collection id from the existing administrative
# collections query and pass it below. Omitting it is refused by non-null argument
# validation before any resolver runs, so there is no channel-wide form to fall back on.
# The narrowing is applied server-side, never as a filter over a fetched page.
query {
  recurringDemand(
    collectionId: "<the id of a seeded collection, read from the collections query>"
    options: { take: 20, skip: 0, sort: { reorderAttemptCount: DESC } }
  ) {
    totalItems
    windowStart
    windowEnd
    items {
      id
      productVariantId
      display {
        productVariantName
        sku
      }
      sellerId
      reorderAttemptCount
      reorderedUnitCount
      distinctCustomerCount
      savedListOccurrenceCount
      cadenceCustomerCount
      firstReorderedAt
      lastReorderedAt
    }
  }
}
```

**Expected response shape.** A `RecurringDemandList` carrying `totalItems` as an integer, `windowStart` and `windowEnd` as the inclusive and exclusive bounds of the scanned window, and `items` as an array of `RecurringDemand` ordered by `reorderAttemptCount` descending with `productVariantId` as the total tie-break. **Two shapes above are worth reading twice because an earlier revision of this block had both wrong.** The `collectionId` argument is a **server-resolved** category selector, so a category manager narrows the aggregate by naming one collection rather than by assembling a list of variant identifiers the server would have to accept unbounded [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change]; the argument is **required**, so omitting it is refused rather than answered with the whole channel. And the variant's two display values are **nested** inside `display` rather than flat on the row, because they are hydrated after the aggregate has grouped, ordered and paginated and are therefore sortable and filterable by nothing. Against a freshly seeded database no reorder attempt has been recorded, so the demonstrable outcome is `totalItems` equal to zero and `items` equal to the empty array — **an empty list and not an error**, which is the specified behaviour rather than a gap. To see a populated list, insert `ReorderAttempt`, `ReorderAttemptLine` and `PurchaseCadence` rows through a test fixture, or exercise the buyer-facing reorder paths that FEATURE-001-02 and FEATURE-001-05 deliver. The read is acceptable either way, which is what makes this story independent of them.

**Then read the dashboard page, and no further command is needed to serve it.** This is a correction: an earlier revision of this paragraph named the package's dashboard-only development script as the way the page is reached, which reads as a second command the runbook never issues. **The `dev` script already started it.** That script runs the command-line interface's `dev all` target [packages/dev-server/package.json:L13], and that target starts three processes rather than two — server, worker and build [packages/cli/src/commands/dev/dev.ts:L70] — the third running the `vite` binary [packages/cli/src/commands/dev/dev.ts:L123-L129], which the published command help states in words [packages/cli/src/README.md:L59-L60]. The page renders the same rows the operation above returns, and its navigation entry carries a client-side permission hint of the kind the precedent uses [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L48] — which **hides a menu item and authorises nothing**, as section 5 states.

### 4.3 The Page Contract — Arrival, Labels, States And Presentation

**Why this sub-section exists.** Section 5 fixes the operation; it says nothing about the page, and a read-only aggregate page still has four ways of misleading the person reading it: it can show a category-scoped heading over channel-wide rows, it can show seller identifiers where a name was promised, it can render a refused or failed query as an empty table, and it can print counts and timestamps in a form that means something different to a reader in another locale. Each is settled below and carried into section 5, section 6's dashboard line and section 10.

**What this sub-section is not.** **No design system, component-library version, style guide or design source is named anywhere in this ticket set, and none was supplied to this project** — an absence stated rather than quietly filled in, following the convention this epic applies to every absence it found [tickets/EPIC-001-reorder-and-replenishment.md:§11.8 Tooling Findings, Including The Absences]. So nothing below states a pixel value, a colour, a font, a spacing figure or a contrast ratio. Every obligation is a *behaviour* expressed against a dashboard building block that exists in this checkout and is cited, as the shipped precedent composes its own list surface from published blocks [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9].

#### 4.3.1 One Route, One Page Identity, One Navigation Entry — And This Story Owns All Three

- **This story registers the route `/recurring-demand`, one stable `pageId` on the page it renders — the framework's list page taking that identity as a declared property [packages/dashboard/src/lib/framework/page/list-page.tsx:L48] — and exactly one navigation entry, in the shape the shipped precedent uses [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L42-L50].** The `pageId` is what keeps a reader's column-visibility preference on this page rather than leaking it to another, the framework keying default visibility per page [packages/dashboard/src/lib/framework/page/list-page.tsx:L286-L288].
- **Story 08-02 registers no second route, no second `pageId` and no second navigation entry; it extends this page.** That is the parent feature's ruling rather than an accommodation reached between two story files [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§4.3 Intra-Feature Story Order — One Edge, And It Is Declared Rather Than Denied], and it is why this story precedes that one. **The earlier revisions of the two files each claimed the same route, which would have produced either a duplicate registration or a silent shadowing depending on load order** — recorded here as a resolved collision rather than removed without trace.

#### 4.3.2 The Category Selection Is A Route Parameter And The Narrowing Happens On The Server

- **A labelled category selector sits above the table, it is REQUIRED, and the read behind it carries an existing permission requirement this story must state.** It reads the platform's existing administrative collection list `collections(options: CollectionListOptions): CollectionList!` [packages/core/src/api/schema/admin-api/collection.api.graphql:L2] — the same document the shipped collection list already issues, returning each collection's identifier, `name`, `slug` and breadcrumbs [packages/dashboard/src/app/routes/_authenticated/_collections/collections.graphql.ts:L10-L28] — and composed from the dashboard's own relation-selector primitive [packages/dashboard/src/lib/components/data-input/relation-selector.tsx:L1]. **No new read operation is added for it**, which is why this story's operation count stays at one. The selector's own label is a catalogue entry — **it carries no cleared option, the selection being required** — and the collection's own `name` is the label shown, resolved under the `languageCode` the request carries from the operator's selected content language [packages/dashboard/src/lib/graphql/api.ts:L41-L44] because a collection is translatable [packages/core/src/entity/collection/collection.entity.ts:L58].
  - **The role prerequisite is `Permission.ReadCollection` [packages/core/src/common/constants.ts:L67], and it is a hard prerequisite rather than a recommendation**, that being the platform's own gate on the operation the selector reads. A role holding only `ReadReorderDemand` opens this page and finds the selector refused — and because `collectionId` is non-null there is then no legal aggregate request to issue at all, so the page is broken rather than degraded. **An earlier revision of this section named no baseline permission**, leaving a reader to infer that the reorder read permission somehow covered the collection read. Requiring an existing member grows the published `Permission` enum by nothing, and `ReadCollection` is the narrowest existing member that admits this read.
- **The selection is held in a route search parameter, not in component state, and there is NO wider scope to fall back to when it is absent.** The page is therefore deep-linkable and shareable, a reload keeps the category, and the browser's back and forward actions move between categories. **There is no clearing affordance and no all-categories view**, because `collectionId` is non-null on the operation [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change]: a cleared parameter leaves no legal request to issue. **An earlier revision of this bullet said a cleared selection "removes the parameter and returns the channel-wide set"**, which described a form the contract does not offer. **Arriving with no parameter is therefore its own state**, not an aggregate: the page renders the selector with an explanatory prompt to choose a category and issues no aggregate query, which is the same shape §2.12b requires when the collection read itself is unavailable.
- **The narrowing is server-side and is passed as `collectionId`, and it is never a client-side filter over a fetched page.** A page that fetched channel-wide rows and then hid the ones outside the category would report a `totalItems` for one scope beside rows for another, and would page through the wrong set — which is the specific defect this rule prevents. The argument is **required and non-null** on the operation, intersects with the channel bound and the seller predicate, and narrows rather than widens [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change]. AC-6 asserts it, an earlier revision of this bullet having pointed at AC-8, which is the introspection criterion.
- **A category selection that resolves to no collection in the requesting channel renders the not-found state of 4.3.4** and not an empty aggregate, because "no such category" and "this category has no recorded activity" are different facts.

#### 4.3.3 Seller Labels Come From One Bulk Read, And The Label Is Language-Invariant

- **The row carries `sellerId` and no name, so the page resolves labels itself.** For the identifiers present on the **current page only**, the page issues **one** read of the platform's existing administrative `sellers(options: SellerListOptions): SellerList!` [packages/core/src/api/schema/admin-api/seller.api.graphql:L2], filtered to those identifiers, exactly as the shipped seller picker reads id and name together [packages/dashboard/src/lib/components/shared/seller-selector.tsx:L5-L15]. **One read per page and never one per row** — a per-row read is the defect this rule names, and it is asserted as an exact call count rather than described.
- **`Seller.name` is language-invariant and is rendered as stored.** The entity implements soft deletion and custom fields and **does not implement the platform's translatable contract**; `name` is a plain column [packages/core/src/entity/seller/seller.entity.ts:L26]. So the label does not change with the request's `languageCode`, no translation of it is looked up, and **any statement that a seller name follows the request language would be false** — which is why this file states the invariance rather than leaving it to be assumed.
- **An identifier the bulk read cannot resolve renders a translated unattributed label carrying the identifier**, never a blank cell and never the identifier alone. The row itself is still shown. **Two distinct causes now reach this cell and the page renders both the same way**, which is a correction: the aggregate no longer excludes an unattributable row, so `sellerId` may arrive **null** — the wide read's documented outcome for a variant with no single seller-bearing channel, which AC-5 asserts — and separately a non-null identifier may fail to resolve to a name in the bulk seller read. **Neither is a reason to hide the row**, and the distinction between an absent attribution and an unresolved label is carried in the page's own copy rather than in whether the row appears [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.7 The Seller-Scoping Rule, Stated As A Hard Contract].

#### 4.3.4 Every State The Page Can Be In, Named — Including The Two That Are Refusals

- **Loading and refetching.** The table renders the loading state it already takes as a property [packages/dashboard/src/lib/components/data-table/data-table.tsx:L142], which the shipped paginated list wires from its own fetching flag [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L506], and a refetch is available through the refresh control the same table renders [packages/dashboard/src/lib/components/data-table/data-table.tsx:L452]. Previous rows stay on screen during a refetch rather than the table blanking, which is the application-wide query default [packages/dashboard/src/app/app-providers.tsx:L12-L19] — **and it is safe here only because the query key includes the channel, the selected category and the selected content language**, so any previous data belongs to the same scope and the same language. The third of those is part of the key because the language travels as a request parameter the client sets from the operator's own settings [packages/dashboard/src/lib/graphql/api.ts:L41-L44], so a cached result carries the language it was fetched under. A change of any of the three is a change of subject and the previous rows are cleared rather than kept.
- **Empty.** Zero rows for a resolvable scope renders the table's own empty state [packages/dashboard/src/lib/components/data-table/data-table.tsx:L588] **together with the scope and window summary of 4.3.6**, so a reader can see which window and which category returned nothing. This is a specified outcome, which the first scenario in section 7 fixes.
- **Not found.** A category parameter resolving to no collection in the requesting channel renders a distinct not-found state carrying the selector, so the reader can choose again without editing a URL.
- **Read failure.** A failed query renders a retry affordance and the safe message of 4.3.5, and **never an empty table** — the two must not look alike on a page whose whole purpose is to report whether activity happened.
- **Refusal.** A caller holding `ReadReorderDemand` without the platform's existing `Permission.ReadSeller` [packages/core/src/common/constants.ts:L71] is refused by the resolver before any row is read, and AC-4 asserts that. **The page renders that refusal as its own explanatory state rather than as an empty table or a raw error**, and it is distinguishable on screen from both an empty result and a failed read. The platform's permission guard renders nothing at all when a permission is absent [packages/dashboard/src/lib/components/shared/permission-guard.tsx:L44-L49], which is right for hiding a navigation entry and wrong for a whole page, so the guard covers the entry and an explicit refusal state covers the body. **Neither is an access control:** the operation is gated server-side and the entitlement is checked in the resolver.
- **Pending selection.** While a category selection is in flight the selector stays operable and the table shows the loading state; the sort and pagination controls are inoperable until the new scope has resolved, so a reader cannot page a scope that is being replaced.
- **Prompt, because no category is selected yet.** Arriving with no route parameter renders the selector above an explanatory prompt and **issues no aggregate query at all**, per 4.3.2. It is not the empty state and must not look like it: nothing was read, so nothing is known about whether activity happened.
- **Three degraded states, each independent of the primary read and each distinguishable on screen from an empty result.** The page makes up to two **secondary** reads beside its own aggregate — the collection read behind the selector and the bulk seller-label read of 4.3.3 — and offers one on-demand third, the curated-alternatives read of 4.3.9. A secondary read can fail or be refused while the aggregate succeeds, most obviously where a role holds `ReadReorderDemand` and not the baseline permission the secondary read requires, and the parent settles all three behaviours for every surface in the feature so no page invents its own [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.12b The Two Secondary Reads Every Surface Makes, And What Each Surface Does When One Fails Independently Of The Primary]. **An earlier revision of this sub-section defined none of the three.**
  - **A failed or refused COLLECTION read blocks the primary rather than degrading it.** Because `collectionId` is non-null there is no legal request to issue without a selection, so the page renders an explanatory state naming the missing capability — `Permission.ReadCollection` [packages/core/src/common/constants.ts:L67] where that is the cause — and issues no aggregate query. This is the one secondary failure that is not a degradation, and it shares its shape with the prompt state above while carrying different copy.
  - **A failed or refused SELLER-LABEL read degrades the label column and nothing else.** Every row is rendered in full with its counts intact; each row's seller cell shows the unattributed label of 4.3.3 carrying the identifier the response returned, or the null-attribution label where the response carried null; and **one** page-level note states that seller names could not be resolved. **The rows are never withheld**, because the label is presentation and the demand figures are the answer. This is distinguishable on screen from a row whose `sellerId` is genuinely null, which is a fact about the data rather than a failure to resolve a name.
  - **A failed or refused CURATED-ALTERNATIVE read degrades that panel alone.** The panel renders its own explanatory state and the demand table beside it is unaffected; no row is withheld and no count changes. A reader holding no `ReadReorderSubstitution` sees the affordance hidden rather than failing, per 4.3.9, which is a different state again from the panel having been opened and failed.

#### 4.3.5 Error Content — What Is Shown, And What Is Never Shown

**The shipped default is the other way, which is why this is a rule.** The platform's own detail page surfaces a caught error's message straight into a notification [packages/dashboard/src/lib/framework/page/detail-page.tsx:L166-L170], and copying that here would put whatever a resolver, a driver or a proxy produced onto an administrator's screen.

- **Every failure this page renders shows a translated, page-authored explanation naming what failed and the retry available**, drawn from the extension's own catalogues. **The two expected refusals are mapped to their own translated copy** — a forbidden response to the entitlement explanation, and an input error to the page-size explanation — and **everything else renders one generic unexpected-error explanation.**
- **Never rendered: a raw exception message, a stack frame, a driver or SQL fragment, an internal identifier, a file path, a table or column name, or any part of the generated aggregate statement.** An aggregate failure is the case most likely to carry a dialect-specific statement in its message, which is exactly why the generic branch exists.
- **The detail is relocated rather than destroyed:** it belongs in the server's own log, under the epic's own constraint on what a log entry may carry [tickets/EPIC-001/FEATURE-001-07-reorder-instrumentation.md:§2.11 Observational Neutrality — And The Shipped Mechanism That Would Break It].

#### 4.3.6 The Scope And The Window Are On The Screen, Not Only In The Response

**A demand table with no visible scope is the single easiest way for this page to mislead**, because every number on it is true only of one channel, one category selection and one window, and a reader who assumes otherwise draws a conclusion about the whole marketplace from a slice of it.

- **The page owns its query, and that is what makes this whole sub-section renderable at all.** `windowStart` and `windowEnd` are **sibling fields of the list wrapper**, not fields of a row, and the dashboard's shipped paginated table has no route by which a caller receives a wrapper field: its typed contract knows a paginated result as `{ items, totalItems }` and nothing else [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L134] and [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L141]. So this route is the **plugin-local page composing one typed query of its own** that the parent feature declares for all three of its surfaces, with the shipped table used beneath it as a presentation component that receives `items` and `totalItems` [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.12a The Dashboard Composition Every Surface In This Feature Uses — A Plugin-Local Typed Query And Page, NOT The Stock `ListPage`]. **An earlier revision of this bullet bound the summary line to the stock component's own data**, which that component cannot supply. Pagination state is the page's: it sends `skip` and `take` explicitly rather than inheriting the primitive's `take: Math.min(itemsPerPage, 100)` [packages/dashboard/src/lib/components/shared/paginated-list-data-table.tsx:L481-L482], and AC-1's `take` of 20 is the page's own choice.
- **A summary line is rendered above the table on every state including the empty one**, naming: the active channel, by the channel label the dashboard already renders for the selected channel; the selected category by its `name`, there being **no all-categories value to render** because the selector is required and a missing selection is the prompt state of 4.3.2 rather than a wider scope; and the window as `windowStart` and `windowEnd`, which AC-1 asserts are returned non-null for exactly this purpose.
- **Every part of that line is a catalogue entry with the values interpolated**, never an assembled English sentence, and the two window bounds are rendered through the locale-aware date formatter of 4.3.8.
- **The window is described as it is defined — an inclusive lower bound and an exclusive upper bound** — rather than as a vague "recent" period, and the summary states that the figures inside it describe recorded past activity and forecast nothing.
- **The summary line does NOT claim the window governs every figure, because it governs five of the seven basis-bearing fields and not all seven.** This is a correction: an earlier revision of this sub-section described all of them as being inside the activity window. The parent labels each field with its own time basis in that field's own docstring and states the split in one place [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.5 Named API Surfaces — Three New Admin API Operations, Zero Shop API Change], and the page carries that labelling onto the screen per column rather than in one sentence over the table.
  - **Windowed, and described by the summary line's window:** `reorderAttemptCount`, `reorderedUnitCount`, `distinctCustomerCount`, `firstReorderedAt` and `lastReorderedAt`. The third of those is additionally a **lower bound** that can decrease between two runs of the same query, because an attempt row whose acting customer has been erased leaves the two counts beside it intact and drops out of that one, and the column carries that qualification rather than the summary line carrying it for every figure.
  - **Current as at `windowEnd` and NOT windowed:** `savedListOccurrenceCount` and `cadenceCustomerCount`. A saved list is a standing intention with no event date to bound and a derived cadence is a current derivation, so neither moves when `windowStart` moves. Each of those two columns carries its own translated as-at qualification in the column header, and neither is presented as activity.
  - **The two bases are never summed, averaged or placed in one total.** A figure that mixed them would be true of no period at all, which is why the labelling is a page obligation here rather than a note the reader is expected to hold.

#### 4.3.7 Operable Without A Mouse, And Usable On A Narrow Viewport

- **The table is a table.** Rows, cells and column headers are rendered through the data table's own semantic markup rather than as generic containers [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L3-L9], which is what gives assistive technology the row-and-column relationships a ten-column table of counts and timestamps depends on. Each sortable column header is a control with an accessible name and its current sort direction exposed rather than shown only as an icon.
- **Every control has an accessible name and a visible focus indication, and the focus order follows the page**: category selector, then the sort and refresh controls, then the table, then pagination. The category selector is labelled rather than relying on placeholder text.
- **A change of result set is announced.** After a category selection, a sort or a page change completes, the new row count and the resolved scope are announced through a live region, because a reader who cannot see the table repaint otherwise has no signal that anything happened. The announcement text is a catalogue entry.
- **Narrow-viewport behaviour is stated because the platform's own column control is not available there.** The data table's column-settings trigger is hidden below the large breakpoint [packages/dashboard/src/lib/components/data-table/data-table-view-options.tsx:L91], so a narrow viewport cannot be repaired by the reader hiding columns — and this page is the densest in the epic, with **ten** columns per row — the three that are always present and the seven that give way, drawn from the row's eleven published fields with `id` rendered as no column at all. The page therefore declares a column priority: the variant label, the seller label and `reorderAttemptCount` are present at every width; `sku`, `reorderedUnitCount`, `distinctCustomerCount`, `savedListOccurrenceCount`, `cadenceCustomerCount`, `firstReorderedAt` and `lastReorderedAt` are the columns that give way first, reached by horizontal scrolling of the table region rather than truncated to a form that hides a digit. **No layout value is stated here** — the requirement is that no value is silently clipped, that the summary line of 4.3.6 stays visible at every width, and that sorting and pagination stay reachable.
- **A truncated number is a wrong number.** No count is abbreviated, rounded or shortened to fit; where the column cannot show it in full the region scrolls.

#### 4.3.8 Presentation Is Locale-Aware, And The Page Formats Nothing By Hand

- **Counts.** Every one of the five count fields is rendered through the dashboard's own locale-aware number formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L59-L64] from the hook the dashboard already exposes [packages/dashboard/src/lib/hooks/use-local-format.ts:L27], so the group separator is the one the display locale implies rather than a hard-coded comma. **No count is formatted by string concatenation and none is abbreviated.**
- **Timestamps.** `firstReorderedAt`, `lastReorderedAt`, `windowStart` and `windowEnd` are rendered through the locale-aware date formatter [packages/dashboard/src/lib/hooks/use-local-format.ts:L66-L71] or the display component built on it [packages/dashboard/src/lib/components/data-display/date-time.tsx:L3-L9], never as a raw transport string, because an unformatted timestamp reads as a different date in different conventions.
- **There is no money on this page at all**, every published field being a count or a timestamp, which is the strongest available discharge of the integer-money constraint: there is no amount that could be rendered with a decimal separator [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.10 Channel Scoping, Language Scoping And Monetary Values].
- **Every label is a catalogue entry.** No literal user-facing string appears in the surface's source; each is marked up through the translation macro the shipped precedent imports [packages/dev-server/test-plugins/reviews/dashboard/review-list.tsx:L2] and extracted into the plugin's own catalogues over a source locale and a second language [packages/dev-server/lingui.config.js:L4-L5] at the path that configuration names [packages/dev-server/lingui.config.js:L8-L9] — the obligation section 10 checks by command.
- **What is translatable and what is not is stated per value, because getting this wrong is how a page promises a translation it cannot deliver.** The variant label and the category label are translated platform values resolved under the **`languageCode` the request carried, which the dashboard client sets from the operator's selected content language** [packages/dashboard/src/lib/graphql/api.ts:L41-L44] and not from the active channel's default; the seller label is language-invariant, per 4.3.3; and the counts and timestamps are language-invariant values given a locale-aware *presentation*, which is a different thing from a translation. **Two selections are therefore in play and they are independent:** the interface locale that drives the catalogue lookups and the number and date formatters of this sub-section, and the content language that drives the platform's own translated values. A change of content language is a change of request, so it refetches.

#### 4.3.9 The Curated Alternative Is Read On Demand For One Selected Variant, Not Projected Onto Every Row

**This closes a promise an earlier revision of this file made and no field could keep.** No field on `RecurringDemand` carries a curated alternative, and none is added by this story.

- **Where a reader wants to know what was curated as a stand-in for a variant on this page, the page issues FEATURE-001-04's own existing operation `substitutionCandidates(originProductVariantId: ID!, options: SubstitutionCandidateListOptions)` for the *one* variant that reader selected** [tickets/EPIC-001/FEATURE-001-04-unavailable-line-resolution.md:§2.7 Named API Surfaces — Zero New Buyer-Facing Operations, Two New Admin Operations], the parent feature fixing that as the mechanism rather than a projection [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.3 Named Entities Touched — This Feature Owns No Table].
- **Never once per row of a page.** A per-row call is an unbounded fan-out over a page whose size is set by the caller, and it is the defect this rule prevents; the read is therefore bounded to one origin at a time, gated by the reader's own possession of `ReadReorderSubstitution`, and absent from the page's own first query entirely.
- **A reader holding no such permission sees the curated-alternative affordance hidden** rather than a failing request, the navigation-level guard being the right instrument for hiding one control [packages/dashboard/src/lib/components/shared/permission-guard.tsx:L44-L49] — and the server refuses it independently, because hiding a control authorises nothing.

## 5. Acceptance Criteria

Eight criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. Criteria name operations and their arguments and **never** a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. **The five required coverage classes map onto the eight titles below, and the mapping is read off those titles rather than from an earlier arrangement of them:** valid input is AC-1; invalid input is AC-3, with a second invalid-input case inside AC-6 where an identifier resolving to no collection in the active channel is refused; an error naming the exact type returned is AC-4, and the type it names is the platform's forbidden error; an edge case is AC-5; and the assertion that an existing operation is unchanged is AC-7. ## 7. Edge Cases

Four scenarios, one per required category. The three unconditionally required categories are the first three, and the fourth covers the conditional channel, currency and language category, which applies because the channel is part of every row's grouping key. **Three of the four resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure this read cannot have.** The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — a category in the channel has no recorded reorder activity at all
   * Given an Administrator is authenticated holding both demand permissions on the channel named by the `vendure-token` header, and no `ReorderAttempt`, `ReorderAttemptLine`, `PurchaseCadence` or `ReorderListLine` row exists for any member variant of the `Collection` being reviewed inside the aggregate window
   * When that Administrator executes the `recurringDemand` query with `collectionId` naming that category, the narrowing being applied server-side rather than as a filter over a fetched page
   * Then proceed with an empty result: `items` is the empty array and `totalItems` equals exactly 0, `windowStart` and `windowEnd` are still returned non-null so the reader knows which window returned nothing, and **no error of any type is returned**. **The page renders the table's own empty state together with the scope and window summary** naming the channel, that category and those two bounds, so the reader can see *which* category over *which* window returned nothing rather than facing a bare empty table — an empty result with no visible scope being indistinguishable on screen from a failed read, which is the distinction section 4.3.4 exists to keep. A category with no recorded activity is a specified outcome rather than a failure path, and it is the property that lets this story be accepted before the buyer-facing reorder paths have ever been exercised

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant carrying recorded activity is now disabled or deleted
   * Given an Administrator is authenticated holding both demand permissions on the channel named by the `vendure-token` header, and a variant carrying recorded reorder activity inside the window has since had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53] or has been soft-deleted so that its `deletedAt` column carries a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48]

   * Then proceed and **return the row rather than omitting it** — this is the deterministic ruling for this operation, stated as a choice between the two available behaviours rather than left open. The aggregate reports historical recorded activity and filters on the channel and the window and on none of `enabled`, `deletedAt`, price or stock, so the row stands with its counts intact and its name and sku resolved. It is labelled by the same nested `display.productVariantName` and `display.sku` values every other row carries, with no availability field of its own, because the published row declares none and a category manager reading present availability reads it from the catalogue. * Scenario: A channel, currency or language mismatch — activity recorded under a different token, a second currency code, or a request in a second language
   * Given a variant carries recorded reorder activity under two distinct values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], inside the first of those channels that variant was purchased under two of the currency codes that channel declares as available [packages/core/src/entity/channel/channel.entity.ts:L90-L91], and the two channels declare different values of `defaultLanguageCode` [packages/core/src/entity/channel/channel.entity.ts:L74] and of `defaultCurrencyCode` [packages/core/src/entity/channel/channel.entity.ts:L88]
   * When an Administrator holding both demand permissions executes the `recurringDemand` query once under each token, **each execution carrying the `languageCode` query parameter with the same operator-selected value** [packages/dashboard/src/lib/graphql/api.ts:L41-L44] so that the only thing differing between the two is the channel token — the selected content language being a property of the operator's session and not of the channel, which is what makes this scenario a channel-mismatch test rather than a language one
   * Then proceed with **one row set per channel and never one summed row across the two**: the channel is part of the grouping key, so each execution returns that channel's rows only and neither result contains the other's. Inside the first channel the two currency codes produce a **single** row whose counts include both, because a count is currency-free and the currency code is deliberately not part of the grouping key — **so nothing is ever summed across currencies here, by construction rather than by rule, since no field on the row is monetary and no exchange rate can be applied anywhere.** Any translatable label rendered beside the rows, a category label among them [packages/core/src/entity/collection/collection.entity.ts:L58], resolves against the requested language code, while the counts and timestamps are language-invariant

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this operation performs no availability check and commits nothing; the staleness it does have is the aggregate's own — it describes the window it names and nothing after it — and it is carried by the second and third scenarios above and by the `windowStart` and `windowEnd` fields AC-1 asserts. A concurrent modification or race is likewise not a separate scenario: two simultaneous reads cannot conflict, and a row written by an upstream feature while a page is being read is observable only as that row appearing in a later page or a later request, which the declared total tie-break on `productVariantId` makes deterministic within one request rather than something this story locks against.
