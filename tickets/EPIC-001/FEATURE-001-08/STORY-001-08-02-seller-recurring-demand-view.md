## 4. User Story

```text
As a Seller Operations Manager,
I want the recurring-demand aggregate to answer me only for the variants my own seller sells in the channel I am authorised for, with the scope resolved by the server from that channel rather than from anything I send,
So that I can name the repeat-purchase behaviour of my own catalogue from recorded activity while no row of another seller's trading is ever disclosed to me.
```

### 4.1 INVEST Criteria

- **Independent:** stated honestly rather than claimed. **This story is not independent of STORY-001-08-01**, and pretending otherwise would misrepresent it: that story delivers the `recurringDemand` operation, its two published types, its options mapping and the two permission definitions this story is gated by, so there is no operation for this story to scope until it has shipped. **What it still delivers alone is the whole of the tenant boundary** — a seller who can see its own demand and nothing else. That is a distinct, separately valuable and separately testable outcome: 08-01 without it answers every seller's rows to any caller who can address a channel with no seller, and 08-02 is what closes that. The parent records no *design* edge between the three stories, all three delegating to one service class whose shared surface is the class declaration and the permission registrations [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§4.3 Intra-Feature Story Order — There Is None, By Construction]; section 8 therefore classifies 08-01 as a **shared code path** rather than a data dependency, and says so rather than filing it under a looser heading.

**The prerequisite this story cannot skip, stated rather than glossed: superadmin is not seller-scoped.** The seeded superadmin holds every permission the deployment publishes, including the entitlement to the aggregate's seller-unscoped form, so a request made as superadmin demonstrates that the operation answers and demonstrates **nothing whatever** about scoping. To exercise this story's own audience a reader must obtain a seller-scoped administrator session, and every operation needed for that already exists:

- Create a second seller with the existing `createSeller(input: CreateSellerInput!): Seller!` mutation [packages/core/src/api/schema/admin-api/seller.api.graphql:L8], and read both sellers back with `sellers(options: SellerListOptions): SellerList!` [packages/core/src/api/schema/admin-api/seller.api.graphql:L2].
- Create one channel per seller with the existing `createChannel(input: CreateChannelInput!): CreateChannelResult!` mutation [packages/core/src/api/schema/admin-api/channel.api.graphql:L9], supplying the optional `sellerId` input field [packages/core/src/api/schema/admin-api/channel.api.graphql:L41] on each so that neither channel's scope column is null. The seeded default channel is guaranteed a seller of its own, assigned during initialisation [packages/core/src/service/services/channel.service.ts:L541-L550], so it may serve as the first of the two.
- Create a role with the existing `createRole(input: CreateRoleInput!): Role!` mutation [packages/core/src/api/schema/admin-api/role.api.graphql:L8] granting **only** the first seller's channel through `channelIds` [packages/core/src/api/schema/admin-api/role.api.graphql:L24] and, in its `permissions` array [packages/core/src/api/schema/admin-api/role.api.graphql:L23], the aggregate read capability **without** the seller-unscoped entitlement. On a freshly populated database no reorder attempt exists at all, so either insert `ReorderAttempt`, `ReorderAttemptLine` and `PurchaseCadence` rows through a test fixture or exercise the buyer-facing reorder paths FEATURE-001-02 and FEATURE-001-05 deliver. **A single-seller dataset is not a lighter version of this demonstration; it is a dataset on which the scoping silently appears to work.**

**Carry the channel.** The active channel is named by the request header whose key is declared as `vendure-token` [packages/common/src/shared-constants.ts:L19] and matched against the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], which is what that column's own documentation says it is for [packages/core/src/entity/channel/channel.entity.ts:L56-L60]. Send the first seller's channel token.

**Send the operation.** POST to `http://localhost:3000/admin-api` carrying the seller-scoped administrator's bearer token and that channel token.

```graphql
query {
  recurringDemand(options: { take: 20, skip: 0, sort: { reorderAttemptCount: DESC } }) {
    totalItems
    windowStart
    windowEnd
    items {
      id
      productVariantId
      productVariantName
      sku
      sellerId
      reorderAttemptCount
      reorderedUnitCount
      distinctCustomerCount
      savedListOccurrenceCount
      firstReorderedAt
      lastReorderedAt
    }
  }
}
```

**Expected response.** A `RecurringDemandList` whose `items` contains rows **only** for variants reachable through the first seller's channel, every `sellerId` on every returned row equal to that seller's identifier, ordered by `reorderAttemptCount` descending with `productVariantId` as the total tie-break, and `totalItems` equal to the number of such rows rather than to the number of rows in the database. Repeating the identical request while substituting the second seller's channel token in the header returns the platform's forbidden result, because that channel is not among the ones the role grants. **Neither the count nor the row set changes if the reader adds a filter, a sort or an invented seller argument**, which is the observable form of the ruling that the scope is derived rather than supplied. Against a freshly seeded database with no fixture inserted, the demonstrable outcome is `totalItems` equal to zero and `items` equal to the empty array — **an empty list and not an error**, which is the specified behaviour rather than a gap.

## 5. Acceptance Criteria

Seven criteria. Each names exactly one GraphQL operation, so a failing criterion points at a single published contract. Criteria name operations and their arguments and **never** a resolver class, a file path or an internal method name, because a published operation is a stable contract and an internal name is not. The five required coverage classes map onto them as follows: valid input is AC-1, invalid or incomplete input is AC-4, an error naming the exact type returned is AC-3, an edge case is AC-6, and the assertion that an existing operation is unchanged is AC-7. **AC-2 and AC-3 are this story's two mandatory scoping criteria and are deliberately separate criteria rather than one**, because they assert different failures: AC-2 says a foreign row never arrives, and AC-3 says an underivable scope is refused instead of widened. AC-5 carries the do-not-duplicate mandate the epic attaches to this feature.

Nine properties of the operation are stated once here rather than repeated in every criterion.

- **This story publishes no operation and changes no signature.** `recurringDemand` is delivered by STORY-001-08-01 through the plugin's `adminApiExtensions` on an `extend type Query` block, the mechanism the shipped reviews plugin demonstrates [packages/dev-server/test-plugins/reviews/api/api-extensions.ts:L69-L72]; this story composes a predicate and an entitlement check into it. **The Shop API delta is zero and no existing operation's arguments, return type or nullability change anywhere.** The read is synchronous: it enqueues no job and schedules no task, so there is no asynchronous trigger and no observable completion signal to name.
- **This story registers no permission definition, so its own published enum delta is zero.** The aggregate read capability and the seller-unscoped entitlement are both registered by STORY-001-08-01, which declares their growth as two members. **That growth is nonetheless a real published-schema effect and is neither re-argued nor accepted in silence here**: the `Permission` enum is declared with no members in source and annotated as populated at run time [packages/core/src/api/schema/common/common-enums.graphql:L20-L21], and it is filled by the platform's generator [packages/core/src/api/config/generate-permissions.ts:L42] from the default and custom definitions together [packages/core/src/api/config/generate-permissions.ts:L46]. - **Authentication and capability are stated in every criterion, and the two are separate.** Every request below is made on an authenticated Administrator session. **A Seller Operations Manager holds the aggregate read capability and does NOT hold the seller-unscoped entitlement**, and its role grants only channels whose scope column is non-null [packages/core/src/entity/channel/channel.entity.ts:L71-L72]. ## 7. Edge Cases

Four scenarios, one per required category. The three unconditionally required categories are the first three, and the fourth covers the conditional channel, currency and language category, which applies because the channel is part of every row's grouping key and because one seller owning more than one channel is the ordinary case here. **Three of the four resolve to *proceed* rather than to a block or a warning, and that is stated honestly rather than force-fitted into a failure this read cannot have.** The remaining conditional categories are addressed at the end of this section rather than omitted.

* Scenario: Zero, null or empty collection — a seller has no recorded reorder activity in any of its channels
   * Given an Administrator is authenticated holding the aggregate read capability and not the seller-unscoped entitlement, its role granting only channels whose seller column is non-null [packages/core/src/entity/channel/channel.entity.ts:L71-L72] and the request naming one of them in the `vendure-token` header, and no `PurchaseCadence`, `ReorderAttempt` or `ReorderAttemptLine` row exists inside the aggregate window for any variant reachable through any channel that seller owns
   * When that Administrator executes the `recurringDemand` query
   * Then proceed with an empty result: `items` is the empty array and `totalItems` equals exactly 0, `windowStart` and `windowEnd` are still returned non-null so the reader knows which window returned nothing, and **no error of any type is returned**. An empty scope is an empty page and never a refusal — the refusal case is a caller who is not entitled to the scope, which AC-3 owns, and the two are deliberately distinguishable. A seller with no recorded activity is a specified outcome rather than a failure path, and it is the property that lets this story be accepted before the buyer-facing reorder paths have ever been exercised

* Scenario: An item unavailable, deleted or disabled since the last purchase — a variant carrying recorded activity is now disabled or deleted, or the seller itself is soft-deleted
   * Given an Administrator is authenticated holding the aggregate read capability and not the seller-unscoped entitlement on a channel whose seller column is non-null, one variant carrying recorded reorder activity inside the window has since had its `enabled` column set to false [packages/core/src/entity/product-variant/product-variant.entity.ts:L53], a second has been soft-deleted so that its `deletedAt` column carries a timestamp [packages/core/src/entity/product-variant/product-variant.entity.ts:L48], a third has been hard-deleted so that no catalogue row remains to resolve a name from, and separately the owning `Seller` has itself been soft-deleted, which its own entity permits by implementing the platform's soft-delete contract [packages/core/src/entity/seller/seller.entity.ts:L18] through a nullable timestamp column [packages/core/src/entity/seller/seller.entity.ts:L23-L24]
   * When that Administrator executes the `recurringDemand` query requesting `productVariantId`, `productVariantName`, `sku`, `sellerId` and `reorderAttemptCount` for every row
   * Then proceed and **return the disabled row and the soft-deleted row rather than omitting them** — this is the deterministic ruling for this operation, stated as a choice between the two available behaviours rather than left open. The aggregate reports historical recorded activity and filters on the channel, the seller and the window and on none of `enabled`, `deletedAt`, price or stock, so each row stands with its counts intact and its name and sku resolved, labelled by the same `productVariantName` and `sku` fields every other row carries and with no availability field of its own, because the published row declares none and a seller reading present availability reads it from the catalogue. Where the variant has been **hard**-deleted the row is still returned with `productVariantName` null, `sku` null and the variant relation null, the three being nullable precisely so an erased catalogue row cannot fail the response. **Where the seller itself is soft-deleted the scope still resolves**, because the predicate reads the channel's seller column rather than the seller's own state, so the rows remain visible to a caller whose role still grants that channel; and **where a row's seller cannot be attributed at all the row is excluded rather than returned unattributed**, `sellerId` being published non-null as the fail-closed form of that rule, with the consequence stated plainly in the operation's own documentation: the aggregate understates demand for variants whose attribution has been erased

* Scenario: A price changed since the last purchase — the catalogue price of a variant carrying recorded activity has moved
   * Given the price of a variant carrying recorded reorder activity has changed since the orders that activity was derived from were placed, and an Administrator is authenticated holding the aggregate read capability and not the seller-unscoped entitlement on a channel whose seller column is non-null
   * When that Administrator executes the `recurringDemand` query
   * Then proceed with no warning and no price field: **this operation reports no monetary value at all, and that boundary is explicit rather than an oversight.** Every field on the published row is a count or a timestamp, so this story holds no price that could go stale and the aggregate is **not a quotation**. Were a monetary aggregate ever added it would be an integer in the smallest unit of its currency stated alongside its currency code, defaulting to the channel's own default code [packages/core/src/entity/channel/channel.entity.ts:L87-L88], and never a decimal, and it would have to re-enter the grouping key to avoid spanning two codes. A buyer is made aware of a price movement before committing through FEATURE-001-03's `reorderPreview` operation, which owns that comparison against the platform's own prorated historical operand [packages/core/src/entity/order-line/order-line.entity.ts:L213-L229]; answering the same question here would put two answers to one question in two features

* Scenario: A channel, currency or language mismatch — one seller owning two channels that declare different currency and language codes
   * Given one seller owns two channels with different values of the unique `Channel.token` column [packages/core/src/entity/channel/channel.entity.ts:L62], the two declaring different default currency codes [packages/core/src/entity/channel/channel.entity.ts:L87-L88] and different default language codes [packages/core/src/entity/channel/channel.entity.ts:L74], a variant carries recorded reorder activity in both, and inside the first of them that variant was purchased under two of the currency codes that channel declares as available [packages/core/src/entity/channel/channel.entity.ts:L90-L91]
   * When an Administrator holding the aggregate read capability and not the seller-unscoped entitlement, with both channels granted by its role, executes the `recurringDemand` query once under each token with the language resolved from each channel in turn
   * Then proceed with **one row set per channel and never one summed row across the two**: the channel is part of the grouping key, so each execution returns that channel's rows only and neither result contains the other's, and the two rows carry different `id` values. Inside the first channel the two currency codes produce a **single** row whose counts include both, because a count is currency-free and the currency code is deliberately not part of the grouping key — **so nothing is ever summed across currencies here, by construction rather than by rule, since no field on the row is monetary and no exchange rate can be applied anywhere.** This matters more for a seller than for a category manager, because a single seller owning more than one channel is the ordinary marketplace shape; a per-channel report is therefore the specified answer and a single cross-channel total is not on offer. Any translatable label rendered beside the rows, the seller name among them [packages/core/src/entity/seller/seller.entity.ts:L26], resolves against the requested language code while the counts and timestamps are language-invariant

**The remaining conditional categories, and why each is placed where it is.** A point-in-time read gone stale between check and commit is not written as a separate scenario, because this operation performs no availability check and commits nothing; the staleness it does have is the aggregate's own — it describes the window it names and nothing after it — and it is carried by the second and third scenarios above and by the `windowStart` and `windowEnd` fields AC-1 asserts. A concurrent modification or race is likewise not a separate scenario, and the observable outcome is stated rather than a locking design: two simultaneous reads cannot conflict; a row written by an upstream feature while a page is being read is observable only as that row appearing in a later page or a later request, which the declared total tie-break on `productVariantId` makes deterministic within one request; and **a channel reassigned from one seller to another mid-read changes which rows a subsequent request returns and never retrospectively widens one already answered**, because the predicate is composed from the channel resolved at the start of the request rather than re-read per row.

### 8.1 Decisions This Story Waits On

Three decisions bear on this story and one that a reader might expect to is closed. None is resolved here; each belongs to a maintainer.

- **Open — the three recurring-demand read parameters: what qualifies a variant as recurring, how far back the aggregate window reaches, and what a default page returns.** The epic carries all three together as one ranked product decision, with the page-size half additionally appearing as an architectural decision covering every paginated surface in the set [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions] and [tickets/EPIC-001-reorder-and-replenishment.md:§8.2 Architectural Decisions]. **No number is supplied here and none may be**, because a threshold invented in a ticket is an invented metric wearing a technical hat, and the parts interact: two purchases over a long window and three over a short one select different variants and would populate the same page differently. **What this story ships while the decision is open** is a scope, an entitlement branch and a page whose criteria in section 5 assert ordering, scoping, pagination and permission behaviour, none of which turns on those values, and which assert no qualifying count and no ranking cut-off. **What is not open is the page-size ceiling**, which is not a decision at all: the operation returns a paginated-list implementor and is therefore capped by the platform's own configured Admin limit at its shipped default [packages/core/src/config/default-config.ts:L84], enforced rather than documented [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L637] and [packages/core/src/service/helpers/list-query-builder/list-query-builder.ts:L638].
- **Open — the form each permission definition takes, though not how many capabilities exist.** The epic records the form as an architectural decision [tickets/EPIC-001-reorder-and-replenishment.md:§8.2 Architectural Decisions]. **The count is settled at three across the feature, none of them registered by this story, and collapsing any two of the three is a privilege-escalation defect rather than a tidying** [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.8 Permission Gating, And The Enum Growth Referenced Rather Than Re-Argued]. What remains open is whether the single-member base form is accepted over the read-and-write or four-permission shapes, which changes only how many members the published enum gains and therefore only a number STORY-001-08-01 asserts, not one this story does. In-resolver enforcement is not optional under any of the three options, because the platform states that a permission alone is the equivalent of public access [packages/core/src/api/config/generate-permissions.ts:L32-L34].
- **Open, and this one reaches this story harder than any other in the feature — whether the cadence data is read per channel or aggregated across channels.** The epic records it as a product decision blocking five stories, two of which are this feature's [tickets/EPIC-001-reorder-and-replenishment.md:§8.1 Product Decisions]. It bites hardest here because **one seller frequently owns more than one channel**, so the decision determines whether a seller's view is one page per channel or one page per seller. A cross-channel total would collide directly with the per-channel rule wherever two of that seller's channels declare different currency codes [packages/core/src/entity/channel/channel.entity.ts:L87-L88], and the aggregate publishes no monetary field partly for that reason. **What this story asserts while the decision is open** is the per-channel behaviour AC-6 and the fourth scenario in section 7 fix, which is the epic's own settled ruling for every read in the set.
- **Closed — whether a seller-unscoped read is reachable without an explicit grant.** It is not, and the parent settles it rather than leaving it to an implementer: an unresolvable seller scope is a refusal, and only a caller explicitly holding the seller-unscoped entitlement receives the channel's full row set [tickets/EPIC-001/FEATURE-001-08-recurring-demand-visibility.md:§2.7.1 The Audience Is A Role Configuration, Not A Persona — And That Is What Makes It Checkable]. **It is recorded here as closed rather than omitted**, because an earlier reading of the same rule treated "no seller to filter by" and "authorised to see every seller" as one branch, which is fail-open on a default channel carrying every seller's variants. AC-3 asserts the two branches separately, which is this story's share of that ruling.

**The honest limit of what this story can enforce, stated because overstating it would be the more comfortable thing to write.** A caller whose roles grant a channel with no seller **and** who holds the seller-unscoped entitlement sees that channel's full rows whatever the deployment intended, and no code here can prevent it: `Administrator` carries no seller relation [packages/core/src/entity/administrator/administrator.entity.ts:L19-L39] and `Role` carries none either [packages/core/src/entity/role/role.entity.ts:L22-L31], so there is no persona to test against and no caller-to-seller mapping to consult, and inventing one would mean a new column the additive constraint refuses. **What is genuinely prevented is the cross-channel case, and that is the one that matters**: no caller of any configuration reads rows recorded in a channel their roles do not grant, so a misconfigured seller role widens a view within one channel and never across two. Confining a seller to seller channels is a role-configuration act by an operator, it is the platform's own mechanism, and section 10 requires it to be asserted as a fixture precondition rather than assumed.

**One merge gate, not a design dependency.** The branch target is a three-way conflict in this repository's own documentation rather than a choice already made [tickets/EPIC-001-reorder-and-replenishment.md:§11.1 The Branch Target Is A Three-Way Conflict, Not A Choice Already Made]: feature work is directed to the `minor` branch [CONTRIBUTING.md:§New features] while a database-schema change is classified as breaking-change work [CONTRIBUTING.md:§Breaking Changes]. **This story adds no table, so the schema-change classification does not bite on it directly** — but its two upstream row-owning features each add one, so the conflict reaches this story through them regardless. It gates the merge and blocks no part of the build.
